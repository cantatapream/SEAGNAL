# 자식해역 특보 표출 — 3.5 로그 형식

## 0. 본 파일의 위치

본 파일은 `03_OPERATIONS/` 시리즈의 다섯 번째 파일이며, 자식해역 처리 과정에서 생성되는 모든 로그의 형식을 정의합니다.

본 작업의 사용자 요구사항 중 하나는 **"개발자 친화 형식 + 평문 서술형 두 형식 병행"** 입니다.

---

## 1. 로그의 두 가지 형식

### 1.1 개발자 친화 형식

코드 함수명, 변수, 코드 위치 등 디버깅에 직접 사용되는 정보.

```
[자식해역] [매핑누락] regId=S2999900 regKo="○○평수구" parentRegId=S1131000 wrnTp=풍랑 wrnLvl=2
```

### 1.2 평문 서술형

운영자/관리자가 코드를 모르더라도 이해 가능한 한글 문장.

```
[자식해역] 2026년 04월 30일 22시 05분, 방재기상시스템에서 받은
자식해역 'S2999900 (○○평수구)' 에 대해 우리 앱의 매핑 테이블에
등록된 이름이 없습니다. 매핑 테이블에 추가가 필요합니다.
```

### 1.3 두 형식의 병행

본 작업의 모든 로그는 두 형식을 함께 출력합니다.

- 콘솔/파일 로그: 개발자 형식 (한 줄)
- `subregion_error_log.json`의 `narrativeDescription` 필드: 평문 서술형
- `developerInfo` 필드: 개발자 형식 정보

---

## 2. 로그 출력 채널

### 2.1 채널 분류

| 채널 | 용도 | 형식 |
|---|---|---|
| `console.log` | 개발/디버깅 | 개발자 친화 (한 줄) |
| `subregion_error_log.json` | 운영자 검토 | 두 형식 병행 |
| `admin_push` (FCM) | 즉시 알림 | 평문 서술형 |
| `admin_ui` (UI) | 시각적 표시 | 평문 서술형 + 개발자 정보 펼침 |

### 2.2 일관성 보장

같은 사건은 모든 채널에 일관된 정보로 기록되어야 합니다.

```
function logEvent(event):
  # 콘솔
  console.log(formatDeveloperLog(event))

  # 영구 저장
  if event.persist:
    appendToErrorLog(event.errorType, {
      developerInfo: event.developerInfo,
      narrativeDescription: event.narrative,
      actionRequired: event.actionRequired
    })

  # 푸시
  if event.shouldPush:
    triggerAdminPush(event.narrative)
```

## 3. 개발자 형식 표준

### 3.1 콘솔 로그 형식

```
[CATEGORY] [EVENT_TYPE] key1=value1 key2=value2 ...
```

- `CATEGORY`: 로그 카테고리 (자식해역, 통보문, 시스템 등)
- `EVENT_TYPE`: 이벤트 종류
- 값 쌍: 디버깅에 필요한 정보

### 3.2 본 작업의 카테고리

- `[자식해역]`: 자식해역 처리 일반
- `[자식해역-AFSO]`: 방재기상 API 관련
- `[자식해역-매핑]`: 매핑 테이블 관련
- `[자식해역-잠금]`: 동시 사라짐 잠금 관련
- `[자식해역-캡]`: 캡 규칙 적용

### 3.3 이벤트 타입 예시

```
[자식해역] [신규발효] regId=S2122000 wrnTp=풍랑 wrnLvl=2
[자식해역] [해제] regId=S2122000 reason=2회연속누락
[자식해역] [잠금] regId=S2122000 parentTmCc=2026-05-01T06:00
[자식해역-AFSO] [응답오류] statusCode=503
[자식해역-매핑] [누락] afsoRegId=S2999900 afsoRegKo=○○평수구
[자식해역-캡] [레벨캡] regId=S2122000 자식=3 부모=2
[자식해역-캡] [시각캡] regId=S2122000 자식=12:00 부모=06:00
```

## 4. 평문 서술형 표준

### 4.1 일반 형식

```
[시각], [무슨 일이 발생했는지]. [영향]. [조치].
```

### 4.2 표준 구성 요소

평문 서술형은 다음 요소로 구성됩니다.

- **시각**: 한글로 풀어 쓴 발생 시각 (예: "2026년 04월 30일 22시 05분")
- **사건 설명**: 무엇이 일어났는지 명확히
- **영향**: 시스템/사용자에게 미치는 영향
- **조치**: 운영자가 해야 할 일 (있을 경우)

### 4.3 예시 모음

#### 매핑 누락

```
2026년 04월 30일 22시 05분, 방재기상시스템에서 자식해역 정보를 받았으나
우리 앱의 매핑 테이블에 등록되지 않은 해역이 있습니다.

  - 방재기상 코드: S2999900
  - 방재기상 이름: ○○평수구
  - 부모해역: S1131100 (울산앞바다)
  - 발효 특보: 풍랑 주의보

[조치 필요] region_alias_map.json 파일에 이 해역을 추가해주세요.
추가 전까지 이 해역의 특보 정보는 사용자에게 표시되지 않습니다.
```

#### 자식 신규 발효

```
2026년 04월 30일 14시 00분, 가파도연안바다에 풍랑 주의보가
신규 발효되었습니다. 부모해역(제주도서부앞바다)이 같은 시각에
풍랑 주의보 발효 중입니다.
```

#### 자식 해제 (2회 연속 누락)

```
2026년 04월 30일 22시 05분, 가파도연안바다의 특보 정보가 방재기상
시스템에서 2회 연속 누락되어 해제 처리했습니다. 부모해역(제주도서부
앞바다)은 통보문상 여전히 풍랑 경보 발효 중입니다.
```

#### 부모-자식 동시 사라짐 잠금

```
2026년 04월 30일 21시 50분, 부모해역(제주도서부앞바다)과 그 자식해역
(가파도연안바다 외 2개)이 방재기상시스템에서 동시에 사라졌습니다.
부모 통보문에 명시된 해제 예정 시각(2026년 05월 01일 06시 00분)까지
자식해역을 추정 발효 상태로 유지합니다.
```

#### 레벨 캡 적용

```
2026년 04월 30일 22시 05분, 가파도연안바다 자식해역의 방재기상 레벨이
부모해역의 통보문 레벨보다 높습니다 (자식=경보, 부모=주의보). 안전을
위해 부모 레벨로 캡 적용했습니다. 이는 보통 방재기상이 격상 발표를
사전 표시했기 때문입니다.

[조치] 통보문 갱신 시 자동으로 캡이 풀립니다. 별도 조치는 불필요합니다.
```

#### 방재기상 응답 오류

```
2026년 04월 30일 22시 05분, 방재기상시스템 API에 응답 오류가 발생
했습니다 (HTTP 503). 자식해역 상태는 직전 사이클의 정보를 그대로
유지합니다. 일시 오류면 자동으로 복구됩니다.

[조치] 30분 이상 지속 시 점검이 필요합니다.
```

#### Stale 부모 (24시간 무변화)

```
2026년 05월 02일 22시 05분, 부모해역 제주도서부앞바다의 통보문이
24시간 이상 변화 없이 유지되고 있습니다. 통보문 시스템 점검이
필요할 수 있습니다.

[조치] 통보문 크롤러와 기상청 페이지를 확인해주세요.
```

#### 범위형 시각 잠금

```
2026년 05월 09일 06시 00분, 부모해역 제주도서부앞바다의 통보문 해제
예정 시각이 범위형 (오전 06시~12시)으로 표시되어 정확한 시각을 알
수 없습니다. 자식해역들은 정확한 통보문 갱신 시점까지 발효 상태로
유지합니다.
```

## 5. 시각 형식 규칙

### 5.1 한글 시각 형식

```
"2026년 04월 30일 22시 05분"
```

- 4자리 연도, 2자리 월/일/시/분
- "년", "월", "일", "시", "분" 한글 단위 사용

### 5.2 변환 함수

```
function formatKoreanDate(isoString):
  d = new Date(isoString)
  return `${d.getFullYear()}년 ${pad(d.getMonth()+1)}월 ${pad(d.getDate())}일 ${pad(d.getHours())}시 ${pad(d.getMinutes())}분`
```

### 5.3 일관성 원칙

본 작업의 모든 평문 로그는 위의 한글 시각 형식 사용.

## 7. 로그 양 제어

### 7.1 콘솔 로그 양

콘솔 로그는 디버깅 외에는 양을 제어할 필요가 있습니다.

- 정상 동작 시: 사이클당 1~2줄 (요약)
- 이벤트 발생 시: 해당 이벤트 1줄
- 오류 발생 시: 상세 정보 + 스택 트레이스

### 7.2 영구 로그 양

`subregion_error_log.json`은 누적되므로 양 제어 정책 필요. 자세한 내용: `02_DATA_MODEL/05_error_log_schema.md`의 8장 참조.
