### 1-2. 수집 방식

- 1분 사이클로 9개 광역 `list.do` **병렬 호출**
- `kind=met` (특보) + `kind=pwn` (예비특보) 모두 수집
- 같은 reportId 가 광역간 중복되므로 dedup 필수
- 본문(`fetchReportDetail`) 은 unique reportId 만 호출

---

## 2. 1분 사이클 흐름

```
[Step 1] 9개 광역 list.do 병렬 호출 (~1.3초)
[Step 2] reportId dedup (~0.1초)
[Step 3] 신규 reportId 의 본문 fetch 병렬 (~0.5초/건)
[Step 4] AI 파서 + 자식해역 정규식 파서 (Dual Validation)
[Step 5] 장부(weather_alerts.json) 갱신
[Step 6] 변경 종합 + 일괄 푸시 발송 (광역별 즉시 푸시 X)
```

### 2-1. 실측 소요시간

| 시나리오 | 새 통보문 | 총 소요 | 1분 한도 여유 |
|---|---|---|---|
| 평상시 | 0건 | ~1.4초 | ~58초 |
| 통상 | 5건 | ~6.6초 | ~53초 |
| 격변기 | 20건 | ~22초 | ~38초 |

### 2-2. 광역별 호출 URL

```
https://www.weather.go.kr/w/special-report/list.do?stn={STN}&kind=met&date={YYYY-MM-DD}
https://www.weather.go.kr/w/special-report/list.do?stn={STN}&kind=pwn&date={YYYY-MM-DD}
```

## 3. 일괄 푸시 정책

- 9 광역 수집 완료 후 직전 장부와 diff 계산
- **부모해역 변화만** 푸시 발송 (자식해역 변화는 푸시 X)
- 같은 사용자의 여러 광역 변화는 **한 알림으로 묶어 발송**
- 푸시 양식은 기존 `push_helpers.js` 의 9가지 시나리오 유지

## 4. 안전장치

### 4-1. 네트워크 지연
- 광역별 요청 타임아웃 10초
- 일부 광역 실패 시 다음 사이클 재시도 (다른 광역은 정상 처리)
- 타임아웃 발생 시 어드민 알림

### 4-2. 사이클 겹침
- mutex 락(`crawlPaused` 플래그)으로 이전 사이클 미완료 시 새 사이클 skip

### 4-3. 기상청 서버 부담
- User-Agent 명시
- 요청 간 약간의 지터 추가 (선택)
- 시간당 540회 호출 (일반 사용자 새로고침 수준)
