# 6단계 운영 모니터링 가이드 — 검증 및 운영

운영자가 1주일~1개월 운영하면서 **무엇을 확인하고, 어떻게 대응할지** 정리합니다.

## 1. 모니터링 진입점 (3개 위치)

운영자는 다음 3곳에서 자식해역 시스템 상태를 모니터링합니다.

### 1.1 통합관리자 센터 — 특보수집오류 탭의 자식해역 비교 불일치 (index1만)

**경로**: 통합관리자 센터 → 특보 알림 → 특보수집오류 → "자식해역 비교 불일치"

**확인 항목**:
- 미확인 오류 수
- 누적 발생 횟수 (반복 빈도)
- 각 오류의 서술형 메시지 + 코드형 정보

### 1.2 관리자 푸시 알림

**발송 조건**:
- HIGH severity (활성 여부 불일치, 종류 다름) → 첫 발생 즉시 + 1시간 간격 반복
- MEDIUM severity (레벨 차이, 신규가 더 높음) → 첫 발생 즉시 + 6시간 간격 반복
- LOW severity (레벨 차이, 신규가 더 낮음) → 미발송

### 1.3 index1 화면 (테스트 페이지)

**확인 항목**:
- `#subregion-section`에 자식해역 표출 정상
- 추정 마커(ⓘ) 표시 정상
- 비교 검증 결과 표시 (기존 vs 신규)

### Day 2~3 — 비교 검증 동작 확인

- [ ] 통합관리자 센터의 자식해역 비교 불일치 탭 정상 표시
- [ ] 비교 일치 케이스에서 오류 없음
- [ ] 강제 상이성 발생 시 (예: 매핑 일시 제거) 푸시 알림 도착
- [ ] 코드 형식 + 서술 형식 둘 다 정상 표시

### Day 4~7 — 운영 데이터 누적 모니터링

매일 다음 항목을 확인하여 빈도 추이 파악:

| 항목 | 기대 빈도 | 비정상 신호 |
|---|---|---|
| `MAPPING_MISSING` | 0건 (전수조사 완료) | 1건 이상 → 새 해역 추가 필요 |
| `LEVEL_CAP_APPLIED` | 발효 시기에 종종 발생 | 시간당 10회 이상 → 데이터 이상 의심 |
| `TIME_CAP_APPLIED` | 가끔 | 매분 발생 → 시각 형식 또는 매핑 점검 |
| `AFSO_RESPONSE_ERROR` | 0~1건/일 | 시간당 5회 이상 → 외부 API 점검 |
| `PARENT_CHILD_MISMATCH` | 시간차 발생 시 (사용자 정책) | 1시간 이상 지속 → 통보문 점검 |
| `STALE_PARENT` | 매우 드묾 | 발생 시 통보문 시스템 즉시 점검 |
| `COMPARISON_MISMATCH` | 격상/격하/시간차 시 발생 | 동시 5건 이상 발생 → 정책 재검토 |

## 3. 핵심 모니터링 메트릭 (수집 항목)

### 3.1 데이터 품질 메트릭

매핑 / 캡 / 누락 빈도:

```
- 매핑 누락 발생 자식해역 수
- 캡 적용 발생 자식해역 수 (레벨 / 시각)
- 매핑 누락이 운영자에 의해 추가되기까지 걸린 시간
- 응답 실패율 (1주간 응답 실패 사이클 / 전체 사이클)
```

### 3.2 비교 검증 메트릭

기존 ↔ 신규 일치율:

```
- 비교 매칭 일치 비율 = (matches / (matches + mismatches))
- 카테고리별 mismatch:
  · LEGACY_ACTIVE_AFSO_INACTIVE
  · LEGACY_INACTIVE_AFSO_ACTIVE
  · BOTH_ACTIVE_DIFFERENT_LEVEL
  · BOTH_ACTIVE_DIFFERENT_TYPE
- 평균 mismatch 지속 시간
- mismatch 발생 후 자동 해소까지 평균 시간
```

### 3.3 운영 부하 메트릭

```
- subregion_lifecycle.json 파일 크기 (KB)
- subregion_error_log.json 파일 크기 (KB)
- 매 사이클당 자식해역 처리 소요 시간 (ms)
- 푸시 발송 건수
- 디스크 I/O 빈도
```

### 3.4 시각 차이 메트릭 (신규 시나리오)

방재기상 ↔ 통보문 시간차:

```
- 시나리오 ② (격하 사전 차단) 발동 횟수
- 시나리오 ④ (신규 발효 사전 차단) 발동 횟수
- 평균 시간차 (방재기상 변동 → 통보문 변동까지)
```

## 5. 정책 조정 가이드

운영 데이터를 바탕으로 다음 정책을 조정 가능합니다.

### 5.1 푸시 발송 빈도 (스팸 vs 적시 알림)

현재: HIGH 1시간 / MEDIUM 6시간 / LOW 미발송

조정 옵션:
- 운영자 피로도 높음 → MEDIUM 12시간 또는 24시간으로 완화
- 중요 이슈 늦게 발견 → HIGH 30분으로 단축

### 5.2 missedCount 임계 (즉시 해제 vs 보수)

현재: 2회 누락 시 해제

조정 옵션:
- 일시 누락이 많음 → 3회로 완화
- 빠른 갱신 필요 → 1회로 단축 (위험)

### 5.3 STALE 임계 (24시간 vs 더 짧게)

현재: 24시간 무변화 시 알림

조정 옵션:
- 짧게: 12시간 (기상 활발기)
- 길게: 48시간 (기상 안정기)

### 5.4 환경변수 즉시 롤백

운영 중 큰 문제 발견 시:
```bash
# Fly.io secrets 또는 .env
AFSO_ENABLED=false
```
→ 다음 사이클부터 자식해역 처리 전체 스킵 (사용자 영향 0)

**도입 기준**: ack 처리와 자동 갱신 충돌 발견 시
**작업**: 파일 락 또는 단일 mutex 도입

## 7. 확장 결정 (index2 적용 여부)

검증 완료 후 index2 확장 결정. 결정 기준:

### 7.1 도입 가능 신호

- 비교 일치율 99% 이상
- 운영 데이터 안정 (오류 빈도 정상 범위)
- 사용자 피드백 양호

### 7.2 도입 미루기 신호

- 비교 mismatch 빈번 (시간차 외 원인)
- 매핑 누락 정기 발생
- 푸시 스팸 발생

### 7.3 index2 적용 절차

1. `index2.html`에 페이지 식별 플래그 (현재는 `'index2'` 그대로)
2. `index2_features.json`의 방재기상_자식해역 = true (구조 도입 시)
3. `subregion_display.js`의 페이지 가드 완화 (`index1 || index2`)
4. 1단계 인프라(`#subregion-section` 컨테이너) index2.html에 추가
5. 검증 후 운영

## 8. 비상 대응 플레이북

### 8.1 자식해역 화면이 갑자기 비어 있음

확인 순서:
1. `subregion_lifecycle.json` 파일 존재/내용 확인
2. 스케줄러 로그에서 `runSubregionPipeline` 호출 확인
3. `AFSO_ENABLED` 환경변수 확인
4. 방재기상 API 직접 호출 테스트
5. 매핑 테이블 무결성 확인

### 8.2 푸시 알림 폭주

확인 순서:
1. 어떤 오류 유형의 푸시인지 확인
2. 같은 오류 반복인지 (signature 확인)
3. 빈도 제어 로직 작동 여부 확인
4. 임시 비활성화: `AFSO_ENABLED=false`

### 8.3 매핑 누락 다발

확인 순서:
1. unmapped 섹션 누적 확인
2. 새 해역 추가인지 (방재기상 정책 변경 가능성)
3. 매핑 테이블 갱신 → 다음 사이클 정상화

### 8.4 비교 mismatch 폭증

확인 순서:
1. 어떤 diffType이 많은지 확인
2. 시간차로 인한 일시적인지 (시간 지나면 해소)
3. 정책 위반인지 (예: 자식 단독 격상)
4. 운영자 판단으로 임시 푸시 비활성화 여부 결정
