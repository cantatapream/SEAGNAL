## 1. 작업 진행 원칙

### 1.1 핵심 원칙

본 작업은 다음 원칙에 따라 진행됩니다.

- **단계별 진행**: 6단계로 구분, 한 단계씩 완전히 마친 후 다음으로
- **단계 진입 직전 재검토 필수**: 사용자 결정 사항
- **단계 완료 후 검증 필수**: 다음 단계 진입 전 동작 확인
- **롤백 가능 우선**: 모든 단계는 즉시 롤백 가능하도록 설계
- **운영 영향 0**: index2 운영에 영향 가는 변경은 절대 적용 안 함

### 1.2 단계 진입 직전 재검토 표준 절차 (★ 매 단계마다 반복)

각 단계 작업을 시작하기 직전에 다음 4가지 관점에서 재검토합니다.

#### (1) 문서 기반 적정성 검토
- 본 단계 작업이 설계 문서들과 일치하는가?
- 분리 분석 6개 문서의 정책과 부합하는가?
- 작업 내용에 누락된 부분이 없는가?

#### (2) 코드 기반 적정성 검토
- 현재 코드베이스의 실제 상태에서 본 단계 작업이 가능한가?
- 작업 대상 파일이 실제로 존재하고 예상한 구조인가?
- 다른 코드와의 의존 관계 중 새로 발견된 것이 있는가?

#### (3) 로직 기반 적정성 검토
- 본 단계 작업 후 동작이 의도와 일치하는가?
- 기존 로직과 신규 로직의 상호작용이 의도대로인가?
- 예상치 못한 부작용 가능성이 있는가?

#### (4) 누락 점검
- 본 단계의 작업 항목이 빠짐없이 포함되었는가?
- 검증 방법이 명시되었는가?
- 롤백 절차가 명시되었는가?

### 1.3 재검토 후 결정

재검토 결과:

- **이상 없음**: 작업 진행
- **소소한 누락 발견**: 누락 보완 후 진행
- **중대한 문제 발견**: 단계 계획 재설계 후 사용자 확인

## 3. 각 단계별 개요

### 3.1 [1단계] 분리 인프라 구축

**목표**: index1과 index2의 강한 분리를 위한 기초 인프라 구축

**포함 작업**:
- 작업 1: index1.html에 페이지 식별 플래그 추가
- 작업 2: index1.html에 자식해역 신규 섹션 (`#subregion-section`) 추가
- 작업 4: 신규 CSS 파일 (`subregion.css`) 작성 + index1.html에서만 link
- 작업 14: cctv1.js / cctv4.js 분류 정정 (문서)
- 작업 15: 신규 모듈 가드 강화 패턴 정립

**산출물**:
- 수정: `local_server/index.html` (플래그 + 섹션)
- 신규: `local_server/css/subregion.css`
- 갱신: `00_docs/SUBREGION_ALERT/separation/01_inventory.md` (분류 정정)

**사전 조건**:
- 본 마스터 플랜 사용자 승인 완료
- 1단계 상세 계획 작성 + 재검토 완료

**검증 방법**:
- index1 접속 → `window.__SEAGNAL_PAGE === 'index1'` 확인
- index1 접속 → `#subregion-section` DOM 존재 확인 (빈 상태)
- index2 접속 → 변화 없음 (모든 기존 기능 정상 동작)
- 기존 자식해역 표출 (`.coastal-zones`) 양 페이지 모두 정상

**롤백 방법**:
- 추가된 라인만 제거 (git revert로 1커밋 되돌림)

**예상 위험도**: **매우 낮음**

### 3.2 [2단계] 데이터 파일 준비

**목표**: 자식해역 처리에 필요한 신규 데이터 파일 3개 준비 + 백업 시스템 통합

**포함 작업**:
- 작업 6: 신규 데이터 파일 3개 생성
  - `local_server/data/subregion_lifecycle.json` (자식해역 라이프사이클)
  - `local_server/data/region_alias_map.json` (해역 이름 매핑 — audit/에서 이동)
  - `local_server/data/subregion_error_log.json` (오류 로그)
- 작업 10: `cloud_backup.js`의 백업 대상 목록에 `region_alias_map.json` 추가

**산출물**:
- 신규: 3개 JSON 파일 (초기 빈 상태 또는 매핑 데이터)
- 수정: `local_server/cloud_backup.js`

**사전 조건**:
- 1단계 완료 + 검증 통과
- 2단계 상세 계획 작성 + 재검토 완료

**검증 방법**:
- 3개 파일 존재 + JSON 파싱 가능 확인
- 매핑 테이블 무결성 검증 (스키마)
- 클라우드 백업 다음 사이클 시 새 파일 포함 여부 확인 (또는 모킹 테스트)

**롤백 방법**:
- 신규 파일 3개 삭제
- cloud_backup.js의 추가 항목 제거

**예상 위험도**: **매우 낮음**

### 3.3 [3단계] 백엔드 모듈 작성

**목표**: 자식해역 처리의 백엔드 핵심 로직 작성

**포함 작업**:
- 작업 5: `routes/subregion.js` (신규 API 라우트 4개)
  - GET `/api/subregion/state`
  - GET `/api/subregion/error-log`
  - POST `/api/subregion/error-ack`
  - POST `/api/subregion/error-ack-all`
- 작업 7: `services/afso_poller.js` (방재기상 API 폴링)
- 작업 8: `services/subregion_judge.js` (LOGIC 판정 로직 9단계)
- 작업 19: `services/subregion_comparator.js` (비교 검증 모듈) ★
- 작업 20: 비교 결과 푸시 발송 정책 + 스팸 방지

**산출물**:
- 신규: `routes/subregion.js`
- 신규: `services/afso_poller.js`
- 신규: `services/subregion_judge.js`
- 신규: `services/subregion_comparator.js`
- 신규: `services/subregion_push_throttler.js` (또는 통합)

**사전 조건**:
- 2단계 완료 + 검증 통과
- 3단계 상세 계획 작성 + 재검토 완료

**검증 방법**:
- 각 신규 모듈 단위 테스트 (입력별 출력 검증)
- afso_poller가 실제 방재기상 API에서 응답 정상 수신
- subregion_judge가 통보문 + 방재기상 입력으로 정상 판정
- comparator가 두 결과 비교하여 상이성 정확히 감지
- 신규 라우트 응답 정상

**롤백 방법**:
- 신규 모듈 파일 삭제
- 라우트 등록 제거

**예상 위험도**: **중간** (가장 큰 백엔드 변경)

### 3.4 [4단계] 프론트엔드 표출

**목표**: index1에서 자식해역 두 결과를 나란히 표시

**포함 작업**:
- 작업 3: `js/subregion_display.js` (신규 자식해역 표출 모듈)
- 작업 21: index1 화면에 두 결과(기존+신규) 나란히 표시 ★
- 작업 16: localStorage 키 네임스페이싱 (`seagnal_subregion_*`)
- 작업 17: 신규 이벤트 네임스페이싱 (`seagnal:subregion-*`)

**산출물**:
- 신규: `local_server/js/subregion_display.js`
- 수정: `local_server/index.html` (`<script>` 태그 추가)

**사전 조건**:
- 3단계 완료 + 검증 통과 (백엔드 API가 정상 응답)
- 4단계 상세 계획 작성 + 재검토 완료

**검증 방법**:
- index1 접속 → 신규 자식해역 표출 영역에 데이터 표시
- index1에 기존 + 신규 둘 다 표시 확인
- index2 접속 → 변화 없음 (신규 모듈 동작 안 함 확인)
- 페이지 가드 동작 확인

**롤백 방법**:
- `<script>` 태그 제거
- 신규 JS 파일 삭제

**예상 위험도**: **낮음**

### 3.5 [5단계] 통합 및 어드민

**목표**: 스케줄러 통합 + 통합관리자 센터 자식해역 비교 결과 통합

**포함 작업**:
- 작업 9: `scheduler.js`에 신규 잡 등록 (1분 사이클 안 통보문 다음에)
- 작업 22: 특보수집오류 탭에 비교 불일치 항목 통합 + index1 페이지 가드 ★
- 작업 11: 통합관리자 센터 UI 정정 (별도 탭 아닌 기존 탭 통합)
- 작업 12: 관리자 푸시 통합 (기존 admin_push 호출)
- 작업 18: index1만 표시 정책 적용 (옵션 b)

**산출물**:
- 수정: `local_server/scheduler.js`
- 수정: `local_server/js/admin.js` (특보수집오류 탭 확장)
- 수정: `local_server/routes/admin.js` (자식해역 오류 처리 추가)

**사전 조건**:
- 4단계 완료 + 검증 통과
- 5단계 상세 계획 작성 + 재검토 완료

**검증 방법**:
- 1분 사이클 통보문 → 방재기상 → 비교 → 영속화 정상 동작
- 강제 상이성 발생 시 (테스트 데이터로) 푸시 도착
- 통합관리자 센터에서 자식해역 비교 항목 표시
- 코드 형식 + 서술 형식 둘 다 정상 표시
- index2의 어드민에서는 자식해역 비교 항목 안 보임

**롤백 방법**:
- 환경 변수 `AFSO_ENABLED=false`로 즉시 비활성화
- 또는 스케줄러 잡 등록 제거

**예상 위험도**: **중간** (가장 통합적인 변경)

## 6. 전체 작업 진행 순서 (반복 사이클)

각 단계마다 다음 사이클을 반복합니다:

```
[1] N단계 상세 계획 작성
  ↓

  ↓

  ↓

  ↓

  ↓
[6] N단계 작업 실제 수행
  ↓
[7] N단계 검증
  ↓
[8] git 커밋 + 푸시
  ↓
[9] 사용자 다음 단계 진행 승인
  ↓
(N+1단계로)
```

이 사이클이 6번 반복되어 본 작업이 완료됩니다.
