## 1. 원칙 1 — 부모해역은 통보문이 진실이다 (Parent Truth Source)

### 1.1 정의

부모해역의 특보 상태(발효 여부, 레벨, 시각, 종류)에 대한 **유일한 근거는 통보문**이다. 다른 어떤 데이터 소스도 부모해역의 진실을 결정하지 못한다.

### 1.2 적용 범위

- 부모해역의 발효 여부 판정 → 통보문
- 부모해역의 특보 레벨(예비/주의보/경보) → 통보문
- 부모해역의 발효/해제 시각 → 통보문
- 부모해역의 특보 종류(풍랑/태풍/폭풍해일 등) → 통보문
- 부모해역의 자동 해제 시점 → 통보문의 `tmCc`(해제예정시각)

### 1.3 함수 형태

```
function getParentState(regionId):
  return readFromTongbomun(regionId)
  # 방재기상 데이터는 절대 부모 상태 결정에 사용되지 않음
```

### 1.4 이 원칙이 만들어진 이유

방재기상시스템은 격상/격하/해제 발표가 나는 즉시 그 정보를 표시 또는 제거합니다. 따라서 방재기상시스템이 보여주는 상태는 "현재 발효 상태"가 아니라 "미래 적용 예정 상태"가 섞여 있습니다.

만약 방재기상시스템을 부모해역의 진실로 채택한다면, 통보문은 풍랑 주의보 발효 중인데 우리 앱은 풍랑 경보로 잘못 표시하는 일이 발생합니다. 이를 방지하기 위해 부모해역은 무조건 통보문이 우선합니다.

## 2. 원칙 2 — 자식해역의 트리 존재 여부는 방재기상이 진실이다 (Child Existence Source)

### 2.1 정의

자식해역이 현재 트리에 발효 상태로 존재하는지 여부에 대한 **유일한 근거는 방재기상시스템**이다. 통보문은 자식해역 정보를 제공하지 않으므로 자식해역의 존재 여부를 알 수 없다.

### 2.2 적용 범위

- 자식해역이 현재 발효 중인지 → 방재기상시스템 응답에 비어있지 않은 행이 있는가
- 자식해역이 트리에서 사라졌는지 → 방재기상시스템 응답에서 행이 빠졌는가
- 자식해역이 새로 등장했는지 → 직전 사이클에 없었는데 이번 사이클에 등장했는가

### 2.3 함수 형태

```
function isChildActive(childRegId):
  rows = readFromAfsoApi()
  match = rows.find(r => r.regId == childRegId)
  if (match == null): return false
  if (match.wrnSeq == "99"): return false  # 빈 행 = 특보 없음 신호
  return true
```

### 2.4 이 원칙이 만들어진 이유

기존 텍스트 스크래핑 방식은 자식 일부만 빠진 경우와 모두 빠진 경우를 구분할 수 없었습니다. 방재기상시스템은 트리 단위로 응답을 제공하므로, "이 자식이 지금 트리에 어떻게 존재하는지"의 가장 정확한 정보원입니다.

다만 이 원칙은 **"자식해역의 트리 등장 여부"** 에만 적용되며, **"자식해역의 레벨"** 은 원칙 3에 의해 별도 캡 처리됩니다.

## 3. 원칙 3 — 자식의 레벨/시각은 부모로 캡한다 (Child Capping)

### 3.1 정의

자식해역의 특보 레벨과 종료 시각은 방재기상시스템에서 가져오되, **부모해역 통보문의 현재 발효 레벨과 종료 시각을 상한으로** 삼는다. 자식이 부모를 초과하면 부모 값으로 강제 절단(캡)한다.

### 3.2 캡 규칙

- **레벨 캡**: `자식 레벨 ≤ 부모 통보문 현재 발효 레벨`
  - 자식이 부모보다 같거나 낮을 수 있음
  - 자식이 부모보다 높을 수 없음 (있으면 부모 값으로 캡)
- **시각 캡**: `자식 종료 시각 ≤ 부모 통보문 종료 시각`
  - 자식이 부모보다 더 짧게 끝날 수 있음
  - 자식이 부모보다 더 길게 끝날 수 없음 (있으면 부모 값으로 캡)

### 3.3 함수 형태

```
function applyCapping(childRaw, parentTongbomun):
  level = min(childRaw.level, parentTongbomun.currentLevel)
  endTime = min(childRaw.tmEd, parentTongbomun.tmCc)

  if (childRaw.level > parentTongbomun.currentLevel):
    log("[데이터 이상] 자식 레벨이 부모보다 높음 — 캡 적용")

  if (childRaw.tmEd > parentTongbomun.tmCc):
    log("[데이터 이상] 자식 시각이 부모보다 길음 — 캡 적용")

  return { level, endTime }
```

### 3.4 이 원칙이 만들어진 이유

방재기상시스템은 격상 발표가 나면 즉시 자식을 새 레벨로 표시합니다. 통보문상 부모는 아직 주의보인데 방재기상상 자식은 경보로 표시되는 경우가 발생합니다.

이때 사용자에게 "가파도 경보"라고 표시하면 사실과 다릅니다. 통보문은 "지금 부모는 주의보, 14:00부터 경보"인데, 경보 발효는 14:00 이후입니다. 14:00 이전에는 자식도 주의보로 표시되어야 정확합니다.

또한 자식이 부모보다 더 높은 레벨이 자연 발생하는 일도 없습니다 (부모해역 = 자식해역의 합집합 영역이므로). 따라서 자식이 부모를 초과하면 항상 데이터 이상이며, 캡으로 안전하게 처리합니다.

### 3.5 자식이 부모보다 낮을 수 있는 케이스 (정상)

부모는 경보, 자식 중 가파도연안만 주의보인 경우는 정상적으로 발생할 수 있습니다.

- 부모 통보문: 제주도서부앞바다 = 풍랑 경보 발효 중
- 방재기상시스템: 북서연안 = 경보, 남서연안 = 경보, 가파도연안 = 주의보
- 우리 앱 표시: 가파도연안만 주의보 (캡 적용 대상 아님, 그대로 표시)

이 경우 자식이 부모보다 낮으므로 캡 절단 없이 그대로 사용합니다.

## 4. 원칙 4 — 보수적 판정을 우선한다 (Conservative Judgement)

### 4.1 정의

자식해역의 상태를 모호하게 판정해야 할 때, **사용자에게 안전한 쪽(거짓 해제 방지)으로 보수적으로 판정**한다. 즉, "확정 해제"보다 "추정 발효 유지"를 선호한다.

### 4.2 적용 케이스

- **부모-자식 동시 사라짐**
  - 가능성: 진짜 지금 해제, 또는 미래 해제 예정으로 사전 삭제
  - 보수적 판정: 부모 해제 시각까지 자식 발효 유지 (거짓 해제 방지)
- **자식 1회 빠짐**
  - 가능성: 진짜 해제, 또는 일시 오류
  - 보수적 판정: 다음 사이클 한 번 더 확인 후 판정 (1회 빠짐 = 표시 유지)
- **통보문 폴링 실패**
  - 가능성: 부모 상태가 갱신됐을 수도, 그대로일 수도
  - 보수적 판정: 자식 신규 해제 처리 보류
- **방재기상 응답 오류**
  - 가능성: 자식 상태 갱신 가능, 또는 데이터 신뢰 불가
  - 보수적 판정: 자식 상태 갱신 보류

### 4.3 함수 형태

```
function judgeChildStatus(childRegId, currentResponse, previousResponse):
  if (currentResponse.isError or currentResponse.isEmpty):
    return previousState  # 갱신 보류 (보수)

  if (childMissing(childRegId, currentResponse)):
    if (parentSurvives(parentOf(childRegId))):
      if (missedCount(childRegId) >= 2):
        return RELEASED
      else:
        return previousState  # 1회 빠짐은 유지 (보수)
    else:
      return PENDING_RELEASE_AT_PARENT_TIME  # 동시 사라짐 (보수)

  return childRaw.status  # 정상 응답이면 그대로 사용
```

### 4.4 이 원칙이 만들어진 이유

자식해역에 푸시 알림은 없지만, 사용자(특히 선원)가 화면을 보고 발효 여부를 판단합니다. 거짓 해제(실제로는 발효 중인데 해제로 표시)는 사용자의 안전에 직접적인 영향을 미칠 수 있습니다.

반대로 거짓 발효(실제로는 해제됐는데 발효로 표시)는 안전 측 오차이므로 상대적으로 위험이 낮습니다. 따라서 모든 모호한 케이스는 거짓 해제를 회피하는 방향으로 판정합니다.

이 원칙의 부작용으로 사용자가 보는 정보 일부는 "추정"이 됩니다. 추정 표시 정책은 `15_estimation_display.md`에서 다룹니다.

## 5. 원칙 5 — 부모해역이 없으면 자식해역도 없다 (Parent-Child Coupling)

### 5.1 정의

자식해역의 특보는 부모해역의 특보의 일부로만 존재한다. **부모해역이 발효되지 않은 상태에서 자식해역만 단독 발효되는 일은 없다.** 부모가 해제되면 자식도 함께 해제된다.

### 5.2 적용 결과

- 부모해역의 통보문이 자동 해제되는 시점에 그 부모의 모든 자식해역도 일괄 정리
- 부모가 자동 해제 후 자식만 발효된 채로 남아있는 일을 코드 차원에서 방지
- 이를 "고아 자식(orphan child) 방지"라고 한다

### 5.3 함수 형태

```
function onParentAutoRelease(parentRegId):
  parentZone.current = null
  parentZone.history = []

  for each child in subregionsOf(parentRegId):
    child.current = null
    child.status = "released"
    log("[부모 해제 연동] 자식 " + child.name + " 함께 정리")
```

### 5.4 이 원칙이 만들어진 이유

자식해역은 부모해역의 영역 일부이므로 자식만 단독 존재하는 것은 자연 현상에서 불가능합니다. 부모해역이 영향권에서 벗어나면 자식해역도 동시에 벗어납니다.

코드 차원에서 부모와 자식을 별도 자료구조로 관리하면 부모만 해제되고 자식이 남는 버그가 발생할 수 있습니다. 이 원칙을 명시적으로 반영하면 그러한 버그를 원천적으로 방지할 수 있습니다.

## 6. 원칙 간 우선순위 (충돌 시 적용 순서)

여러 원칙이 동시에 충돌하는 경우 다음 순서로 적용합니다.

| 우선순위 | 원칙 | 비고 |
|---|---|---|
| 1 | 원칙 1 (부모는 통보문) | 가장 강한 원칙. 다른 모든 원칙에 우선 |
| 2 | 원칙 5 (부모-자식 결합) | 부모가 없으면 자식도 강제 정리 |
| 3 | 원칙 4 (보수적 판정) | 모호하면 안전 측으로 |
| 4 | 원칙 3 (자식 캡) | 자식 데이터에 캡 적용 |
| 5 | 원칙 2 (자식 트리는 방재기상) | 캡 후 자식 상태 확정 |

이 순서는 한 사이클 안에서 규칙을 적용하는 구체 순서로 이어지며, 자세한 내용은 `14_rule_order.md`에서 다룹니다.
