# 자식해역 특보 표출 로직 — 1.1 배경 및 문제 정의

## 0. 본 문서의 위치

본 파일은 SEAGNAL 앱의 "자식해역 특보 표출" 기능 도입에 관한 종합 문서 시리즈의 **첫 번째 파일**입니다.

문서 시리즈는 다음 세 묶음으로 나뉘어 있습니다.

- **01_LOGIC/** — 판정 로직, 케이스 분기, 규칙 적용 순서
- **02_DATA_MODEL/** — 방재기상 API 명세, 데이터 파일 스키마, 매핑 테이블
- **03_OPERATIONS/** — 오류 처리, 관리자 알림, index1/index2 분리, 운영 항목

본 파일은 이 중 `01_LOGIC/`의 1번 파일이며, **"왜 이 작업이 필요했는가"** 를 다룹니다. 본 파일을 읽고 나면 이후 모든 결정 사항의 배경을 이해할 수 있습니다.

## 1. 우리 앱의 기존 동작 방식 (작업 도입 전)

### 1.1 부모해역의 정보 수집 방식

부모해역(예: 동해남부앞바다, 제주도서부앞바다, 서해남부앞바다 등)에 대한 특보 정보는 **기상청에서 발표되는 통보문(텍스트 발표문)** 을 통해 수집합니다.

- 통보문에는 다음 정보가 명시되어 있습니다.
  - 발표 시각 (`tmFc`)
  - 발효 시각 (`tmEf`)
  - 해제 예정 시각 (`tmCc` 또는 `tmEd`)
  - 특보 종류 (풍랑, 태풍, 폭풍해일 등)
  - 특보 수준 (예비, 주의보, 경보)
- 따라서 우리 앱은 부모해역의 특보 상태를 명확히 알 수 있으며, 미래 해제 시점도 알 수 있습니다.
- 통보문 기반의 자동 해제 로직은 이미 코드에 반영되어 있습니다.
  - 함수: `resolvePendingStatuses()`
  - 위치: `local_server/weather_alerts_crawler.js:284-334`
  - 동작: 매 1분 사이클마다 부모해역의 `tmCc`(해제예정시각)가 현재시각보다 작거나 같으면 `current = null` 처리
  - 별도 해제 통보문이 도착하지 않아도 시각이 도달하면 자동 해제됨

### 1.2 자식해역의 정보 수집 방식 (기존)

자식해역(예: 가파도연안바다, 울산앞바다중 평수구역, 서해남부남쪽안쪽먼바다중조도부근평수구역 등)은 통보문이 별도로 발표되지 않습니다.

- 우리 앱은 기상청 홈페이지의 텍스트를 스크래핑(긁어옴)하여 자식해역 특보 정보를 수집합니다.
- 텍스트 페이지에는 부모해역과 자식해역이 모두 나열되어 있습니다.
- 우리 앱은 다음 규칙으로 판정해 왔습니다.
  - 텍스트가 있으면 → 해당 자식해역에 특보가 발효 중
  - 텍스트가 없으면 → 해당 자식해역에 특보가 없거나 해제됨

이 방식은 단순하지만 다음 절에서 설명하는 심각한 한계를 가집니다.

## 2. 텍스트 스크래핑 방식의 한계 (문제 발생 지점)

### 2.1 기상청 홈페이지의 표출 특성

기상청 홈페이지는 특보 정보를 다음과 같이 다룹니다.

- **발표/발효 시점**
  - 발표가 나는 즉시 텍스트가 페이지에 표출됨
  - 우리 앱은 이를 정상적으로 수집하여 발효 처리

- **해제 발표 시점 (문제 시점)**
  - 해제 통보문이 나오면 페이지에서 **즉시 텍스트를 삭제**해버림
  - 페이지에는 명시적인 "해제 시각"이 표시되지 않음
  - 우리 앱은 텍스트가 사라지는 것만 보고 "해제됐구나"라고 판단

- **격상/격하/회전(다른 종류로 변경) 발표 시점 (문제 시점)**
  - 미래 시점에 적용될 격상/격하 발표가 미리 나오면, 페이지에서 **현재 텍스트를 미리 삭제**해버림
  - 예: 14:00에 격하 적용 예정인 발표가 10:00에 나오면, 10:00에 이미 페이지에서 현재 발효 중인 텍스트가 사라짐
  - 우리 앱은 10:00에 "사라졌으니 해제됐구나"라고 잘못 판단

### 2.2 부모해역에서는 큰 문제가 없는 이유

부모해역은 통보문에서 발표되는 정보이므로, 우리 앱은 **통보문에 명시된 해제 시각까지 발효 상태를 유지**하도록 보완 로직을 두고 있습니다.

- 즉, 텍스트 페이지에서 부모해역 텍스트가 미리 사라져도, 통보문이 알려주는 "06:00 해제 예정" 정보가 있으니 우리 앱은 06:00까지 발효 상태로 유지합니다.
- 이는 텍스트 스크래핑 방식의 한계를 통보문이 보완해 주는 구조입니다.

### 2.3 자식해역에서는 보완이 불가능한 이유

자식해역은 통보문이 없습니다. 텍스트 스크래핑이 유일한 정보원입니다.

- 텍스트가 사라지면 그것이 다음 둘 중 어느 경우인지 구분할 수 없습니다.
  - **(가) 진짜 지금 해제된 경우** → 텍스트 즉시 제거가 정확한 동작
  - **(나) 미래 해제 예정으로 인한 사전 삭제** → 사실은 아직 발효 중인데 우리 앱이 해제로 잘못 판단
- 마찬가지로 격상/격하 발표가 미리 나오는 경우에도 잘못 판단할 수 있습니다.

### 2.4 가장 큰 문제 — 자식해역 부분 사라짐의 모호함

구체 예시: 제주도서부앞바다(부모) — 북서연안 / 남서연안 / 가파도연안 (자식 3개)

이 구조에서 다음 두 상황이 발생할 수 있습니다.

- **상황 A — 자식 일부만 텍스트 사라짐 (부모와 다른 자식은 살아있음)**
  - 가능성: 그 자식만 정말 해제되었을 확률이 높음
  - 다른 자식과 부모는 그대로 살아있으므로, 미래 해제 예정으로 인한 사전 삭제로 보기 어려움
  - 우리 앱의 판정: 그 자식만 표출 제거 (정상)

- **상황 B — 부모와 자식 전부 텍스트 사라짐**
  - 가능성 1: 부모 해제 발표가 났고, 부모-자식 모두 미래 해제 예정으로 사전 삭제됨
  - 가능성 2: 정말로 지금 부모-자식 모두 해제됨
  - 텍스트 스크래핑만 보고는 두 가능성을 구분할 수 없음
  - 따라서 자식해역의 표출을 어떻게 해야 할지 판단이 어려움

이 모호함이 본 작업의 도입 배경의 핵심입니다.

## 3. 방재기상시스템의 특성 (대안 데이터 소스)

### 3.1 방재기상시스템 개요

기상청은 별도로 모바일 방재기상시스템을 운영합니다.

- URL: `https://afso.kma.go.kr/m/wrnSpec.jsp`
- 시스템 명: 모바일 방재기상시스템
- 표출 내용: 부모해역과 자식해역의 트리 구조 + 각 해역의 현재 특보 정보

### 3.2 방재기상시스템의 강점

- **모든 부모/자식 해역을 항상 응답에 포함**
  - 특보가 없는 해역도 빈 행(`wrnSeq=99`)으로 응답에 들어옴
  - 즉, "특보 없음을 명시적으로 확인하는 신호"를 받을 수 있음
- **자식해역 단위의 트리 구조**
  - 자식 일부만 빠짐 / 모두 빠짐 / 새로 등장을 코드 차원에서 구분 가능
  - 이를 통해 텍스트 스크래핑 방식보다 훨씬 정밀한 상태 추적이 가능

### 3.3 방재기상시스템의 약점 (한계)

- **해제 발표 시 즉시 페이지에서 빠짐**
  - 기상청 홈페이지와 동일한 문제
  - 방재기상시스템 단독으로는 "지금 해제"와 "미래 해제 예정"을 구분 불가
- **격상/격하 발표 시 즉시 새 레벨로 표시**
  - 예: 통보문상 14:00부터 격상 예정이라도, 10:00에 발표가 나면 그 시점부터 방재기상시스템은 이미 격상된 레벨로 표시
  - 따라서 방재기상시스템의 자식 레벨 정보를 그대로 따르면 잘못된 정보가 사용자에게 표시될 수 있음

## 4. 본 작업의 목표 (핵심 아이디어)

### 4.1 두 데이터 소스의 역할 분담

본 작업은 다음과 같이 두 정보원의 역할을 명확히 분리합니다.

- **부모해역의 truth source** = 통보문 (기존 그대로, 변경 없음)
  - 부모해역의 발효 여부, 레벨, 발효 시각, 해제 예정 시각의 진실은 모두 통보문에서만 결정
- **자식해역의 truth source** = 방재기상시스템 (신규 도입)
  - 자식해역의 발효 여부, 트리에서의 등장/이탈은 방재기상시스템에서 결정
  - 단, 자식해역의 레벨/시각은 부모해역 통보문 기준으로 캡(상한 적용)

### 4.2 방재기상시스템 활용의 핵심 포인트

자식해역이 방재기상시스템에서 빠지는 패턴을 부모해역의 통보문 상태와 결합하여 해석합니다.

- **부모 살아있음 + 자식 일부만 빠짐** → 자식 즉시 해제로 판정
- **부모 살아있음 + 자식 전부 빠짐** → 자식 즉시 해제로 판정 (자식만 해제된 케이스)
- **부모 통보문 해제 시각 임박 + 부모-자식 동시 사라짐** → 부모 해제 시각까지 자식 유지 (미래 해제 예정으로 추정)
- **자식이 새로 등장** → 자식 신규 발효로 판정 (단, 부모 통보문이 격상되어야 진짜 격상)

### 4.3 방재기상시스템의 약점 보완 방법

방재기상시스템은 격상/격하 발표를 즉시 표시하는 약점이 있으므로, 우리 앱은 다음 캡 규칙을 적용합니다.

- 자식해역의 레벨이 부모해역 통보문 레벨보다 높으면 → 부모 레벨로 캡 (강제 절단)
- 자식해역의 종료 시각이 부모해역 통보문 종료 시각보다 길면 → 부모 시각으로 캡

이렇게 하면 방재기상이 미리 격상해 버린 정보가 사용자에게 잘못 노출되지 않습니다.

## 5. 본 작업의 표출 정책

### 5.1 자식해역에 표시하지 않는 정보

자식해역은 부모해역에 비해 표출 정보가 단순합니다.

- 발표/발효/해제 시각의 상세값은 사용자에게 표시하지 않음
- 미래 격상/격하 예고도 표시하지 않음
- 다른 종류의 특보가 다가오는 정보도 표시하지 않음
- 푸시 알림도 발송하지 않음

### 5.2 자식해역에 표시하는 정보

다음 항목만 사용자에게 보여줍니다.

- 현재 발효 중인 특보 종류 (풍랑/태풍/폭풍해일 중 하나)
- 현재 수준 (예비/주의보/경보)
- 단순 상태 라벨 (발표됨, 발효됨, 격상됨 정도)

### 5.3 표시의 신뢰도 구분 (추정 표시)

- 방재기상시스템 응답에 정상적으로 등장한 자식해역은 "확정" 상태로 표시
- 추정 로직(부모 해제 시각까지 유지, 1회 빠진 후 유지 등)으로 유지되는 자식해역은 "추정" 상태로 표시
- 추정 상태에는 다음 툴팁을 부가
  - "본 정보는 실제 발표내용과 다를 수 있습니다."

상세 정의는 `01_LOGIC/15_estimation_display.md`에서 다룹니다.

## 6. 본 작업의 적용 범위 (기능적 경계)

### 6.1 변경되지 않는 영역

- 부모해역의 통보문 수집 로직 (`weather_alerts_crawler.js`, `report_alert_processor.js`, `ai_report_parser.js` 등)
- 부모해역의 자동 해제 로직 (`resolvePendingStatuses()`)
- 부모해역의 푸시 알림 정책
- 기존 데이터 파일 (`weather_alerts.json`, `active_lifecycle.json`)의 부모해역 부분

### 6.2 신규 추가되는 영역

- 방재기상시스템 API 호출 로직 (신규)
- 자식해역 상태 판정 로직 (신규)
- 신규 데이터 파일
  - `subregion_lifecycle.json` (자식해역 활성 상태)
  - `region_alias_map.json` (방재기상 ↔ 우리 앱 해역 이름 매핑)
  - `subregion_error_log.json` (자식해역 관련 오류 로그)
- 통합관리자 센터의 자식해역 오류 영역 (신규)
- 자식해역 오류 발생 시 관리자 푸시 알림 (기존 패턴 재활용)

### 6.3 테스트 적용 범위

- 본 기능은 우선 `index1` 페이지에만 도입
- `index2` 페이지(현재 사용자 운영 페이지)는 영향 없음
- 충분한 검증 후 `index2`에 적용 여부 결정

## 7. 본 작업의 도입 효과 (요약)

본 작업이 완료되면 자식해역 특보 표출의 정확성이 다음과 같이 개선됩니다.

- 자식 일부만 해제되었는지, 부모와 함께 미래에 해제되는지 구분 가능
- 격상/격하 발표가 미리 나와도 사용자에게 보이는 자식해역 레벨은 통보문 기준으로 정확
- 부모 통보문이 살아있는 동안 자식해역의 일시적 사라짐을 안전하게 보수적으로 처리
- 자식해역 데이터 이상이나 매핑 누락이 운영자에게 즉시 인지됨
