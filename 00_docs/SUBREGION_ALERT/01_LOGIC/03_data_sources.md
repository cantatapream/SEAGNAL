# 자식해역 특보 표출 로직 — 1.3 두 데이터 소스의 역할 분담

## 0. 본 파일의 위치

본 파일은 `01_LOGIC/` 시리즈의 세 번째 파일입니다. 이전 파일(`02_design_principles.md`)에서 정리한 5가지 원칙을 실제 데이터 흐름에 어떻게 매핑하는지 다룹니다.

## 1. 두 데이터 소스의 개요

본 작업은 두 개의 독립된 데이터 소스를 결합하여 자식해역 상태를 결정합니다.

### 1.1 데이터 소스 1 — 통보문 (Tongbomun)

| 항목 | 값 |
|---|---|
| 정보원 | 기상청 통보문 발표 |
| 수집 방식 | 기존 크롤링 + AI 파싱 |
| 수집 주기 | 1분 (기존 스케줄러) |
| 담당 함수 | `weather_alerts_crawler.js`, `report_alert_processor.js`, `ai_report_parser.js` |
| 저장 위치 | `local_server/data/weather_alerts.json`, `active_lifecycle.json` |
| 담당 영역 | **부모해역만** |

### 1.2 데이터 소스 2 — 방재기상시스템 (AFSO)

| 항목 | 값 |
|---|---|
| 정보원 | https://afso.kma.go.kr/m/wrnSpec.jsp |
| API 엔드포인트 | `POST /afsOut/mmr/warning/retMmrWarningSeaNow.kajx` |
| 수집 방식 | 신규 폴링 (HTTP POST) |
| 수집 주기 | 1분 (신규 스케줄러) |
| 담당 함수 | (신규 구현 예정) |
| 저장 위치 | `local_server/data/subregion_lifecycle.json` (신규) |
| 담당 영역 | **자식해역만** |

> 부모해역 정보도 방재기상 응답에 포함되지만 본 작업에서는 자식해역에만 활용합니다. 부모해역은 통보문이 진실(원칙 1)이기 때문입니다.

## 2. 데이터 소스별 책임 분담 (역할 분리)

### 2.1 통보문이 담당하는 정보

- 부모해역의 발효 여부 (현재 발효 중인지)
- 부모해역의 특보 수준 (예비/주의보/경보)
- 부모해역의 특보 종류 (풍랑/태풍/폭풍해일 등)
- 부모해역의 발표 시각 (`tmFc`)
- 부모해역의 발효 시각 (`tmEf`)
- 부모해역의 해제 예정 시각 (`tmCc`)
- 부모해역의 자동 해제 트리거

### 2.2 방재기상이 담당하는 정보

- 자식해역의 트리 등장 여부
- 자식해역의 발효 시각 (자식 자체 시각, 부모와 다른 경우)
- 자식해역의 종료 예정 시각 (자식 자체 시각, 캡 적용 대상)
- 자식해역이 사라지는 패턴 (자식만 빠짐 / 동시 사라짐 / 신규 등장)
- 빈 행(`wrnSeq=99`)에 의한 "특보 없음 확인 신호"

### 2.3 두 소스가 결합하여 결정하는 정보

- 자식해역의 최종 표시 레벨 (방재기상 자식 레벨을 부모 통보문 레벨로 캡)
- 자식해역의 최종 표시 종료 시각 (방재기상 자식 시각을 부모 통보문 시각으로 캡)
- 자식해역의 추정 vs 확정 여부 (방재기상 응답 + 직전 사이클 비교)
- 자식해역의 신규 발효 / 격상 / 격하 / 해제 이벤트 분류

## 3. 한 사이클 안에서의 데이터 흐름

### 3.1 1분 사이클의 단계

매 1분마다 다음 순서로 실행됩니다.

```
[Step 1] 통보문 크롤링 및 파싱
  └─ 부모해역 상태 갱신 (weather_alerts.json, active_lifecycle.json)
  └─ resolvePendingStatuses() 호출 → 자동 해제 처리
[Step 2] 방재기상 API 폴링
  └─ retMmrWarningSeaNow.kajx 호출
  └─ 응답 저장 (raw 응답 보관 권장)
[Step 3] 자식해역 상태 종합 판정
  └─ Step 1과 Step 2의 결과를 결합
  └─ 캡 규칙 / 보수적 판정 / 격상 판정 등 적용
  └─ subregion_lifecycle.json 갱신
[Step 4] 사용자 표출용 데이터 생성
  └─ 부모 + 자식 통합 화면 데이터 구성
```

### 3.2 단계 간 의존성

- Step 2는 Step 1과 독립적으로 실행 가능 (병렬 실행 가능)
- Step 3은 Step 1과 Step 2의 결과 모두 필요 (직렬 실행)
- 한 단계의 실패는 다음 단계의 처리에 영향 (오류 처리는 별도 정책)

### 3.3 함수 형태

```
function runOneCycle():
  # Step 1
  parentResult = crawlTongbomun()
  resolvePendingStatuses(parentResult.zones)

  # Step 2
  afsoResult = pollAfsoApi()

  # Step 3
  judgeSubregions(parentResult, afsoResult)

  # Step 4
  generateDisplayData()
```

## 4. 단일 책임 원칙 — 데이터 소스 침범 금지

### 4.1 통보문 영역에 방재기상이 끼어들지 않는다

- 부모해역의 레벨 결정에 방재기상의 부모 행은 사용하지 않음
- 부모해역의 시각 결정에 방재기상의 부모 행은 사용하지 않음
- 부모해역의 자동 해제 트리거에 방재기상의 부모 사라짐은 사용하지 않음

### 4.2 방재기상 영역에 통보문이 끼어들지 않는다

- 자식해역의 트리 등장 여부는 통보문으로 판정하지 않음 (통보문은 자식 정보가 없음)
- 자식해역의 신규 발효 시점은 통보문 시각이 아닌 방재기상 등장 시점

### 4.3 결합은 Step 3에서만 일어난다

- Step 1과 Step 2는 각자의 데이터 소스만 처리
- Step 3에서만 두 결과를 비교 / 캡 / 결합
- 코드의 역할 분리를 명확히 유지

## 5. 데이터 소스의 신뢰 수준

### 5.1 통보문의 신뢰 수준

- **신뢰도: 매우 높음**
- 기상청에서 공식 발표하는 텍스트
- 자동 해제 트리거에 사용되는 정확한 시각 정보 포함
- 단점: 자식해역 정보 부재

### 5.2 방재기상의 신뢰 수준

- **신뢰도: 중간**
- 트리 구조는 정확
- 그러나 격상/격하/해제 발표가 즉시 표시에 반영되어 "현재 발효 상태"와 다를 수 있음
- 단독으로는 자식해역의 미래 해제 예정과 즉시 해제를 구분 불가
- 빈 행(`wrnSeq=99`)이 "특보 없음" 명시 신호이므로 부분적 신뢰는 가능

### 5.3 결합 시 신뢰 수준

- 부모 = 통보문 (높음) + 자식 = 방재기상 (중간) + 캡 적용 + 보수적 판정
- 결합된 결과의 신뢰도는 단일 소스보다 높지만, 일부 케이스는 추정으로 분류
- 추정 케이스에는 사용자 안내 툴팁 부가

## 6. 두 소스의 갱신 시점 차이 (시간 동기화 이슈)

### 6.1 갱신 시점이 다를 수 있다

- 통보문 발효: 14:00:00 (예: 통보문에 명시된 발효 시각)
- 방재기상 등장: 14:00:00 ~ 14:01:30 (방재기상 갱신은 약간의 지연 가능)

### 6.2 이로 인한 일시적 불일치

- 14:00:30 시점:
  - 통보문 = 부모 풍랑 경보 발효 중
  - 방재기상 = 자식 행 아직 미등장

### 6.3 우리 앱의 처리 방침

- 자식해역은 방재기상이 진실 → 자식 행 미등장이면 "특보 없음"으로 표시 (옵션 A 채택)
- 짧은 시간(약 1~2분)의 일시적 깜빡임은 허용
- 사용자 영향: 자식해역에 푸시 알림이 없으므로 큰 문제 없음

자세한 정책은 `06_case_child_disappear.md` 및 `08_case_new_child.md`에서 다룹니다.
