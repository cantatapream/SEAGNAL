# 자식해역 특보 표출 로직 — 1.4 부모/자식 해역 트리 구조

## 0. 본 파일의 위치

본 파일은 `01_LOGIC/` 시리즈의 네 번째 파일로, 방재기상시스템의 해역 트리 구조와 코드 체계를 정리합니다.

본 작업의 모든 케이스 분석에서 자식해역 식별과 부모-자식 매핑은 핵심이므로, 트리 구조에 대한 정확한 이해가 필요합니다.

---

## 1. 해역 트리의 기본 구조

### 1.1 3단계 계층 구조

방재기상시스템의 해역은 3단계로 구성됩니다.

```
[1단계] 광역 (예: 동해)
   └── [2단계] 부모해역 (예: 동해남부앞바다, 울산앞바다, 경북남부앞바다)
            └── [3단계] 자식해역 (예: 울산앞바다중 평수구역, 울산앞바다중 연안바다)
```

### 1.2 본 작업의 대상

본 작업에서 "부모해역"은 위의 **2단계**를, "자식해역"은 **3단계**를 의미합니다.

- 1단계는 이름 표시용으로만 활용 (집계 단위 아님)
- 2단계 = 통보문이 발표되는 단위
- 3단계 = 통보문 없이 방재기상에서만 정보 제공되는 단위

---

## 2. regId 코드 체계

### 2.1 코드 형식

방재기상 API의 `regId` 필드는 다음과 같은 패턴을 가집니다.

```
S{prefix}{level}{detail}

예시:
  S1131000  - 동해남부앞바다 (부모)
  S1131100  - 울산앞바다 (부모)
  S2110200  - 울산앞바다중 평수구역 (자식)
  S2120400  - 울산앞바다중 연안바다 (자식)
```

### 2.2 첫 두 글자 (`S1` vs `S2`)

방재기상 페이지(`seaWarningStatus.js`)의 분기 로직에 따르면 코드의 첫 두 글자는 다음과 같이 구분됩니다.

- **`S1`로 시작**: 일반 해역 (앞바다, 먼바다 등)
- **`S2`로 시작**: 평수구역, 연안바다, 특정먼바다 등 자식해역

### 2.3 `S1` 내부의 세부 구조

`S1` 코드의 4~7번째 자리(`regId.substring(4,8)`)에 따라 다음 분기가 적용됩니다.

| substring(4,8) | 의미 | 예시 |
|---|---|---|
| `2000`, `4000`, `2100`, `2200` | 가장 큰 부모 단위 (광역) | 동해남부앞바다 |
| `1000`, `3000` | 중간 부모 단위 | 울산앞바다, 강원북부앞바다 |
| 그 외 | 자식 해역 | (드물게 S1 안에 자식이 있는 경우) |

이 분기는 방재기상 페이지의 표시 색상 결정에도 사용됩니다(연한 보라/연한 하늘/흰색).

### 2.4 본 작업에서의 코드 활용

본 작업에서는 `regId`를 식별자로만 사용하며, 위의 세부 분기 규칙은 **참고용**입니다. 실제 부모-자식 관계는 응답 객체의 `regUp` 필드에서 직접 가져옵니다.

---

## 3. `regUp` 필드 — 부모 식별자

### 3.1 정의

방재기상 API 응답의 각 행은 `regUp` 필드를 가지며, 이 필드에는 해당 해역의 **부모해역 코드**가 들어 있습니다.

### 3.2 예시

```json
{
  "regId": "S2122000",
  "regKo": "가파도연안바다",
  "regUp": "S1232000",          ← 부모해역 코드
  "regUpKo": "제주도서부앞바다"   ← 부모해역 이름
}
```

### 3.3 본 작업에서의 활용

- 자식해역의 부모 식별: `child.regUp`
- 부모해역의 자식 목록 만들기: `rows.filter(r => r.regUp == parentRegId)`
- 통보문의 부모해역 ↔ 방재기상의 `regUp` 매핑 필요 (이름 표기 차이 보정)

---

## 4. 부모해역 자기 자신이 응답에 포함되는 케이스

### 4.1 부모도 응답 행으로 들어온다

방재기상 API는 부모해역 자기 자신도 한 행으로 응답에 포함합니다.

```json
{
  "regId": "S1131100",      ← 부모 자신
  "regKo": "울산앞바다",
  "regUp": "S1131000",      ← 부모의 상위 (광역)
  "regUpKo": "동해남부앞바다"
}
```

### 4.2 본 작업에서의 처리 방침

- 부모해역의 진실은 통보문이므로 (원칙 1), **방재기상의 부모 행은 자식 판정에 사용되지 않음**
- 다만 부모 행의 `wrnSeq=99` 여부로 "방재기상도 부모를 트리에서 빼버렸는지"를 추가 신호로 활용 가능
- 이 신호는 "부모-자식 동시 사라짐 케이스" 판정의 보조 근거가 됨

### 4.3 함수 형태

```
function classifyRow(row):
  if row.regId == row.regUp:
    return PARENT  # 자기 자신이 부모인 행
  else:
    return CHILD
```

## 5. 통보문 ↔ 방재기상 부모해역 매핑

### 5.1 표기 차이의 가능성

통보문과 방재기상은 같은 해역이라도 표기가 미세하게 다를 수 있습니다.

- 통보문: "제주도서부앞바다"
- 방재기상: "제주서부앞바다" 또는 "제주도서부앞바다" 등

### 5.2 매핑 테이블의 필요성

이름 한 글자 차이로 매칭이 깨지면 부모-자식 결합이 동작하지 않습니다. 따라서 다음 두 가지 매핑이 필요합니다.

- **부모해역 매핑**: 통보문의 부모 이름 ↔ 방재기상의 `regId`
- **자식해역 매핑**: 우리 앱의 자식해역 이름 ↔ 방재기상의 `regId` 및 `regKo`

### 5.3 매핑 테이블 위치

매핑 테이블은 별도 파일로 관리합니다.

- 파일: `local_server/data/region_alias_map.json` (신규)
- 자세한 스키마: `02_DATA_MODEL/04_alias_map_schema.md` 참조
- 운영 정책: `02_DATA_MODEL/06_mapping_policy.md` 참조

### 5.4 알려진 표기 차이 사례

작업 시작 전 이미 확인된 표기 차이 예시:

- 우리 앱: "서해남부남쪽안쪽먼바다중조도부근평수구역"
- 방재기상: "서해남부남쪽안쪽먼바다중조도부근평수구"
- 차이: 끝의 "역" 한 글자 누락

이런 차이가 다른 해역에도 있을 수 있으므로 본 작업 시작 시 **전수조사 1회 작업**이 선행됩니다.

## 6. 트리 구조의 1:N 관계 (부모-자식)

### 6.1 일반 관계

- 한 부모해역은 여러 자식해역을 가질 수 있음 (1:N)
- 한 자식해역은 단일 부모해역에 속함 (1:1 from child)

### 6.2 자식이 0개인 부모해역

일부 부모해역은 자식해역을 갖지 않을 수 있습니다.

- 예: 동해중부안쪽먼바다 (자식해역 없음)
- 이 경우 본 작업의 대상이 아니며, 부모해역만 통보문으로 처리됨

### 6.3 함수 형태

```
function getChildrenOf(parentRegId):
  rows = afsoResponse.metData
  return rows.filter(r => r.regUp == parentRegId and r.regId != parentRegId)

function hasChildren(parentRegId):
  return getChildrenOf(parentRegId).length > 0
```

## 7. 트리 구조 변경 가능성

### 7.1 변경 빈도

해역 코드 체계와 트리 구조는 거의 변경되지 않습니다.

- 새 해역 추가 (드묾)
- 해역 이름 변경 (매우 드묾)
- 코드 체계 변경 (사실상 없음)

### 7.2 변경 발생 시 대응

본 작업은 다음 메커니즘으로 변경에 대응합니다.

- 매핑 테이블에 없는 새 해역 등장 시 → 운영 로그에 기록 (즉시 운영자 인지)
- 자세한 운영 정책: `03_OPERATIONS/02_error_handling.md` 참조
