# index1/index2 분리 분석 — 4. 재검토 (누락 / 위험 / 보완)

## 0. 본 파일의 목적

이전 3개 분리 분석 문서(`01_inventory.md`, `02_dependencies.md`, `03_risk_assessment.md`)를 사용자 요청에 따라 **재검토**한 결과입니다.

**사용자 요구 기준**: "**인덱스 페이지1을 당장 삭제해도 인덱스 페이지2가 정상 작동할 정도의 수준의 연계 분리**"

이 기준은 이전 분석이 채택한 "신규 자원만 추가" 기준보다 훨씬 강합니다. 본 파일은 그 차이를 좁히는 보완 사항을 정리합니다.

## 1. 핵심 발견 — 두 가지 중대한 누락

### 1.1 [누락 ❶] index2도 자식해역(연안바다/평수구역) 표출 중

**이전 분석의 가정**: 자식해역 표출은 본 작업으로 신규 도입.

**실제 사실**: **index2도 현재 자식해역을 그대로 표출하고 있다.**

```
[현재 자식해역 표출 흐름 — 양 페이지 공유]

weather_alerts.json (children 객체 'Y'/null)
   ↓ [공유] js/data.js processSingleAlert() (line 206-308)
   ↓ [공유] appState.coastalAlerts = coastalMap (line 194)
   ↓ [공유] dispatchEvent('seagnal:alerts-changed') (line 199)
   ↓ [공유] js/render.js createAlertElement() → createCoastalElement() (line 940)
   ↓ [공유] js/render_coastal.js .coastal-zones / .coastal-item 렌더
   ↓ DOM #alert-content 안에 표시
```

이 흐름은 **양 페이지 모두에서 그대로 작동 중**입니다.

**의미**:
- 본 작업이 신규 방재기상 기반 자식해역 표출을 추가하면 **index1에서 두 가지 표출이 동시 동작** (텍스트 스크래핑 기반 기존 + 방재기상 기반 신규)
- 이전 분석에서는 이 사실을 가정에서 빠뜨림
- 03 보고서의 "신규 자원만 추가, 기존 영향 0" 주장이 사실상 틀림

### 1.2 [누락 ❷] cctv1.js와 cctv4.js는 index2에서도 로드된다

**이전 분석의 분류**: `cctv1.js ~ cctv6.js` 6개 모두 **index1 전용**.

**실제 사실**:
- `index2.html:2599` — `<script src="js/cctv1.js"></script>` **로드됨**
- `index2.html:2600` — `<script src="js/cctv4.js"></script>` **로드됨**
- 다른 4개(`cctv2.js`, `cctv3.js`, `cctv5.js`, `cctv6.js`)는 index1 전용 맞음

**의존 관계**:
- `js/ocean_cctv.js:26, 246, 855-856, 1357-1358` — `window.CCTV_PROVIDERS` 사용 (cctv1.js 정의)
- `js/ocean_cctv.js:275-276` — `showCctvPopup()` 호출 (cctv4.js 정의)
- `js/ocean_cctv.js:1341-1378` — `window.CctvFavorites` shim → `toggleCctvFavorite()` (cctv4.js 정의)

**의미**:
- `cctv1.js`와 `cctv4.js`는 사실상 **공유 자원**이며 index2의 운영에 필수
- 즉, **index1을 즉시 삭제할 때 이 두 파일은 보존해야** index2가 정상 동작
- 이전 보고서의 "index1 전용" 분류가 부정확했음

## 2. 누락 ❶이 만드는 위험 5가지 (자식해역 표출 충돌)

방재기상 기반 신규 표출을 도입할 때 기존 텍스트 스크래핑 기반 표출과 충돌하는 시나리오:

### 2.1 글로벌 상태 충돌 (`appState.coastalAlerts`)

- 위치: `js/data.js:194`
- 위험: 신규 백엔드가 `subregion_lifecycle.json`에 쓰고 신규 프론트가 그것을 읽는 동안에도, 기존 `processSingleAlert()`이 매번 `appState.coastalAlerts`를 덮어씀
- 결과: 같은 글로벌 객체가 두 가지 데이터로 번갈아 쓰임 → 사용자 화면 깜빡임 또는 데이터 혼선

### 2.2 DOM 컨테이너 충돌 (`.coastal-zones`)

- 위치: `js/render.js:907, 940`, `js/render_coastal.js:314`
- 위험: 신규 모듈이 같은 `.coastal-zones` 컨테이너에 접근하면 기존 렌더와 충돌
- 결과: 항목 중복 표시 또는 누락

### 2.3 이벤트 충돌 (`'seagnal:alerts-changed'`)

- 위치: `js/data.js:199` (디스패치)
- 위험: 이벤트가 트리거되면 신/구 양쪽 모두 반응 → 같은 화면을 두 번 그림

### 2.4 CSS 클래스 충돌 (`.coastal-item`, `.coastal-detail-box`)

- 위치: `js/render_coastal.js:316, 481`
- 위험: 신규 모듈이 같은 클래스를 사용하면 기존 스타일과 의도치 않게 결합
- 결과: 시각적 깨짐 또는 이벤트 핸들러 중복

### 2.5 모달 충돌 (`showImageModal`)

- 위치: `js/render_coastal.js:207-277`
- 위험: 신/구 양쪽이 모달을 띄우면 정리/이벤트 처리 충돌

## 3. 사용자 요구 기준에 따른 분리 수준 재정의

### 3.1 "index1 즉시 삭제 가능" 의 정확한 의미

이 기준을 만족하려면 다음 셋이 모두 성립해야 합니다.

- **(a) 코드 의존**: index2가 로드하는 모든 자원이 index1과 무관하게 존재 가능해야 함
- **(b) 데이터 의존**: index2가 사용하는 데이터 파일이 index1 동작과 무관하게 유지 가능해야 함
- **(c) 동작 의존**: index2의 현재 표출 결과가 index1의 존재 유무와 무관해야 함

### 3.2 현재 상태 평가

| 기준 | 현재 만족? | 사유 |
|---|---|---|
| (a) 코드 의존 | **❌ 부분** | `cctv1.js`/`cctv4.js`가 index2에서 로드됨 → 필수 보존 필요 |
| (b) 데이터 의존 | ✅ 만족 | index1 전용 데이터 파일 없음 |
| (c) 동작 의존 | ✅ 만족 | index2의 표출은 index1 존재 무관 |

### 3.3 본 작업 후 도달할 상태 (보완 적용 시)

| 기준 | 보완 후 만족? | 사유 |
|---|---|---|
| (a) 코드 의존 | ✅ 만족 | cctv1.js/cctv4.js를 'index1 전용 → 공유'로 재분류만 필요 (실제 코드 변경 없음) |
| (b) 데이터 의존 | ✅ 만족 | 신규 데이터 파일은 index1 가드 |
| (c) 동작 의존 | ✅ 만족 | 신규 모듈은 index1만 동작, index2 무영향 |

→ 보완 적용 후 **사용자 요구 기준 충족 가능**.

## 5. 기능 저하 우려 검토

### 5.1 검증 기간 동안 두 페이지의 자식해역 표출 차이

- **index1**: 방재기상 기반 신규 표출
- **index2**: 텍스트 스크래핑 기반 기존 표출 (그대로)

**우려**: 한 사용자가 두 페이지를 다 보는 경우 정보가 다르게 보일 수 있음.

**평가**:
- 사용자 운영 페이지는 index2이며, 일반 사용자는 index1에 접근하지 않음
- 관리자/테스터만 index1을 봄 → 의도된 차이로 인지 가능
- 검증 후 index2에 적용하면 차이 해소

→ **기능 저하 아님**. 검증 절차로서 정상.

### 5.2 데이터 무결성

- 신규 데이터 파일과 기존 `weather_alerts.json`의 children 객체는 **별도 진실 소스**
- 두 데이터가 일관성을 맞출 필요는 없음 (다른 소스 기반이므로)
- 단, 부모해역 통보문 정보는 양쪽 모두 같은 통보문 시스템 사용 → 일관성 보장

→ **무결성 우려 없음**.

### 5.3 푸시 알림 영향

- 자식해역에는 푸시 알림이 없으므로 푸시 시스템 영향 없음
- 부모해역 푸시는 기존 그대로 작동

→ **영향 없음**.

### 5.4 성능 영향

- 신규 폴링: 1분마다 35KB 응답 1회 추가
- 신규 모듈: index1에서만 동작, index2 무영향
- 디스크 I/O: 신규 JSON 파일 쓰기 매분 1회

→ **무시할 수준**.

## 6. 오류 발생 여지 검토

### 6.1 첫 사이클의 불일치

- 신규 폴링이 처음 시작되는 1~2분 동안 데이터 파일이 비거나 부분적
- 신규 모듈이 빈 데이터로 초기 렌더 시도
- **방어**: 빈 응답에도 안전하게 빈 화면 표시 (오류 처리 정책에 이미 포함)

### 6.2 통보문 시스템 문제 시 자식해역 표출

- 통보문 폴링 실패 시 자식해역 신규 해제 처리 보류 (정책)
- 그러나 신규 모듈은 직전 데이터로 화면 그대로 유지
- **잠재 오류**: 통보문이 오랫동안 stale인데 화면은 그대로 → stale 안전장치(24시간)가 잡아냄

### 6.3 두 페이지 동시 운영 시 자원 경합

- 같은 백엔드 프로세스에서 두 페이지 데이터 모두 처리
- 동시 사용자가 많아도 백엔드는 단일 처리
- **방어**: 신규 폴링과 기존 폴링이 try/catch로 격리

### 6.4 캐시 / 새로고침 동작

- 브라우저 캐시: 페이지별 별도 (index.html과 index2.html이 다른 URL)
- 신규 모듈도 별도 JS 파일로 캐시 분리
- **무위험**.

## 8. 본 재검토의 결론

### 8.1 이전 분석에서 누락된 핵심

1. **자식해역 표출이 양 페이지 공유 코드로 동작 중** — 가장 큰 누락
2. **cctv1.js/cctv4.js는 index2도 로드** — 분류 오류

### 8.2 사용자 요구 기준 충족 가능 여부

- 보완 작업 13, 14, 15를 추가하면 **충족 가능**
- 추가 작업의 위험도는 모두 "낮음 이하"
- 본 작업 범위 내에서 해결 가능

### 8.3 즉시 결정 필요 사항

- **Q1**: 추가 작업 13의 옵션 선택 (A: data.js 가드 / B: render.js 가드)
- **Q2**: 검증 기간 동안 index1에서 기존 자식해역도 함께 보고 싶은지, 아니면 신규만 보고 싶은지
  - 사용자 답변 따라 작업 13의 적용 범위 결정
- **Q3**: cctv1.js/cctv4.js 분류 정정 외에 다른 누락 자원이 더 있을 가능성 — 추가 검증 필요?
