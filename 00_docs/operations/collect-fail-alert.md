# 이안류·기상청 MMIS 수집 실패 관리자 푸시 (2026-10-15)

코드: `local_server/services/collect_fail_alert.js` · 검사: `local_server/scripts/test_collect_fail_alert.js`(`verify_all.sh` SUITES 등록)

## 1. 사용자 확정 사항 (원문)

- 「이안류, mmis는 데이터를 호출했을 때 받아올 수 없다면 그 때 알려줘 보통 천기가 그런 경우가 많아.」
- 추천안에 대한 답: 「추천하는 방식으로 하고. 고르는건 나로 하자.」 → 추천안을 따르고, 천기(시정 예측)는 (나).

추천안(사용자 승인):
1. 실패가 시작될 때 1번, 다시 받아지면 「복구」 1번. 같은 실패가 이어지는 동안 다시 보내지 않음.
2. 천기(시정 예측, 기상청 MMIS)만 **연속 3번 실패하면** 알림((나)). 나머지(이안류, MMIS 특보·강풍·너울, MMIS 기상부이·파고부이·등표·시정계 관측)는 첫 실패 때.
3. 문장 예: 「시정 예측 (기상청 MMIS) 수집 실패 — 빈 응답, 10/16 03:00부터」 / 복구 「… 수집 복구 — 10/16 06:00」. 시각은 KST.
4. MMIS 관측 4종은 실패 기록이 없었다(시각으로 노랑만) → 실패 기록부터 남긴다.

**추가 결정 (2026-10-17, 원문)** — 관리자 휴대폰 알림 목록(「해상 특보·육상 강풍특보 (기상청 MMIS)」 실패 13:28 / 복구 13:28, 실패 12:19 / 복구 12:19, 실패 11:02 / 복구 11:02 …)을 보고:
- 「이 이미지에서 리스트를 보면 알림이 오고 있는데 특히 특보의 경우에는문제가 1분안에 문제가 해결되는 부분이 대다수임 특보의 경우 5분이상 수집이 되지 않는 경우에만 푸시알림을 보내줄 수 있도록 해줘.」

→ **특보(`warnings`)만** 이번 연속 실패의 처음 실패 시각부터 **5분 이상** 이어져야 실패 1통(§4-2). 사용자가 특보를 지목했으므로 다른 항목은 그대로다. 같은 목록에 있던 「시정계 관측 (기상청 MMIS)」 실패 11:13 → 복구 12:03 은 50분 이어진 실패라 5분 대기를 걸어도 그대로 갔을 알림이다 — 시정계에도 걸지는 사용자 판단으로 남긴다(`ITEMS.marineVs.minFailMs` 한 칸이면 된다).

## 3. 알림 규칙

항목마다 「관리자가 지금 무엇을 알고 있나」(`notified`)를 `data/collect_fail_alert.json` 에 남기고, 보고가 올 때마다 「지금 사실」(연속 실패 수 ≥ 기준)과 비교해 **다를 때만** 1통 보낸다. 상태(state)를 사건(event)처럼 중복제거하지 않는다(CLAUDE.md 결정로그 ①).

| 상황 | 보내나 |
|---|---|
| 기준 도달(시정 3회째, 특보는 처음 실패에서 5분 지난 뒤의 실패 보고, 나머지 1회째) & 아직 안 알림 | 실패 1통 「{이름} 수집 실패 — {분류}, {처음 실패 MM/DD HH:mm}부터」 |
| 실패가 이어짐(이미 알림) — 분류가 바뀌어도 | 안 보냄 |
| 성공 & 실패를 알렸음 | 복구 1통 「{이름} 수집 복구 — {처음 다시 받은 MM/DD HH:mm}」. **복구는 성공 보고로만** 일어난다 — 알린 뒤 연속 실패 수가 줄어 보고돼도(시정 `vsby_check_state` 손상·저장 실패로 0부터 다시 셈) 실패 중으로 둔다. 그래서 「시각 모름」 복구 문장은 나가지 않는다 |
| 성공 & 실패를 알린 적 없음(시정 1·2회 실패 뒤 성공 / 특보 5분 안에 성공 / 푸시가 전달되지 않았음) | 안 보냄 |
| 복구 후 다시 실패 | 다시 실패 1통 |
| 강풍(`gale`) | 보내지 않음(특보 알림에 포함), 기록만 |

**전달**: 운영(`FLY_ALLOC_ID` 있음)에서만 `admin_push.sendAdminPush` 를 부른다. `sent > 0` 이면 전달로 친다. `sent 0`(기기 없음·Firebase 미초기화·발송 오류 — 그 함수는 셋을 구분해 돌려주지 않는다)이거나 예외면 「전달 안 됨」 — `notified` 를 바꾸지 않고 콘솔 경고 + 상태 파일 `pushError` 에 남긴 뒤 **다음 보고 때 다시 시도**한다(조용히 삼키지 않는다). 개발에서는 보내지 않고 콘솔 한 줄 「개발 환경 — 관리자 푸시 생략」.

**보이는 곳**: 데이터 수집현황 카드 상세에 「마지막 수집 실패: {분류} (연속 N회, MM-DD HH:mm KST부터)」, 연속 실패 중(1회 이상)이면 **파일 시각과 무관하게 빨강**(근거 「수집 실패 중(연속 N회)」) — 이안류는 전 지점이 실패해도 수집기가 새 시각으로 파일을 써서 시각만 보면 정상으로 남았기 때문이다(독립 검토 3). 푸시가 전달되지 않았으면 「관리자 푸시 미전달: {사유} (MM-DD HH:mm KST)」 한 줄(시정 예측 포함 — 독립 검토 4). 더 보낼 푸시가 없어지면(알린 적 없이 성공) 그 줄은 지운다. 시정 예측의 실패 줄·판정은 `vsby_check_state.json`·오류현황(3회 기준)이 이미 하므로 겹쳐 하지 않는다.

## 4-2. 특보 5분 대기 — 대기 중 상태 변화 표 (2026-10-17, 각 행 = 회귀 검사 1:1)

**규칙**: `ITEMS.warnings.minFailMs = 5분`. 아직 알리지 않았으면 「연속 실패 수 ≥ 1 **이고** 지금 − 처음 실패 시각(`since`) ≥ 5분」일 때만 실패 1통(`wantFailing`). 시도 횟수가 아니라 **시각**으로 잰다 — 주기가 바뀌어도 5분이 5분이게. 한 번이라도 성공하면 `since` 가 비워져 연속이 끊긴다. 실패 알림을 보내지 않았으니 「복구」도 없다(기존 `notified` 규칙 그대로).

**깨우는 타이머가 없는 까닭**: 특보 크롤러는 `scheduler.js` 1분 마스터 `setInterval(…, 60000)` 에서 매번 `marineWarningCrawler.run()` 을 부르고(일시정지 아닐 때), `run` 이 매번 특보·강풍을 보고한다(`marine_warning_crawler.js` `fetchAllRealtimeEndpoints` 앞뒤). 그래서 5분이 지난 뒤 **첫 실패 보고** 때 판정하면 된다 — 늦어도 1주기(약 1분) 뒤다. 주기가 정확히 60초가 아니어서(매 주기 `await syncTime()`, endpoint 시간초과 15초) 5분째 시도가 4분 59초에 오면 그다음 시도(약 6분째)에 보낸다(W3). 보고가 끊기면(크롤러 일시정지·서버 중단) 보내지 않는다 — 그건 「수집이 돌지 않는 경우」로 수집현황 「다음 기대 시각」(노랑)이 잡는다(§2 끝).

**재기동 뒤 오래 멈춰 있었다면**: 실패 중에 서버가 꺼졌다가 한참 뒤 켜지고 첫 시도가 실패하면, 처음 실패 시각이 5분보다 오래전이라 곧바로 1통 간다(문장의 「…부터」는 꺼지기 전 처음 실패 시각). 「재기동을 넘어 처음 실패 시각을 잇는다」(W4)를 택한 결과이며, 꺼져 있던 동안은 수집도 없었으므로 그 시각부터 특보를 받지 못한 것은 사실이다.

**데이터 수집현황 화면은 바꾸지 않았다**: 특보 실패 기록이 1회 이상이면 푸시를 아직 안 보냈어도(`notified=false`) **첫 실패부터 빨강**(「수집 실패 중(연속 N회)」)이다. 5분 대기는 「휴대폰을 울리는 것」을 줄이는 결정이고, 화면은 열었을 때 지금 사실을 보여야 한다 — 실패를 정상처럼 보이게 하면 「조용한 것이 이상 없는 것처럼 보인다」(CLAUDE.md 결정로그 ②). 검사: `test_data_collection_status` 「특보: 관리자 푸시는 5분 기다리지만 화면은 첫 실패부터 빨강」.

## 5. 기존 오류현황(`risk_error_history`) 전이 감지를 재사용하지 않은 까닭

`risk_error_history` 는 1분 감시가 **파일 상태**(ok·stale·missing·error)를 보고 `opened`/`recovered` 사건을 남긴다. 확인해 보니 「호출이 실패했다」를 보지 못한다:
- 특보·강풍·너울: 호출이 실패해도 파일은 그대로라 10분·24시간이 지나 `stale` 이 될 때까지 「정상」이다.
- 이안류: 시도 상태 파일이 없고 신선도 상한도 없어(`risk_store.sources`) 받아오지 못해도 `error`/`stale` 이 되지 않는다.
- MMIS 관측 4종은 원천 목록(`SOURCES`)에 없다.
- 감시는 운영(`FLY_ALLOC_ID`)에서만 돈다.
시정 예측만 `failStreak ≥ 3` 을 `error` 로 보므로, 기준 3회는 같은 상수와 맞대 본다(검사 A — `ITEMS.visibility.threshold === VSBY_FAIL_STREAK`).
