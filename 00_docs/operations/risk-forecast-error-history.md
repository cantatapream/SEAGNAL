# 위험예측 관리자 오류현황

사용자가 요청한 과제16: 일반 지도·바텀시트의 특보/해구/행사 실패·낡음·결측 공통 메시지를 숨기고 **통합 관리자 센터 → AI → AI 사고예측 → 오류현황**에 내역을 보관한다. 개별 기상값의 자료 없음과 상세 요청의 다시 시도는 유지한다. 자료 상태·점수·공식 사고지수를 정상으로 바꾸지 않는다.

## 파일과 흐름

| 파일 | 역할 |
|---|---|
| `services/risk_collector_io.js` | 실제 수집 결과 저장 후 오류 이력 연결. 이력 실패는 수집 성공을 바꾸지 않음 |
| `services/risk_error_history.js` | 오류/누락/낡음의 발생·변경·복구, 중복 제거, 저장 상한, 운영 60초 감시 |
| `services/risk_history_sources.js` | JSON 본문 값을 즉시 버리는 메타데이터 읽기, 기존 `risk_store.sources` 신선도 규칙 재사용 |
| `services/risk_store.js` | 화면의 기존 원본 자료 조회 유지; 내부 감시만 `readData/metadataOnly` 옵션 사용 |
| `routes/risk_errors.js` | 기존 관리자 토큰을 검사하고 목록·필터·페이지 제공 |
| `client/js/admin/admin.js` | AI 하위탭, KST 현재 상태/최종 감시시각/이력, 30건 페이지, 필터·새로고침 |

운영 `FLY_ALLOC_ID` 환경에서만 주기 감시가 시작된다. 첫 감시는 시작 1분 뒤이며 외부 API·Gemini 호출 없이 저장된 실제 자료를 읽는다. 수집 실패는 `io.status` 연결에서 즉시 기록하고, 수집이 중단되어 낡아지는 경우는 분 단위 관찰로 기록한다. 비운영 검사에서는 자동 감시나 수집을 시작하지 않는다.

원천: 특보, 강풍, 해구예보, 너울, 이안류, 혼잡예보, 공식 선박 사고예보, 관광집중률, 월별 행사, 실시간 선박 교통, 해구별 시정 예측(2026-10-15 추가, 아래 절). 이안류 비수기는 정상 상태다. 행사 월별 기록과 공통 수집기 상태는 같은 월 식별자로 합쳐 중복하지 않는다. 공식 원천의 `source` 설명문이 고정 원천 식별자를 덮지 못한다.

## 해구별 시정 예측 (`visibility`, 2026-10-15 사용자 결정 「진행」)

배경: 기상청 RDPS 시정 imgList 가 HTTP 200·0바이트를 돌려 2026-10-11 21:10 KST 수집본 이후 갱신이 멈췄는데, 관리자 화면 어디에도 보이지 않았다. `vsby_smallzone.getStatus()`(같은 서버 프로세스 메모리, `/api/vsby-smallzone/status` 와 같은 값)를 분 감시가 읽어 `risk_history_sources.visibilitySource` 로 판정한다. 다른 원천처럼 같은 상태가 이어지는 동안 **현재 원천 상태에는 매 감시마다 계속 보이고**, 이력에는 발생·변경·복구 때만 한 건씩 쌓인다(같은 오류 반복은 한 건).

| 상태 | 조건 | 이 경계가 없으면 무엇이 잘못되나 |
|---|---|---|
| `error` 수집 실패 | 마지막 imgList 확인 실패 **그리고 연속 실패 3회 이상**(1시간 주기 → 최소 2시간) | 1회 실패로 오류를 열면 기상청 연결이 한 번 끊길 때마다 발생·복구 한 쌍이 쌓여 실제 장애가 묻힌다(2026-10-15 조사 컨테이너에서도 기상청 연결 간헐 끊김을 겪음). |
| `stale` 자료 오래됨 | 마지막 래스터 수집(`collectedAt`)이 **36시간** 넘음 | 확인은 성공하는데 새 수집이 안 되는 경우(같은 런 반복·PNG 실패)나 재기동으로 연속 실패 수가 0이 된 경우, 받아둔 예측(운영 실측 67프레임 = 67시간치)이 다 떨어질 때까지 정상으로 보인다. 런 주기는 확인하지 못했으므로 하루 1회 런이어도 오탐하지 않게 24시간+12시간 여유로 둔다. |
| `missing` 자료 없음 | 수집본이 아예 없음 | — |
| `ok` 정상 | 위 어느 것도 아님(1~2회 실패는 정상) | — |

현재 상태 줄의 「마지막 정상 수집」은 `collectedAt`(마지막 래스터 수집 시각), 「최신화 확인」은 마지막 imgList 확인 시각(`lastCheckAt`)이다. 오류 분류는 고정값만 남긴다: 빈 응답→`empty response`, JSON 아님→`invalid response`, `imgList 503`→`HTTP 503`, 그 밖(주소가 들어간 node-fetch 네트워크 오류 등)→`network or parse error`. 원문 오류문·주소는 저장하지 않는다.

한계: 연속 실패 수는 서버 메모리라 재기동하면 0으로 돌아간다. 장애 중 재기동하면 `error`→`stale`(변경 1건)로 바뀌었다가 재기동 후 세 번째 확인(약 2시간 뒤)에 다시 `error`(변경 1건)가 된다 — 정상으로 잘못 복구되지는 않는다(수집이 36시간 넘게 오래되었으면). 장애 초기 36시간 안에 재기동하면 다시 3회 실패까지 약 2시간 동안 `ok`로 보일 수 있다. 감시 시작은 다른 원천과 같이 운영(`FLY_ALLOC_ID`)에서만이다.

## API·인증·보관

`GET /api/admin/risk-forecast/errors?source=accident&status=error&page=1&limit=30`

`from/to`는 시간대가 포함된 ISO 초 단위 시각을 허용한다. page는 1 이상, limit는 1~100이다. 기존 `X-Admin-Token`만 허용하고 비밀번호를 추가하거나 소스에 넣지 않는다. 응답 캐시는 `no-store`; 손상 이력을 정상 빈 목록으로 감추지 않고 고정 503 메시지를 반환한다. UI는 데이터를 escape하고 탭 이동 뒤 늦은 응답을 무시한다.

영속 파일은 `data/risk_forecast/error_history.json`. 최대 **30일·2000건·1MiB**, 먼저 도달하는 상한으로 오래된 이력을 제거한다. 현재 전역 원천 상태와 최근 행사 4개월은 별도 작은 목록으로 유지한다. 현재 상태를 같은 상태로 반복 확인해도 발생 이벤트를 늘리지 않는다. 마지막 성공시각은 자료가 삭제되어도 보존하고, 복구시각은 후속 정상 감시에도 유지한다. raw URL·키·쿠키·원문 에러·자유 텍스트 대신 고정 오류 분류와 유효 시각만 기록한다.

공유 파일 잠금과 원자적 교체를 사용한다. 이력 저장 잠금이 다른 프로세스에 잡혀 있거나 파일이 손상된 동안에는 수집 자체를 막지 않는다. 분 감시는 지속 문제를 다시 확인하지만, 그 사이 발생했다 복구된 아주 짧은 오류의 완전 기록은 보장하지 않는다. 복구 이벤트가 오래되어 상한으로 삭제될 수 있어 무기한 감사 로그로 쓰면 안 된다.

## 메모리 한계와 검증

감시에서 화면용 전체 예보 캐시를 강제 로드하지 않는다. `stream-json@1.9.1`을 직접 고정 의존성으로 등록하여 JSON 토큰 조각을 순서대로 처리하고 날짜·수집시각·상태 및 이안류 자료 유무의 실제 개수만 남긴다. 메타데이터 읽기 캐시는 파일 서명이 바뀔 때만 다시 파싱하며 매 감시마다 신선도를 다시 계산한다. 정적 관광지·특보 폴리곤·사고 이력은 감시에서 읽지 않는다. 내부 감시용 부가 통계는 공개 화면의 통계 응답을 대체하지 않는다.

압축파일도 파일 스트림과 gzip 스트림으로 16KiB씩 읽는다. 파일과 해제된 총량의 상한은 각각64MiB지만 전체 해제 버퍼를 한꺼번에 만들지 않는다. 문자열·키 조각도 제한하고 본문 배열을 만들지 않는다. 감시 중 작은 I/O 조각 사이에 다른 요청이 처리될 수 있고, 이전 감시가 진행 중이면 다음 주기를 중첩하지 않는다. 파서 토큰 할당·압축 버퍼·V8 여유 힙에 따른 일시 RSS 증가는 남는다. 메모리 사용을0으로 만든다는 의미는 아니다. V8의 메모리 회수/RSS 시점과 운영 VM 전체 피크는 별도 배포 후 관찰이 필요하다. Fly 힙/VM 한도는 변경하지 않는다.
