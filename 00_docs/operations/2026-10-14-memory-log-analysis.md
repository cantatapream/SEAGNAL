### 15:38 물빠짐 로딩의 별도 모의 재현

실제 물빠짐 라우트와 같은 셀 수(89,061),301개 합성 앵커,72개 바이너리 프레임으로 독립 Node24에서 첫 로딩을 측정했다. RSS44.53→236.51MiB, GC 후234.93MiB였다. heap은 GC 전7.56→67.34MiB, GC 후52.06MiB였다. 이는 **합성 좌표·앵커의 결과**이며 운영 서버가 같은 양을 사용했다는 뜻은 아니다. 바이너리12.23MiB만 보고 전체 로딩 비용을 판단할 수 없다는 점은 재현됐다.

### KHOA 갱신과 잘못 읽기 쉬운 성공 집계

외부 KHOA 주소의 HTTP 오류다. 앱 정적 파일이 없다는 의미의 404가 아니다. 22:40 KST에 같은 주소로 현재22시와 로그에서 실패했던 10월17일16시를 다시 확인하니 두 요청 모두 **HTTP200, JSON data 배열 포함**이었다. 이때의 복구를 16~17시에도 정상 서비스였다는 증거로 쓰면 안 된다. 일시 장애의 내부 이유는 알 수 없다.

`getStream`은 실패해도 24시간 안의 기존 자료가 있으면 `stale:true,_failed:true`로 반환한다. 그러나 `refreshCycle`은 반환되기만 하면 `ok++`한다. 그래서 404가 다수여도 “성공72/실패1”로 보일 수 있다. **신규 갱신·과거 캐시 보완·완전 실패를 분리 집계해야 한다.** 과거 자료로 보완하는 정책 자체를 없애라는 뜻은 아니다.

### TideBED 누락과 no_grid

기대한 페이지 자료/조석 상수가 없다는 사실은 확인된다. 원응답의 HTTP 상태와 안전한 provider 오류 코드가 없고 `N/A`만 남아, 인증·할당량·서비스 오류·빈 자료 중 세부 원인은 확정할 수 없다. 900건/600건 “수집 완료”는 하루1440분 완전 자료가 아니다. 부분자료와 경계 극값 미검출을 error로 남겨 재시도하는 것은 보호 동작이다.

`getGridHash`는 조회 오류와 실제 격자 없음 모두 null로 돌아올 수 있다. 배치의 no_grid101건을 전부 확정적인 미제공 해역이라고 해석하면 안 된다. 전송 실패·빈 목록·스키마 불일치·실제 미제공을 구분하는 진단과 상태가 필요하다.

### CCTV와 시정

CCTV는 배열 없음이라는 로그만으로 응답 구조 변경인지 서비스 오류인지 판단할 수 없다. `body.items.item`만 검사하는 파서가 다른 정상 응답 형태도 처리해야 하는지는 응답 구조 확인 후 결정해야 한다. API 키가 틀렸다고 단정할 근거는 없다.

시정은 기상청 목록 JSON을 끝까지 읽지 못했다. 기상청 생성, 중간 프록시, 전송 중단 중 어디에서 잘렸는지는 미정이다. 서버의 저장 JSON이 손상됐다는 기록은 아니다. 안전한 응답 길이·유형과 제한된 재시도 기록이 필요하다.

### FCM: 복구된 오류와 실제 보완점

- 15:01의 `messaging/internal-error`는 250ms 재시도로 성공했다. 해당 일반 푸시의 최종 실패는0이다.
- 16:01의 만료 토큰은 등록 해제된 단말로, 구독1개가 정리됐다. 해당 일반 푸시 집계는 성공738/실패1이다.
- 별도 **위치기반 data 스냅샷은 5,772 / 4,458 / 4,925바이트**로 모두4KiB를 넘었다. `buildDataMessage`는 경고만 하고 그대로 보낸다. 일반 푸시 성공은 이 data 메시지의 성공 증거가 아니다. 실제 응답이 없어 세 번 모두 실패했다고 확정할 수는 없다.
- `_defaultSendFn`은 개별 실패 사유를 남기지 않는다. 오류/관리자 미구성 결과에 `successCount`가 없으면 `dispatchWake`가 전체 토큰 수로 발송 이력을 남길 수 있는 집계 결함도 있다.
- 구역을 임의 삭제하면 단말이 무특보 구역으로 오판정할 수 있다. 단말의 스냅샷 계약과 함께 축약/분할 및 실패 집계를 검증해야 한다. 이번 분석에서 실제 푸시는 발송하지 않았다.

## 다음 처리 순서와 남은 한계

1. 확정된 혼잡예보 매분 재파싱을 별도 커밋·PR로 검증한다. 관리자 오류현황 #1377은 이 수정의 선행조건이 아니다.
2. 물빠짐 최초 로딩의 메타·인덱스·바이너리별 RAM을 측정하고, 폴백 인덱스의 지연 생성을 검토한다.
3. KHOA fresh/stale/fail 집계, 외부 오류 진단·백오프, FCM 크기·개별 실패 기록은 별도 수정 범위로 다룬다.

최신 main68995bceb9 기반으로 전체 게이트 종료0, **85스위트3454 PASS/0 FAIL**, 실제 앱 smoke 회귀0을 확인했다. 기존 법령 자료의 기준선 경고는 남아 있으며 아래 인계 문서에 총정리를 보존했다. 코드가 운영 Fly에 반영됐다는 뜻은 아니다. 관리자 오류현황 PR1377도 GitHub 검증SUCCESS를 확인했다. 이번 수정과 독립적으로 검토·머지할 수 있다.

## 후속 수정 상태 — PR1378/1379 및 통합 검증

위 시제품·검토 후보라는 서술은 분석 당시 상태다. 이후 혼잡예보의 비수집시간 전체 읽기 제거는 PR1378(149dac2590), 물빠짐 폴백 앵커 연결의 지연 계산은 PR1379(fc979cf271)로 구현했다. 두 PR 모두 독립 전체 검증과 GitHub 검증 SUCCESS를 확인했다. 운영 main 머지나 Fly 배포는 수행하지 않았다.

물빠짐 최종 제품 소스를 같은 합성 자료로 재현한 결과, 첫 로딩 RSS44.32→98.21MiB, GC 후94.82MiB, GC 후heap22.73MiB였다. 준비된 프레임 값·결측·보간·메타 갱신·디버그 동작을 실제 HTTP로 검사했다. 바이너리, 메타, 타일 인덱스는 유지하고 실제 폴백 조회 셀의 앵커 연결만 필요할 때 계산한다. 오래 사용하면 조회된 셀의 연결 캐시가 늘 수 있으므로 이 첫 로딩 수치를 장시간 운영 상한으로 해석하지 않는다.

현재 두 메모리 개선과 관리자 오류현황1377을 합친 전체 검증을 별도로 진행했다. 최종 결과와 세 PR을 함께 머지할 링크는 `handoff_combined_risk_1377_1379.md`의 마지막 결과를 따른다. 혼잡예보와 물빠짐의 독립 모의 RSS 감소량을 더해서 운영 절감량으로 제시하지 않는다.

남은 진단·수정 범위는 다음과 같다.

- KHOA 새 자료 갱신/기존 캐시/빈 실패의 집계를 분리한다. 수집 로그의 성공73은 최신 데이터73건을 뜻하지 않는다.
- TideBED는 HTTP 상태, 안전한 provider 오류 코드, 예상 구조 충족 여부를 구분해야 한다. 현재 N/A만으로 인증·일일 한도·빈 자료를 판별할 수 없다. 실제 미제공과 조회 실패를 no_grid 한 상태로 합치지 않는다.
- 해무CCTV는 원응답 구조와 provider 코드 확인이 선행돼야 한다. 배열 없음만 보고 정상 응답 스키마나 API 키를 임의 변경하지 않는다.
- 시정 imgList는 응답 길이·유형·전송 완료 여부를 안전하게 기록하고 제한된 재시도를 검토한다. 오류가 원격 생성/중간 전송/프록시 중 어디에서 발생했는지 현재 로그로는 모른다.
- 위치기반 FCM은 전체 구역을 유지하면서 4KiB 안에 넣는 송수신 형식과 실제 성공/실패 집계를 함께 고쳐야 한다. 일반 푸시의 성공 집계로 위치기반 data의 성공을 대신하지 않는다.

위 외부 자료·푸시 오류를 이번 메모리 수정으로 해결했다고 간주하지 않는다. 원본 로그와 인증 정보는 이 문서·커밋에 포함하지 않았다.
