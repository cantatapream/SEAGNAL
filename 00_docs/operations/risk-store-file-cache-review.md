# 위험예측 원천 파일 재파싱 완화 검토 — 2026-10-13 KST

이 문서는 Fly 메모리 장애 대응 중 `risk_store`의 이번 서버 PR에 적용한 개선을 설명한다. 운영 배포나 원천자료 수집은 실행하지 않았다. UI 수정은 별도 PR #1373이며, KHOA 캐시 상한과 함께 서버 메모리 PR에 포함한다.

## 개선 이유와 범위

기존 `risk_store.refresh()`는 모든 자료·상태·쿼터·정적 파일의 stat 서명을 묶어서 입력버전을 만든다. 이때 `accident_status.json`처럼 작은 파일 하나만 바뀌어도 기상자료, 혼잡 예측, 사고 예보, 정적 관광지·특보구역을 모두 다시 읽고 JSON 객체로 파싱한다. 예측 계산이 달라질 수 있으므로 **전체 입력버전 변경과 계산 결과 캐시 무효화는 유지**한다. 재사용할 것은 내용이 바뀌지 않은 개별 원천 객체다.

수정된 `local_server/services/risk_store.js`는 다음과 같이 동작한다.

- 매 refresh에서 이미 얻는 파일별 mtime·size·inode 서명을 활용한다. 서명이 같으면 이전 `io.read()` 결과 객체를 다시 사용한다. 같은 월의 행사 파일을 두 번 읽던 경로도 한 번으로 합쳐진다.
- 자료·상태·쿼터 중 하나가 바뀌면 기존처럼 전체 inputVersion을 증가시키고 detail/frame/sourceInfo 등의 계산 캐시를 무효화한다. 따라서 새 수집 실패나 freshness·날짜 전환이 계산에 반영된다.
- 실제 기상·사고·위치·정적 파일의 서명이 바뀌면 그 파일만 다시 읽는다. 파일 삭제는 `data:null, exists:false`; 손상된 기존 파일은 `data:null, exists:true`로 처리한다. 정상 원천값이나 누락을 임의로0으로 바꾸지 않는다.
- 현재 조회범위에서 빠진 행사 월 등의 파일 메모는 제거한다. 월 경계 후 과거 파일이 참조된 채 계속 남는 누적 캐시를 만들지 않는다.
- IO 읽기 결과를 그대로 참조하며 원천 전체를 복사하지 않는다. 공개 API 스키마·실패 표시 정책·30초 갱신 간격·전체 버전 규칙은 유지한다.

`io.read()`는 기존처럼 동기 JSON 파싱을 사용한다. 실제 대형 원천이 변경될 때의 원문·버퍼·객체 메모리 피크는 이번 개선으로 없어지지 않는다. 메타데이터 전체버전 변경 시 계산 결과가 무효화되는 CPU 비용도 유지된다.

## 검증과 측정

새 검사 `test_risk_store_file_cache.js`는 임시 파일만 사용하며, io.read 호출수를 직접 계수하고 혼잡·사고·위치 객체 참조가 같은지 검사한다.

- 상태·쿼터 변경 시 대형/정적 파일 읽기 횟수와 원천 참조 유지.
- inputVersion 증가와 이미 계산된 프레임 교체 유지.
- 실제 사고 및 기상 파일 변경 반영.
- 삭제·손상·복구, 오류 시도 우선순위, 정적 버전 변경·삭제.
- 월 경계 후 이전 행사 월 메모 제거, 다시 해당 월을 조회하면 재독해.

새 검사 **21건 통과** — UTC 및 America/Los_Angeles 환경. 원래 코드에서는 첫 검사부터 같은 월 행사 JSON을2번 읽어서 실패한다. 기존 `test_risk_store.js` **22건 통과** — 두 시간대 모두. 개선안을 주입한 기존 해상 통합26건, 위험예측 라우트8건, 공식 사고 예보19건도 통과했다. 실제 적용 후 전체 검증 결과는 handoff_server_memory.md에 기록한다.

실제 로컬 정적·기상 파일을 사용하는 격리 실험에서 작은 `accident_status.json`만 갱신하면 기존 코드 RSS가 약88.9→114.2MiB로 상승하며 대형 파일을 모두 다시 읽었다. 개선안에서는 대형 재읽기0회, RSS 약89.9→89.9MiB였다. 측정은 Node24.19.0, `--expose-gc --max-old-space-size=480 --max-semi-space-size=4`, JSON 파싱 시점과 GC 후 관찰이다. 운영 Docker는 Node20이므로 이 값이 Fly의 절감량이라고 보장할 수 없다.

## 장애 원인과 구분

사용자 로그의 Node heap limit 초과는 확정됐지만, 실제 오류를 일으킨 JSON 파일/요청은 아직 특정하지 못했다. #1371 신규 수집·통합, 기존 KHOA 캐시 누적, 여러 수집기의 원문·중간 배열·압축 버퍼가 동시에 존재하는 피크 및 불필요한 프레임 요청이 모두 검토 대상이다. 이번 수정은 독립적으로 확인된 **상태 변경에 따른 대형 재파싱**을 줄이는 것이며, 이것만으로 서버 OOM이 해결됐다는 뜻은 아니다.

배포 전 전체 검증과 코드 검토, 배포 후 Node heap/RSS/external/arrayBuffers 및 수집별 단계 로그 관찰이 필요하다. 원천파일별 저장 형식·압축 해제 크기·행 수를 함께 기록하되 인증키 URL·쿠키·원문 응답을 로그에 남기지 않아야 한다.


## native 파서 스택 추가 단서

오류 스택의 `JsonParser<unsigned short>`는2바이트 문자열 파싱 경로다. 내용은 출력하지 않고 실제 로컬 파일의Latin1범위를 넘는 문자 유무만 확인한 결과, KHOA 백업은없음, 기상 JSON·정적 위험지점·기존 선박사고 JSON은있음이었다. 혼잡·사고 예보의 한글 단계명도2바이트 파싱 후보가 된다. 운영 원문은 로컬 파일과 다를 수 있으므로 최종 할당 파일을 특정할 수는 없지만, **KHOA 백업 파싱이 직접 오류를 냈다고 단정하면 안 된다.** KHOA 등 기존 상주 객체가 힙을 채운 상태에서 다른 한글 JSON의 파싱이 마지막 추가 할당이었을 가능성도 검토해야 한다.
