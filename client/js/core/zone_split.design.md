## 3. 어떻게 — 「서버가 전환을 감지 + 쓰는 곳이 그때그때 묻기」

서버·화면 모두 미리 배포해 둔다. 쓰는 곳이 **읽을 때마다** `isActive()` 를 묻고, 전환은 서버가 정한다(한 번 넘어가면 되돌아가지 않는다 —
운영 볼륨 `data/zone_split_state.json`).

**전환 조건 — 둘 중 먼저 오는 쪽** (`config/zone_split.observe` ← `marine_warning_crawler._observeZoneSplit`, 정기 주기에서만)
1. MMIS 가 새 구역코드(S1324120·S1324220)를 쓰기 시작 — 특보 자료(warn/list·ready)에 보이거나, 포털 특보구역 지도 목록(WFS `mmis:shp_wrn_poly`, 5분마다)에 보일 때. **보는 즉시**(그 주기에 바로 — 기다리면 전환 전 규칙으로 새 이름 푸시가 나간다).
   - 실측 2026-11-24: 특보 자료에는 **특보가 걸린 구역만** 온다(발효 82줄, 등급 0 줄 없음). 지도 목록은 44개 구역이 코드와 함께 늘 온다(S1324020 「제주도 남쪽 바깥먼바다」).
1-2. 통보문(방재기상플랫폼)이 새 두 구역 이름으로 특보·예비특보를 내기 시작 — 특보 통보문의 해당 구역·발효 현황 칸, 예비특보 통보문의 목록 칸에 새 이름이 나오면 **보는 즉시**
   (사용자 2026-11-24 「변경시점에 추가로 통보문에서 그렇게 나누어서 발표하는 시점도 포함」). 참고사항·날씨해설은 보지 않는다 — 예고 문장에 새 이름이 먼저 실릴 수 있다.
2. 2026-11-25 00:00 KST(`ZONE_SPLIT_AT` 으로 바꿀 수 있다) 뒤, 옛 구역에 특보·예비가 하나도 없을 때 — **10주기(약 10분) 연속**, 해제·예비취소 디바운스가 끝난 스냅샷 기준.
- 전환하면 관리자 휴대폰에 알림(`admin_push`) — **전달될 때까지 매 주기 다시 보낸다**(전달되면 상태 파일에 `notified`). 푸시가 안 와도 `GET /api/zone-split` 이 전환 시각·사유를 보여 준다. 손으로 켜고 끄기: `ZONE_SPLIT_FORCE=on|off`.

## 5. 알려진 한계·남은 일

- **MMIS 가 새 구역을 실제로 어떻게 주는지는 전환되는 순간이 처음이다.** 전환 알림(관리자 푸시)이 오면 운영 화면을 확인한다.
- 조건 ②로 먼저 전환한 뒤 기상청이 끝내 옛 코드를 계속 쓰는 동안에는 두 구역이 늘 같은 특보로 보인다(옛 구역 = 두 구역이라 틀린 것은 아니다).
- 전환을 되돌리려면 `ZONE_SPLIT_FORCE=off`(재시작) — **되돌리기는 깨끗하지 않다**: 한 번 전환을 본 기기는 기억하고(`zoneSplitActive_v1`) 새 이름으로 구독해 옛 구역 푸시를 놓치며,
  특보가 발효 중이면 서버가 거짓 「발효(옛 이름)」「해제(새 이름)」를 낸다(독립 검토 2026-11-24 재현). 비상용으로만 쓴다.
- 전환 주기에 걸린 작은 어긋남: 시각 변경 3분 관찰 중이던 변경·연장 푸시가 즉시 나가거나, 해제 푸시가 1~3분 늦을 수 있다(중복·누락은 아니다).
- 새 코드로 넘어간 뒤에도 옛 코드 줄이 MMIS 에 남아 있으면 해제된 쪽이 다시 「발효」로 읽힐 수 있다(MMIS 가 실제로 그렇게 주는지는 모른다).
