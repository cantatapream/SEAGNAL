# 위험예측 구현과 검증 기록

## 구현 범위

최신 사용자 결정 U77·U78에 맞춰 실제 앱의 해양안전에 위험예측 버튼을 연결했다. 초기에는 연안만 켜지고, 지도 선택으로 상세 창이 열린다. 시간 슬라이더, 연안·해상 전환, 경고 경계, 위험구역 이동, 산출 근거 보기와 두 PDF 내려받기를 포함한다. 메인 활동 브리핑과 AI 설정 연결은 이번 범위에서 미룬 결정대로 별도 작업이다.

계산은 서버의 순수 함수로 모으고, 기존 수집 자료와 세 신규 수집기를 읽는 API를 추가했다. 신규 수집기는 Fly 운영 환경에서만 자동 기동한다. 개발 환경의 화면 조회는 외부 API를 자동 호출하지 않는다. 혼잡도는 하루 실제 요청 90회, 관광지 집중률은 900회로 제한하고 재시작 후에도 요청 장부를 유지한다. 행사 수집은 기존 Gemini 키와 Kakao 장소 검색을 사용한다.

## 확인한 결과

- 원본 관광지 1,354행의 3km 위험구역 및 파출소 연결을 독립적으로 다시 계산하여 불일치 0건을 확인했다.
- 정적 공간 자료를 Shapely 2.2.0·pyproj 3.8.0으로 재생성하여 저장된 JSON과 바이트가 일치했다.
- 같은 좌표의 후속 행 28개와 육지 교차 결과가 없는 6개는 빈 면을 유지한다. 검색 행은 삭제하지 않고 지도에서는 유효한 1,320면을 그린다. 실제 전체 표와 제품 OpenLayers로 검증하는 회귀 검사를 포함한다.
- 산출 근거 두 PDF를 생성하고 한국어 텍스트 추출을 확인했다. 공개 근거 문서의 숫자 1,908개 대조에서 없는 숫자는 0개였다.
- 새 기능의 계산·자료 계약·서식·화면 생명주기·수집 실패 복구 검사를 전체 검사에 등록했다. 시험 응답을 사용하는 브라우저 검증은 운영 수집 성공을 뜻하지 않는다.
- 새 기능 검사는 13개 스위트, 275건이 통과했다(계산·공간 64, 화면·서식·생명주기·전수 지도 174, 서버 37). 기존 오류 처리 검사 22건도 통과했으며 기준선을 올리지 않았다.
- 처음의 브라우저 검사는 다각형 1개짜리 시험 응답을 사용해 빈 면 문제를 발견하지 못했다. 이후 실제 API와 전체 원천을 제품 OpenLayers에 넣는 검사를 추가하고, 별도 검토자가 관광지 1,354행·유효 면 1,320개·브라우저 미처리 오류 0건을 독립적으로 확인했다.

## 종합 검사 결과 — 2026-10-11

공식 응답 형식 두 곳을 수정한 후 13:34 KST에 끝난 `verify_all.sh`는 종료 코드 0으로 전체 회귀 게이트를 통과했다. 80개 스위트, 3,241 PASS / 0 FAIL이며 위험예측 13개 스위트·275건을 포함한다. 경로·로드 순서·절대경로·HTTP 응답 검사를 통과했다. 브라우저 주행의 새 코드 오류·새 404·깨진 시나리오·사라진 전역 함수는 모두 0개다. 기존 환경 오류와 기준선 내 경고는 남아 있으므로 외부 지도 제공자까지 정상이라고 주장하지 않는다.

이전 실행의 V4 `ERR_TUNNEL_CONNECTION_FAILED`는 환경 설정 초안에 `tile.openstreetmap.org`를 추가한 뒤 재검사에서 재현되지 않았다. TLS 검증과 기존 검사 기준선을 유지했다. 초안 저장만으로 환경이 게시됐다고 주장하지 않는다.

사용자 첨부 관광공사 공식 v4.1 매뉴얼을 추가 대조하여 관광지명 응답 필드 `tAtsNm`을 수정했다. 수정 전에는 공식 XML 예제의 행을 거부하는 오류를 재현했다. 수정 후 공식 7개 응답 필드로 날짜·집중률·동일 시군구의 이름 연결을 확인했고 수집기 집중 검사는 19 PASS / 0 FAIL이다. 사용자 제공 성공 기록의 해양 API `200 / NORMAL_SERVICE`도 공통 요청기에 반영했다. `153 / NOT_FOUND_DATA`와 성공 메시지가 아닌 코드200은 거부하며, 정상 코드200으로 48시각 수집·풍속/파고 null을 확인하는 집중 검사도 19 PASS / 0 FAIL이다. 이 수정 이후 전체 게이트도 다시 실행하여 종료 코드 0을 확인했다.

신규 테스트 등록에 따라 공통 규칙집의 자동 검사 목록도 생성 도구로 갱신했다. 자동 목록 밖의 사람이 쓴 본문은 바이트가 일치하며, 법률 위키 본문과 자료는 변경하지 않았다. 검사 실행이 쓰는 추적 보고서는 실행 전 내용으로 복원했다. 운영 배포나 main 병합은 진행하지 않았다.

## 실제 외부 자료와 남은 작업

해양교통 혼잡도와 관광지 집중률 API는 클라우드의 공식 명세 요청에 HTTP 400, `INVALID_REQUEST_PARAMETER_ERROR`(코드 10)를 반환했다. 관광공사 v4.1 매뉴얼의 필수 항목과 응답 필드, 첨부 시군구 코드표를 대조했다. 앱의 코드 60개 중 코드표에 없는 것은 0개다. 사용자 제공 해양 REST 화면의 승인·요청 항목을 확인했고, 전달한 키를 디코딩해 기존 서버 설정과 일치함을 확인했다. 키 값은 기록하지 않았다.

사용자가 보내준 포털 응답은 `153 / NOT_FOUND_DATA`였다. 이어 받은 화면은 2026-10-03 14:00으로 클라우드의 당일 조회와 날짜·시간이 달랐다. 화면과 같은 10월 3일 14시 조건도 클라우드에서는 코드 10이었다. Node와 curl 양쪽에서 재현했다. 요청 주소의 조회 문자열을 아직 확보하지 못했으므로 원인을 단정하지 않는다.

과거 성공 기록은 커밋 `42a4514a22`의 설계서 §4.2·§9에서 확인했다. 당시 10월 10일 03시·12시 4단계 혼잡 예보와 관광 집중률 84,810행을 실측했다고 기록되어 있다. 커밋 `68e25d122b`의 `12_traffic.py`는 세션 임시 응답 `mtc4_1010_03.json`·`mtc4_1010_12.json`을 입력으로 사용한다. 현재 체크아웃과 Git의 도달 가능한 파일 경로 전체에서 두 원본 응답을 찾지 못했다. 문서에 기록된 10월 10일 03시·7,000행 조건으로 재요청했지만 현재 클라우드에서는 코드 10이었다. 기록된 성공과 현재 재현 실패를 구분한다.

추가로 사용자가 전달한 실제 호출 기록에서 2026-10-10 12:00, `numOfRows=3`, `gridLevel=4`의 `200 / NORMAL_SERVICE` 응답과 `totalCount=6165`를 확인했다. 항목 순서를 포함해 기록의 요청을 기존 키로 재현했지만 현재 클라우드에서는 HTTP400·코드10이다. 정상 응답 코드를 거부하던 구현 오류는 수정했으며, 현재 전송 오류의 원인과 구분한다. 당시 `$S/get.sh`의 인코딩·헤더·전송 방식을 대조하기 위해 스크립트 내용을 요청했다.

수집기의 모의 응답과 공식 예제 검증은 실제 수집 성공을 뜻하지 않는다. 오류를 정상 값으로 대체하지 않고 API 상태와 화면에서 결측을 표시한다. 실제 호출 차이를 좁히려면 포털 또는 성공한 세션의 인증키를 제거한 요청 URL이 필요하다.

클라우드의 `GEMINI_API_KEY_26_8`·`KAKAO_REST_API_KEY`는 아직 설정되지 않았다. 행사 실수집은 환경의 보안 설정에 키를 넣은 후 확인해야 한다. 기존 해양 API 키 값은 문서·화면·시험 기록에 남기지 않았다.

환경 설치 스크립트, 시작 안내와 네트워크 허용 도메인은 검토용 초안에 저장했다. 초안 저장은 현재 환경 적용이나 환경 게시를 뜻하지 않는다. 환경 설정에서 초안을 검토·저장한 뒤 환경을 게시해야 한다. 전체 앱 회귀 게이트는 통과했지만 외부 지도·기상 제공자 접속의 환경 경고는 남아 있다. 운영 배포, Android 실제 기기의 PDF 저장, 실제 신규 API 응답 검증은 완료 주장에 포함하지 않는다.
