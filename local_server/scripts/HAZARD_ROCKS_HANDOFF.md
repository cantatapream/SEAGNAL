# 간출암·노출암 핸드오프 — 상세 (브이월드 도입부터 고립판정까지 전체 히스토리)

> **용도**: 이 문서는 SEAGNAL의 "위험물(간출암·노출암)" 기능 라인 — 브이월드 위성지도 도입 →
> 위험물 데이터/레이어 → 간출암 잠김경고 → 노출암 높이(되돌려짐) → 노출암 고립판정(현재 진행 중)
> — 전체를 처음부터 끝까지, 다른 세션/계정이 읽고 바로 맥락을 파악할 수 있도록 빠짐없이 기록한다.
> 기존 `local_server/knowledge/legal/HANDOFF.md`(법률 챗봇 "나리야"용)와는 완전히 별개다.
>
> **바로 이어서 할 일**은 [`HAZARD_ROCKS_HANDOFF_BRIEF.md`](./HAZARD_ROCKS_HANDOFF_BRIEF.md) 참고.
> 관련 기술 문서: [`TIDE_FIELD_README.md`](./TIDE_FIELD_README.md)(물빠짐·고립판정 운영 가이드).

## 0. 전체 그림 — 왜 이 순서로 만들어졌나

1. **브이월드 위성지도**가 먼저 들어왔다 — 갯벌·암초가 실제로 어떻게 생겼는지 위성사진으로
   보여주기 위한 배경지도 인프라.
2. 그 위에 국립해양조사원(KHOA) 전자해도 원본에서 뽑은 **간출암·노출암 위험물 데이터**가 마커로 얹혔다.
3. 간출암(밀물에 잠기는 바위)에 대해 **"3시간 후 잠김" 경고** 기능이 먼저 완성됐다(조위 데이터가
   이미 있는 서해·남해 물빠짐 인프라를 재사용).
4. 노출암(항상 마른 땅)에 대해서도 "높이"를 표시하려는 시도가 있었으나 **되돌려졌다**(사유 불명,
   현재 비활성).
5. 그러다 사용자가 "노출암은 안 잠기지만, **밀물에 연결 갯벌길이 잠겨서 고립될 수 있다**"는
   핵심 통찰을 제시했고, 이게 이번 세션(2026-08-02)의 메인 작업 — **노출암 고립판정**이다.
   진행 중 "BADA2024 수심 데이터가 해안 근접부에서 못 믿을 정도로 부정확하다"는 걸 발견해서,
   KHOA 전자해도를 AI가 직접 읽는(OCR) 검증 파이프라인까지 별도로 구축하게 됐다.

## 1. 브이월드(VWorld) 위성지도 도입

- **최초 도입** (`a4c115e1`, 2026-07-31): "해양생활" 탭을 10회 연타하면 열리는 **히든 화면
  "해양생활안전"**(현재 명칭 "해양안전생활") 전용 배경지도로 위성지도를 추가. 아직 시험 단계라
  일반 사용자가 보는 해양종합정보 배경지도 메뉴에는 넣지 않았다. 서버(`local_server/routes/ocean1.js`)에
  `GET /api/ocean/vworld-tile` 타일 프록시를 신설해, 브이월드 WMTS가 인증키를 URL 경로에 그대로
  넣는 방식이라 브라우저에서 직접 부르면 키가 노출되는 걸 막으려 했다(기존 KHOA `khoa-wms` 프록시와
  동일 구조). 레이어 화이트리스트(Satellite/Hybrid) + z/y/x 정수 검증으로 SSRF 차단.
- **서버 프록시 → 단말 직접 호출로 전환** (`cdcb1fa0`, 같은 날): 운영 배포 후 실측 결과, Fly.io
  `nrt`(도쿄) 서버에서 `api.vworld.kr` 연결이 0.9초 안에 **즉시 연결 오류**(타임아웃이 아니라 즉시
  거부)로 실패했다. 커밋 메시지엔 "브이월드가 해외·데이터센터 IP를 막는 것으로 보인다"고 추정으로
  적혀 있다(확정 진단은 아님). 대응: 타일 프록시(`vworld-tile`)를 없애고 인증키만 내려주는
  `GET /api/ocean/vworld-key`를 신설, 브라우저가 `api.vworld.kr`을 직접 호출하도록
  `client/js/ocean-map/`의 `createVworldLayer`를 수정(`source.setUrl()`로 키를 채워 넣음). 키가
  URL에 그대로 노출되지만, 브이월드 측에 등록된 서비스 도메인(seagnal-server.fly.dev)에서만
  동작하도록 도메인 검증에 묶여 있어 도용이 어렵다.
- **고DPI 대응** (`f85487f3`, 같은 날): 브이월드는 256px 타일 하나만 주고 `@2x` 레티나 전용
  엔드포인트가 없다. 픽셀밀도(DPR) 3배 단말에서 같은 256px 타일을 3배로 늘려 그리다 보니 뿌옇게
  보이는 문제를 확인(DPR3, 화면줌16 → 실제 요청은 z16 타일). 해법: 타일 그리드를 "한 칸당 128px"로
  선언하고 `tilePixelRatio: 2`를 설정 → OpenLayers가 한 단계 더 깊은 줌(z17 등)의 타일을 받아
  절반 크기로 그림. 화면당 요청 타일 수가 4배로 늘어(데이터 사용량 약 4배) 화질과 트래픽을 맞바꿨다.
- **해양종합정보(전 화면)로 확장** (`07cdc427`, 같은 날): 사용자 요청으로 해양종합정보 탭과
  해양생활안전 모든 하위탭에서 쓰도록 확장. `#ocean-basemap-menu`에 `vworld` 옵션 추가, 위성지도
  선택 시 줌 한계를 15 → 19로 늘림.

## 2. 위험물(간출암·노출암) 데이터 및 레이어

### 2.1 데이터 출처
`0e0fa98a`(2026-08-01)에서 `local_server/scripts/build_hazard_rocks.js`(1회성 전처리 스크립트)를
신설. **국립해양조사원(KHOA) 전자해도 shapefile**인 `TL_UWTROC_P_LV5`(간출암·세암·암암)와
`TL_LNDARE_P_LV5`(노출암)를 한반도 범위로 걸러 EPSG:5179(KGD2002 중부원점) → EPSG:4326(WGS84
위경도)로 좌표변환해 `client/hazard_rocks.json`으로 저장한다. 총 6,829건(간출암류 2,542 +
노출암 4,287). 원본 shapefile(비압축 68MB+)은 저장소에 커밋하지 않는다 — 갱신이 필요하면 KHOA
국가해양정보 마켓센터에서 재다운로드해 스크립트를 재실행한다.

### 2.2 k값 의미 (필수로 알아둘 것)
- `k=0`: **노출암** — 항상 마른 땅(약최고고조면 위). 이번 세션 "고립판정" 작업의 대상.
- `k=1`: **간출암** — 저조 때만 드러남(밀물엔 잠김). "3시간 전 잠김경고" 기능의 대상.
- `k=2`: 세암 — 저조 시 수면과 거의 같은 높이.
- `k=3`: 암암 — 항상 물속(항상 잠김).
- `v`: 간출암(k=1)의 경우 해도 기준면(약최저저조면) 위 노출 높이(m) — 조위 데이터(TideBED/조석표)와
  같은 기준면이라 별도 보정 없이 잠김경고 계산에 바로 쓸 수 있다.

### 2.3 마커 UI 변천사 (커밋 순)
단일 "위험물" 토글(`0e0fa98a`) → 사용자 요구로 노출암/간출암 2버튼 분리 + 지연로드(첫 클릭 시
1회만 fetch, Promise 공유) + `ol.source.Cluster`(45px 픽셀거리) 클러스터링(`4ca8aced`) → k값별
3종 SVG 아이콘 도입 + 줌14 이상에서 `setDistance(0)`으로 낱개 고정 표시(`4b286f8e`) → 사용자가
직접 제공한 참고 PNG 원본으로 SVG 교체(알파채널 기준 크롭 후 120×120 정규화, `c24b6f73`) → 마커
1.5배 확대(scale 0.345) + 좌표 완전동일 중복(실측 4쌍)은 확대해도 안 갈라지므로 번호 매긴 목록
팝업으로 처리(`b7792698`) → "너무 크다"는 피드백으로 1.25배(scale 0.2875)로 하향 + 클러스터
표시를 "색깔원+숫자" → "대표 아이콘+숫자 배지"로 교체(`c18c017c`) → 배지가 이중 원이라 지저분하다는
피드백에 숫자를 아이콘 안쪽 텍스트로 단순화, 동시에 해양안전→해양종합정보 이동 시 오버레이가 안
꺼지던 잠재 버그(`_restoreOceanOverlays()`의 조기 return이 "끄기" 단계까지 건너뜀)를 발견·수정
(`87e7938d`). **현재 상태**: 노출암/간출암 2버튼 독립 토글, 줌14 미만은 클러스터(대표아이콘+숫자),
줌14 이상은 낱개 마커 고정.

## 3. 간출암 잠김경고(3시간 전 예보) 기능 — k=1 대상, 완료됨

핵심 구현(`549b2986`, 2026-08-01): 간출암이 저조→고조로 넘어가 완전히 잠기기 **3시간 전부터**
마커에 빨간 펄스 테두리 + "OO:OO 후 완전히 잠김" 카운트다운을 표시한다. 해역별 계산 방식이 다르다:

- **서해·남해**: 기존 물빠짐(tide_field) 앵커 곡선을 그대로 재사용 — 신규 수집 없음.
- **제주**: 물빠짐이 애초에 제주를 대상 해역에서 제외하므로(BADA 갯벌 셀 기반이라 무관), 전용
  0.1° 버킷 앵커(17개, `local_server/scripts/build_hazard_rock_anchors.js`)를 신설해 물빠짐 수집
  직후 같은 배치에서 순차 수집(`local_server/services/hazard_rocks_tide_collector.js` —
  TideBED 키를 물빠짐과 공유하므로 **동시 발사 금지**, `scheduler.js`가 KST 23:30 물빠짐 완료
  직후 이어서 호출).
- **동해**: TideBED 자체가 미제공 해역이라, 기존 연간 조석표(`client/tide_data/`) 표준항 IDW
  보간을 서버에서 재현해 반정현파(half-cosine)로 교차시각을 해석적으로 구한다 — 새 수집 없음.

계산 결과는 `local_server/services/hazard_rocks_submersion.js`의 `computeAllCrossings()`가
`data/hazard_rocks/submersion.json`에 저장하고(오늘~+2일 전체 윈도우, 분단위×3일×전체 암초라
무거운 연산이므로 제주 앵커 수집 직후 배치당 1회만 실행), `GET /api/hazard-rocks/submersion`
(`local_server/routes/hazard_rocks.js`)이 이걸 읽어 `{ warnings: { rockId: etaMin(분) } }`
(0<etaMin≤180만 포함)로 응답한다. 프론트(`client/js/marine-life/safety/hazard_rocks.js`)는 이
API를 1분마다 폴링해, 클러스터에 뭉치지 않고 낱개로 보이는 마커에만 경고를 얹는다.

**⚠ 이 기능은 `/api/hazard-rocks/submersion`이라는 API를 쓴다 — 이번 세션의 "노출암 고립판정"과는
완전히 다른 기능이니 헷갈리지 말 것.** (세션 중 실제로 한 번 혼동해서 사용자가 직접 지적한 바 있음.)

### 3.1 Opus 5 독립검토로 발견·수정된 문제들 (`4a183016`)
간출암 잠김경고 초기 구현을 Opus 5로 독립검토받아 아래를 고쳤다 — **Opus를 소넷 결과의 독립
검토자로 쓴 선례**로, 이번 세션의 "500개 OCR 판독 소넷 vs 오퍼스 비교"와 같은 맥락이다.

1. `computeAllCrossings`가 분마다 곡선 파일을 `fs.statSync`로 재조회해 이벤트 루프를 수십 초
   블로킹하던 성능 문제 → (앵커,날짜)당 1회 사전로드 + 암초 50개마다 `setImmediate` 양보로 수정.
2. `hazard_rocks_tide_collector`에 anchors.json 부재(최초 배포·빈 볼륨) 시 자동 부트스트랩
   추가(물빠짐의 `ensureBuilt()` 패턴과 동일화) — fly.toml이 `local_server/data` 전체를 볼륨
   마운트해서, 커밋해둔 anchors.json이 있어도 운영 배포에선 빈 볼륨에 가려 안 보이는 문제였다.
3. `scanAnchorCrossings`의 결측 구간 보간이 구간 길이를 반영하지 않던 버그 수정 + 60분 초과
   구간은 보간 안 하도록 제한.
4. `classifyRegion`의 동해 판정 경계가 tide_field의 실제 제외 기준(경도 129.2 이상)과 어긋나
   부산·울산·포항 인근 간출암이 미커버되던 문제 수정.
5. 프론트에서 뷰포트 밖 마커에는 경고 오버레이를 만들지 않도록 필터링 추가.
6. submersion.json 읽기에 mtime 캐시 추가(1분 폴링 트래픽 대비).

## 4. 노출암 높이 추정치 — 구현 후 되돌려짐 (현재 비활성, 사유 불명)

- **구현 내용** (`f54a5666`, 2026-08-01): KHOA 원본(`TL_LNDARE_P_LV5`)에는 노출암 높이 필드가
  아예 없다. 대신 **국토지리정보원 "연속수치지형도 표고점"**(브이월드 다운로드 카탈로그,
  `dsId=30245, table_id=N3P_F0020000`)에서 노출암 좌표 반경 100m 이내 후보 중 "물리적으로
  그럴듯한(0~20m, `MAX_PLAUSIBLE_H_M`)" 값만 골라 가장 가까운 것을 채택하는 알고리즘
  (`local_server/scripts/build_hazard_rocks_elevation.js`, 227줄, 현재는 삭제됨)을 만들었다.
  표고점(NUME)은 평균해수면(MSL) 기준이라, 간출암 VALSOU와 같은 약최저저조면 기준으로 맞추려고
  물빠짐(tide_field)이 쓰는 **Z₀(평균해면고)를 IDW 보간해 더하는 보정**을 했다(문서에서 "고도점
  매칭+Z0보정"으로 부르는 게 이거다). 결과: 노출암 4,287개 중 2,741개(63.9%) 높이 확보, 팝업에
  "노출암 · 높이 약 X.Xm(추정)" 표기.
- **되돌림** (`51eff5ef`, 같은 날): 커밋 메시지가 `Revert "feat(...): 노출암 높이 추정치 추가"`
  뿐이고, **되돌린 구체적 사유(버그/데이터 품질/성급한 병합 등)가 커밋 메시지·관련 마크다운
  어디에도 남아있지 않다** — 조사했으나 못 찾음. 이번 세션 시작 시점에 "되돌림 PR을 머지해달라"는
  지시가 있었던 걸 보면 **이전 세션에서 이미 되돌리기로 결정된 상태**였던 것으로 보이나, 근거 자체는
  당시 세션 대화 로그(`Claude-Session: https://claude.ai/code/session_01SKjqi6JDKCakCXUVoTuZYG`)를
  직접 봐야 알 수 있다.
- **현재 상태(이 브랜치 HEAD 기준)**: **비활성**. `client/js/marine-life/safety/hazard_rocks.js`의
  노출암 라벨 로직은 `if (k === 0) return '노출암';`뿐 — 높이·추정 표기 없음(원복된 원래 형태).

## 6. 노출암 고립판정 — 이번 세션(2026-08-02)의 메인 작업

### 6.1 문제의식 (사용자가 제시한 핵심 통찰)
간출암(k=1)은 "바위 자체가 잠기는지"가 문제지만, **노출암(k=0)은 바위 자체는 절대 안 잠긴다
(정의상 항상 마른 땅)**. 그런데도 위험한 이유는: 밀물이 들면 노출암과 해안선을 잇는 **갯벌길(연결
경로)이 물에 잠겨**, 그 위에 있던 사람이 물에 둘러싸여 **고립**될 수 있기 때문이다. 사용자의 원래
표현: *"내가 이것을 한 요의도는… 결국 그 노출함에 낚시를 하러 들어간 사람이 주변에 물에 둘러싸여서
혼자 남느냐. 그게 중점 포인트였거든."* 이 정의 덕분에 "해안선 자체는 조석과 무관하게 항상 마른
땅"이라는 전제가 알고리즘의 기준점(seed)이 됐다(6.2).

이 문제의식이 나오기 전, 초반에는 "노출암 주변 수심을 정확히 알면 고립 여부를 계산할 수 있지
않겠냐", "해안선까지 고려할 필요가 있는가" 같은 논의가 먼저 있었고, 사용자가 위 인용문으로
목적을 명확히 하면서 **"해안선까지의 연결성"**이 알고리즘의 핵심으로 확정됐다.

### 6.3 BADA2024 근접-해안 신뢰도 문제 발견
고립판정은 노출암 주변 수심이 정확해야 의미가 있는데, BADA2024 수심 데이터는 해안선에 가까울수록
(간출지/조간대 근방) 신뢰도가 떨어진다는 걸 세 가지 방법으로 독립 검증했다:
1. BADA 좌표 자체가 해안선과 median 138m 떨어져 있음(원시 좌표 대조).
2. KHOA 실제 전자해도 OCR 판독 대조 시, 근접-해안 표본에서 최대 60%까지 "육지 vs 수심" 판정이
   BADA와 충돌.
3. 근접-해안 표본의 16.7%는 반경 내 BADA 커버리지 자체가 없음.

**결론**: 노출암 주변 BADA 값을 그대로 믿을 수 없고, 특히 해안선에 가까운 지점은 실제 전자해도를
직접 판독(OCR)해서 검증해야 한다.

### 6.4 OCR 검증 방법론 — 규모를 키워온 과정

**왜 OCR인가, 왜 클로드가 직접 읽는가**: 처음엔 "Gemini AI로 OCR"을 검토했으나, 사용자가
명시적으로 "클로드에서 진행하고자 했던 것"이라고 방향을 정했다 — BADA2023/2024 자체가 부적합할
가능성이 높다고 의심했기 때문에, 별도 벤더(Gemini) 판독을 또 하나 얹기보다 **클로드가 앱에 이미
반영된 KHOA 전자해도 이미지를 Read 도구로 직접 읽는** 방식을 택했다. 이 판단은 나중에 실제로 옳았던
것으로 확인됐다(§6.3의 BADA 신뢰도 문제).

**표본 규모를 단계적으로 키운 이유**: 사용자가 "그냥 말하기보다는 실제 OCR을 진행함으로써" 검증해
보자고 요구해, 처음엔 12곳 정도로 시작했다가 → 서해·남해·제주별로 각 10장씩 뽑아 조석 다른
시점까지 적용해보자는 요구로 30개 규모로 확대 → 최종적으로 "단순히 한두 장으로 볼 게 아니라"는
지적에 따라 **60개**(서해·남해·제주 각지역, 제주는 이후 조석 데이터 문제로 제외)까지 늘려 판독
정확도·신뢰도 통계를 낼 수 있는 규모를 확보했다. 이 60개 표본이 초록=간출지 오분류 버그(아래)와
줌아웃 폴백 기법을 발견한 기반이다.

**타일 정렬 정밀화**: 최초엔 KHOA WMS z16 타일 1장(≈611m)만 받아 크로스헤어를 표시했는데, 타일
경계가 조회 좌표와 정렬돼 있지 않아 크로스헤어가 타일 아무 위치에나 찍혔다 — "가장 가까운 숫자"를
사람이 골라도 실수하기 쉬운 배치였다. 사용자가 "크로스헤어가 중앙에 나오도록 찍고…"라고 정확히
요구해서, 3×3 타일을 통째로 받아 스티칭한 뒤 Mercator 투영 픽셀 좌표를 직접 계산해 조회 좌표가
정확히 크롭 중앙(500m 창)에 오도록 만들었다(`annotate_points.py` → 이후 재사용 가능하게
`fetch_one.js`/`stitch_one.py`로 일반화).

**줌아웃 폴백 발견 계기**: 서해 7번 표본(id 5891)에서 중앙 크롭에 아무 정보가 없어 처음엔
"데이터 없음"으로 단정했는데, 사용자가 "등심선을 확대해도 없다고 하면 줌 레벨을 조금 더 조정해서
확인할 수 있는 부분이 있을 것 같다"고 지적 — 실제로 줌12 광역(≈9.8km) 이미지로 넓혀보니 그 지점이
해도에 표시된 위험구역/암초 무더기 심볼 군집 안에 있어서 숫자가 아예 없는 게 "데이터 누락"이 아니라
"해도 설계상 의도된 표기"였음을 확인했다. 이후 모든 판독에 "중앙 크롭에 정보 없으면 반드시 광역
이미지도 확인" 폴백을 표준으로 넣었다.

- 3×3 KHOA WMS z16 타일을 스티칭한 뒤 Mercator 투영 픽셀 계산으로 조회 좌표를 정중앙(빨간
  크로스헤어)에 오도록 정밀 크롭(약 500m 창) — 단일 z16 타일(≈611m)만 쓰면 조회 좌표가 타일
  아무 데나 걸려 "가장 가까운 숫자"를 잘못 고를 위험이 컸음. 데이터가 없으면 z12 광역(≈9.8km)
  이미지로 폴백. 재사용 스크립트: `fetch_one.js`(타일 확보) + `stitch_one.py`(스티칭+정밀 크롭).
- **색상 판정 규칙(확정)**: 황토색/베이지=진짜 육지(`land`). **초록색=간출지(조간대) — 육지가
  아니다!** 밀물에 잠기고 썰물에 드러나는 지형이라 반드시 `water_reading`으로 분류해야 한다.
  파란색=항상 물. 초기 프롬프트가 "노란/베이지=육지"만 명시하고 초록을 명시적으로 제외하지 않아,
  60개 표본의 "land" 판정 25건 중 18건(72%)이 실은 초록 간출지를 육지로 오분류한 것으로 드러났다.
  **발견 경위**: 사용자가 60개 결과표를 보고 "육안으로 봤을 때 사실상 육지와 다름없어요… 이 부분은
  확인을 해봐야 되지 않을까?"라고 의심을 제기해, 25건의 land 판정 이미지를 하나하나 재확인한 결과
  18건(72%)이 초록 간출지 오분류, 5건만 진짜 황토색 육지, 2건은 애매했다. 이후 모든 배치 프롬프트에
  "초록=간출지, 절대 land 아님"을 굵게 명시하는 규칙을 반영했다(500개 배치의 최종 프롬프트 문구는
  스크래치패드 `workflow_500_batch*.js` 참고).
- **모델 비교 결론**:
  - **하이쿠 대체 시도 → 기각**: 60개 표본 중 이미 판독된 30곳을 하이쿠로 재판독(기존 이미지 재사용,
    재다운로드 없음 — `hazard-rock-haiku-compare` 워크플로우). 소넷 원 판독 대비 **43% 판정
    불일치**(verdict 자체가 달라짐), 토큰 절감 효과도 기대만큼 뚜렷하지 않아 "비용 절감 대안"으로서
    가치가 없다고 결론.
  - **오퍼스 대체 시도 → 채택**: 같은 방식(기존 이미지 재사용)으로 5개 표본(r2673/r2806/r3610/
    r4327/r4497)을 오퍼스로 재판독하려 했으나, **원본 소넷 판독의 정확한 토큰 사용량을 알아야
    공정 비교가 되는데, 원본 60개 배치를 돌렸던 Workflow 트랜스크립트가 이미 만료돼 있었다** —
    그래서 같은 5개 표본을 **오늘 다시 한 번 소넷으로도** 재실행해(동일 이미지, 동일 프롬프트,
    같은 날) 진짜 동시조건 비교를 만들었다. 이 재실행 과정에서 흥미로운 부수 발견도 있었다:
    소넷 자체도 같은 이미지를 재판독할 때마다 결과가 미묘하게 달라진다(r2673의 채택 수심이
    원래 23m였다가 재실행 시 20.9m로 바뀌는 등, 크로스헤어와 거리가 비슷한 두 후보 숫자 중 어느
    쪽을 고르는지의 노이즈) — 즉 판독 자체에 어느 정도 run-to-run 변동성이 있다는 걸 감안해야 한다.
    결과: 토큰 소모량이 소넷과 비슷하거나(5개 표본: 오퍼스 179,346 vs 소넷 197,387, 오퍼스가
    오히려 약 9% 적음) 오히려 더 적었고(500개 규모 전체에서도 재확인 — 오퍼스 18.69M vs 소넷
    20.83M 토큰), 경계 사례(간출지 vs 육지 애매 지점) 판독 정확도도 더 안정적으로 확인됨(500개
    규모 소넷/오퍼스 판정 불일치 32건 중 24건이 "소넷=육지, 오퍼스=물(간출지)" 방향 — 소넷이
    초록 간출지를 육지로 오분류하는 경향이 규칙 수정 후에도 오퍼스보다 더 남아있다는 뜻; 대표
    사례가 5개 표본 중 r3610: 소넷은 재실행 시 land로, 오퍼스는 water_reading(간출지)로 올바르게
    판정). **오퍼스를 메인 데이터로 채택, 소넷은 비교·검증용 보조자료로만 유지**(2026-08-02 확정).
    단, 오퍼스는 토큰당 단가가 소넷보다 높아 계정 사용한도 소모 속도는 더 빠를 수 있다는 점은
    감안해야 함(토큰 "양"과 "실제 소모되는 한도"는 다른 개념).
- **후보 선정 설계(방향 전환)**: 처음엔 "지금 고립 상태인가"만 정적으로 봤으나, 사용자가 "사실
  내가 중요하게 생각하는 것은 연결됐다가 고립됐다가 하는 그런 개수가 중요한 거야"라고 짚으면서,
  실제 안전상 의미 있는 건 조석에 따라 **연결↔고립이 전환되는** 지점이라는 방향으로 바뀌었다(항상
  고립/항상 연결인 곳은 애초에 위험 신호로서 가치가 적다는 논리). 이 재구상 이후 2단계 후보 설계로
  정리됐다:
  1. (Task #19, 미착수) 정밀 조석-스윕 물리 기반 스크리닝 — 전체 3,130개 노출암에 OCR 없이
     플러드필만으로 저렴하게 "실제로 전환되는" 후보를 찾는다.
  2. (진행 중) 해안선 근접 안전망 — BADA가 특히 부정확한 근접-해안 구간을 OCR로 직접 검증. 격자
     해상도(CELL_DEG≈150m) 자체가 근접-해안에서 부정확하다는 걸 알고 있었기 때문에, 임계값을
     100m/300m 두 옵션으로 비교해봤고("100m로 잡히면 어떻게 될까?"라는 질문에 대한 실측 답변
     포함) 최종적으로 **300m**를 채택 — 후보 수가 적당히 늘어나면서도(2,678개) 근접-해안 부정확
     구간을 충분히 커버한다고 판단. 300m 기준 총 후보 2,678개 중 지역별(서해·남해·제주) 비례
     층화로 1,000개(500개씩 2차) 표본 조사 진행.

### 6.5 500개 단위 배치 진행 상황

**Workflow 파이프라인 구축 중 겪은 문제**: 500개 규모로 올리면서 Claude Code Workflow 도구의
`args` 파라미터에 500개짜리 배열을 넘겼는데, 두 번 연속으로 실패했다(Task `wsjb0cc8m`,
`whn5fvh8m`) — `args`로 전달한 큰 객체가 스크립트 안에서 파싱된 배열이 아니라 **JSON으로
이중 인코딩된 문자열**로 도착해 `args.rocks.map is not a function` 오류가 났다. `scriptPath`+`args`
조합, `script`+`args` 조합 둘 다 같은 문제였다. **해결**: 데이터를 `args`로 넘기지 않고 워크플로우
스크립트 본문 텍스트 안에 `const ROCKS = [...]` 리터럴 배열로 직접 박아 넣는 방식으로 우회 —
이게 이후 모든 배치(500개×2차, 소넷/오퍼스 각각)의 표준 패턴이 됐다.

### 6.6 로그 통일 (관련 유지보수)
사용자가 제주 앵커 TideBED 3일치 수집이 실제로 되고 있는지 Fly.io 로그로 확인하고 싶어 해서, 처음엔
`scheduler.js`의 로그 문자열("🪨 간출암 제주 앵커 곡선 수집 시작…" / "✅ 간출암 제주 앵커 수집
결과…")을 검색 키워드로 알려줬다. 그런데 사용자가 최근 3일 로그에서 이 키워드로 아무것도 못
찾았다고 하면서, **"별도 로그의 이름이 통일되지 않아서 적절하지 않은 것 같다"**며 서해·남해와
동일한 로그 형식으로 통일해달라고 요청했다. 재조사 결과 로그가 두 겹 구조였다: ① scheduler.js
바깥쪽 요약 로그(서해·남해 "🌊 물빠짐 앵커 곡선 수집…" vs 제주 "🪨 간출암 제주 앵커 곡선 수집…" —
문구가 서로 다름), ② 각 수집기 모듈 안쪽 진행상황 로그는 이미 문구가 동일했지만(scheduler가 넘긴
동일한 `log` 함수를 그대로 쓰므로) 모듈 기본값(fallback) prefix만 `[tide_field_collector]` vs
`[hazard_rocks_tide_collector]`로 달랐음(실제 운영에서는 항상 opts.log가 주입되므로 이 fallback
prefix는 프로덕션에 안 보임). **바깥쪽 요약 로그를 "🌊 TideBED 앵커 곡선 수집 (서해·남해)" /
"(제주)"로 통일**(커밋 `ea24b036`) — 지역만 괄호로 구분하고 검색 키워드는 하나("TideBED 앵커 곡선
수집")로 양쪽 다 잡히게 만들었다. 이 과정에서 사용자가 실시간으로 정확히 23:30:35 KST에 찍힌
로그 줄(`🪨 간출암 제주 앵커 곡선 수집 시작...`)을 직접 캡처해 보여줘, 배치가 스케줄대로 살아있다는
것도 함께 확인됐다. 같은 세션에서 `TIDE_FIELD_README.md`도 이번 세션 확정 내용 전반(플러드필 버그
수정+실검증, BADA 신뢰도 문제, OCR 방법론, 모델 비교, 애매 판정 보존 원칙, 연 1회 정기 갱신 필요성)
으로 대폭 보강했다(같은 커밋).

### 6.7 재사용 가능한 도구 모음

**2026-08-03부터 핵심 파이프라인 스크립트 3개 + HTML 템플릿을 저장소에 커밋해서 세션이 바뀌어도
살아남게 만들었다**(그 전까지는 스크래치패드에만 있어서 세션이 끝나면 사라졌다) — `local_server/scripts/`에:

- **`hazard_rocks_ocr_fetch.js`** — 단일 노출암 라벨/좌표를 받아 KHOA WMS z16 3×3 타일 + z12
  광역 타일을 받아온다. `node hazard_rocks_ocr_fetch.js "<label>" "<lat>" "<lon>" "<outDir>"`.
  로컬 서버(포트 3001)의 `/api/ocean/khoa-wms` 프록시가 떠 있어야 동작한다.
- **`hazard_rocks_ocr_stitch.py`** — 위 타일을 스티칭하고 Mercator 픽셀 계산으로 조회 좌표를
  정중앙에 배치한 크롭(`{label}_centered.png`)과 z12 광역 표시 이미지(`{label}_wide_marked.png`)를
  만든다. `python3 hazard_rocks_ocr_stitch.py "<label>" "<outDir>"`.
- **`hazard_rocks_ocr_build_review.py` + `hazard_rocks_ocr_review_template.html`** — 배치 결과
  JSON에서 **애매 판정만(land 자동 제외)** 골라 이미지를 base64로 내장한 HTML 검토 페이지를
  만든다(16MB 넘으면 자동 분할). **`verdict=land`는 코드 레벨에서 필터링돼 검토 큐에 아예 안
  올라간다** — 283건 전수검토 결과 AI land 판정이 한 번도 틀린 적이 없어 2026-08-03에 이렇게
  확정했다(§6.5 참고, 사용자가 직접 지시). 사용법:
  ```
  python3 hazard_rocks_ocr_build_review.py \
    --results <배치결과.json> \
    --image-dir <이미지폴더1> [--image-dir <이미지폴더2> ...] \
    --out <출력.html>
  ```
  이 파일을 Artifact로 배포해 사람이 검토하면 된다. **이 필터를 우회해서 land를 다시 검토 큐에
  넣지 말 것** — 사용자가 명시적으로 "재차 묻지 않도록" 요청한 사항이다.
- `workflow_500_batch1.js`/`_batch2.js`(소넷), `workflow_500_batch1_opus.js`/`_batch2_opus.js`
  (오퍼스), `workflow_500c_batch1_opus.js`/`_batch2_opus.js`(2차, 오퍼스만) — Workflow 스크립트
  템플릿. 색상 규칙·판독 순서·SCHEMA가 전부 프롬프트에 박혀 있어, 다음 배치도 이 파일을 복제해
  `ROCKS` 배열과 `OUT_DIR`, `meta.name`만 바꾸면 된다.
  ⚠ **판독에 쓸 모델은 반드시 `agent(prompt, { ..., model: 'claude-opus-5' })`로 명시할 것**
  (지정 안 하면 세션 기본 모델로 돈다).
  ⚠ **`ROCKS` 데이터는 `args`로 넘기지 말고 스크립트 본문에 리터럴로 박아 넣을 것**(§7 이중 인코딩
  버그 참고).
  ⚠ **한 번에 4개까지 Workflow를 동시에 launch해도 괜찮다** — 이번 세션에서 실제로 소넷2+오퍼스2를
  동시에 돌렸고 문제없이 각각 8~9백만 토큰·8분대에 완료됐다(단, 같은 이미지 디렉터리를 동시에 쓰면
  파일 경합이 날 수 있으니 배치마다 `OUT_DIR`을 분리할 것 — 실제로 오퍼스 배치는 소넷과 별도 폴더
  `ocr_batch500_*_opus`를 썼다).
- `build_review_page.py` + `review_template.html` — 애매 판정 사람 검토용 HTML 페이지 생성기.
  `opus500_ambiguous.json`(애매 판정만 골라낸 배열)을 읽어 이미지를 base64로 내장한 단일 HTML을
  만든다. Artifact로 배포할 것(로컬 파일로 열면 이미지는 보이지만 다운로드 링크가 blob URL이라
  세션 간 공유는 안 됨).
- `select_next500.py`(1차, Python) / `select_and_fetch_next500.js`(2차, Node) — 300m 이내 후보
  재계산 + 이미 처리된 id 제외 + 지역 비례 층화 선정 + BADA 참고값 조회까지 한 번에 하는 스크립트.
  §6.5 후반부의 재현 방법을 그대로 코드화한 것.

## 7. 알아둘 것 (교훈/시행착오 요약)

- **버퍼는 정합 오차 흡수용이지 검사 우회용이 아니다** — 6.2의 치명적 버그가 정확히 이 원칙 위반이었다.
- **초록색(간출지)을 육지로 착각하기 쉽다** — AI든 사람이든, 반드시 "육지 아님, water_reading"
  규칙을 명시해야 한다.
- **BADA2024는 해안 근접부에서 믿을 수 없다** — 근접-해안(300m 이내) 판정은 반드시 KHOA 전자해도
  OCR로 직접 검증할 것.
- **토큰 "양"과 계정 "사용한도 소모 속도"는 다르다** — 오퍼스가 토큰량은 비슷/적어도 단가가 높아
  한도는 더 빨리 줄 수 있음.
- **애매한 AI 판정은 자동 확정하지 말고 이미지를 보존한 채 사람에게 제시**하는 절차를 표준으로 삼을 것.
- **Workflow 도구의 `args` 파라미터에 큰 데이터를 넘기면 이중 JSON 인코딩되는 버그가 있다** — 데이터는
  스크립트 본문에 리터럴 배열로 직접 박아 넣을 것.
- **아티팩트(Artifact) 샌드박스는 JS로 시뮬레이션한 `<a>.click()` 다운로드를 막는다** — 실제
  사용자가 직접 클릭하는 진짜 `<a href download>` 링크로 우회해야 한다.
- **/api/hazard-rocks/submersion(간출암 잠김경고)과 노출암 고립판정은 다른 기능이다** — 절대
  혼동하지 말 것.
- **51eff5ef(노출암 높이 되돌림)처럼, 되돌린 이유를 커밋 메시지에 안 남기면 나중에 완전히 미스터리가
  된다** — 앞으로 되돌림 커밋엔 반드시 사유를 적을 것.
- **API 응답 필드를 있는 그대로 믿지 말고 정의를 정확히 확인할 것** — `anchors[].distKm`을
  "질의 좌표-매칭 격자 거리"로 착각해 제주 격자 매칭이 3km 이내라고 잘못 판단한 사례(실제 53km)가
  있었다. 원시 응답 하나를 까보고 직접 재계산해서 검증하는 습관이 필요하다.
- **`/api/tide-field?time=&bbox=` 같은 캡(cap)이 있는 API는 결과가 잘렸는지(`budget_dropped`)
  반드시 확인하고, 잘렸으면 bbox를 재귀 분할해서 전량 수집할 것.**
- **타일 기반 지도 이미지를 "정확한 좌표"로 판독할 땐 타일 경계 정렬에 주의** — 조회 좌표가 타일
  아무 데나 찍히면 "가장 가까운 값"을 잘못 고르기 쉽다. 여러 타일을 스티칭해 조회 좌표를 크롭
  중앙에 오도록 정밀 배치할 것.
- **"중앙 크롭에 정보 없음"을 "데이터 없음"으로 바로 단정하지 말 것** — 줌아웃(광역) 이미지로
  넓혀보면 등심선·심볼 등 추가 정보가 있을 수 있다(서해_7 사례).
- **Workflow 도구의 `parallel()`은 하나의 호출 안에 수십~수백 개를 몰아넣어도 이 환경의 동시처리
  한도(대략 16-way) 때문에 기대만큼 병렬로 안 돌 수 있다** — 큰 배치는 처음부터 여러 개의 별도
  Workflow 호출로 쪼개 한 메시지에서 동시에 디스패치하는 편이 체감 속도가 낫다(CLAUDE.md 결정로그에도
  동일 내용 기록돼 있음, 이번 세션 500개×2 배치를 4개 워크플로우로 병렬 디스패치한 것도 이 원칙).
- **오퍼스(및 소넷)가 `land`로 판정한 건 신뢰도가 매우 높다** — 1,000개 전체 검토(애매 판정 283건)에서
  AI가 land로 판정한 게 사람 검토로 뒤집힌 사례가 0건이었다. 반대로 `water_reading`(특히
  `color_zone_only` 근거)은 여전히 오분류(주로 육지 쪽으로 정정) 비율이 있다. **비대칭적 신뢰도이므로
  향후 검토 대상에서 land는 빼고 water_reading의 애매 근거만 사람에게 보여주면 검토량을 크게
  줄일 수 있다**(2026-08-03 확정).
- **아티팩트 파일 크기 제한(16MB)을 넘으면 즉시 실패한다** — base64 이미지 여러 장을 한 HTML에
  욱여넣을 땐 사전에 총 용량을 가늠해서(1건당 대략 90~100KB 안팎) 필요하면 처음부터 여러 페이지로
  쪼갤 것(187건은 8.6MB+8.7MB 두 페이지로 쪼개야 했다).
