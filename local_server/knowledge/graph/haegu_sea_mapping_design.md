# 해구 ↔ 해역 매핑표 설계안

## 1. 목적
SEAGNAL "나리야"의 해구 기반 데이터(랭킹·조회)와 사용자가 말하는 **명명 해역(예보구역)**
사이를 잇는다. `data/zone_coords.json` 의 **해구 1296개**(0.5° 격자 번호→경위도)를,
`seaZoneCoordinates.js` 의 **명명 해역 48개**(대표 중심좌표) 중 하나에 결정론적으로 배정한다.

## 2. 입력 출처 (모두 읽기 전용, 수정 금지)

| 항목 | 파일 | 구조 | 비고 |
|---|---|---|---|
| 해구 좌표 | `data/zone_coords.json` | `{ "<번호>": { lat, lon } }` × 1296 | 위도 25.25~44.75 / 경도 119.25~139.75, **0.5° 등간격 격자** |
| 해역 대표좌표 | `seaZoneCoordinates.js` (`SEA_ZONE_COORDINATES`) | `{ code:{ code,name,lat,lon,region,type } }` × 48 | **대표 중심점**이 명시된 권위 출처. `assistant.js` 의 `ZONE_COORDS` 도 바로 이 파일을 정규식 파싱하여 적재 |
| 해역명↔코드 | `routes/assistant.js` `ZONE_NAME_TO_CODE` / `ZONE_NAMES` | name→code | 사용자 발화 해역명을 코드로 정규화. 매핑표는 code 기준이므로 이 표와 키가 맞물림 |

> **해역 대표좌표 출처 정확성:** `seaZoneCoordinates.js` 주석에 "각 구역의 대표 중심점 좌표"라
> 명시돼 있고 `assistant.js` 의 `ZONE_COORDS` 도 동일 파일을 쓴다. 즉 매핑의 기준점은 런타임이
> 실제로 사용하는 좌표와 **완전히 동일**하다. 별도 좌표 출처를 새로 만들지 않는다.

## 3. 알고리즘 (결정론적, 2 pass)

### 1차 — 최근접 명명 해역 배정
각 해구 점 `p`에 대해 48개 해역 대표좌표와의 거리를 구해 **가장 가까운 해역**에 배정.

- **거리 함수:** cos(위도) 가중 유클리드.
  `d = sqrt( (Δlat)² + (Δlon·cos(lat_mid))² )` — 한반도 위도대(≈35°)에서 경도 1°의 실거리가
  짧으므로 보정. 단조·결정론적이면 충분하지만 거리비 판정을 위해 도(˚) 단위 실거리를 산출.
- **포함 vs 최근접:** 해역은 폴리곤이 아니라 점(대표좌표)으로만 주어지므로 **포함 판정은 불가**.
  격자가 등간격(0.5°)이라 최근접점 방식이 사실상 보로노이 분할과 동치 → 충분히 안정적.
- **동률 tie-break (결정 보장):** ① 거리 오름차순 ② 같으면 **해역코드 사전순**. 입력이 같으면
  출력 항상 동일.

### 2차 — 경계 해구 모호성 처리
보로노이 경계 근처 해구는 최근접/차순위 거리가 비슷해 오배정 위험. 이를 **표시**한다.

- 최근접 거리 `d1`, 차순위 `d2`에 대해 `d2/d1 < AMBIGUOUS_RATIO(=1.15)` 이면 `ambiguous:true`.
- 모호 해구는 차순위 후보를 `alt:{code,name}` 로 함께 기록 → 런타임이 "○○ 또는 △△ 부근"
  식으로 안내하거나, 상위 로직이 추가 신호(직군/문맥)로 재판정 가능.
- 배정 자체는 항상 1순위로 확정(결정론 유지). 모호 플래그는 품질 메타데이터일 뿐.

## 4. 출력 포맷 — `haegu_sea_mapping.json`

런타임 소비가 쉽도록 **해구→해역**을 1순위 객체로, 역방향과 좌표 스냅샷을 보조로 둔다.

```jsonc
{
  "_meta": {
    "generated": "2026-06-03",
    "source": ["data/zone_coords.json", "seaZoneCoordinates.js"],
    "algorithm": "nearest-named-zone (cos-lat weighted euclidean)",
    "ambiguousRatio": 1.15,
    "haeguCount": 1296, "seaZoneCount": 48, "ambiguousCount": <n>
  },
  "haeguToSea": {                       // ★ 런타임 1순위: 해구번호 → 해역
    "325": { "code": "12B20103", "name": "부산앞바다", "region": "남해동부",
             "distKm": 12.3, "ambiguous": false, "alt": null }
  },
  "seaToHaegu": {                       // 보조: 해역코드 → 소속 해구번호[](숫자 정렬)
    "12B20103": [320, 321, 325, ...]
  },
  "seaZones": {                         // 검증·표시용 대표좌표 스냅샷
    "12B20103": { "code":"12B20103","name":"부산앞바다","lat":35.0,"lon":129.1,"region":"남해동부" }
  }
}
```

## 5. 런타임 활용 (`routes/assistant.js` 비수정 — 소비 측 신규 코드에서)

기동 시 1회 로드해 메모리 맵으로 사용. 두 방향 모두 O(1).

1. **해구 → 해역 라벨링:** 해구 랭킹/조회 결과(`HAEGU_COORDS` 기반)에 사람이 읽는 해역명을
   붙인다. `MAP[해구번호].name` → "325번 해구(부산앞바다)".
2. **해역 발화 → 해구 후보:** 사용자가 "부산앞바다" 라고 하면
   `ZONE_NAME_TO_CODE["부산앞바다"]` = `12B20103` → `seaToHaegu["12B20103"]` 로
   해당 해역 소속 해구 목록을 얻어 랭킹/집계 대상으로 사용.
   - ⚠️ **부분 키 불일치 주의:** `ZONE_NAME_TO_CODE` 의 값 중 5개 코드
     (`12A30100`·`12A30200`·`12B10100`·`12B10200`·`12B10300`)는 `SEA_ZONE_COORDINATES`
     (=대표좌표 출처)에 **존재하지 않는다**. 이 코드는 해당 해역의 광역/대표 코드인데
     좌표 파일에는 세부 코드(예: `12B10301`~`12B10304`, `12A30101`~`12A30202`)만 있기 때문.
     따라서 "제주도앞바다·서해남부앞바다/먼바다·남해서부앞바다/먼바다" 등 **11개 발화명**은
     `seaToHaegu[code]` 가 `undefined` 가 된다. 소비 측은 이 경우
     (a) 같은 region 의 세부 코드 해구들을 합산하거나 (b) `coordsFor()` 좌표 경로로 폴백해야 한다.
3. **경계 안내:** `ambiguous` 인 해구는 `alt.name` 을 곁들여 모호성을 사용자에게 노출.

좌표가 직접 주어지면 기존 `coordsFor()` 경로를 그대로 쓰고, 이 표는 **해구↔명명해역 변환**
전용 보조 인덱스로만 결합한다. 키 체계(코드)는 `ZONE_NAME_TO_CODE` 와 **동일한 KMA 구역코드**라
충돌은 없으나, 위 ⚠️ 처럼 **모든 코드가 양쪽에 다 존재하지는 않으므로**(5개 코드는 좌표 파일 미수록)
런타임은 `seaToHaegu[code]` 가 비었을 때의 폴백을 갖춰야 한다 — "무변환 즉시 사용"은 좌표 파일에
존재하는 코드(43개 중 38개가 명명 대응)에 한해 성립.

## 6. 생성기
`knowledge/graph/build_haegu_sea_mapping.js` (초안). 실행:
```bash
node knowledge/graph/build_haegu_sea_mapping.js   # → haegu_sea_mapping.json 생성
```
- `seaZoneCoordinates.js` 는 정규식 파싱(브라우저/서버 공용 전역이라 require 회피 — `assistant.js`
  의 `ZONE_COORDS` 적재 방식과 동일 철학).
- 입력 미수정, 신규 산출물만 기록. 멱등(같은 입력→같은 출력).

## 7. 자체검토 결론
- **경계 모호성:** 점-기반이라 보로노이 경계 해구가 생김 → `ambiguous`/`alt` 로 명시, 결정 배정은 유지.
- **대표좌표 출처:** 런타임이 실제 쓰는 `seaZoneCoordinates.js` 와 동일 → 좌표 불일치 위험 없음.
- **포맷:** `haeguToSea`(정방향)·`seaToHaegu`(역방향) 양방향 인덱스 + 키가 기존 코드 체계와
  일치 → 정방향(해구→해역)은 추가 변환 없이 즉시 사용 가능.
- **부분 키 불일치(검증으로 확인됨):** 역방향(해역명→해구)은 완전하지 않다. `ZONE_NAME_TO_CODE`
  값 5개 코드(`12A30100`·`12A30200`·`12B10100`·`12B10200`·`12B10300`)가 `SEA_ZONE_COORDINATES`
  에 없어 `seaToHaegu` 키로 등장하지 않으며, 이 코드에 매핑된 발화명 11개는 폴백이 필요(§5-2 참고).
- **한계:** 48개 해역이 모든 해구(원해 격자 등)를 의미 있게 덮지 못해 먼 해구는 distKm 가 매우 크게
  잡힘(실측 검증: 최북동 격자 lat 42.75/lon 131.75 → 동해북부먼바다 약 430km, haversine 일치).
  `distKm` 임계로 "해역 미지정" 처리하는 후처리는 소비 측 선택 사항.
- **모호 비율:** 현행 `AMBIGUOUS_RATIO=1.15` 에서 1296개 중 735개(약 57%)가 `ambiguous` 로
  표시된다 — 점-기반 보로노이가 조밀(48점)해 경계 폭이 넓은 탓. 모호 플래그를 실제 UX 분기에
  쓰려면 임계를 낮추거나(예: 1.05) distKm 절대값과 함께 판단할 것.

## 8. 2차 검토 (독립 재검수)
- **실행성:** `node -c` 통과, 실제 실행 시 해구 1296 → 해역 48 정상 산출(멱등 확인).
- **출처 경로:** 스크립트 위치(`knowledge/graph/`) 기준 `../../seaZoneCoordinates.js`·
  `../../data/zone_coords.json` 모두 실존, 구조 일치(해구 1296 flat, 해역 48). 정상.
- **알고리즘/tie-break:** 거리 오름차순 → 코드 사전순 2단 정렬로 결정론 보장. 정상.
- **수정:** ① 좌표 파서를 필드순서 비의존(블록내 개별 매칭)으로 견고화(출력 불변 확인).
  ② 위 "부분 키 불일치" 사실을 §5-2·§5·§7 에 정정 반영(기존 "런타임 무변환" 주장 보정).
