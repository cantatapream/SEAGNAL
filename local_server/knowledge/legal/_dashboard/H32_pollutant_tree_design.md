## 1. 데이터 형태 — 선례와 같은 이유로 JSON

`wiki/`류 산문 페이지는 사람이 읽는 글이고, 이 자산은 **프로그램(되묻기)이 타고 내려가는 구조**다. 그래서 H-35 `delegation_graph_*.json`·H-36 `vessel_doc_tree.json`과 같은 성격의 **신규 JSON 아티팩트**로 만들고, 헤더 규약(`generated`/`scope`/`semantics`/`caveats`/`summary`/`scan`/`unmapped`/`tree`)도 선례를 그대로 따른다. 파일 형태를 통일해 두어야 §8의 유지보수 스크립트가 **트리 파일명만 바꿔 재사용**된다.

## 2. 스키마

### 2.1 최상위

```jsonc
{
  "generated": "2026-08-10T..+09:00",
  "scope": "74법 raw 전수 스캔 — '오염물질 종류별 배출규제' 계층 트리",
  "semantics": { "규제_상속": "…", "요건유형": "…", "질문_선택지": "…", "추가확인": "…" },
  "caveats": ["…"],
  "summary": { "laws_in_scope": 74, "scan_candidate_articles": N, "nodes": N, "leaves": N,
               "rule_entries": N, "entries_by_kind": {}, "entries_by_tier": {}, "per_law": {} },
  "scan": { "laws_with_candidates": [], "laws_without_candidates": [] },
  "unmapped": { "법_단위": [], "물질_단위": [], "유형_단위": [] },
  "tree": { …노드… }
}
```

### 2.2 노드

```jsonc
{
  "id": "oil",                       // 프로그램용 안정 식별자
  "라벨": "기름",                     // 사용자에게 보이는 법률 용어 그대로
  "정의": "「석유 및 석유대체연료 사업법」에 따른 원유 및 석유제품…",  // raw 정의조항 요지
  "provenance": [ { "법령","계층","조문","법령ID","파일","인용" } ],   // ★출처 없는 노드 금지
  "구분근거": [ … ],                  // 형제와 배타임을 보이는 조문(있을 때만)
  "질문": "…", "선택지": [ {label,hint,next} ],   // ★비-리프에만
  "추가확인": [ … ],                  // ★리프에만 — 트리로 안 쪼갠 잔여 축
  "규제": [ …규제항목… ],             // 어느 노드에나 올 수 있다(상속 규약 아래)
  "children": [ … ]
}
```

**★규제 상속 규약**(선례의 서류 상속과 동일): 어떤 물질에 걸리는 규제 = **루트에서 그 리프까지 경로상 모든 노드의 `규제`를 합집합**으로 모은 것. 예컨대 "누구든지 선박으로부터 오염물질을 해양에 배출하여서는 아니 된다"(제22조제1항)는 `marine_pollutant` 노드에 **한 번만** 두고 그 아래 폐기물·기름·유해액체물질·포장유해물질이 전부 상속한다. 리프마다 복제하면 법 하나가 바뀔 때 N곳을 고쳐야 해서 §8의 유지보수 매칭이 무너진다.

### 2.3 규제 항목

```jsonc
{
  "요건": "선박에서 기름을 배출할 때의 요건",
  "요건유형": "배출기준",     // 금지행위 | 배출기준 | 처리의무 | 적용제외
  "근거법령": "선박에서의 오염방지에 관한 규칙",
  "근거법령_slug": "선박에서의오염방지에관한규칙",
  "계층": "규칙",            // 법률 | 시행령 | 시행규칙 | 규칙 | 별표
  "근거조문": "제9조",
  "법령ID": "…",             // _meta.json families.<계층>.법령ID (H-29 11항·L-74)
  "파일": "raw/15_관련타부처/선박에서의오염방지에관한규칙/법률.txt",
  "인용": "…배출액 중의 기름 성분이 0.0015퍼센트(15ppm) 이하일 것…",   // ★raw에서 직접 읽음
  "조건": "선박(시추선·플랫폼 제외)의 항해 중",
  "적용제외": null,
  "위임": [ {"법령","계층","조문"} ],
  "주의": null
}
```

**불변식**
1. `인용`은 **빌더가 raw에서 읽어 채운다.** SPEC에는 "어느 법 몇 조 + 그 조문에 있어야 할 앵커 문구"만 적는다.
2. 앵커가 그 조문 원문에 없으면 **빌드 실패**(JSON을 만들지 않는다).
3. 여러 항목을 묶은 요건은 `also` 인자로 **개별 문구가 같은 조문에 실재하는지 추가 검증**한다(선례 §6이 5건의 오인용을 잡아낸 뒤 도입한 장치).
4. `조건`·`적용제외`는 원문 문구를 옮긴 사람 서술이지 정규화된 값이 아니다(caveat).

### 2.4 왜 `요건유형`에 "적용제외"를 넣었나

지시는 "배출기준·금지행위·처리의무"였다. 그런데 이 주제의 조문은 **금지와 예외가 한 몸**이다 — 제22조제1항은 "배출하여서는 아니 된다. **다만** 다음 각 호의 경우에는 그러하지 아니하다", 제48조는 대기 규제 전체(제41조·제42조~제47조의2)를 통째로 적용제외한다. 예외를 항목으로 만들지 않으면 ①그 조문의 인용문이 어디에도 안 남거나 ②금지 항목의 `적용제외` 문자열에 사람이 요약해 넣어야 하는데, 후자는 **앵커 검증을 못 받는 자유 서술**이라 환각 위험이 생긴다. 그래서 예외도 **근거조문을 가진 항목**으로 만들어 같은 검증을 받게 했다. 지시의 3종은 전부 그대로 담기고, 4번째는 그 3종을 정확히 읽기 위한 보조다.

## 3. 계층 도출 — 상향식, 임의분류 금지

### 3.1 방법

1. **정의 조항 먼저**: 해양환경관리법 제2조(정의)를 읽어 이 법이 **스스로 이름 붙여 구분한 물질 용어**만 모은다.
2. 그 용어들 사이의 **포함·배타 관계를 조문으로 확인**한다.
3. 근거가 확인된 것만 노드로 만든다. "이쯤에서 나누면 좋겠다"고 지어내지 않는다.

### 3.2 실측 — 정의 조항이 이미 계층을 그어 두었다

해양환경관리법 제2조가 직접 정의한 물질 용어(호 번호는 원문 그대로):

| 호 | 용어 | 이 트리에서의 자리 |
|---|---|---|
| 4 | **폐기물** | `waste` |
| 5 | **기름** | `oil` |
| 6 | **선박평형수** (「선박평형수 관리법」 제2조제2호 인용) | `ballast_water` |
| 7 | **유해액체물질** | `nls` |
| 8 | **포장유해물질** | `packaged_hazmat` |
| 9 | **유해방오도료** | `antifouling` |
| 10 | 잔류성오염물질 | ❌ 트리 밖(§5.4) — 배출규제 조문이 없다(제39조는 **조사**뿐) |
| 11 | **오염물질** = "폐기물ㆍ기름ㆍ유해액체물질 및 포장유해물질" | `marine_pollutant`(4·5·7·8호의 **상위 개념, 법이 직접 정의**) |
| 12 | 오존층파괴물질 | `ods` |
| 13 | **대기오염물질** = "오존층파괴물질, 휘발성유기화합물과 「대기환경보전법」 제2조제1호의 대기오염물질 및 같은 조 제3호의 온실가스 중 이산화탄소" | `air_pollutant`(12·15호 등의 **상위 개념, 법이 직접 정의**) |
| 15 | 휘발성유기화합물 | `voc` |

**핵심**: 1단계 분기를 우리가 만든 게 아니다. **제2조제11호와 제13호가 각각 "오염물질"과 "대기오염물질"이라는 상위 개념을 스스로 정의하며 하위 물질을 열거**해 두었다. 이 트리의 1·2단계는 그 열거를 그대로 옮긴 것이다.

법의 편(篇) 구조도 같은 선을 긋는다 — **제3장 "해양오염방지를 위한 규제"**(제22조~제40조, 오염물질) vs **제4장 "해양에서의 대기오염방지를 위한 규제"**(제41조~제48조, 대기오염물질). 선박평형수는 아예 **별도 법**(선박평형수 관리법)이 규율하고 해양환경관리법 제2조제6호가 그 법을 인용만 한다.

### 3.3 스펙의 "5분류"와 실제 raw의 차이 — 상향식이 만든 수정

후보목록이 예상한 5분류(폐기물/기름/유해액체물질/대기오염물질/선박평형수)는 **대체로 맞았지만 완전하지 않았다.** raw에서 실제로 확인된 차이:

| 차이 | 내용 | 근거 |
|---|---|---|
| **+ 포장유해물질** | "오염물질"의 4번째 구성요소인데 5분류에 없었다. 배출 허용례가 **아예 없는**(제22조제1항 각 호에 포장유해물질이 없다) 유일한 오염물질이라 규제 성격도 다르다 | 제2조제8호·제11호·제29조 |
| **+ 유해방오도료** | 배출이 아니라 **사용 금지**형 규제라 5분류에 안 잡혔다 | 제2조제9호·제40조 |
| **대기오염물질이 하위 4종으로 갈린다** | 하나의 분류가 아니라 오존층파괴물질·질소산화물·황산화물·휘발성유기화합물(+이산화탄소)로 조문이 갈린다 | 제42조·제43조·제44조·제47조·제41조의2~6 |
| **폐기물이 둘로 갈린다** | 분뇨와 그 밖의 폐기물이 **다른 별표의 다른 기준**을 받는다 | 「선박에서의 오염방지에 관한 규칙」 제8조제1호·제2호(별표 2 vs 별표 3) |
| − 잔류성오염물질 | 정의는 있으나 **배출규제 조문이 없다** — 넣으면 빈 리프가 된다 | 제39조(조사·측정만) |

**후보목록의 "계층은 얕고 넓다"는 관찰은 맞았다** — 실제 트리도 깊이 3(최장 root→marine_pollutant→waste→sewage)에 노드 19·리프 12로, 서류 트리(깊이 3·노드 13·리프 8)와 같은 모양이다.

### 3.4 트리로 쪼개지 **않은** 축 — 왜 `조건`·`추가확인`으로 남겼나

배출 가부를 실제로 가르는 축은 물질 종류 말고도 최소 4개가 더 있다.

- **해역**(영해기선 3해리/12해리/50해리, 배출규제해역, 극지해역, 무역항 수상구역)
- **선박 종류·규모**(총톤수 400톤, 최대승선인원 16명, 유조선, 국제항해 여부)
- **설비 보유 여부**(분뇨마쇄소독장치·기름오염방지설비·배기가스정화장치를 작동 중인가)
- **항해 상태**(항해 중인가 정박 중인가, 4노트 이상인가)

이 축들은 물질 종류와 **직교**한다. 트리 레벨로 올리면 같은 조문이 리프마다 복제돼 유지보수가 무너진다(선례 §3.3과 정확히 같은 판단). 그래서:

- **트리 레벨** = 오염물질의 종류. **깊이 2~3.**
- **잔여 축** = 규제 항목의 `조건` 문자열 + 리프의 **`추가확인`** 배열(되묻기가 이어서 물을 수 있게 질문 문구까지 넣음).

특히 **선박 종류 축은 이 트리가 일부러 비워 둔 자리**다 — 그 축은 이미 `vessel_doc_tree.json`이 담고 있고, 두 트리를 나중에 교차시키는 것이 맞다(§9.4).

### 3.5 중첩(overlap)의 정직한 표시

- **선박평형수는 두 곳에 걸린다.** 그 자체로는 선박평형수 관리법의 규율 대상이지만, *화물유가 섞인* 선박평형수(제22조제1항제2호나목·다목)는 **기름** 규제로, *유해액체물질 화물창에서 세정된* 선박평형수(같은 항 제3호나목)는 **유해액체물질** 규제로 간다. 세 자리 모두에 항목을 두고 `주의`로 서로를 가리킨다.
- **폐기물은 법이 여럿이다.** 선박에서 나온 폐기물(해양환경관리법) / 육상 폐기물의 해양투기(해양폐기물 및 해양오염퇴적물 관리법 제7조) / 육상 투기(폐기물관리법 제8조) / 무역항 수상구역 투기(선박의 입항 및 출항 등에 관한 법률 제38조) / 공공수역 투기(물환경보전법 제15조)가 각각 다른 법이다. 전부 `waste` 리프에 담되 `조건`으로 적용 국면을 구분한다.
- **`유해액체물질·포장유해물질` 중간 노드는 우리가 만든 묶음이다.** `marine_pollutant`의 자식이 4개(폐기물·기름·유해액체물질·포장유해물질)라 §4의 "선택지 3개 이하" 규칙을 넘어서, 제2조제7호("액체물질")·제8호("포장된 형태로 …운송되는 유해물질")가 그은 선을 그대로 써서 둘을 한 번 더 묶었다. **법에 "유해물질"이라는 상위 노드가 따로 정의돼 있는 것은 아니다** — 이 사실을 `caveats`와 노드의 `주의`에 명시한다.

## 4. 비-리프 노드의 `질문`·`선택지`

선례 §4의 규칙을 그대로 따른다.

1. **모든 비-리프는 `질문`·`선택지`를 반드시 갖는다**(빌드 시 강제).
2. `선택지[].label`은 **raw에 실재하는 법률 용어**를 쓴다(임의 조어 금지).
3. `선택지[].next`는 반드시 그 노드의 **자식 id**(참조 무결성 검사).
4. `선택지[].hint`는 그 용어의 법정의를 한 문장으로 푼 것. hint도 정의 조항을 벗어나지 않는다.
5. `질문`은 존댓말 한 문장, 기존 `decideClarify` 반환 스키마(`intro`/`question`/`options`)와 호환되는 톤.
6. **선택지 수 = 자식 수, 3개 이하**(`CLARIFY_OPTION_MAX = 3`). 이 규칙 때문에 실제로 두 번 재구성했다 — ①`marine_pollutant` 아래 4갈래(폐기물/기름/유해액체물질/포장유해물질)를 3갈래로(§3.5) ②`air_pollutant` 아래 5갈래(오존층파괴물질/질소산화물/황산화물/이산화탄소/휘발성유기화합물)를 3갈래로. ②의 묶음은 **제2조제13호의 열거 순서 그대로**다: 오존층파괴물질 / 「대기환경보전법」상 대기오염물질·온실가스(=질소산화물·황산화물·이산화탄소) / 휘발성유기화합물.

## 5. 추출 방법론

### 5.1 조문 분리 — 계열별 이중 형식 (L-54)

raw는 계열마다 조문 마커가 다르다. 하나의 정규식으로 짜면 고시계열에서 **조용히 0건**이 된다.

| 계열 | 파일 | 마커 |
|---|---|---|
| 법률·시행령·시행규칙·부령(규칙) | `법률.txt`·`시행령.txt`·`시행규칙.txt` | `[제10조] 제목 (시행 …)` — **대괄호** |
| 고시·훈령 등 행정규칙 | `행정규칙/*.txt` | `제7조(제목) ①…` — **무대괄호** |
| 별표 | `별표/별표N.txt` | 조문 마커 없음 — **파일 전체가 하나의 단위** |

셋을 각각 다르게 읽는다. 별표는 조로 쪼개지 않고 **파일 전체를 대상으로 앵커를 찾는다.**

### 5.2 74법 전수 스캔 — 커버리지 산출

설계상 "정확도"가 아니라 **"어디까지 봤는지"**를 수치로 남기는 것이 목적이다(선례 §6-1과 같은 태도). 조건:

- **물질어**: 폐기물·분뇨·기름·유류·선저폐수·유해액체물질·포장유해물질·대기오염물질·오존층파괴물질·질소산화물·황산화물·황함유량·휘발성유기화합물·선박평형수·방오도료·방오시스템
- **규제어**: `배출하여서는 아니` / `배출해서는 아니` / `배출기준` / `배출허용기준` / `처리기준` / `버려서는 아니` / `투기하여서는` / `배출할 수 없` / `사용하여서는 아니` / `배출규제` / `누출·유출` 등
- 둘이 **같은 문장 안**에 있어야 후보로 센다. 문장은 항 기호(`①`)와 `한다./된다./아니한다.`로 쪼갠다.
- 집계 단위는 **조문**이다(`summary.scan_candidate_articles` = 조건을 통과한 문장이 하나라도 있는 조문의 수). 문장 수가 아니다.

매 빌드마다 실제로 다시 돌려 `summary.scan_*`·`scan.laws_with_candidates`에 싣는다. 후보가 나왔는데 트리에 반영하지 않은 법은 `unmapped.법_단위`에 사유를 남긴다(이번엔 항만법·해양생태계법 2건 — 둘 다 고시에 전사된 표·정산 문구였다).

### 5.3 ★계열 범위 — 74법만 보면 배출기준이 통째로 빈다(실측으로 확인)

지시는 "74법 전수 스캔"이었고 그대로 했다. 다만 스캔 도중 구조적 문제를 확인했다:

**해양환경관리법 제22조제1항 각 호는 배출기준을 전부 "해양수산부령"에 위임**하는데, 그 해양수산부령은 `시행규칙.txt`가 **아니라** 별도의 부령 **「선박에서의 오염방지에 관한 규칙」**이다. 실제로 해양환경관리법 시행규칙 제11조제1항(선박 배출기준 자리)은 **`삭제 <2020.12.4>`** 이고, 남은 제11조제2항~제4항은 *해양시설*의 기준만 정한다.

그 규칙은 raw에 **이미 수집돼 있다** — `raw/15_관련타부처/선박에서의오염방지에관한규칙/`, `_meta.json`에 `"tier": 1`, `"분류": "기준법급(해양환경관리법 하위 기술기준, 2026-07-19 재분류 — H-15 #4)"`. 즉 **74법 목록(`audit12_groups*.json`)에는 없지만 우리 raw가 기준법급으로 관리하는 문서**다.

→ **결정: 이 규칙 한 건과 그 별표를 스캔·채택 범위에 포함한다.** 근거는 세 가지다. ①제외하면 `oil`·`sewage`·`garbage`·`nls` 리프의 **배출기준이 전부 비어 "raw에 없다"가 아니라 "우리가 안 봤다"가 된다** ②우리 raw 자신이 이 문서를 tier 1 기준법급으로 분류해 두었다 ③선례가 같은 상황(유·도선 장비 수량이 고시가 아니라 시행령에 있었던 건, 선례 §11.4)에서 내린 결정과 같다. *이 판단은 지시 문언("74법")을 넓힌 것이므로 최종 보고에서 확인 대상으로 올린다.* 커버리지 수치는 74법과 이 규칙을 **분리해** 보고한다.

### 5.4 무엇을 트리에서 뺐나(scope-out) — 정직 기록

`unmapped`에 사유와 함께 남긴다.

| 유형 | 예 |

| 정의는 있으나 **배출규제 조문이 없음** | 잔류성오염물질(제2조제10호) — 제39조는 조사·측정만 |

## 6. 완결성·정확성 판정 — 무엇을 "다 뽑았다"로 보는가

**성공 기준(검증 가능, 카파시 4)**

1. **커버리지 수치 공개**: 74법 전부를 스캔했음을 파일 수·조문 수로 밝히고 "후보 발견 N법 / 무관 확인 M법"을 보고한다.
2. **전량 재대조(표본 아님)**: 트리에 들어간 **모든** 규제항목·노드 provenance에 대해 빌더가 raw를 열어 ①그 조문이 실재하는지 ②그 조문 본문에 앵커가 실제로 있는지 확인한다. 하나라도 실패하면 **빌드 실패**.
3. **질문·선택지 무결성**: 모든 비-리프에 `질문`·`선택지`가 있고, `next`가 실재하는 자식 id이며, 선택지 수 = 자식 수 ≤ 3. 리프에는 `질문`·`선택지`가 없고 `추가확인`만. 위반 시 빌드 실패.
4. **독립 재대조**: 빌더의 조문분리 로직을 **재사용하지 않는 별도 검사**로, 파일을 통짜 문자열로 읽어 인용문이 부분문자열로 실재하는지 + 그 인용이 정말 그 조문 범위 안인지 다시 확인한다. 빌더에 `--verify` 로 내장하되 **경로가 완전히 분리**돼 있다.
5. **재현성**: `python3 local_server/knowledge/legal/_dashboard/loop/build_pollutant_tree.py` 한 번으로 재현된다.

**확산도 43법 vs 실제 8법 — 차이의 뜻**: `H32_hierarchy_candidates.md`의 "43법"은 *물질 이름이 한 번이라도 나오는 법*의 수였다(그 문서 §0이 스스로 "확산도는 결과 예측치가 아니다"라고 경고했다). 이번 스캔은 **물질어와 규제어가 같은 문장에** 있어야 후보로 세므로 8법으로 줄었다. **"언급"과 "규제"는 다르다** — 43법 대부분은 벌칙·정의 인용·행정계획에서 물질명을 언급할 뿐이다.

**빌드 게이트 음성 테스트(실제로 실행해 확인)** — 6가지를 일부러 깨뜨려 전부 빌드 중단(exit 1)을 재현했다:
①가짜 앵커 → `원문에 앵커 없음` ②없는 조문(제999조) → `조문 없음` ③깨진 `next` → `선택지 next가 자식이 아님` ④선택지 4개 → `선택지 수 ≠ 자식 수` + `CLARIFY_OPTION_MAX 위반` ⑤`also` 문구 변조 → `also 문구 없음` ⑥리프에 `질문` 부착 → `리프에 질문/선택지가 붙음`.
**독립 재대조도 따로 음성 테스트**했다 — 산출 JSON의 인용문을 실재하지 않는 문장으로 바꾸고, 근거조문을 다른 조로 바꾸고, 파일 경로를 없는 경로로 바꿨더니 각각 `인용문이 파일에 없음` / `인용문이 제37조 범위 밖에서 나옴` / `파일 없음`으로 3건을 잡아냈다.

**빌드 과정에서 실제로 걸러낸 오류(정직 기록)** — "빌드가 통과했다"와 "내용이 맞다"는 다른 문제라는 선례 §6의 교훈대로, 통과한 인용문 107건을 사람이 한 줄씩 읽어 대조했다.

1. **인용문이 옆 호(號)까지 끌고 왔다.** 첫 빌드에서 제22조제2항 항목의 인용이 *"…세정된 선박평형수를 배출하는 경우에는 …정화방법에 따라 배출할 것 ②누구든지 해양시설 또는…"* 로 나왔다 — **앞의 제1항제3호나목이 통째로 딸려 온 것**이다. 원인은 두 가지가 겹쳤다: ⓐ이 raw는 항 기호 뒤에 공백이 없어(`①누구든지`) 공백을 전제한 문장-시작 탐지가 헛돌았고(L-54와 같은 계열의 형식 차이) ⓑ인용 끝을 `"다. "` 하나로만 잘라 다음 호까지 넘어갔다. → `quote_of()`를 **조문의 구조 표지(항 `①`·호 `1.`·목 `가.`)로 앞뒤를 모두 막는** 방식으로 다시 만들었다. 목 기호는 `"…한다. "`와 헷갈리므로 **앞에 공백이 있는 한 글자 + 마침표**만 표지로 본다.
2. **조문 시작 오프셋 버그.** 문장 끝 탐색이 실패(-1)했을 때 `j + 3`을 그대로 시작점으로 써서 인용이 `"12조의2] 극지해역에서…"`, `"안의 일상생활에서…"` 처럼 **두 글자 잘린 채** 시작했다. 3건에서 재현 → 표지가 없으면 조문 첫머리(0)부터 인용하도록 고쳤다.
3. **장(章) 제목이 인용문에 딸려 붙었다.** 제40조제2항 인용 끝에 `"제4장 해양에서의 대기오염방지를 위한 규제"`가 붙어 있었다 — raw에서 장 제목이 조문 본문과 같은 블록에 들어 있기 때문. `split_articles()`가 편·장·절 제목 줄을 건너뛰도록 고쳤다.
4. **물환경보전법 제15조제1항제1호는 앵커를 고를 수 없었다.** 원하는 문구(`…"유류"라 한다)`)가 **괄호 안에 마침표를 품고 있어**(`석유가스는 제외한다. 이하 "유류"라 한다`) 인용 경계가 그 안에서 끊겼고, 빌더가 `인용문에 앵커가 안 담김`으로 **실제로 빌드를 실패시켰다**. 앵커를 호 끝의 `"누출ㆍ유출하거나 버리는 행위"`로 바꾸고 `also`로 유류 문구를 따로 검증하게 했다. — **게이트가 설계대로 작동한 사례**다.
5. **`별표5.txt`의 내용이 실제로는 별표 5의2(배출률 승인 표시)였다.** 유해액체물질 배출요건인 진짜 별표 5는 raw에 없다. 그 파일에서 배출요건을 인용하려던 것을 발견해 `수치출처: "별표(raw 미수집)"`로 남기고 caveat에 올렸다(§7-3).
6. **해양환경관리법 시행규칙 제11조제1항은 `삭제 <2020.12.4>`였다.** 선박 폐기물 배출기준을 거기서 뽑으려다 발견 → §5.3의 계열 범위 결정으로 이어졌다.

**"완결성"에 대한 정직한 한계**: 이 트리는 *"raw 원문에 배출 금지·기준·처리 의무가 문장으로 적혀 있는 것"* 을 목표로 한다. 값이 **별표 안에만 있고 그 별표가 raw에 없는 경우**(§7-3)는 원리적으로 못 담는다.

## 7. caveats (JSON에 그대로 싣는 한계 목록)

1. 1·2단계 분기는 해양환경관리법 제2조제11호·제13호가 **법 스스로 정의한 상위 개념**이라 근거가 확실하다. 반면 `유해액체물질·포장유해물질` 중간 노드는 **선택지 3개 규칙을 지키려고 우리가 묶은 것**이며, 법에 그런 상위 용어가 정의돼 있는 것은 아니다(§3.5).
2. 해역·톤수·설비 보유·항해 상태는 트리 레벨이 아니라 규제 항목의 `조건`과 리프의 `추가확인`으로만 표현된다. `조건`은 원문 문구를 옮긴 것이지 프로그램이 판정할 수 있게 정규화한 값이 아니다.
3. **유해액체물질의 배출요건 별표(「선박에서의 오염방지에 관한 규칙」 제11조가 가리키는 별표 5)는 raw에 없다** — `별표/별표5.txt`에 들어 있는 것은 별표 5의2(배출률 승인 표시)다. 그래서 유해액체물질 리프의 배출기준은 **조문 수준까지만** 담기고 구체 수치는 비어 있다. 없는 값을 다른 별표에서 끌어와 채우지 않았다.
4. 「선박에서의 오염방지에 관한 규칙」은 74법 목록 밖 문서다(§5.3). 이 트리에서 나온 규제 항목의 상당수가 이 문서 소관이므로, 74법만 갱신 감시하는 파이프라인은 이 트리를 온전히 지키지 못한다(§8.3).
5. 배출규제해역·극지해역·휘발성유기화합물규제항만의 **구체 범위는 고시로 정해진다.** 해당 고시가 raw에 있는 것(휘발성유기화합물규제항만 지정 등에 관한 기준)도 있고, 조문이 "해양수산부장관이 정하여 고시하는"이라고만 하는 것도 있다 — 후자는 `위임`으로 링크만 남겼다.
6. 벌칙(징역·벌금·과태료)은 **일부러 담지 않았다**(§0). "이거 하면 얼마 물어요?"는 별도 주제(후보목록 A절)다.
7. 기록부·증서 등 서류 의무는 `vessel_doc_tree.json` 소관이라 담지 않았다. 다만 기관일지 기재처럼 **배출행위와 한 몸인 기록의무**는 `처리의무`로 담았다(제22조의2제2항·제43조제4항·제44조제3항).
8. 자치법규(`raw/_자치법규/`)와 국제협약 텍스트(MARPOL 등)는 이번 스캔 대상이 아니다.
9. 물환경보전법·폐기물관리법은 **환경부 소관 육상·공공수역 규제**라, 해양 배출 규제와 적용 국면이 다르다. 같은 리프에 담되 `조건`으로 구분했으니 그대로 합쳐 읽으면 안 된다.

## 8. 유지보수 통합 설계 (H-29 연동 — **설계만**)

### 8.1 조인 키

선례 §8.2와 같다. H-29(`loop/detect_law_changes.py`)가 주 1회 만들어 두는 `law_change_queue.json`의 각 항목은 `{law.slug, layer, changed_articles[].조문번호}`를 갖고, 이 트리의 모든 규제항목·provenance는 `{근거법령_slug, 계층, 근거조문}`을 갖는다 → **조인 키 `(slug, layer, 조문번호)`**. `changed_articles[]`가 빈 변동(법령명·소관부처 변경)은 법 단위(slug)로 조인.

### 8.2 이 트리에만 있는 두 가지 추가 문제

- **(a) 74법 밖 문서가 섞여 있다.** 「선박에서의 오염방지에 관한 규칙」은 H-29의 감시 목록에 없다. 이 트리를 유지하려면 **H-29 대상에 이 규칙을 한 건 추가**하거나(권고), 최소한 이 트리 전용으로 그 문서의 `_meta.json` 시행일 변화를 확인해야 한다.
- **(b) 별표를 근거로 쓰는 항목이 있다.** 조문이 안 바뀌어도 **별표만 개정되면** 인용문이 낡는다. `law_change_queue.json`은 조문 단위라 별표 개정을 못 잡는다. 지금 할 수 있는 것은 `계층: "별표"` 항목을 **별도로 표시해 두는 것**뿐이고(이번 빌드가 그렇게 한다), 실제 감시는 다음 라운드 과제다.

### 8.3 제안 파이프라인 (다음 라운드)

```
detect_law_changes.py (H-29, 이미 있음)  →  law_change_queue.json
        ↓
[신규] loop/flag_trees.py            ← 트리 파일명만 인자로 받는 공용 스크립트
        ├ 큐의 각 item에서 (slug, layer, 조문번호) 추출
        ├ <tree>.json 을 순회하며 같은 키를 가진 노드·항목 탐색
        └ 매치되면 사이드카 <tree>_review.json 에 review 플래그
```

**설계 결정(선례 §8.3과 동일한 이유로 같은 선택)**: ⓐ 트리를 직접 고치지 않고 사이드카에 쓴다(트리는 빌더의 결정론적 산출물이라 손으로 고치면 다음 빌드에서 날아간다) ⓑ **자동 재빌드하지 않는다**(개정으로 앵커 검증이 실패하는 것은 "사람이 봐야 한다"는 **정상 신호**이고, 자동 재빌드는 그 신호를 지운다) ⓒ 새 트리도 `{근거법령, 계층, 근거조문}` provenance 규약만 지키면 같은 스크립트를 재사용한다 — **provenance 규약이 곧 유지보수 인터페이스**다. 그래서 이 트리는 선례와 **필드명·구조를 일부러 동일하게** 맞췄다(`계층`·`근거조문`·`법령ID`·`파일`·`인용`·`조건`·`위임`·`주의`).

## 9. 되묻기(`decideClarify`) 연동 설계 (**설계만**, 이번엔 배선 안 함)

### 9.1 지금의 `decideClarify()`

`local_server/services/legal_retriever.js` — 검색 상위 6페이지 발췌를 LLM에 넣어 되묻기 JSON `{needed, intro, question, options:[{label,hint}]}`를 즉석 생성한다. 한계: 질문마다 LLM 1회 + 근거자료 9,000자를 태우고, 같은 질문에도 선택지가 달라질 수 있으며, top-6에 그 구분이 안 뜨면 못 묻는다.

### 9.2 트리 연동 — 제안 흐름

```
질문 "배에서 나온 폐유 바다에 버려도 되나요?"
  ↓ matchPollutantTopic(query)          ← 주제 매칭(물질어 키워드, LLM 0회)
  ↓ clarifyFromTree(node)               ← 트리에서 질문·선택지를 그대로 꺼냄
  ↓ 사용자 선택 → 질의에 ' — 기름' 이 붙어 재질의
  ↓ resolvePollutantPath(query, tree)   ← 라벨로 현재 위치 복원
  ↓ 리프 도달 → 경로상 `규제` 합집합으로 답변 조립(+ `추가확인` 남아 있으면 한 번 더)
  ↓ 매치 안 되면 기존 decideClarify() 폴백
```

### 9.3 반드시 지킬 것

- **(a) 반환 스키마를 기존과 동일하게 유지한다** — `{needed,intro,question,options[{label,hint}]}` 그대로면 `routes/legal.js`·`ai_chat.js`를 **한 줄도 안 고쳐도** 된다(카파시 3).
- **(b) 라운드 상한**: H-36 미결①이 이미 확정됐다 — *트리 기반 경로는 깊이가 데이터로 유한해 무한루프가 원리적으로 불가능하므로 인위적 라운드 캡을 두지 않는다*(AI 즉석판단형 경로만 `CLARIFY_MAX_ROUNDS=4` 유지). 이 트리의 최대 깊이는 3이라 그 확정 사항 안에 들어온다.
- **(c) 라벨 문자열이 계약이다.** `CLARIFY_JOINER(' — ')` 뒤 문자열을 노드 라벨과 대조하므로, 라벨을 바꾸면 진행 중인 대화가 깨진다. 라벨은 법률 용어 그대로 고정하고, 표시용 변형이 필요하면 별도 필드를 쓴다.
- **(d) canonical 게이트**: 이 트리는 raw 직인용이라 위키 `answerCanonicalOnly` 정책과 축이 다르다. H-36 미결②와 같은 쟁점이며 **이번 범위 밖**이다.

### 9.4 ★두 트리의 교차 — 이 주제에서 특히 중요하다

`vessel_doc_tree.json`(선박 종류)과 이 트리(오염물질 종류)는 **직교**하고, 실제 질문은 두 축을 동시에 갖는 경우가 많다("낚싯배에서 음식물쓰레기 버려도 되나요?" = 어선 × 폐기물). 지금 구조로도 **순차 되묻기**(먼저 물질을 좁히고, 리프의 `추가확인`에 선박 축을 넣어 이어 묻기)는 가능하다 — 실제로 관련 리프의 `추가확인`에 "선박 종류" 축을 넣어 두었다. 다만 두 트리를 **교차 색인**(선박종류 × 물질 → 항목)으로 만드는 것은 별개 작업이고, 그때는 `vessel_doc_tree.json`의 리프 id를 이 트리가 참조하는 형태가 자연스럽다. **이번엔 하지 않았다.**
