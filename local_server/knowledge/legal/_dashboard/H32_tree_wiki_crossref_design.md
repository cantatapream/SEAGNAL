**둘은 지금 서로를 모른다.** 트리가 "선박법 제10조"를 근거로 서류 항목을 만들어도, 그 조문을 이미 산문으로 해설해둔 `wiki/statutes/선박법.md`로 갈 길이 없다. 반대로 위키 페이지에서 "이 조문은 어떤 되묻기 트리의 어느 갈림길에 걸려 있나"를 알 길도 없다.

이 지도는 그 사이를 잇는 **조회용 조인 테이블**이다. 위키도 자산 JSON도 수정하지 않는다.

## 1. 조인 방법론 — 검증된 로직의 확장

### 1.1 위키 인용 추출: `lint_coverage.py`의 정규식을 그대로 재사용

`_dashboard/loop/lint_coverage.py`(H-33)에는 이미 위키에서 조문 인용을 뽑는 검증된 로직이 있다:

```python
CITATION_RE = re.compile(r'(시행령|시행규칙)?\s*제(\d+조(?:의\d+)?)')
def extract_wiki_citations(paths):   # 반환 {'법률': set, '시행령': set, '시행규칙': set}
```

이 함수는 **여러 파일을 합쳐 하나의 집합**으로 돌려주므로 "어느 파일이 인용했는지"가 사라진다. 그래서 빌더는 이 함수를 **다시 구현하지 않고 `import`해서 파일 하나씩 호출**한다:

```python
from lint_coverage import CITATION_RE, find_wiki_files   # 정규식·파일탐색 규칙 원본 재사용
```

즉 **가족(법률/시행령/시행규칙) 판정 규칙과 조문번호 정규식은 H-33과 바이트 단위로 동일**하고, 이번에 새로 더한 것은 "파일 단위로 쪼개 기록한다"는 루프 구조뿐이다. 새 파싱 알고리즘을 지어내지 않는 이유는 명확하다 — H-33 규칙과 결과가 어긋나면 어느 쪽이 맞는지 판정할 기준이 없어진다.

### 1.2 페이지 → 문서(법령) 귀속 규칙: `find_wiki_files(slug)`의 역함수

`lint_coverage.find_wiki_files(slug)`는 슬러그로부터 페이지를 찾는다:

```
wiki/statutes/<slug>.md
wiki/concepts/<slug>__*.md
```

역인덱스는 이 규칙을 그대로 뒤집는다.

| 파일명 형태 | 귀속 문서(doc) | 예 |
|---|---|---|
| `statutes/<슬러그>.md` | 그 법 | `statutes/선박법.md` → `선박법` |
| `concepts/<슬러그>__<개념>.md` (919개) | `__` 앞부분의 법 | `concepts/선박법__선박등록.md` → `선박법` |
| `concepts/<고시명>.md` (`__` 없음, 12개) | `고시:<고시명>` | `concepts/선박구명설비기준.md` → `고시:선박구명설비기준` |

**가족 없는 인용(`제N조`)은 그 페이지가 귀속된 문서의 법률로 본다** — H-33 `extract_wiki_citations`의 `key = fam if fam else '법률'`과 동일한 가정이다. 단 `고시:` 페이지에서는 가족 없는 인용을 그 고시 자신의 조문(`행정규칙`)으로 본다(고시 페이지의 "제3조"는 고시 제3조이지 상위법 제3조가 아니다 — `concepts/강선의구조기준.md` 실물 확인).

### 1.3 ★타문서 인용 처리 — 이 작업에서 새로 더한 판단 규칙 전부

위 1.2의 가정("가족 접두어 없는 `제N조`는 그 페이지의 법")에는 **실재하는 오탐**이 있다. `statutes/선박법.md`는 본문에서 「어선법」 제2조제1호를 인용하는데, 규칙대로면 이게 "선박법 법률 제2조"로 잡힌다. 실측: 전체 인용 매치 98,353건 중 이런 형태가 **1만 5천 건 이상**이었다(상위: 형법·행정절차법·질서위반행위규제법·행정심판법·행정소송법 — 전형적 준용조항).

**아래 4개 규칙은 처음부터 이렇게 설계한 것이 아니라, ①「」 가드만 넣고 빌드한 뒤 ②표본 20건을 사람이 정독해 오탐 6건을 실제로 발견하고 ③그 유형을 하나씩 막아 도달한 것이다**(L-75 "자동검증 2겹 통과 ≠ 내용 정확" 패턴 그대로 재현 — §6.2에 경위 기록).

#### (a) 인용 앞의 문서명 탐지 — 3가지 표기 모두

인용 매치 직전 45자에서 그 인용이 가리키는 문서 이름을 찾는다:

| 표기 | 예 | 처리 |
|---|---|---|
| `「…」` 로 묶인 이름 (닫는 괄호 뒤 꼬리 ≤6자) | `「어선법」 제2조제1호` | 그 문서 이름으로 |
| 괄호 없는 이름 (법·법률·규칙·기준·규정·지침·고시·협약·조약·령으로 끝나는 2~24자, 뒤 꼬리는 공백·표구분자 `|`·링크닫기 `]` 4자 이내) | `근로기준법 제107조`, `[[…\|해상교통안전법]] 제13조`, `\| 시행규칙 \| 제38조` | 그 문서 이름으로 |
| 지시어 + 일반명사 | `이 법 제3조`, `동 규칙 제5조` | **그 페이지 자신**(타문서 아님) |

#### (b) 이름 → 문서 해소, 그리고 두 갈래 결말

찾은 이름을 **실재 데이터로만 만든 별칭 사전**(위키 파일명 슬러그 + 자산이 실제로 쓴 (법령명→슬러그) + 자산의 고시명)으로 해소한다. 이름 끝의 `시행령`·`시행규칙`은 떼어내 계층으로 쓴다.

- **해소 성공 & 이 페이지의 법과 다름** → 그 인용을 **그 문서에 귀속**시켜 `wiki_pages_명시인용`에 넣는다. 예: `concepts/해양환경관리법__오염물질해양배출금지.md`가 「선박에서의 오염방지에 관한 규칙」 제9조를 인용 → 그 규칙의 제9조 매칭으로 잡힌다. **버리는 게 아니라 제자리를 찾아주는 것**이고, 이 채널 덕에 전용 위키 페이지가 없는 부령·고시도 매칭된다.
- **해소 실패**(형법·행정절차법 등 74법 코퍼스 밖) → `wiki_pages_타법의심`으로 분리한다. 버리지 않는 이유: 가드도 휴리스틱이라 반대 방향 오탐이 가능하고, 분리해두면 사람이 나중에 판정할 수 있지만 지우면 그 기회가 사라진다.

어떤 키에 대해 그 페이지의 인용이 **전부** 의심이면 그 페이지는 의심 목록으로만 가고 `wiki_pages`에는 안 들어간다.

#### (c) 연쇄 인용의 귀속 상속

`「행정절차법」 제21조(처분의 사전 통지)·제22조(의견청취)`처럼 한 문서명 뒤에 조문이 연달아 나오면, 뒤 조문에는 이름이 안 붙는다. 앞 인용과의 사이가 **괄호 주석을 지운 뒤 구분자(`·`,`및`,`,` 등)뿐이고 10자 이내**면 앞 인용의 귀속을 그대로 물려받는다.

#### (d) ★"가족 불확정"은 매칭하지 않고 버린다

`| 시행규칙 | 제38조 |`(표의 계층 칸)나 `시행령 제53조·제50조①`(연쇄)에서는 그 조문이 **이 페이지 법의 법률 조문이 아니라는 것**까지는 확실하지만, 어느 가족인지는 **독립 재대조(V1의 `시행령\s*제N조` 인접 검사)로 확인할 수 없다.**

이런 인용은 `시행령`/`시행규칙` 인덱스에 넣지 **않고 그냥 버린다**(2,511건). 넣었다면 V1이 확인할 수 없는 주장을 산출물에 싣는 셈이고, 실제로 처음엔 넣었다가 **빌드 게이트 V1이 12건을 잡아내 중단**시켰다. 커버리지를 조금 잃더라도 "확인할 수 없는 매칭은 만들지 않는다"를 택했다.

### 1.4 자산 provenance 파싱 — 스키마가 자산마다 다른 문제

13개 자산은 필드명이 조금씩 다르다(각 `H32_*_design.md` 확인). 공통 축만 뽑아 쓴다:

| 축 | 실제 필드명(자산에 따라) |
|---|---|
| 법령명 | `근거법령` \| `법령` \| `적용법령` |
| 슬러그 | `근거법령_slug` \| `법령_slug` |
| 계층 | `계층` (법률/시행령/시행규칙/행정규칙) |
| 조문 | `근거조문` \| `조문` \| `벌칙조문`(dict → `표시`\|`조`) \| `조` |

**루트 화이트리스트**(스캔·unmapped·보류를 조인에 섞지 않기 위해 명시적으로 지정):

| 파일 | 조인 대상 루트 | 조인에서 뺀 것 |
|---|---|---|
| `vessel_doc_tree.json` | `tree` | `scan`·`equipment_scan`·`insurance_scan`·`unmapped` |

### 1.5 결측치 보정 (지어내지 않고 데이터 안에서만)

- **슬러그 결측**: `penalty_tree`의 양벌규정 참조 760건 등은 `법령`만 있고 슬러그가 없다. → 13개 자산 전체에서 (법령명 → 슬러그) 쌍을 먼저 수집해 사전(67개)을 만들고, 그 사전으로만 보정한다. **실측 확인: 이 사전에 이름 하나가 서로 다른 슬러그로 매핑되는 충돌은 0건**이라 보정이 모호하지 않다. 사전에 없으면 보정하지 않고 `문서미상`으로 남긴다(74법 코퍼스 밖 법 — `해소: not_in_corpus`가 붙은 것들).
- **계층 결측**: 760건(전부 `penalty_tree`의 양벌규정)이 `계층`이 없다. → 가장 가까운 조상 노드의 `계층`을 상속하고 `계층_추정: true`를 붙인다. 상속할 조상도 없으면 `법률`로 두되 역시 추정 표시.
- **조문 정규화**: `제(\d+)조(의\d+)?`의 **첫 매치**를 조 단위 키로 쓴다(`제27조제2호` → `제27조`, `제5조의2(별표1의3)` → `제5조의2`). 위키 인용도 조 단위(`CITATION_RE`)라 축이 맞는다. 항·호까지 내려간 대조는 하지 않는다(H-33의 `hang_gap_candidates`가 다루는 별개 층위).
- **조문 없는 provenance**: `별표3`처럼 조문번호가 없는 13건은 조인 대상에서 빼고 `조문없음`으로 집계만 한다.

## 2. 스키마 — `tree_wiki_crossref.json`

H-35/H-36 자산과 같은 헤더 규약(`generated`/`scope`/`semantics`/`caveats`/`summary`/…)을 따른다.

```jsonc
{
  "generated": "2026-08-10T..+09:00",
  "scope": "13개 계층자산 provenance × wiki/statutes+concepts 1,005페이지 조문 단위 조인",
  "semantics": { "키": "...", "매칭의_의미": "...", "타법의심": "..." },
  "caveats": [ "..." ],
  "summary": {
    "tree_refs_total": N, "unique_keys": N,
    "matched_keys": N, "match_pct": 0.0,
    "per_asset":  { "서류": {"refs":N,"keys":N,"matched":N,"pct":0.0}, ... },   // 13개
    "per_layer":  { "법률": {...}, "시행령": {...}, "시행규칙": {...}, "행정규칙": {...} },
    "per_law":    { "선박법": {...}, ... },
    "wiki_only":  { "unique_keys": N, "per_law": {"선박법": N, ...} },
    "결측":       { "문서미상": N, "조문없음": N, "계층추정": N }
  },
  "crossref": {
    "선박법::법률::제10조": {
      "법령": "선박법", "계층": "법률", "조문": "제10조",
      "tree_refs": [
        { "asset": "서류", "file": "vessel_doc_tree.json",
          "node_id": "general_ship", "field": "tree.children[2].서류[0].근거조문",
          "라벨": "선박국적증서", "조문_원표기": "제10조" }
      ],
      "wiki_pages": ["statutes/선박법.md", "concepts/선박법__임시선박국적증서.md"],
      "wiki_pages_명시인용": [],
      "wiki_pages_타법의심": []
    }
  },
  "tree_only": [ "…키…" ],          // 트리는 걸었는데 위키 인용이 0인 조문
  "wiki_only": { "<법슬러그>": ["제3조", ...] }   // 위키는 인용하는데 어느 트리도 안 건 조문
}
```

**키 형식**: `<문서>::<계층>::<제N조>`
- 문서 = 법령 슬러그(법률/시행령/시행규칙) 또는 `고시:<고시명>`(행정규칙).
- 계층을 키에 넣는 이유: **같은 번호의 시행령 제10조와 법률 제10조는 다른 조문**이다. 지시의 예시 스키마(`"선박법::제10조"`)는 방향성만 준 것이라 여기서 계층을 한 칸 더 넣어 확정한다.

**`field`**: JSON 경로를 문자열로 그대로 적는다(예 `tree.children[2].서류[0]`). 사람이 원본 JSON에서 그 항목을 다시 찾아갈 수 있어야 검증이 가능하기 때문. `node_id`는 가장 가까운 조상의 `id`(없으면 `null`).

## 4. 위키 노출 설계 (설계만 — 이번에 위키 파일은 건드리지 않는다)

연결지도가 있으면 위키 페이지에서 "이 조문이 어느 되묻기 트리의 어느 갈림길에 걸려 있는지"를 보여줄 수 있다. 다만 **지금 위키를 고치자는 제안이 아니다** — 실제 반영은 사용자 결정 사항이고, 아래는 선택지와 각각의 대가를 적은 것이다.

### 안 A — 위키 본문에 `## 관련 계층자산` 절을 넣는다 (권장하지 않음)

```md
## 관련 계층자산
| 조문 | 자산 | 어디에 걸려 있나 |
|---|---|---|
| 제10조 | 서류 | 일반선박 → 선박국적증서(필수) |
| 제13조 | 서류 | 일반선박 → 국제톤수증서(조건부: 길이 24m 이상 국제항해) |
```

- 장점: 사람이 위키만 읽어도 보인다.
- **단점(치명적)**: 1,005페이지 중 매칭된 페이지 전부를 고쳐야 하고, 자산이 갱신될 때마다 **위키 본문과 자산이 어긋난다**. 위키는 `status: canonical` 심사를 통과한 사람 검수 산출물인데, 여기에 기계 생성 표를 섞으면 그 심사의 의미가 흐려진다. H-29 유지보수 설계가 "자동 재빌드는 하지 않는다(사람이 봐야 한다는 신호를 지우기 때문)"고 정한 것과 같은 이유로 **반대**.

### 안 B — 렌더 시점 주입 (권장)

위키 파일은 그대로 두고, 페이지를 **읽어 보여주는 쪽**(챗봇 답변 조립·위키 뷰어)이 `tree_wiki_crossref.json`을 조회해 "관련 계층자산" 블록을 붙인다.

- 파일 무수정 → 자산이 갱신되면 다음 조회부터 자동으로 최신.
- 조회 키가 `<문서>::<계층>::<제N조>`라 페이지 하나당 그 페이지가 인용하는 조문 키들로 O(1) 조회 가능.
- 역방향(자산 → 위키)도 같은 파일 하나로 된다: 트리 리프를 답할 때 `wiki_pages`를 "더 읽을거리"로 제시.

### 안 C — 사이드카 md (안 B의 보조)

`_dashboard/`에 법별 `crossref/<슬러그>.md`를 생성해 사람이 훑어볼 수 있게 한다. 위키 본문은 안 건드리되 사람 가독성은 확보. 안 B와 병행 가능.

### ★노출 시 반드시 함께 지킬 규약 (H-36 "배선 전 필수 규약" 승계)

연결지도를 통해 자산 항목을 위키 옆에 노출할 때는, 그 항목이 속한 자산의 규약이 **그대로 따라붙어야** 한다:
1. `penalty_tree` 항목 → "**법정형**이지 선고형이 아님"으로 표현.
2. `port_entry_flow`의 폐지 구법 인용 항목 → `주의` 필드 동반 노출.
3. `qualification_tree`의 별표 항목 → `표_원문` 전체 동반 제시.
4. `wiki_pages_타법의심`에만 걸린 매칭은 **사람 확인 전까지 사용자에게 노출하지 않는다**(오탐 가능성이 설계상 남아 있는 자리). `wiki_pages_명시인용`은 본문에 문서명이 적혀 있어 근거가 뚜렷하므로 노출해도 되지만, 어느 채널이든 §6.3의 **잔여 오탐 유형 A·B**(문맥형·별표관련조문형, 페이지 단위 약 5%)가 남아 있으므로 "이 조문을 다루는 페이지"가 아니라 **"이 조문을 인용하는 페이지"** 라는 문구로 제시할 것.

## 5. 한계 (caveats — 산출물 JSON에도 그대로 싣는다)

1. **조 단위 조인이다.** 항(①②)·호까지는 대조하지 않는다. 트리가 "제27조제2호"를 근거로 삼고 위키가 "제27조제5호"만 해설했어도 이 지도는 "매칭"으로 센다. 항 단위 정밀도는 H-33 `hang_gap_candidates`의 소관이다.
2. **매칭 = "그 위키 페이지가 그 조문을 인용한다"이지 "그 조문을 제대로 해설한다"가 아니다.** 표의 `근거` 열에 조문번호만 적힌 경우도 매칭으로 잡힌다.
3. **타문서 인용이 대규모로 실재**한다(§1.3). 명시인용(4,683건)은 제자리를 찾아줬고 의심(11,285건)은 분리했으나, 두 판정 모두 휴리스틱이다. **§6.2에 기록한 잔여 오탐 2유형은 원리상 이 방식으로 못 잡는다.**
4. **`행정규칙` 계층은 구조적으로 매칭률이 낮다(37.0%).** 자산이 인용한 고시 21종 중 전용 위키 페이지가 있는 건 4종(선박구명설비기준·어선설비기준·선박소방설비기준·선박설비기준)뿐이다. 낮은 수치는 데이터 결함이 아니라 **위키가 고시를 아직 그만큼 안 다뤘다는 사실**이며, 그대로 "다음에 채울 곳" 목록이 된다.
5. **74법 코퍼스 밖 법**(형법·행정절차법 등, `penalty_tree` 참조해소의 `not_in_corpus`)은 애초에 위키가 없어 매칭 불가다. 통계에서 `문서미상`으로 분리한다.
6. `wiki/comparisons/`·`wiki/activities/`·`wiki/annexes/`는 이번 대상이 아니다(지시 범위: statutes·concepts).
