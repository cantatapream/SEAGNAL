## 1. 왜 이 작업을 시작했나 (배경)

사용자가 나리야 법률 챗봇의 §4-U(미등재 구어 확인 — 예: "깔때기"가 조리도구인지 어구인지)를
구현하는 데 **Gemini의 구글검색 그라운딩(검색+답변 한번에, 검색 건당 별도 유료)** 대신
**네이버 검색 API(무료 쿼터가 넉넉함)** 를 쓸 수 있는지 문의하면서 시작됨. 조사 결과 이 좁은
용도(단어 뜻 확인)엔 네이버 쪽이 비용상 유리하고, 한국어 구어·사투리 데이터도 더 풍부할
가능성이 커 채택하기로 함.

## 2. 검토했으나 기각한 방향 (참고, 재검토 불필요)

- **`anthropics/claude-for-legal` 플러그인 마켓플레이스**: Apache 2.0, Claude Code/Cowork
  플러그인+MCP 커넥터 구성이나, 내용이 미국 상거래·프라이버시·회사법 등 실무라 **우리(한국
  해양수산 행정법) 도메인과 완전히 다름 → 적용 대상 아님**으로 결론.
- **나리야 챗봇 자체의 MCP화**: "우리 앱에서만 쓴다"면 MCP(외부에 도구로 노출하는 규격)를 만들
  이유가 없음 — 채택 안 함. (초기에 "감사 작업 토큰 절감" 논거를 들었으나, 실측해보니 감사 비용의
  대부분은 300문항 생성·채점(AI 추론)이지 파일 찾기(grep, 사실상 공짜)가 아니라서 그 논거 자체가
  틀렸음을 사용자 지적으로 정정함. **결론 "안 함"은 유효, 근거만 이걸로 갱신**.)

### 3-1. ★2026-08-16 후속 세션에서 전부 실측 확인 완료 (GitHub Actions 경유 실호출)

## 4. §4-U(모르는 구어 해소) 최종 설계 — 전체 확정본

### 4-1. 기존 설계 원칙 (`_CHATBOT.md` §4-U, 이미 있던 것)

```
1. 먼저 우리 DB(위키·glossary) 재확인
2. 없으면 웹 검색으로 뜻 확인
3. 사용자에게 되물어 확인
4. 맞으면 재검색→답변 + _candidates 학습후보 적재
```
**불변식(유지)**: DB우선 → 웹은 뜻확인용만 → **웹 내용을 법적 근거로 인용하지 않음**(법 조문·
처벌은 항상 위키 원문 기준). 이 원칙 때문에 환각0 불변식과 충돌하지 않음.

### 4-2. 오타 변환 — 파이프라인 맨 앞단

사용자 입력 직후, 어떤 검색(내부 DB든 §4-U 웹검색이든)이든 타기 전에 적용. 이유: 우리 DB
검색도 결국 키워드 매칭이라 오타가 있으면 이미 아는 단어도 못 찾을 수 있음.

### 4-3. 검색 소스 3종 (동시 검색)

**백과사전 + 지식iN + 카페글**을 함께 검색(넉넉히 20개, 1회 API 호출 — 여러 개 받아도 쿼터는
호출 1회로 동일).

### 4-4. 3단 필터링 전략

```
1단계(검색 전, 비용0): 질의어에 도메인 키워드 미리 삽입
   예) "깔때기" → "깔때기 어구"
2단계(응답 후, 비용0): 스니펫에서 <수산>·"통발"·"그물"·"어업" 등 도메인 신호를
   문자열매칭으로 찾아 그 항목을 최상위로 재정렬
3단계(그래도 애매하면, 소량비용): 걸러진 후보를 Gemini에 넘기되
   "당신은 해양수산 법률 챗봇입니다" 정체성 문맥을 먼저 주고 최종 선택시킴
```

### 4-5. 페이지네이션/확장 전략

"몇 개까지 볼지"는 API 제약이 아니라 우리가 정하는 값(`display` 파라미터). 20개 안에서 못
찾으면 `start` 파라미터로 다음 페이지(2회째 호출)까지 확장. **합리적 상한(예시로 든 상위
40~50개, 확정치 아님·실측 필요)까지 봐도 없으면 절대 억지로 고르지 않고 4-6으로.**

### 4-6. 실패 시 재질문 흐름 (무한반복 방지)

```
① 검색 성공 → 후보 확정 → 사용자에게 되물어 확인
② 검색 실패 → "조금 더 자세히 설명해달라" 재질문 (딱 1회만)
③ 재질문 후에도 실패 → 정직하게 "확인 못 함" + 막다른 길 아니게 다음 행동 안내
   (예: "다른 이름으로 다시 말씀해 주시거나, 어떤 상황·장비에서 쓰는 말인지 설명해 주시면
        다시 찾아보겠습니다")
④ ①에서 "맞다" 확인되면 → glossary 학습후보(`_candidates`) 적재 → 다음부턴 검색 없이 즉답
```

### 4-7. ★파이프라인 통합 다이어그램 (최종)

```
사용자 입력
  → [오타 변환] (한/영 자판 오류 보정)
  → 우리 DB(위키+glossary) 검색 — search(), AI 없음, 순수 키워드/glossary/그래프 매칭
      ├─ 결과 있음 + 스코어 충분(임계치 이상) ──────────────┐
      └─ 결과 없음 OR 스코어 임계치 미만(★"0건"만이 아니라   │  ← 지금 코드가 여기서 그냥
           "약한 매치"도 포함해야 함, §5 참조)                │     조용히 끊기던 지점
            → §4-U 웹검색(백과사전+지식iN+카페글, AI 처음 개입) │
            → 사용자 확인 → 뜻 확정 → search() 재실행(위로 복귀)
                                                            ↓
  → synthesizeAnswerStream() (AI, 여기서 조건 되물음·스코프판단 — 기존 로직 그대로 유지)
  → 답변
```

**핵심 발견**: `routes/legal.js`는 지금 `contextPages`가 빈 배열이면 AI 호출도 없이 바로
"찾지 못했습니다"로 끝난다(코드 확인됨). §4-U는 **정확히 이 지점**에 끼어들어야 하며, 매
질문마다 별도의 "이해단계" AI를 추가로 부르는 방식(비용 2배)은 채택하지 않고, **검색이 실패할
때만 §4-U가 개입**하는 최소 수정 방식으로 확정함(카파시 원칙 — 최소한으로).

### 4-8. 다수 키워드 스코어링 — 코드로 확인된 사실

`legal_retriever.js`의 `scoreOne()`은 추출된 **모든 키워드를 순회하며 스코어를 누적**한다(한
키워드만 보고 끝내지 않음). glossary 강제매칭(+4)과 title/body 직접매칭(+2~+3)이 합산되어
여러 관련 페이지가 함께 상위 후보(`PRIMARY_TOPK`)로 뽑힌다. 실측 예시: "낚싯배 승선정원
초과"라는 질문에서 "낚싯배"는 `_glossary.md`(10행)에 이미 "낚시배·선상낚시·낚싯배 →
낚시어선업" 매핑이 등록돼 있어 정상적으로 개념이 연결됨을 확인.

**termsOf()의 한계(발견, 미해결)**: 형태소 분석기가 없어 조사가 안 떨어짐 — "배에서"(3글자,
4글자 미만이라 접두어 축약 대상도 아님)처럼 단일음절 명사에 조사가 붙으면 그 단어 자체가
검색어로 거의 안 쓰인다. 예: "배에서 쓰는 뽀짝이"에서 "배"라는 맥락이 사실상 소실됨. 지금
당장 고칠 필요는 없어 보이나(§4-U 구현과 별개), 개선 여지로 기록.

## 12. §4-U를 파이프라인 어디에 끼울지 재검토(2026-08-16 밤, 사용자 제안 → 대화로 검증) — 아직 코드 미반영, 다음 결정을 위한 기록

§5-B(적대검증 D1~D4)를 본 뒤, 사용자가 "지금처럼 2차 조회까지 다 실패한 뒤에 §4-U를 끼우지 말고,
**질문이 들어오자마자 키워드·문맥부터 확인하고, 문제가 있을 때만 §4-U(키워드)나 이해확인(문맥)으로
보내자**"는 대안 순서를 제안했다. 오케스트레이터가 반박 3가지를 냈고, 그중 2개는 사용자가 실측
근거로 재반박해 정정됐다. **아직 코드에는 반영 안 됨** — 다음에 §4-U 배선을 손볼 때 이 절부터
읽을 것.

### 12-1. 사용자 제안 원안

```
질문 도착
 ├─ 키워드+문맥 동시 확인
 │   ├─ 둘 다 정상 → 바로 위키 검색
 │   ├─ 키워드 불명(=구어) → 네이버로 뜻 확인
 │   │     ├─ 찾음 → 그 뜻으로 문맥 재확인 → 정상이면 위키 검색
 │   │     └─ 못 찾음 → 사용자에게 재질문 → 그래도 안 되면 포기
 │   └─ 문맥만 불명 → AI가 문맥 정리 시도
 │         ├─ 정리됨 → "이런 뜻 맞나요" 확인
 │         └─ 정리 안 됨 → 사용자에게 재질문(반복 가능)
```

### 12-2. 검증 결과 — 오케스트레이터가 정정한 것 (사용자가 맞았음)

1. **"조사·어미 필터링이 안 되지 않냐"는 반박은 틀렸다.** 코드에 이미 `NAVER_JOSA_TAIL`(끝에서부터
   조사·어미를 떼는 정규식)이 있었다 — 목록이 `면·으면·주세요·하면` 등 몇 개 빠져 불완전했을 뿐,
   "형태소분석기가 새로 필요한 어려운 문제"가 아니라 **목록만 보강하면 되는 문제**였다(§5-B D4로
   기록, 아직 미수정).
2. **"문맥확인(H-37)은 안 켜져 있으니 검증 이력이 부족하다"는 반박은 절반만 맞다.** HANDOFF 실측
   기록을 다시 보니, H-37 이해확인은 **8/14~8/15 사이 최소 5차례 실제 배포 서버에 진짜 키로 스위치를
   켜고 다회전 검증**한 이력이 있고, 그때마다 구체적 결함(설정값 재배포시 리셋·ctx 무한루프·타임아웃
   버그·"네" 눌러도 재진술이 검색에 안 실림·재진술이 정보이득 없이 어미만 바꿔 오히려 검색을
   악화시킨 실측 사례)이 나왔다 — "안 켜봐서 모른다"가 아니라 "켜봤더니 구체적 문제가 반복 발견된
   것"이다. **반면 §4-U(naverTermLookup)는 정말로 실키 검증이 한 번도 없었다** — 이 구분은 정확히
   해야 한다(오케스트레이터가 두 기능을 뭉뚱그려 말한 게 부정확했음).
3. **"비용이 늘어난다"는 반박은 절반만 맞다.** 낯선낱말 판정(`unknownTermOf`)은 AI를 안 쓰는 순수
   문자열 대조라 완전히 공짜 — 이걸 앞단으로 옮기는 건 비용이 거의 안 붙는다. 반면 문맥확인
   (`understandConfirmStep`)은 코드 확인 결과 **애매함이 없는 질문에도 매번 Gemini를 부르는 값싼
   사전필터가 없다** — 이건 실제로 고정비용이 붙는 게 맞다. 다만 "그 비용을 내고서라도 애매한 채로
   검색 안 하는 게 낫다"는 사용자의 가치판단은 타당하다(비용이 없다는 뜻은 아니지만, 감수할 만하다는
   뜻으로는 반박이 안 됨).

### 12-3. raw fallback(2차 원문조회)의 위치에 대한 결론

raw fallback은 "AI가 단어 뜻을 몰라서"가 아니라 **"질문은 명확한데 위키에 아직 그 내용이 없을 때"**
(커버리지 공백)를 메우려고 만들어진 기능이다(HANDOFF 2026-08-03 "위키밖질문 2단계 답변" 신규기능
기록으로 확인) — §4-U(이해력 문제)와는 다른 축이다. **결론: raw fallback은 유지하되, 키워드·문맥이
이미 정리된 뒤에도 위키에 없을 때만 도는 자리로 남아야 한다** — 오늘 구현처럼 "이해 못한 문제"와
"커버리지 없는 문제"를 같은 지점(2차 조회 실패 지점)에 섞은 게 §5-B D1의 근본 원인이었다.

### 12-4. 사용자가 제안한 "미리 수집해 시행일에 자동 전환" — 이미 로드맵에 있었다

사용자가 "사서가 개정을 미리 감지해 위키를 미리 보강해두고, 시행일이 되면 자동 전환하는 로직이
필요하다"고 제안 → `MASTER_PLAN.md` H-29를 다시 찾아보니 **정확히 이 설계가 이미 있었다**(H-29
§5~7 "승인 방 + 시행일자 기준 예약 적용" — "예고본을 공포 즉시 미리 받아 대기 상태로 저장해두면
시행일에는 전환만 하면 되어 공백이 없다"). 진행상태: **감지(변경 여부 확인, H-29 1~4·8~12항)는
2026-08-10에 이미 구현+실측검증 완료돼 매주 월요일 04:00 KST 자동 Routine으로 등록까지 돼 있다.**
다만 **"미리 수집→대기→시행일 자동 스왑"의 실제 로직과 승인 UI(H-29 5~7항)는 아직 미구현** —
"Phase F 관리자 UI 미배선이라 다음 결정 대기" 상태로 남아있다. → **새로 반영할 로드맵 항목이 아니라,
이미 설계된 H-29 5~7항의 구현 우선순위를 올리는 문제.**

### 12-5. 대화 중 나온 새 아이디어 2가지 (미구현, 다음에 참고)

- **지시어 기반 값싼 사전 게이트(미구현, 제안만)**: `understandConfirmStep`을 매 질문마다 부르는 대신,

  명백히 애매하지 않은 질문 상당수를 공짜로 통과시킬 수 있다(코드 확인: 판단 기준5가 실제로 지시어

  아이디어임을 확인했다. §13(답변 과잉생성 A/B 테스트)에서 실제로 이 방안(변형D)까지 포함해 실측
