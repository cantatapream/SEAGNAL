## 1. 데이터 형태 — 왜 산문 위키가 아니라 JSON인가

`wiki/comparisons/`류 산문 페이지는 **사람이 읽는 글**이다. 이번 자산은 **프로그램(`decideClarify`)이 타고 내려가는 구조**여야 하므로, H-35 `delegation_graph_pilot.json`/`delegation_graph_full_73.json`과 같은 성격의 **신규 JSON 아티팩트**로 만든다. 헤더 규약도 H-35를 그대로 따른다:

```
{ "generated", "scope", "caveats"[], "summary"{}, ... }
```

`caveats`는 **정직하게 한계를 적는 자리**다(H-35 파일럿이 "법률→시행령 방향은 추출하지 않았다" 등을 명시한 것과 같은 용도). 이 자산의 한계는 §7에 정리하고 그대로 JSON에 싣는다.

## 3. 계층 도출 — 상향식, 임의분류 금지

### 3.1 방법

1. raw에서 **정의 조항**(`[제N조] 정의`, `적용 범위`, `적용 배제`, `적용제외 선박`)을 읽어 **실제로 법이 정의한 선박 구분 용어**만 모은다.
2. 그 용어들 사이의 **상하·배타 관계를 조문으로 확인**한다. 특히 `A법은 B에 적용하지 아니한다` 류 **적용제외 조항**이 형제 노드 간 배타성의 근거가 된다.
3. 근거가 확인된 것만 노드로 만든다. **하향식으로 "이쯤에서 나누면 좋겠다"고 지어내지 않는다.**

### 3.2 실측으로 확인한 1단계 분기(적용법 체계) — 배타성 근거가 원문에 있다

| 노드 | 정의 근거 | 형제와 배타인 근거 |
|---|---|---|
| **어선** | 어선법 제2조제1호 | 선박안전법 제3조제1항제2호의2 — 「어선법」 제2조제1호에 따른 어선에는 선박안전법을 적용하지 않음 |
| **수상레저기구** | 수상레저안전법 제2조제3호 | 선박안전법 시행령 제2조제1항제2호 — 수상레저기구법 제15조 안전검사를 받은 수상레저기구는 선박안전법 적용제외 |
| **그 밖의 선박(일반선박)** | 선박법 제1조의2제1항 · 선박안전법 제2조제1호 | 위 두 조항의 반대해석(어선·수상레저기구를 뺀 나머지) |

즉 **1단계는 "지어낸 분류"가 아니라 법이 스스로 그어둔 적용경계**다. 이게 이번 트리의 핵심 설계 근거다.

### 3.3 트리로 쪼개지 **않은** 축 — 왜 `조건`으로 남겼나

서류 요건을 실제로 가르는 축은 선박 종류 말고도 최소 4개가 더 있다:

- **국제항해 여부**(국제톤수증서·국제선박보안증서·해사노동적합증서·선박에너지효율관리계획서)
- **총톤수/길이 구간**(길이 24m 이상, 총톤수 400톤/5천톤/1천톤/200톤 이상, 총톤수 20톤 미만 어선 등)
- **화물 종류**(산적 유류·유해액체물질·위험물)
- **항해구역**(평수/연해/원양 — 해도·항해용 간행물)

이 축들은 선박 종류와 **직교(orthogonal)** 한다. 트리 레벨로 올리면 같은 서류 목록이 리프마다 복제돼 유지보수가 무너진다(법 하나 바뀌면 N개 리프를 고쳐야 함). 그래서:

- **트리 레벨** = 선박 종류(적용법 체계 → 용도·영업형태). **2~3단.**
- **잔여 축** = 각 서류 항목의 `구분: "조건부"` + `조건` 문자열, 그리고 리프의 **`추가확인`** 배열(되묻기가 이어서 물을 수 있게 질문 문구까지 미리 넣음).

**대안(검토했으나 채택 안 함)**: 국제항해 여부를 3단 노드로 승격 → 리프 수가 3배가 되고 문서 중복이 생겨 카파시 2(단순함 우선)에 위배. 대신 `추가확인`으로 같은 되묻기 효과를 낸다.

### 3.4 중첩(overlap)의 정직한 표시

2단계(용도·영업형태)는 1단계와 달리 **완전 배타가 아니다.** 예: 유·도선도 13인 이상 여객을 태울 수 있으면 선박안전법 제2조제10호의 "여객선"에 해당할 수 있다. 이런 노드에는 `중첩주의` 필드로 그 사실을 적고, 되묻기 선택지에도 그 취지를 담는다. **모른 척 배타인 척하지 않는다.**

## 4. ★비-리프 노드의 `질문`·`선택지` (사용자 추가 지시, 2026-08-10)

> 사용자 지시 원문 요지: "트리의 각 분기(비-리프) 노드마다 **무엇을 물어볼지 자체도 데이터로** 미리 만들어 저장하라. … `decideClarify()`가 매번 '이 갈림길에서 뭐라고 물어야 하지'를 즉석 판단하지 않고 트리에서 그대로 꺼내 쓸 수 있게(속도·일관성)."

### 규칙

1. **모든 비-리프 노드는 `질문`과 `선택지`를 반드시 갖는다**(빌드 시 강제 — §6 검증 4번).
2. `선택지[].label`은 **raw에 실재하는 법률 용어**를 쓴다(임의 조어 금지). 예: "어선", "수상레저기구", "낚시어선".
3. `선택지[].next`는 반드시 **그 노드의 자식 id**여야 한다(빌드 시 참조 무결성 검사).
4. `선택지[].hint`는 그 용어의 법정의를 한 문장으로 풀어 쓴 것 — 사용자가 자기가 어디에 해당하는지 고를 수 있게 한다. **hint도 정의 조항 근거를 벗어나지 않는다.**
5. `질문` 문장은 존댓말 한 문장, 기존 `decideClarify` 프롬프트가 만들던 것과 같은 톤(`intro`/`question` 규약과 호환).
6. **선택지 개수는 자식 수와 같게 유지**하고, **3개를 넘기지 않는다** — `decideClarify`의 기존 상한이 `CLARIFY_OPTION_MAX = 3`이라, 4개를 만들면 되묻기 UI가 선택지를 잘라 먹는다. 실제로 이 규칙 때문에 "그 밖의 선박" 아래를 (여객선/유도선/유조선/그밖) 4갈래로 두려던 초안을 **(여객선/유도선/화물선·그밖) 3갈래 + 화물선 아래 (유조선/그밖) 2갈래**로 다시 쪼갰다. 빌더가 이 조건을 검사해 위반 시 빌드를 실패시킨다.

```jsonc
]
```

### 리프의 `추가확인`(잔여 축 질문)

```jsonc
"추가확인": [
  { "축": "국제항해",
    "질문": "이 선박이 국제항해에 종사하나요?",
    "선택지": [ { "label": "국제항해" }, { "label": "국내항해만" } ],
    "영향": ["국제톤수증서", "국제선박보안증서", "해사노동적합증서"] }
]
```

`영향`은 그 축이 켜졌을 때 추가/제외되는 서류명 목록이라, 되묻기가 답을 좁힌 뒤 **어떤 항목을 보여줄지 계산**할 수 있다.

## 5. 추출 방법론

### 5.1 조문 분리 — 계열별 이중 형식 (L-54)

raw는 계열마다 조문 마커가 다르다. **하나의 정규식으로 짜면 고시계열에서 조용히 0건**이 된다(`_LESSONS.md` L-54).

| 계열 | 파일 | 마커 |
|---|---|---|
| 법률·시행령·시행규칙 | `법률.txt`·`시행령*.txt`·`시행규칙.txt` | `[제10조] 제목 (시행 …)` — **대괄호** |
| 고시·훈령 등 행정규칙 | `행정규칙/*.txt` | `제7조(허용기준안 작성) ①…` — **무대괄호** |

두 정규식을 계열별로 적용한다.

### 5.2 후보 추출 — "동사 × 서류명사 × 장소구" 3중 조건

- **동사**: `갖추어 두` / `갖춰 두` / `비치` / `게시하여야` / `지니고 있어야` / `휴대하여야` / `소지하여야`
- **서류명사**: 증서·증명서·면허증·허가증·등록증·신고필증·신고확인증·검사증·수첩·원부·일지·기록부·해도·명부·매뉴얼·계획서·간행물·서류 등
- **장소구(배 위)**: 선박/선내/어선/여객선/유선/도선/수상레저기구/조타실/기관실 … 이 **동사 앞 90자 이내**에 있어야 함

**적응 이력(정직 기록)**: 처음엔 장소구 창을 32자로 잡았다가, 해상교통안전법 제51조제3항("그 선박에는 선박안전관리증서나 … 사본을 갖추어 두어야 하며")과 낚시법 제33조제5항("해당 낚시어선에 승선자명부 … 의 사본을 3개월 동안 갖추어 두어야")을 **놓치는 것을 확인**하고 90자로 넓혔다(20법 → 23법). 창 크기는 실측으로 정했지, 추정으로 정하지 않았다.

### 5.3 위임 추적(2차 패스) — 이게 없으면 절반을 놓친다

1차 추출은 **장소구가 같은 문장에 없는 위임 하위조문을 구조적으로 못 잡는다.** 실제 사례:

- 선원법 제20조제1항제5호 "그 밖에 해양수산부령으로 정하는 서류" → **선원법 시행규칙 제13조제2항**이 선박검사증서·해도·기관일지·속구목록·승무정원증서·해사노동협약 도서를 열거. 이 문장에는 "선박에"가 없어 1차 추출에서 안 걸린다.
- 선박안전법 제32조(해양수산부령으로 정하는 항해용 간행물) → **시행규칙 제74조**(종류)·**제75조**(비치 방법).
- 어선법 제15조 단서 → **시행규칙 제33조의2**(비치의무 **면제** 어선 3종).

그래서 1차에서 찾은 각 요건 조문에 대해 **"해양수산부령/대통령령으로 정하는 …" 문구가 있으면 그 하위법령을 직접 열어 확인**하는 2차 패스를 돌린다. 트리에는 `위임` 필드로 그 링크를 남긴다.

### 5.4 무엇을 트리에서 **뺐나**(scope-out) — 정직 기록

스캔에 걸렸지만 "선박에 비치하는 서류"가 아닌 것은 `unmapped`에 사유와 함께 남긴다. 유형:

| 유형 | 예 |
|---|---|
| 사무소·사업장 비치 | 유선및도선사업법 제23조제2항(영업소 선원명부) · 신항만건설촉진법 시행령 제28조(주된 사무소 토지상환채권원부) |
| 관청 비치 등록원부 | 항만법 제25조제2항 · 마리나항만법 제22조제1항 |
| 공무원 신분 증표 | "권한을 표시하는 증표를 지니고" — 정규식에서 애초에 배제 |
| 서류가 아닌 **장비** | 구명부환·구명조끼 "비치"(선박구명설비기준 등) |
| 신청·첨부 서류 | "…신청서에 다음 각 호의 서류를 첨부하여" |
| 선박 종류와 무관한 개인 휴대 | 출입국관리법 제27조(체류 외국인의 여권등 휴대) |

이 목록은 산출물 JSON의 **`unmapped`** 키에 그대로 들어 있다(법 단위 3건 + 유형 단위 6종).

## 6. 완결성·정확성 판정 — 무엇을 "다 뽑았다"로 보는가

**성공 기준(검증 가능, 카파시 4)**:

1. **커버리지 수치 공개**: 74법 전부를 스캔했음을 파일 수·조문 수로 밝히고, "서류요건 발견 N법 / 무관 확인 M법"을 보고한다. *(정확도가 아니라 "어디까지 봤는지"를 정직하게 밝히는 것 — H-35가 커버리지 80.3%를 그대로 공개한 것과 같은 태도.)*
2. **전량 재대조(표본 아님)**: 트리에 들어간 **모든** {서류명, 근거법령, 근거조문} 항목에 대해, 빌드 스크립트가 raw 파일을 열어 ①그 조문이 실재하는지 ②그 조문 본문에 서류명(또는 지정한 앵커 문구)이 실제로 있는지 확인한다. 하나라도 실패하면 **빌드 실패**(JSON을 만들지 않는다). → 지어낸 항목 0건이 성공 기준.
3. **노드 provenance 검사**: 모든 노드의 `provenance[].인용`도 같은 방식으로 raw 대조. 출처 없는 노드는 빌드 실패.
4. **질문·선택지 무결성**: 모든 비-리프에 `질문`·`선택지`가 있고, `선택지[].next`가 실재하는 자식 id이며, 선택지 수 = 자식 수임을 검사. 위반 시 빌드 실패.
5. **재현성**: 빌드는 스크립트 1회 실행으로 재현된다(`loop/build_vessel_doc_tree.py`).

**"완결성"에 대한 정직한 한계**: 이 파일럿은 *"raw 원문에 비치·구비 의무가 문장으로 적혀 있는 서류"* 를 전수로 잡는 것을 목표로 한다. 원문에 그런 문장이 없이 **실무 관행·서식(별지)으로만 존재하는 서류**는 원리적으로 못 잡는다(H-35에서 "원문에 위임 문구가 없으면 못 찾는다"와 같은 한계). 이건 `caveats`에 명시한다.

## 7. caveats (JSON에 그대로 실을 한계 목록)

1. 1단계 분기(어선/수상레저기구/그 밖의 선박)만 조문상 배타성이 확인됐다. **2단계(용도·영업형태)는 중첩 가능**하다 — 해당 노드에 `중첩주의`로 표시했다.
2. 총톤수·길이·국제항해·화물종류·항해구역은 트리 레벨이 아니라 서류 항목의 `조건`/리프의 `추가확인`으로만 표현된다(§3.3).
3. 행정규칙(고시) 665개 파일도 스캔했지만, 고시에서 나온 "비치" 문장은 대부분 **설비(구명부환·해도 등) 기준**이라 서류 항목으로 채택된 것은 소수다.
4. `수상레저기구의 등록 및 검사에 관한 법률`에는 **등록증·안전검사증을 기구에 비치하라는 명시 조문이 raw에서 확인되지 않았다**(발급·재발급·반납 조문만 존재). "없음"을 지어내지 않고 그대로 기록한다 — 실제로 없는 것인지 우리가 못 찾은 것인지는 소관부서 확인이 필요하다.
5. 자치법규(`raw/_자치법규/`)와 국제협약 텍스트는 이번 스캔 대상에서 제외했다(74법 기준법 체계만).
6. 별표·별지 서식(`별표/` 디렉토리, `_links.json`)은 이번 스캔 대상이 아니다 — 서식 자체가 아니라 "비치 의무 문장"만 봤다.
7. 조건부 서류의 `조건`은 **원문 문구를 그대로 옮긴 것**이지, 우리가 해석해 정규화한 값이 아니다. 톤수 구간 등을 프로그램이 판정하려면 별도 파싱이 필요하다.

## 8. 유지보수 통합 설계 (H-29 연동 — **설계만**, 이번엔 배선 안 함)

### 8.1 문제

법이 개정되면 이 트리는 조용히 낡는다. H-29(`loop/detect_law_changes.py`)가 이미 **주 1회(월 04:00 KST, `trig_01KKZTHKRxDbDxs4HK4jiTgi`)** 변동을 감지해 `_dashboard/law_change_queue.json`에 적재하고 있으므로, **탐지를 새로 만들 필요는 없다. 필요한 건 "그 변동이 이 트리의 어느 노드/서류를 건드리는가"의 매칭이다.**

### 8.2 매칭이 가능한 이유 — provenance가 이미 키다

`law_change_queue.json`의 각 항목은 다음을 갖는다(실측 스키마):

```jsonc
{ "kind": "law_pending", "law": { "slug": "공유수면관리및매립에관한법률", … },
  "layer": "법률", "식별자": { "법령ID": "011186" },
  "changed_articles": [ { "조문번호": "8", "조문가지번호": "", "조문제개정유형": "타법개정", "조문시행일자": "20260918" } ],
  "status": "pending", "scheduled_for": null, "ai_recommendation": null }
```

이 트리의 모든 서류 항목·노드 provenance는 `{근거법령(slug), 계층(=layer), 근거조문}`을 갖는다. 따라서 **조인 키는 `(slug, layer, 조문번호)`** 하나로 충분하다. `changed_articles[]`가 비어 있는 변동(법령명 변경·소관부처 변경·신규 고시)은 **법 단위(slug)로 조인**한다.

### 8.3 제안 파이프라인 (다음 라운드 구현 대상)

```
detect_law_changes.py (H-29, 이미 있음)
        ↓  law_change_queue.json
[신규] loop/flag_vessel_doc_tree.py          ← 이번엔 만들지 않음
        ├ 큐의 각 item에서 (slug, layer, 조문번호) 추출
        ├ vessel_doc_tree.json 을 순회하며 같은 키를 가진 노드·서류 항목 탐색
        └ 매치되면 그 항목에 review 플래그를 붙인 사이드카 파일 생성
             _dashboard/vessel_doc_tree_review.json
             { "flagged": [ { "path": "tree.children[0].children[0].서류[2]",
                              "서류명": "…", "change_id": "chg_…",
                              "reason": "근거조문 개정(시행 20260918)",
                              "status": "needs_review" } ] }
```

**설계 결정 4가지(근거 포함)**:

- **(a) 트리 파일을 직접 고치지 않고 사이드카에 쓴다.** 트리는 빌드 스크립트의 결정론적 산출물이라 손으로 고치면 다음 빌드에서 날아간다. H-29가 raw·위키를 건드리지 않고 큐에만 쌓는 것과 같은 분리(감지와 반영의 분리).
- **(b) 자동 재빌드하지 않는다.** 조문이 개정되면 인용 문구가 바뀌어 §6의 앵커 검증이 실패할 수 있는데, 그건 **정상적인 실패**(사람이 봐야 한다는 신호)다. 자동 재빌드는 이 신호를 지운다.
- **(c) 시행일 기준 예약은 H-29 5~7항 승인방이 생길 때 함께 붙인다.** `scheduled_for` 필드가 큐에 이미 예약돼 있으므로 별도 설계가 필요 없다.
- **(d) 새 계층 주제(산출물 ②)가 채택될 때도 같은 파이프라인을 쓴다.** 조건은 하나뿐 — **새 트리도 모든 노드·항목에 `{근거법령, 계층, 근거조문}` provenance를 갖출 것.** 이 규약만 지키면 `flag_*.py`는 트리 파일명만 바꿔 재사용된다. 즉 **provenance 규약이 곧 유지보수 인터페이스**다.

### 8.4 마이그레이션(H-29 패턴 재사용)

H-29가 `_meta.json`에 `법령ID`를 백필한 것과 같이(`loop/backfill_lawid.py`), 이 트리도 provenance에 `법령ID`를 함께 넣어두면 **법령명이 바뀌어도 추적이 끊기지 않는다**(L-74/H-29 11항 — 법령ID는 개정·명칭변경과 무관하게 불변). 이번 빌드에서 `_meta.json`의 `families.<계층>.법령ID`를 읽어 provenance에 함께 싣는다. *(이번에 미리 해두는 편이 나중에 백필하는 것보다 싸다 — H-29가 실제로 백필 비용을 치른 선례.)*

## 9. 되묻기(`decideClarify`) 연동 설계 (**설계만**, 이번엔 배선 안 함)

### 9.1 지금의 `decideClarify()`

`local_server/services/legal_retriever.js`:

- 입력: `(query, contextPages)` — 검색 상위 6페이지(`CLARIFY_TOPK`)의 본문 발췌 1,500자씩
- 동작: Gemini에게 "이 질문의 답이 갈리는 구분이 **근거자료 문구에 실제로 적혀 있으면**" 되묻기 JSON을 만들라고 시킴
- 출력: `{ needed, intro, question, options:[{label,hint}] }`
- 안전장치: 라운드 상한 `CLARIFY_MAX_ROUNDS=2`(질의의 `' — '` 개수로 셈) · 같은 조건 재질문 차단 · hint의 조문번호를 근거자료와 대조

**한계**: 매 질문마다 LLM 1회 + 근거자료 9,000자를 태우고, 같은 질문에도 그때그때 다른 선택지가 나올 수 있다(일관성 없음). 그리고 근거자료 top-6에 그 구분이 안 뜨면 못 묻는다.

### 9.2 트리 연동 — 제안 흐름

```
질문 "배 서류 뭐 필요해요?"
  ↓
[신규] matchDocTreeTopic(query)            ← 주제 매칭(트리의 topic 키워드와 대조)
  ↓ 매치되면(= 서류 주제)
[신규] clarifyFromTree(query, node)        ← 트리에서 질문·선택지를 그대로 꺼냄(LLM 0회)
  ↓ 사용자가 버튼 선택 → 질의에 ' — 어선' 이 붙어 재질의
[신규] resolveDocTreePath(query)           ← 질의에 붙은 라벨들로 현재 노드 위치 복원
  ↓ 리프 도달
리프의 서류[] 를 근거로 답변 조립(+ 추가확인 남아 있으면 한 번 더 되묻기)
  ↓ 매치 안 되면
기존 decideClarify() 그대로 (폴백)
```

### 9.3 제안 함수 시그니처

```js

 * @param {string} query
 * @returns {{matched:boolean, treeId?:string}}

 * @param {object} node - vessel_doc_tree.json 의 비-리프 노드

 * @param {object} tree
```

### 9.4 설계 결정(연동 시 반드시 지킬 것)

- **(a) 반환 스키마를 기존과 동일하게 유지한다.** `{needed,intro,question,options[{label,hint}]}` 그대로면 `routes/legal.js`·`client/js/ai-chat/ai_chat.js`(`clarifyHTML`)를 **한 줄도 안 고쳐도** 된다. 라이브 경로 변경 최소화(카파시 3).
- **(b) `CLARIFY_MAX_ROUNDS=2` 상한과 충돌한다 — 이게 이번 설계의 최대 미해결 쟁점이다.** 트리는 root→1단→2단으로 **최소 2회**, `추가확인`까지 쓰면 3회를 묻는다. 지금 상한은 2다. 세 가지 선택지가 있고, **어느 쪽인지는 사용자·오케스트레이터 결정 사항**으로 남긴다:
  1. 트리 경로일 때만 상한을 3으로 올린다(상한 자체의 목적은 "모델이 기준3을 어겨 무한루프 도는 것"의 백스톱인데, 트리 경로는 **깊이가 데이터로 유한**하므로 무한루프가 원리적으로 불가능 — 상한을 올려도 안전하다는 근거가 있다).
  2. 트리 경로는 상한 검사를 건너뛰고 **트리 깊이 자체를 상한으로** 쓴다(더 정확하지만 코드 분기 하나가 늘어난다).
  3. 트리를 2단으로 유지하고 `추가확인`은 되묻지 않고 답변 본문에 "국제항해라면 여기에 ○○이 추가됩니다" 식으로 병기한다(코드 변경 0, 대신 답이 길어진다).
  → **`_LESSONS.md` L-49·CLAUDE.md "상한은 '없으면 뭐가 잘못되나'를 한 문장으로 못 쓰면 넣지 않는다"** 원칙에 따라, 상한을 손대기 전에 "이 상한이 트리 경로에서 막는 사고가 무엇인지"를 한 문장으로 적을 수 있어야 한다. 현재로선 적을 수 없어 보인다 → 1번이 유력하나 **결정은 사용자에게 넘긴다.**
- **(c) 트리 답변도 canonical 게이트를 우회하지 않는다.** 리프의 서류 목록은 raw 근거를 갖지만, 챗봇이 최종 답변으로 내보낼 때는 기존 `answerCanonicalOnly` 정책과 어떻게 맞물릴지 별도 검토가 필요하다(트리는 raw 직인용이라 위키 canonical 여부와 축이 다르다). **이번 범위 밖, 다음 라운드 결정.**
- **(d) 되묻기 라벨과 트리 라벨의 문자열 일치가 계약이다.** `resolveDocTreePath`는 `' — '` 뒤 문자열을 노드 라벨과 대조하므로, 라벨을 바꾸면 진행 중인 대화가 깨진다. 라벨은 **법률 용어 그대로 고정**하고 표시용 변형이 필요하면 별도 필드를 쓴다(`CLARIFY_JOINER` 주석이 경고하는 "한쪽만 바꾸면 뚫린다"와 같은 성격의 계약).

### 11.2 스키마 — 장비 항목

```jsonc
{
  "장비명": "구명부환",
  "근거법령": "선박안전법",            // 고시의 모법(raw 디렉토리 기준)
  "근거법령_slug": "선박안전법",
  "계층": "행정규칙",                   // 법률 | 시행령 | 시행규칙 | 행정규칙

  "근거조문": "제93조",
  "파일": "raw/04_선박해운/선박안전법/행정규칙/선박구명설비기준.txt",
  "인용": "① 선박길이 30미터이상의 제4종선에는 최소한 4개의 구명부환을 비치하여야 한다.",

  "수량조건": "선박길이 30미터이상의 제4종선에는 최소한 4개",   // ★raw에 실재하는 문구여야 통과(§11.6)
  "수량출처": "조문본문",               // 조문본문 | 조문본문 표(이미지판독·⚠REVIEW) | 별표·표(raw 미수집) | 해당없음(수량 규정 아님)
  "조건": "제4종선(여객선 이외의 선박으로서 제3종선 이외의 선박 — 같은 기준 제2조제4호)",
  "주의": null

```

**불변식(서류 항목과 동일한 원칙)**:
1. `인용`은 스크립트가 raw에서 직접 읽어 채운다. 사람이 타이핑하지 않는다.
2. `anchor`(SPEC에 적는 검증 문구)가 그 조문 원문에 없으면 **빌드 실패**.
3. **`수량조건`도 raw 원문의 부분문자열이어야 한다** — 서류의 `조건`과 달리 수량은 숫자라 요약하다 틀리면 곧바로 오답이 되므로, 빌더가 `수량조건`을 조문 본문에서 다시 찾아 없으면 빌드를 실패시킨다. 요약이 필요한 경우는 `수량조건: null` + `수량출처`로 남긴다(지어내지 않는다).
4. `조건`(적용 대상 선박)은 서류 항목의 `조건`과 같은 성격 — 원문 문구 기반의 사람 서술이며 정규화된 값이 아니다(caveat).

**★장비 상속 규약**: 서류와 **완전히 같다** — 어떤 선박에 필요한 장비 = 루트에서 그 리프까지 경로상 모든 노드의 `장비` 합집합. 그래서 「선박구명설비기준」의 "제1종선등"(제1~4종선 전부) 조문은 `general_ship`에 한 번만 둔다.

**주의로 남긴 중첩**: 제3·4종선은 "여객선 이외의 선박"이라 문언상 여객선이 아닌 유·도선도 포함될 수 있다. 그러나 유·도선의 인명구조용 장비는 유도선법 시행령 제17조·제18조가 별도로 정하고(그 제17조제3항이 「선박구명설비기준」 적합성을 요구), 트리에서 `excursion_ferry`는 `cargo_ship`의 형제라 상속되지 않는다. 이 중첩은 `caveats`에 명시한다(§3.4 "모른 척 배타인 척하지 않는다"와 같은 태도).

### 11.4 ★계열 범위 — 고시만 보면 절반을 놓친다(실측으로 확인)

착수 지시는 "**고시(admrul) 파일 전수 스캔**"이었고 그대로 했다(커버리지 수치는 `summary.equipment_scan`). 다만 스캔 도중 **유·도선의 인명구조용 장비 수량이 고시가 아니라 「유선 및 도선 사업법 시행령」 제17조·제18조(대통령령)에 있다**는 것을 확인했다("승선 정원의 120퍼센트 이상에 해당하는 수의 구명조끼", "승선 정원의 30퍼센트 이상에 해당하는 수의 구명부환" 등). 고시만 채택하면 `excursion_ferry` 리프가 통째로 비게 되고, 이는 "raw에 없다"가 아니라 "우리가 안 봤다"가 된다.

→ **결정: 장비 항목의 계열은 서류 항목과 마찬가지로 계열 무관(법률·시행령·시행규칙·행정규칙)으로 둔다.** 고시가 1차 소스이고, 같은 주제의 수량을 상위 법령이 직접 정한 경우 그것도 담는다. 채택된 법률계열 항목은 4건뿐이며(유도선법 시행령 제17조·제18조, 낚시법 제29조, 수상레저안전법 제20조) 전부 `계층` 필드로 구분된다. *(이 판단은 지시 문언을 넓힌 것이므로 최종 보고에서 확인 대상으로 올린다.)*

### 11.5 고시 파싱 — L-54를 정면으로 다루는 3가지

1. **조문 마커가 다르다**(L-54): 고시는 `제7조(제목) ①…`로 **대괄호가 없다**. 기존 `split_articles()`(대괄호 전용)를 **고치지 않고**, 고시 전용 `split_articles_admrul()`을 새로 추가했다.
2. **같은 조번호가 파일 안에 두 번 나온다**: 「어선설비기준」은 본문 끝에 이미지 표를 전사한 부록이 붙어 있고 그 줄이 `제104조(거주구역 및 업무구역의 소방설비) 제1항 표 (…)` 형태라 **조문 마커 정규식에 다시 걸린다.** → `split_articles_admrul()`은 **첫 등장만 채택**(뒤에 오는 부록이 본문을 덮어쓰지 못하게).
3. **항 기호에 공백이 없다**: 법률계열은 `① 고정식…`, 고시계열은 `①고정식…`으로 붙어 있는 경우가 많아 기존 `quote_of()`의 문장 시작점 탐지(`'① '` 등 공백 포함 문자열)가 고시에서 헛돈다. → 장비 항목 전용 `quote_of_admrul()`을 새로 추가했다(공백 없는 항 기호 인식 + 호 번호도 문장 시작점으로 인정 + 괄호 안의 `…제외한다. 이하 …`를 문장 경계로 오인하지 않음). **기존 `quote_of()`는 한 글자도 고치지 않았다** — 고치면 56건 서류 인용문이 전부 흔들리기 때문이다(카파시 3). 장비 항목은 계열과 무관하게 전부 이 새 함수를 쓴다(§11.4에서 법률계열도 담기로 했으므로 경로를 하나로 유지).

**작성 중 실제로 걸러낸 오류 4종(정직 기록)** — 전부 빌드는 통과했는데 인용문 내용이 틀렸던 것들이라, §6의 "빌드 통과 ≠ 내용 맞음"이 이번에도 그대로 재현됐다:
  ⓐ `rfind`가 -1을 돌려줄 때 `+3`을 그대로 더해 조문 머리를 두 글자 잘라먹음(`제43조(…` → `3조(…`).
  ⓑ 호 번호를 시작점으로 잡으면서 번호 자체를 한 글자 건너뛰어 `. 유선에는 …`으로 시작(몇 호인지 사라짐).
  ⓒ 괄호 안의 `제2종팽창식구명뗏목을 제외한다. 이하 이조 …`를 문장 끝/시작으로 오인해 인용이 엉뚱한 데서 끊김.
  ⓓ 400자 상한에 잘려 인용문이 정작 anchor를 안 담는 경우 → **anchor가 인용문 안에 실제로 있는지 검사하는 게이트를 추가**해 빌드 실패로 만들었다.
  ⓐ~ⓒ는 자동 검증(앵커 존재·수량조건 존재)을 **전부 통과했다** — 사람이 78건 인용문을 한 줄씩 눈으로 읽어서 찾았다.

### 11.6 별표(수량표)의 한계 — 세 가지 상태를 구분해 기록한다

D절이 예상한 대로 수량의 상당수가 표에 있다. raw에서 표가 어떤 상태인지는 고시마다 다르며, **셋을 구분해 `수량출처`에 남긴다**(뭉뚱그리면 "수량을 모른다"는 사실이 감춰진다):

| `수량출처` | 뜻 | 실례 |
|---|---|---|
| `조문본문` | 수량이 조문 문장 안에 숫자로 있다 → `수량조건`에 원문 그대로 | 선박구명설비기준 제93조 "선박길이 30미터이상의 제4종선에는 최소한 4개" |
| `조문본문 표(이미지판독·⚠REVIEW)` | 표가 `<img>`였는데 **이미지판독(OCR) 전사본이 본문에 이어 붙어** 있다. 값은 있으나 사람 확인 전이다 | 어선설비기준 제104조(총톤수별 휴대식소화기 수), 선박소방설비기준 제72조(소방원장구 수) |
| `별표·표(raw 미수집)` | 조문이 "별표 N에 의한 수"·"다음 표에 따른 수"라고만 하고 **그 표가 raw에 없다**(별표 제목만 있거나 `<img>`만 있고 판독 전사본도 없다) | 선박구명설비기준 제70조·제79조·제86조(제1·2·3종선 구명부환 수, 별표 5·6·7)·제98조·제99조(별표 8·9)·제102조(별표 10), 총톤수 10톤 미만 소형어선 기준 제52조(별표 3)·제59조(소화기 표) |
| `해당없음(수량 규정 아님)` | 수량을 정하지 않는 조문(그냥 갖출 의무·착용 의무·설비 종류 나열) | 선박구명설비기준 제101조(구명조끼등 부착), 수상레저안전법 제20조(인명안전장비 착용) |

**세 번째 경우 `수량조건`은 반드시 `null`이다.** "몇 개인지 모른다"를 그대로 남기지, 다른 고시의 숫자를 끌어와 채우지 않는다(§6 "지어낸 항목 0건").

### 11.7 ★회귀 검증 — 기존 서류 데이터 무변경이 성공 기준의 절반

장비 확장은 **기존 자산에 손대는 작업**이라, "새로 만든 것이 맞나"만큼 "**있던 것이 안 변했나**"가 중요하다.

- 확장 전 `vessel_doc_tree.json`을 백업 → 확장 후 산출물에서 **`장비` 키와 새 summary 키만 제거**하고 `generated`(타임스탬프)를 뺀 나머지를 **정확히 일치(문자열 동일)** 하는지 대조한다.
- 다르면 버그다. 서류 항목 56건·노드 13개·모든 provenance·caveats·unmapped·scan 수치가 **한 글자도** 바뀌면 안 된다.
- 빌더 코드 차원의 규율: 기존 함수(`split_articles`·`article_body`·`quote_of`·`doc`·`prov`·`scan_corpus`·`validate` 본문의 기존 검사)는 **읽기만 하고 수정하지 않는다.** 장비 로직은 전부 새 함수로 추가한다.

### 11.8 전량 재대조(독립 스크립트) — 서류 파일럿과 같은 방식

빌더가 통과시켰다는 것과 내용이 맞다는 것은 다른 문제다(§6에서 실제로 5건을 걸러낸 경험). 그래서 **빌더의 조문분리 로직을 재사용하지 않는 별도 스크립트**로 장비 항목 전량을 다시 대조한다. 검사 항목:

1. `파일` 경로가 실재하고, 그 파일을 **통짜 문자열**로 읽어 공백 정규화했을 때 `인용`이 **부분문자열로 실재**하는가(빌더의 조 분리 로직과 무관하게).
2. `수량조건`이 null이 아니면 그것도 같은 방식으로 실재하는가.
3. `인용`이 정말 그 `근거조문`의 범위 안에서 나오는가 — 독립 스크립트는 조문 경계를 **문자열 검색(`제N조(`의 첫 출현 위치 ~ 다음 조 마커)** 으로 따로 구해 확인한다.
4. `계층`이 행정규칙이면 `고시명`·`고시ID`가 `_admrul.json`과 일치하는가.

실패 0건이 성공 기준이다. 구현: `_dashboard/loop/verify_vessel_equipment.py` (재현 `python3 local_server/knowledge/legal/_dashboard/loop/verify_vessel_equipment.py`).

### 11.9 질문·선택지 — 이번에는 새로 만들지 않는다(근거)

장비 축 때문에 트리를 더 쪼개야 하는지 검토했다. 항해구역(평수/연해/근해/원양)·길이·총톤수로 장비 수량이 갈리는 것은 사실이지만, **이 축들은 §3.3에서 이미 "트리 레벨로 올리지 않는다"고 결론 낸 바로 그 직교 축들**이고, 장비도 서류와 정확히 같은 이유로 같은 결론이 된다(같은 조문 세트가 리프마다 복제됨). 그래서:

- 트리 구조(노드·`질문`·`선택지`)는 **한 글자도 바꾸지 않았다**(§11.7 회귀검증 대상).
- 대신 **리프의 `추가확인`에 "항해구역" 축을 새로 추가**했다 — 장비 요건을 실제로 가르는 축인데 서류 파일럿에는 없었기 때문이다. `영향`에는 그 축이 켜질 때 달라지는 장비명을 넣는다.
  - ※ `추가확인`은 리프에만 붙는 필드이고 빌더가 이미 그 규칙을 검사한다(§6 검증 4번). 기존 `추가확인` 항목(국제항해·총톤수·선원법 적용)은 그대로 두고 **추가만** 한다.

### 11.10 유지보수(H-29 연동) — 고시는 조인 키가 하나 부족하다

서류 항목의 조인 키는 `(slug, layer, 조문번호)`였다(§8.2). 장비 항목은 대부분 `layer="행정규칙"`이라 **어느 고시인지**가 더 필요하다 → 조인 키는 `(slug, "행정규칙", 고시명, 조문번호)`.

`고시ID`는 `_admrul.json`이 가진 **일련번호**라서 **개정되면 값이 바뀐다**(L-73이 실측으로 확인). 개정에도 불변인 `행정규칙ID`는 우리 raw에 저장돼 있지 않다. 따라서:
- 지금은 `고시명`(정규화 전 원문 제목) + `고시ID`를 같이 싣고, **동일 문서 판정은 고시명으로, 신판 판정은 고시ID 변화로** 본다(L-73의 3단 게이트 중 ①③만 가능한 상태).
- **다음 라운드 권고**: `collect_admrul.py`가 `행정규칙ID`를 `_admrul.json`에 함께 저장하도록 보강하면 이 트리도 백필만으로 3단 게이트를 완성할 수 있다(§8.4 `법령ID` 백필과 같은 성격의 값싼 선투자).

**불변식(서류·장비 항목과 같은 원칙 + 하나 추가)**:
1. `인용`은 스크립트가 raw에서 직접 읽어 채운다. 사람이 타이핑하지 않는다.
2. `anchor`(SPEC에 적는 검증 문구)가 그 조문 원문에 없으면 **빌드 실패**. 인용문이 400자 상한에 잘려 anchor를 못 담아도 **빌드 실패**.
3. **★`가입대상`도 raw 원문의 부분문자열이어야 한다.** 이 자산이 답하는 질문이 *"어떤 배가"* 이므로, 대상을 요약·의역하다 틀리면 곧바로 오답이 된다. 장비 축이 `수량조건`에 같은 규율을 건 것과 같은 이유(§11.2-3).
4. **`보장한도`도 부분문자열이어야 한다.** 금액을 요약하다 틀리면 오답이 되므로 빌더가 원문에서 다시 찾는다. 모르면 `null`(지어내지 않는다).
5. `보장한도`와 `보장한도출처`는 **서로 모순될 수 없다** — `보장한도출처`가 `"조문본문"`이면 `보장한도`가 반드시 있어야 하고, 그 외 값이면 반드시 `null`이어야 한다(빌더·독립 재대조기 양쪽이 검사).
6. `조건`은 서류·장비 항목의 `조건`과 같은 성격 — 원문 문구 기반의 사람 서술이며 정규화된 값이 아니다(caveat).

**★보험 상속 규약**: 서류·장비와 **완전히 같다** — 어떤 선박에 필요한 보험 = 루트에서 그 리프까지 경로상 모든 노드의 `보험` 합집합.

### 12.3 커버리지 스캔 — 2중 조건(보험 어휘 × 가입 의무 동사)

- **어휘**: `보험` / `공제` / `보장계약` / `재정보증`
- **의무 동사**: `가입하여야` `가입해야` `가입하거나` `가입할 것` `가입하도록` `가입하게` `가입되어 있어야` `가입한 후` `가입하지 아니하고는` `가입하지 아니한` `체결하여야` `체결해야` `체결할 것` `체결하도록` `체결하지 아니하고는` `체결하지 아니한` `당연가입자` `들어야 한다`
- 계열은 서류 축과 같이 **법률·시행령·시행규칙 + 행정규칙 전부**를 훑는다(장비 축이 고시 중심이었던 것과 다르다 — 보험 가입의무는 대부분 법률·시행령에 있다).

**적응 이력(정직 기록)**: 첫 스캔은 어휘를 `보험|공제`로만 잡았다가 **「유류오염손해배상 보장법」 제14조·제47조(이 주제의 핵심 조문)를 통째로 놓쳤다** — 그 조문들이 "유류오염 손해배상 **보장계약**을 체결하여야 한다"라고만 쓰고 '보험'이라는 단어를 쓰지 않기 때문이다. 어휘에 `보장계약`을 더해 해소했다. 또 「어선원 및 어선 재해보상보험법」 제16조제1항은 *"당연히 …보험가입자(이하 "당연가입자"라 한다)가 된다"* 라 **의무 동사가 아예 없어** 놓쳤고, 동사 목록에 `당연가입자`를 더해 해소했다. **"가입하여야 한다"만 찾으면 이 주제의 가장 중요한 두 법을 놓친다** — 착수 지시가 예시로 준 정규식(`보험에 가입하여야|공제에 가입하여야|보험계약을 체결`)을 그대로 썼다면 둘 다 빠졌을 것이다.

**재현 가능한 반증 그물(recall net)**: 스캔과 별개로, 74법 raw에서 **조문 제목에 `보험|공제|보장계약|재정보증`이 들어간 조 190개를 전수로 뽑아 눈으로 훑었다.** 스캔 후보가 놓친 조문이 없는지 다른 각도로 확인하기 위한 것이고, 이 과정에서 위 두 누락을 찾았다.

### 12.5 보장한도의 세 가지 상태 — 구분해 기록한다

§11.6(장비 수량)과 같은 이유로, 뭉뚱그리면 "얼마인지 모른다"는 사실이 감춰진다.

| `보장한도출처` | 뜻 | 실례 | 건수 |
|---|---|---|---|
| `조문본문` | 한도가 그 조문 안에 문장으로 있다 → `보장한도`에 원문 그대로 | 유·도선법 시행령 제27조②("「자동차손해배상 보장법 시행령」 제3조제1항에 따른 금액 이상") · 유배법 제15조③(책임한도액) · 선원법 제106조②(승선평균임금 이상) | 11 |
| `다른 조문·하위법령 위임(이 조문에는 금액 없음)` | 가입은 명하지만 금액은 다른 조·하위법령이 정한다 → `보장한도`는 반드시 `null`, `위임`에 링크 | 해운법 제4조의3 → 시행규칙 제3조의4 · 유배법 제14조 → 제15조③ | 10 |
| `해당없음(금액 규정 아님)` | 애초에 금액을 정하는 조문이 아니다(가입할 수 있는 보험의 종류만 열거 등) | 해운법 시행규칙 제3조의4 · 해적법 제36조 | 4 |

**주의(사람이 반드시 확인할 것)**: `조문본문`인 11건 중 상당수가 **「자동차손해배상 보장법 시행령」 제3조제1항을 인용**한다. 그 법은 74법 체계 밖이라 **실제 금액(원 단위)은 이 자산에 없다** — 이 트리는 "자배법 시행령 금액 이상"이라는 사실까지만 답할 수 있다. 금액을 답하려면 그 법령을 별도로 확보해야 한다.

또 선원법 제56조②의 `보장한도`("제52조에 따른 임금의 최종 4개월분")는 **금액이 아니라 보장해야 하는 체불임금의 범위**다. 필드 이름과 값의 성격이 달라 항목 `주의`에 그대로 적었다.

### 12.6 전량 재대조(독립 스크립트) — 서류·장비와 같은 방식

빌더가 통과시켰다는 것과 내용이 맞다는 것은 다른 문제다(§6에서 5건, §11.5에서 4종을 실제로 걸러낸 경험). 그래서 **빌더의 조문분리·인용추출 로직을 재사용하지 않는 별도 스크립트**로 보험 항목 전량을 다시 대조한다. 검사 항목:

1. `파일`이 실재하고, 그 파일을 **통짜 문자열**로 읽어 공백 정규화했을 때 `인용`이 부분문자열로 실재하는가.
2. `가입대상`·`보장한도`(null이 아니면)도 같은 방식으로 실재하는가.
3. 1·2가 정말 그 `근거조문` 범위 안에서 나오는가 — 조문 경계를 **줄머리 마커 스캔**으로 따로 구해 확인.
4. `요건유형`·`구분`·`보장한도출처` 값이 규약 집합 안에 있고, `보장한도`와 `보장한도출처`가 모순되지 않는가.
5. `계층`과 파일명이 맞는가(엉뚱한 계층의 파일을 가리키지 않는가). 행정규칙이면 `고시명`·`고시ID`가 `_admrul.json`과 일치하는가.

**⚠이 라운드의 한계(정직 기록)**: 착수 지시가 **커밋 대상을 3개 파일(`vessel_doc_tree.json`·`build_vessel_doc_tree.py`·이 문서)로 못박았으므로**, 위 재대조기는 실제로 작성·실행해 **25건 전량 통과(실패 0건)**를 확인했지만 **저장소에 커밋하지 않았다.** 장비 축의 `loop/verify_vessel_equipment.py`처럼 재현 가능한 자산으로 남기려면 오케스트레이터 승인 후 `loop/verify_vessel_insurance.py`로 추가해야 한다(내용은 위 5개 검사, `verify_vessel_equipment.py`와 같은 구조).

### 12.7 ★회귀 검증 — 기존 서류·장비 무변경이 성공 기준의 절반

§11.7과 완전히 같은 절차를 그대로 반복했다.

- 확장 전 `vessel_doc_tree.json`을 백업 → 확장 후 산출물에서 **`보험`·`보험메모` 키와 새 summary/semantics/caveats/unmapped 항목만 제거**하고 `generated`를 뺀 나머지가 **문자열 단위로 완전히 일치**함을 확인. **결과: 일치.** 서류 56건·장비 78건·노드 13·리프 8·모든 provenance·기존 caveats·unmapped·scan 수치가 한 글자도 바뀌지 않았다.
- 코드 차원의 규율: 기존 함수(`split_articles`·`article_body`·`quote_of`·`doc`·`prov`·`scan_corpus`·`split_articles_admrul`·`quote_of_admrul`·`eq`·`scan_admrul_corpus`·`validate`의 기존 검사)는 **읽기만 하고 수정하지 않았다.** `git diff`가 **삽입 493줄 / 삭제 0줄**임을 확인했다(순수 추가).
- 인용문 추출은 새 함수를 만들지 않고 **`quote_of_admrul()`을 그대로 호출**한다. 보험 조문은 `…보장계약(이하 "보장계약"이라 한다)을 체결하여야 한다` 처럼 괄호가 잦아, 괄호를 모르는 `quote_of()`로 뽑으면 §6에서 실제로 났던 인용 절단이 재현된다. 함수를 고치지 않고 재사용만 했으므로 서류 56건은 영향받지 않는다.

### 12.8 질문·선택지 — 이번에도 새로 만들지 않는다(근거)

보험 축 때문에 트리를 더 쪼개야 하는지 검토했다. 보험 요건을 실제로 가르는 축은 **국제항해 여부**(선원법 유기구제보험)·**총톤수**(유배법 1천톤 초과)·**사업 종류**(해상여객운송/유도선/낚시어선/수상레저)인데, 앞의 둘은 §3.3에서 이미 "트리 레벨로 올리지 않는다"고 결론 낸 직교 축이고, 사업 종류는 **이 트리의 2단계 노드가 이미 그 축**이다(여객선↔해상여객운송사업, 유선·도선↔유·도선사업, 낚시어선↔낚시어선업). 그래서:

- 트리 구조(노드·`질문`·`선택지`·`추가확인`)는 **한 글자도 바꾸지 않았다**(§12.7 회귀검증 대상).
- 리프의 `추가확인`에도 새 축을 더하지 않았다 — 기존 `국제항해`·`총톤수·길이` 축이 보험 항목을 가르는 조건과 그대로 일치하기 때문이다(장비 축이 "항해구역"을 새로 추가해야 했던 것과 다른 점).

### 12.9 유지보수(H-29 연동)

조인 키는 서류 항목과 같다 — `(slug, layer, 조문번호)`. 이번 25건은 전부 법률·시행령·시행규칙 계열이라 §11.10이 지적한 "고시는 키가 하나 부족하다" 문제가 없다. 행정규칙 보험 항목이 나중에 추가되면 그때 §11.10의 `(slug, "행정규칙", 고시명, 조문번호)` 규약을 그대로 쓰면 된다.

## 13. 선박종류 계층 세분화 — 74법 전수 재스캔으로 노드 2개를 더한다 (2026-08-12 추가)

> 착수 배경: 사용자가 *"상선·극지상선 같은 더 세부적인 분류가 있는지"* 물었다. 그 답을 내려면 74법 raw를 다시 훑어 **원문 근거가 있는 선박종류 세분류**가 더 있는지 전수로 확인해야 한다. §11(장비)·§12(보험)이 **같은 트리에 배열을 더한** 확장이었다면, 이번은 **트리 계층 자체를 늘리는** 첫 확장이다. 그래서 §11.7·§12.7이 쓴 회귀검증을 "항목 무변경"에서 **"기존 리프의 상속집합 무변경"**까지 확장했다(§13.6).

### 13.1 채택 기준 — 4개를 모두 만족해야 노드로 세운다

계층은 늘리기는 쉽고 줄이기는 어렵다. 그래서 착수 전에 기준을 먼저 못박고 그 기준으로만 판단했다(카파시 1·4).

|---|---|---|

### 13.2 스캔 방법 — 정의 조문 전수 → 용어 × 의무 문장 교차

1. 74법 raw(법률계열 241 + 고시계열 633 = **874 파일**)에서 **정의 형식 문장**(`"X"이란/이라 함은 …`)을 전수로 뽑아 선박종류 후보 용어를 모았다(215종).
2. 그 용어들을 다시 **의무 문장**(비치·갖추어야·휴대·착용·가입·체결)과 교차시켜, **요건이 실제로 그 용어로 갈리는지**를 건수로 셌다(§13.5 표의 "의무 문장" 열).
3. 건수가 나온 용어만 원문을 열어 §13.1의 4기준으로 판정했다.
4. 노드 출처가 **고시**에 있는 경우가 생겨 `prov_admrul()`을 새로 만들었다 — 기존 `prov()`·`quote_of()`는 한 글자도 고치지 않았다(§11.5·§12.7과 같은 규율).

부모(`fishing_vessel`)의 질문을 *"그 어선으로 낚시 손님을 태우시나요?"*(예/아니오) → *"그 어선을 어떤 일에 쓰시나요?"*(3갈래)로 바꿨다. **자식이 늘면 질문 문장도 함께 바뀌어야 한다** — 이 변경은 회귀검증에서 "예상한 2개 노드에서만 일어났는가"로 확인한다(§13.6).

### 13.6 ★회귀 검증 — 이번엔 "항목 무변경"으로 부족하다

계층이 늘어나면 **항목을 한 글자도 안 바꿔도 리프가 받는 결과가 달라질 수 있다**(상속 경로가 바뀌므로). 그래서 §11.7·§12.7의 검사에 상속집합 대조를 더했다. 확장 전 산출물을 백업해 두고 7가지를 대조한다(`scratchpad/regress.py`, 재현 가능):

| # | 검사 | 결과 |
|---|---|---|
| 1 | 기존 13개 노드의 `서류`·`장비`·`보험` 배열이 **문자열 단위로 동일** | 통과 |
| 2 | 기존 노드의 그 밖 필드(라벨·정의·provenance·추가확인 등) 동일 | 통과 |
| 3 | `질문`·`선택지`가 바뀐 기존 노드가 **예상한 2개(fishing_vessel·cargo_ship)뿐**인가 | 통과 |
| 4 | **기존 리프 8개의 상속집합**(루트→리프 경로 합집합)이 서류·장비·보험 모두 순서까지 동일한가 | 통과 |
| 5 | 항목 총계 56→57 · 80→81 · 25→25 (증가분이 새 노드의 것과 정확히 일치) | 통과 |
| 6 | 기존 `caveats` 원소가 전부 살아 있고(추가만) 기존 `unmapped` 키가 불변인가 | 통과(caveats 23→27, unmapped 신규 키 1) |
| 7 | `scan`·`equipment_scan`·`insurance_scan` 수치 불변 | 통과 |

**규율(다음 라운드도 지킬 것)**: 이번 라운드는 **기존 항목을 다른 노드로 옮기지 않는다.** 옮기는 순간 4번이 무너져 "안 바뀌었다"를 증명할 수 없다. §13.5의 유선/도선·동력수상레저기구 분할이 미채택인 진짜 이유가 이것이며, 그 라운드에서는 **"옮긴 항목의 목록과 옮기기 전/후 리프별 집합 차이"를 명시적으로 승인받는 절차**를 먼저 설계해야 한다.

### 13.8 ★자동검증 2겹을 통과한 뒤 정독·재대조가 잡은 결함 4건 (정직 기록)

## 14. ★"안전검사" 어휘 — D에 넣지 않는다(축 판정)와 `scopeNarrowStep` ⓑ 어휘원 확장 제안 (2026-08-15 추가)

착수 지시: *"'안전검사 안 받으면 어떻게 되나요?'가 D 트리를 못 탄다 — D 항목명에 안전검사 계열 어휘를 원문근거로 보강할지, 아니면 F(검사주기 표)의 축인지 먼저 판정하라"*(HANDOFF 2026-08-15 13:08 KST 착수로그). L-82(축이 다르면 억지로 한 트리에 합치지 말 것)를 그대로 적용해 **판정을 먼저** 했고, 결론은 **D 데이터 무변경**이다.

### 14.1 판정 — "검사 절차·불이행 결과"는 D의 축이 아니라 F의 축이다

세 가지를 **직접 열어** 확인했다(L-80·L-82 "저쪽 소관이라고 적기 전에 저쪽을 열어봐라").

1. **D의 축은 "이 배에 무엇이 실려 있어야 하는가"다.** `caveats`가 스스로 *"raw 원문에 비치·구비 의무가 문장으로 적혀 있는 서류만 담는다"* 라고 못박고 있고, 실제 서류 항목 **57건**은 `비치하여야 한다`·`갖추어 두어야 한다`·`게시하여야 한다` 계열 의무 조문에서 나왔다(조문이 비치를 직접 명령하지 않고 전제만 하는 소수 항목은 그 사실을 항목 `주의`에 적어 두었다 — 예: 어업허가증 사본).
2. **"검사 종류·시기"는 이미 F가 담고 있다.** `inspection_cycle_table.json` 은 검사종류 **50건**·증서 **11건**을 담고 있으며, 그 안에 **"안전검사"가 리터럴로 실재한다** — 「유선 및 도선 사업법」 안전검사 3건(면허·신고 시 / 구조변경·기관교체 시 / 정기), 검사군 "동력수상레저기구 안전검사", 증서 "안전검사증". 즉 이 주제는 **자산이 없어서 못 답하는 것이 아니라 F가 되묻기에 배선돼 있지 않아서** 못 답한다(F 설계 §1 표: 되묻기/서빙 배선 ❌).
3. **D 자신이 이미 이 주제를 F로 넘겨 두었다.** `unmapped.장비_유형_단위` 에 *"정비·유효기간·수압시험 … 축이 다르다(**검사 주기 계층 후보**)"* 가 적혀 있다. 2026-08-10 시점의 판단과 이번 판정이 일치한다.

### 14.3 진짜 원인 — ⓑ 게이트의 **어휘원**이 D 이름 필드로만 좁혀져 있다

`scopeNarrowStep()`의 발화조건 ⓑ는 `vesselHayOf(node)`가 모은 문자열(서류명·장비명·보험명 **뿐**)에 질문 토큰이 있는지를 본다. 질문의 **축(선박 종류)은 유효한데**(아래 ⓒ 실측 참조) 어휘원이 D 전용이라 검사 질문이 문턱을 못 넘는다. `SCOPE_TERM_MIN=3`은 원인이 아니다 — "안전검사"는 4글자이고, D에 그 4글자가 아예 없는 것이 원인이다(`termsOf`는 접두 절단만 하므로 "안전검사"가 "…검사증서"에 걸릴 길도 없다).

**ⓒ(검색 분포)는 이미 통과한다** — 로컬 `search('안전검사 안 받으면 어떻게 되나요?')` 실측: 상위 접전 4법이 수상레저기구등록검사법·수상레저안전법(→수상레저기구 갈래)과 유선및도선사업법·선박안전법(→그 밖의 선박 갈래)으로 **두 갈래에 갈려** `pinned=2, unknown=0`으로 PASS. 즉 **막고 있는 게이트는 ⓑ 하나뿐이다.**

### 14.4 제안(코드 미변경 — 사용자 판단 대기) — ⓑ 어휘원에 F를 더한다

이번 태스크는 데이터·설계까지가 범위라 `legal_retriever.js`는 손대지 않았다. 제안하는 변경은 **`vesselHayOf` 한 함수**다.

```js
// 제안(미구현): D 이름 필드 + F(inspection_cycle_table.json)의 검사 이름
//   - 검사종류[].검사종류               예: "정기검사" "안전검사(면허·신고 시)"
//   - 검사종류[].검사군에서 괄호 제거    예: "동력수상레저기구 안전검사(수상레저기구의…법률)" → "동력수상레저기구 안전검사"
//   - 검사종류[].증서id → 증서[].증서    예: "안전검사증"
//   매핑 키는 F의 `대상_트리노드`(그 노드와 그 자손 id 집합)
```

- **★괄호(법령명)는 반드시 지운다** — 실측으로 확인한 유일한 부작용이다. `검사군` 문자열이 법령명을 통째로 품고 있어서(예: `"동력수상레저기구 안전검사(수상레저기구의 등록 및 검사에 관한 법률)"`) 그대로 넣으면 **검사와 무관한데 법 이름만 겹치는 질문**이 발화한다 — 감사 코퍼스에서 **3건 실측**(*"국제항해선박 해적피해예방법 … 벌칙은 얼마인가요?"* ← `국제항해선박`이 선박보안심사 검사군에, *"안전관리대행업자(해상교통안전법 제53조) … 구상권"* ← `해상교통안전법`이 인증심사 검사군에, *"정선 검사에서 국제톤수확인서만…"* ← `검사에`가 `…등록 및 검사에 관한 법률`에). 괄호를 지우면 3건 모두 사라지고 목표 질문은 그대로 남는다.
- **`대상_트리노드`를 조인 키로 승격하지 않는다.** F의 `semantics`는 그것을 *"근사치 힌트이지 조인 키가 아니다"* 라고 못박았다. 이 제안은 그 힌트를 **"물어볼지 말지"를 정하는 데만** 쓴다 — 답변 내용을 F에서 끌어오는 조인이 아니므로 힌트의 오차가 오답이 되지 않는다(틀려도 결과는 "덜 묻거나 더 묻는다"까지다). **답변 단계에서 F를 쓰려면 그때 별도 설계가 필요하다.**
