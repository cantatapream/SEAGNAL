## 1. 데이터 형태 — 선박종류 트리와 같은 성격의 신규 JSON

`vessel_doc_tree.json`과 같은 이유로 산문 위키가 아니라 **프로그램이 타고 내려가는 JSON**으로 만든다(H-35 `delegation_graph_*.json` 계열). 헤더 규약도 그대로:

```
{ "generated", "scope", "semantics"{}, "caveats"[], "summary"{}, "scan"{}, "unmapped"{}, "별표"{}, "tree"{} }
```

선박종류 트리에 없던 최상위 키가 하나 있다 — **`별표`(별표 레지스트리)**. 왜 필요한지는 §5.3.

## 2. 스키마

### 2.1 노드(공통) — 선박종류 트리와 동일

```jsonc
{
  "id": "navigator_1",                  // 프로그램용 안정 식별자
  "라벨": "1급 항해사",                  // 법률 용어 그대로
  "정의": "…",
  "provenance": [ { "법령","법령_slug","계층","조문","법령ID","파일","인용" } ],   // ★출처 없는 노드 금지
  "질문": "…", "선택지": [ {"label","hint","next"} ],    // ★비-리프에만, 3개 이하
  "자격요건": [ … ],                     // 어느 노드에나 — 경로 상속(§2.4)
  "승무기준": [ … ],                     // 〃
  "추가확인": [ … ],                     // ★리프에만 — 트리로 안 쪼갠 잔여 축
  "children": [ … ]
}
```

### 2.2 `자격요건` 항목

두 가지 출처유형이 있고, **어느 쪽이든 원문 대조로 검증된다.**

```jsonc
// (a) 조문본문형 — 인용문을 조문에서 직접 읽어 채운다
{ "요건": "해기사 시험 합격·승무경력·건강상태·교육훈련 이수 등 면허의 요건",
  "근거법령": "선박직원법", "근거법령_slug": "선박직원법", "계층": "법률",
  "근거조문": "제5조", "법령ID": "…", "파일": "raw/04_선박해운/선박직원법/법률.txt",
  "인용": "해양수산부장관은 다음 각 호의 요건을 갖춘 사람이 …", "출처유형": "조문본문" }

// (b) 별표형 — 별표에서 그 등급의 행 블록을 통째로 verbatim 인용
{ "요건": "1급 항해사 면허를 위한 승무경력",
  "근거법령": "선박직원법", "계층": "시행령", "근거조문": "제5조의2(별표1의3)",
  "별표": "선박직원법_시행령_별표1의3_항해사",     // ★ 최상위 `별표` 레지스트리 키
  "행범위": [[14, 44]],                          // 같은 등급이 여러 행 블록으로 나뉘면 구간이 여러 개다(전자기관사 2행)
  "행_원문": [ "┃1급           │2급 항해사  │연안수역 또는 원양수역을 │선장, 1등 항해사 │1년             ┃", … ],
  "출처유형": "별표(행 블록)" }
```

### 2.3 `승무기준` 항목

```jsonc
{ "구분": "선박직원의 최저승무기준",
  "근거법령": "선박직원법", "계층": "시행령", "근거조문": "제22조제1항(별표3)",
  "별표": "선박직원법_시행령_별표3_1가",          // 레지스트리 키(절 단위)
  "절": "1. 소형선박을 제외한 선박의 갑판부의 승무기준 / 가. 어선 외의 선박",
  "해당행": [ { "줄": 96, "원문": "┃원양수역│200톤 미만  │선장      │3급 항해사 …",
                "앞선_구분행": { "줄": 92, "원문": "…" } },      // 표 안의 행일 때만 붙는다
              { "줄": 592, "원문": "   1. 6급 항해사 이상의 항해사가 소형선박의 …", "표밖": true } ],
  "주의": "표의 병합셀(항행구역·톤수)은 구조화하지 않았다 — §5.4" }
```

### 2.4 ★상속 규약(선박종류 트리와 동일)

**어떤 등급의 자격요건·승무기준 = 루트에서 그 리프까지 경로상 모든 노드의 `자격요건`/`승무기준` 합집합.**
예: "해기사 시험 합격"(선박직원법 제5조)은 해기사 면허 가족 노드에 한 번만 두고 26개 등급 리프가 상속한다.
왜 복제하지 않나 — 법 하나가 개정되면 복제된 N개 리프를 전부 고쳐야 해서 §8의 유지보수 매칭이 무너진다.

## 3. 계층 도출 — 상향식, 임의분류 금지

### 3.1 방법

1. 74법 raw 전수 스캔으로 **"등급으로 구분되는 자격·면허"를 정의한 조문**을 찾는다(§4).
2. 그 조문이 **스스로 열거한 등급만** 노드로 만든다. 없는 등급을 지어내지 않는다.
3. 각 노드의 `provenance`는 그 열거 조문의 **해당 줄 원문**이다(빌드 시 대조, 없으면 빌드 실패).

### 3.2 스캔으로 확인된 등급 체계 6가족 (전부 조문이 스스로 등급을 열거한다)

| 가족 | 근거 조문 | 등급 |
|---|---|---|
| **해기사 면허** | 선박직원법 제4조제2항 | 항해사 1~6급 · 기관사 1~6급 · 전자기관사 · 통신사 1~4급 · 운항사 1~4급 · 수면비행선박 조종사(중형·소형) · 소형선박 조종사 |
| **도선사 면허** | 도선법 제4조제2항 | 1~4급 도선사 |
| **동력수상레저기구 조종면허** | 수상레저안전법 제5조제2항 | 일반조종면허(제1급·제2급) · 요트조종면허 |
| **수상구조사** | 수상에서의 수색·구조 등에 관한 법률 제30조의2제3항 | 지도사 · 1급 · 2급 |
| **선박안전관리사** | 해상교통안전법 제64조제6항 + 시행령 제23조제1항 | 1급 · 2급 · 3급 |
| **해양조사기술자** | 해양조사와 해양정보 활용에 관한 법률 제25조 + 시행령 제11조·별표1 | 특급 · 고급 · 중급 · 초급 |

**상하 순서의 근거**: 선박직원법 제4조제3항("직종별 면허의 상하 등급은 제2항 각 호의 등급별 순서에 따른다")처럼 법이 순서를 스스로 정한 경우만 `상하순서` 필드에 담는다. 정하지 않은 가족은 비워 둔다.

### 3.3 ★선택지 3개 상한 때문에 만든 "묶음 노드"(정직 기록)

`decideClarify()`의 `CLARIFY_OPTION_MAX = 3` 때문에, 자식이 4개 이상인 노드는 그대로 둘 수 없다(선박종류 트리에서 "그 밖의 선박" 4갈래를 3갈래+2갈래로 다시 쪼갠 것과 같은 상황). 이번엔 두 곳에서 발생한다.

1. **가족이 6개** → 루트에서 잔여 묶음(`그 밖의 …`)을 두 번 써서 3갈래씩 내려간다.
2. **항해사·기관사의 등급이 각 6개** → `1급·2급 / 3급·4급 / 5급·6급` 3묶음으로 나눈 뒤 각 묶음이 2개 리프를 갖는다.

이 묶음 노드에는 **`분류근거: "UI 선택지 상한(3개) 때문에 만든 묶음 — 법이 정한 분류가 아니다"`** 를 반드시 붙이고, `caveats`에도 싣는다. **묶음의 라벨에 쓰는 등급명 자체는 전부 법률 용어 그대로**이고, 묶는 순서는 §3.2의 법정 상하 순서를 그대로 따른다(순서를 우리가 재배열하지 않는다).

### 3.4 트리로 쪼개지 **않은** 축

- **한정면허**(상선/어선/특수선박/특정수역/모터보트·동력요트 — 선박직원법 시행령 제4조): 등급과 직교한다. 리프의 `추가확인`으로만 묻는다.
- **전파통신급/전파전자급**(통신사): 등급이 아니라 통신사 면허의 구분이라 `추가확인`으로 둔다.
- **항해전문/기관전문**(운항사): 같은 이유.
- **도선구**(도선법 제4조제2항 "도선구별로"): 등급과 직교.

## 4. 74법 전수 스캔 — 무엇을 어떻게 셌나

선박종류 트리의 3중 조건(동사×명사×장소구)에 대응하는 이번 주제의 조건은 **"등급 신호 × 자격 신호"** 2중 조건이다.

- **등급 신호**: `\d급 (항해사|기관사|통신사|운항사|도선사|선박안전관리사|…)` · `제?\d급 조종면허` · `면허의 등급` · `자격의 등급` · `등급별 자격` · `등급으로 구분` · `특급|고급|중급|초급`
- **자격 신호**: `면허|자격|자격증|해기사|조종사|기술자`
- **제외**: `급수`(물·수도 급수), `승급`, `등급별 과태료` 등 — 스캔 단계에서 배제

스캔 대상은 각 법 raw 디렉토리의 **모든 `.txt`**(법률·시행령·시행규칙 + `행정규칙/` + `별표/`)다. 선박종류 트리 스캔이 `별표/`를 제외했던 것과 달리 **이번엔 별표가 본체**이므로 포함한다(§5).

커버리지 수치(법 수·파일 수·조문 수·후보 수, 후보가 나온 법 목록)는 매 빌드마다 실제로 다시 계산해 `summary`/`scan`에 싣는다. **"정확도"가 아니라 "어디까지 봤는지"를 정직하게 밝히는 자리**다.

## 5. ★별표 결합 방식 (이 과제의 핵심)

### 5.1 왜 별표가 없으면 답이 안 되나

"6급 항해사인데 무슨 배를 탈 수 있나요?"의 답은 **법률·시행령 조문 본문 어디에도 없다.** 선박직원법 제11조 → 시행령 제22조제1항 → **별표3(선박직원의 최저승무기준)** 의 표에만 있다. 면허 요건도 마찬가지로 시행령 제5조의2 → **별표1의3(해기사면허를 위한 승무경력)** 이 실체다. 그래서 별표를 열지 않으면 이 트리의 리프는 껍데기가 된다.

### 5.2 raw에서 별표는 어디에 있나 (L-54·L-55의 연장선)

법률계열(`target=law`)은 별표를 **번호별 파일로 따로** 저장한다: `raw/<법>/별표/시행령_별표3.txt`. 첫 줄이 `[시행령] 별표3 — 제목(제N조 관련)` 형태다.
고시계열(`target=admrul`)은 별표를 본문에 이어 붙인다(L-54). **이번 트리의 별표 근거는 전부 법률계열**이라 번호별 파일만 읽는다 — 고시계열 별표는 이번 범위 밖(caveat).

### 5.3 별표 레지스트리 — 같은 표를 26번 복제하지 않기 위해

별표3 한 절의 표는 100줄이 넘는데, 그 표에 등장하는 등급은 여럿이다. 표 전체를 리프마다 복제하면 JSON이 수 MB로 부풀고 유지보수가 무너진다(§2.4 상속 규약과 같은 이유). 그래서 **최상위 `별표` 레지스트리에 절 단위로 한 번만** 담고, 리프는 키로 참조한다.

```jsonc
"별표": {
  "선박직원법_시행령_별표3_1가": {
    "법령": "선박직원법", "계층": "시행령", "별표": "별표3 — 선박직원의 최저승무기준(제22조제1항관련)",
    "절": "1. 소형선박을 제외한 선박의 갑판부의 승무기준 / 가. 어선 외의 선박",
    "근거조문": "제22조제1항", "파일": "raw/04_선박해운/선박직원법/별표/시행령_별표3.txt",
    "행범위": [7, 183],
    "표_원문": [ "…verbatim 줄…", … ]        // 그 절의 표 전체(줄 끝 공백만 제거)
```

### 5.4 ★표의 병합셀을 구조화하지 **않는다** — 왜 그렇게 정했나(측정 기록)

별표3의 표를 `{항행구역, 총톤수, 선박직원, 승무자격}` 같은 구조 데이터로 푸는 것을 **실제로 시도했고, 세 번 실패했다.**

1. **정규식 분할**(`[┃│]`로 split) → 병합셀 때문에 행마다 칸 수가 달라 열이 어긋난다(`원양수역` 행은 앞 두 칸이 하나로 합쳐져 5칸, 다른 행은 6칸).
2. **표시폭(east-asian width) 기준 열 위치 매핑 + 병합셀 채우기(fill-down)** → 같은 표 안에서도 연안수역 블록과 원양수역 블록의 칸 경계가 1~2칸 어긋나 있어(원문 자체의 정렬 오차) 유령 열이 생겼다.
3. **열별 셀 구간(cell span) 분해** → 부분 가로선(`│  │연안  ├────┼───┤`)이 열마다 다르게 끊겨, 병합셀의 텍스트가 여러 행에 걸쳐 이어질 때 "새 값인지 이어지는 값인지"를 원문만으로는 구별할 수 없다.

3번은 원리적 한계다(표 생성기가 잃어버린 정보를 되살릴 수 없다). **여기서 멈추는 것이 옳다** — 억지로 구조화하면 "3급 항해사가 필요한 배"를 잘못 계산해 사용자에게 틀린 답을 준다. 지어내지 않는 것이 이 자산의 1번 규칙이다(선박종류 트리 §6 "빌드가 통과했다와 내용이 맞다는 다른 문제").

**그래서 채택한 방식**: 표를 **verbatim 그대로** 레지스트리에 담고, 리프에는 그 등급이 등장하는 **행의 원문**과 **바로 위에서 첫 칸이 비어 있지 않은 가장 가까운 행**(`앞선_구분행`, 위치 기반 참고용임을 필드명·`주의`·`caveats`에 명시)을 담는다. 답변 시에는 `표_원문` 전체를 함께 제시해야 한다. 이 한계는 `caveats`의 첫 항목이다.

### 5.5 별표에서 "그 등급의 블록"을 잘라내는 규칙 (등급이 표의 첫 칸인 표)

별표1의3(해기사 승무경력)·별표1의2(수상구조사)·별표7(선박안전관리사)·별표1(해양조사기술자)은 **첫 칸이 등급**이다. 여기서는 행 블록을 이렇게 자른다.

1. 표의 각 줄에서 첫 칸 텍스트(첫 구분자와 두 번째 구분자 사이)를 뽑는다.
2. 첫 칸이 비어 있지 않은데 **바로 윗줄의 첫 칸은 비어 있던** 줄을 블록 시작으로 본다.
3. 블록 시작부터 첫 칸이 이어지는 동안 텍스트를 이어 붙여(`1급`+`항해사` → `1급항해사`) 라벨과 대조한다(공백 무시).
4. 그 등급의 블록 = 시작 줄 ~ 다음 블록 시작 직전(끝에 붙은 빈 줄·가로선만 있는 줄은 뺀다).
5. **매치되는 블록을 전부 담는다.** 첫 매치만 쓰면 같은 등급이 두 행으로 나뉜 표(별표1의3의 전자기관사 — 일반 1행 + 이동식 한정면허 1행)에서 절반을 놓친다(실측으로 확인).

같은 이유로 `cell0`(첫 칸 추출)은 **줄 전체에 가로선이 있는지로 판정하면 안 된다** — 왼쪽은 본문이고 오른쪽만 가로선인 혼합 줄(`┃신사   │신기능사 이  ├─────┤…`)이 실제로 있어서, 그렇게 판정하면 `3급 통`+`신사`가 두 번째 줄에서 끊겨 "3급 통신사 블록 없음"으로 빌드가 실패한다(첫 빌드에서 실제로 발생 → 첫 칸 자리의 가로선만 보도록 수정).

이 규칙은 **찾지 못하면 빌드를 실패시킨다**(SPEC에 적은 등급이 별표에 없다는 뜻이므로 사람이 봐야 한다). 표 자체가 등급을 첫 칸에 두지 않는 절(별표3 등)에는 이 규칙을 쓰지 않고 §5.4의 행 매칭을 쓴다.

## 6. ★비-리프 노드의 `질문`·`선택지`

선박종류 트리 §4의 규칙을 그대로 따른다.

1. 모든 비-리프는 `질문`·`선택지`를 반드시 갖는다(빌드 시 강제).
2. `선택지[].label`은 raw에 실재하는 법률 용어(묶음 노드의 "그 밖의 …"만 예외이고 §3.3에 명시).
3. `선택지[].next`는 그 노드의 자식 id(참조 무결성 검사).
4. `선택지[].hint`는 그 등급/직종의 법정 근거를 한 문장으로 — 정의 조항을 벗어나지 않는다.
5. **선택지 수 = 자식 수, 3개 이하**(`CLARIFY_OPTION_MAX`). 위반 시 빌드 실패.

예시는 §10.

## 7. 완결성·정확성 판정 — 성공 기준

1. **커버리지 수치 공개**: 74법 전부를 스캔했음을 파일 수·조문 수로 밝히고 "등급 체계 발견 N법 / 무관 확인 M법"을 보고한다.
2. **전량 재대조(표본 아님)**: 트리에 들어간 **모든** 인용문·별표 행 원문에 대해, 빌더가 raw를 열어 ①그 조문/별표가 실재하는지 ②그 문구가 실제로 있는지 확인한다. 하나라도 실패하면 **빌드 실패**(JSON을 만들지 않는다).
3. **노드 provenance 검사**: 출처 없는 노드는 빌드 실패.
4. **질문·선택지 무결성**: §6의 5개 규칙을 빌드 시 검사.
5. **별표 인용 무결성**: 레지스트리의 `표_원문` 모든 줄과 리프의 `행_원문`·`해당행` 모든 줄이 그 파일의 실제 줄과 **문자열로 정확히 일치**해야 한다.
6. **독립 재대조**: 빌더의 파싱 로직을 **재사용하지 않는** 별도 스크립트(`--verify`)로 전량을 다시 대조한다. 선박종류 트리에서 "빌드 통과 ≠ 내용 정확"을 5건 실측한 경험 때문에 이 이중 검증은 생략하지 않는다.
7. **재현성**: 스크립트 1회 실행으로 재현된다.

실측 결과는 §11에 기록한다.

## 8. 유지보수 통합 설계 (H-29 연동 — **설계만**)

선박종류 트리 §8과 **완전히 같은 인터페이스**를 쓴다 — 이것이 그 설계가 말한 *"새 트리도 `{근거법령, 계층, 근거조문}` provenance만 갖추면 `flag_*.py`를 파일명만 바꿔 재사용한다"* 의 첫 검증 사례다.

- 조인 키: `(slug, layer, 조문번호)`. `law_change_queue.json`의 `changed_articles[]`와 같은 축.
- **별표는 조인 키가 하나 부족하다** — 별표 근거의 `근거조문`은 `제22조제1항(별표3)` 형태라 조문번호만으로는 "그 별표가 바뀌었는지"를 못 가린다. H-29 큐가 별표 단위 변동을 주지 않으므로, **위임 조문(제22조)이 개정되면 그 조문을 근거로 하는 별표 항목 전부를 재검토 대상으로 플래그**하는 보수적 매칭을 쓴다(놓치는 것보다 과검출이 낫다).
- 트리 파일을 직접 고치지 않고 사이드카(`qualification_tree_review.json`)에 플래그만 남긴다. 자동 재빌드하지 않는다(개정으로 앵커 검증이 실패하는 것은 "사람이 봐야 한다"는 정상 신호다).
- `법령ID`를 처음부터 provenance에 싣는다(H-29 11항·L-74).

## 9. 되묻기(`decideClarify`) 연동 설계 (**설계만**)

선박종류 트리 §9의 3함수 규약을 그대로 재사용한다. 트리 파일만 다르다.

```js
matchQualTreeTopic(query)      // "면허/자격/급/해기사/조종면허…" 키워드로 이 트리 주제인지 판정(LLM 0회)
clarifyFromTree(node)          // 노드의 질문·선택지를 기존 decideClarify()와 동일 스키마로 반환
resolveQualTreePath(query,tree)// CLARIFY_JOINER(' — ')로 누적된 라벨을 노드 라벨과 대조해 현재 위치 복원
```

- **반환 스키마를 기존과 동일하게 유지**하면 `routes/legal.js`·`ai_chat.js` 무변경(카파시 3).
- **라운드 상한**: H-36 미결①이 사용자 확정으로 정리됨 — *트리 기반 경로는 깊이가 데이터로 유한하므로 인위적 라운드 캡을 두지 않는다.* 이 트리는 최대 4단(루트→가족→직종→등급묶음→등급)이라 그 결정이 그대로 적용된다.
- **라벨 문자열이 계약이다**: `resolveQualTreePath`가 `' — '` 뒤 문자열을 노드 라벨과 대조하므로, 라벨을 바꾸면 진행 중 대화가 깨진다. 라벨은 법률 용어 그대로 고정한다.
- **답변 조립 시 주의**: 별표 근거 항목은 §5.4 때문에 **행만 보여주면 오해를 부른다.** 반드시 `별표` 레지스트리의 `표_원문`(또는 raw 링크)을 함께 제시하도록 답변 템플릿에 못 박는다. 이건 연동 시 지켜야 할 계약이지 선택이 아니다.
- 트리 답변(raw 직인용)과 `answerCanonicalOnly` 정책의 관계는 선박종류 트리와 같은 미결(H-36 미결②)로 남는다.

3. 수상구조사의 업무수행 범위를 **등급 토큰 문자열 매칭**으로 뽑았더니, 표가 등급명을 `나. 수상구조사`+`1급` 두 줄로 쪼개 적어 **1급의 진짜 업무 행을 놓치고 지도사 행의 "…1급·2급의 업무"만 잡혔다** → 그 표는 등급이 첫 칸이므로 블록 방식(`duty_annex_block`)으로 교체.
4. **전파전자급 통신사의 승무기준이 통째로 비어 있었다** — 별표3 제3호는 제목부터 "통신급(**전파통신급에 한정한다**)의 승무기준"이라 전파전자급은 **별표3의2**(시행령 제22조의2제1항)에 따로 있다. 처음엔 별표3만 보고 4급 통신사의 승무기준을 0건으로 두고 "확인되지 않았다"는 메모를 달 뻔했다 — 그 메모는 사실이 아니었다. `별표3의2`를 추가해 해소.
5. 비고(표 밖) 줄에서 등급이 언급된 4건에 `앞선_구분행`(표 안 위치 참고값)이 붙어 오해를 부를 수 있어, 표 밖 줄에는 붙이지 않고 `표밖: true`로 표시하도록 변경.

다섯 다 "빌드는 통과했지만 내용이 반쪽"인 유형이라, 선박종류 트리 §6이 남긴 *"빌드가 통과했다와 내용이 맞다는 다른 문제"* 가 이번에도 그대로 재현됐다.
