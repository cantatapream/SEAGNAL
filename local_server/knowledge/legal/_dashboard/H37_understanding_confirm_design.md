### 1-B. 추가 확정 (2026-08-11, 초판 설계의 미결 ③④⑥을 해소한 대화)

**(자) 프로필 확인은 "조건별 개별 확인" — 일괄 스킵 금지** *(초판 미결③ 종결)*
> (오케스트레이터: "프로필로 '네' 하면 관련 없는 다른 질문까지 같이 건너뛰는 지금 방식, 이대로 갈까요?")
> **"3번은 따로 확인해야해"**
> **"내 말은 '①②를 따로따로 확인하게 나눌지 정해주셔야 해요.' 관련 따로해야한다고"**

→ 답이 여러 조건(예: 톤수 + 해상/내수면)에 갈리고 프로필이 그중 **일부만** 채우고 있으면, **그 일부 조건만** 프로필로 확인하고 **나머지는 평소처럼 별도로 되묻는다.** 한 번의 "네"가 그 질문의 모든 미확정 조건을 한꺼번에 확정시켜서는 안 된다. → §7.4 재설계.

**(차) 프로필-되묻기 연동은 트리 되묻기와 일반(위키) 되묻기 **양쪽 다** 처음부터 구현** *(초판 미결④ 종결)*
> **"처음부터 같이 넣고 테스트 하자."**

→ `decideClarify()` 경로와 `zoneTreeStep()` 트리 경로에 **동시에** 후처리를 건다. → §7.5.

**(카) 상황질문 발화 판정은 "검색 후"로 확정** *(초판 미결⑥ 종결 — R2 채택)*
사용자에게 제시해 승인받은 구체 시나리오("구명조끼 몇 개?" → 검색 결과가 여러 선박종류에 걸침을 확인한 뒤 "어떤 배를 타고 계신가요?"를 묻는다)를 그대로 §5.6에 박아 둔다.

**(타) 고시 확장 후 답변 폭증·면책문구 거짓(L-81)은 근본 해법으로**
> **"발견 2 관련 근본적 해결될 수 있도록 설계해야할것같은데?"**

→ 단순 "상위 N건 + 더보기"가 아니라, **사용자가 실제로 입력한 질문 키워드로 그 리프의 적용항목을 한 번 더 걸러 관련도 높은 것부터** 보여준다. 면책 문구도 하드코딩을 걷어내고 **자산의 실제 커버리지에서 뽑아 쓴다**(L-81 교훈 ③). → §13, **다음 구현 1순위**.

### 2.1 ★이 설계가 반드시 피해야 하는 함정 (실측된 사실)

1. **질의 문자열에 아무거나 덧붙이면 세 군데가 동시에 오염된다.**
   - `decideClarify` 라운드 카운트(`:703`) — 새 조각에 `' — '`가 섞이면 그대로 세어진다.
   - `matchZoneTreeTopic` 의 `q0`(`:1427`) — `' — '` **앞**에 덧붙은 것은 전부 원 질문 취급이다. 예컨대 `… 어선` 한 낱말만 붙어도 `ZONE_FISHING_HINT`가 걸려 `navigation_zone` → `fishing_operation_area`로 트리가 바뀐다(`:1437`).
   - `resolveZoneTreePath` 의 `rest`(`:1476`) — 암시하강·백스톱 판정 대상이라 라벨 낱말이 섞이면 리프로 잘못 내려가거나(L-77 결함①) 정상 되묻기가 죽는다.
   → **적대검증 §3.3이 이미 "AI가 붙인 라벨이 `rest`에 들어가 트리 판단에 영향을 준다"를 경미 결함으로 잡아 뒀다.** 새 단계가 조각을 더 붙이면 그 경미 결함이 상시화된다.
2. **라운드 예산은 지금도 공유된다**(적대검증 §3.2, 우선순위 2). `CLARIFY_MAX_ROUNDS`는 "누가 붙였든 구분자 개수"를 센다. 트리가 3라운드를 쓰면 AI에 1라운드만 남는다. 새 단계가 여기에 얹히면 **AI 되묻기가 조용히 0라운드가 된다.**
3. **질의 문자열은 서버에 흔적을 남긴다.** `routes/legal.js:899 logKnowledgeCandidate(q, raw)`(파일 append)와 `:922 pendingAnswers.store(q, …)`(푸시용 임시보관)가 **질의 원문을 저장**한다. 프로필을 질의에 섞으면 "서버 미저장" 원칙이 그 자리에서 깨진다.

## 3. 확정 설계 — 맥락은 질의 문자열이 아니라 **별도 필드**로 나른다

### 3.1 왜 별도 필드인가 (대안 비교, 카파시 1)

| 안 | 방식 | 판정 |
|---|---|---|
| A. `CLARIFY_JOINER` 재사용 | ` — 어선` 으로 덧붙임 | **탈락.** 라운드 카운트에 그대로 잡힌다(사용자 확정 (다) 위반) |
| B. 새 구분자를 질의 뒤에 덧붙임 | ` ‖ 어선` 등 | **탈락.** §2.1-1의 `q0`·`rest` 오염을 못 피한다. 조각 순서(클라리파이 체인과 ctx 체인이 각각 자란다)까지 관리해야 해 규약이 두 벌이 된다 |
| C. 새 구분자를 붙이되 게이트에서 떼어냄 | 파싱 후 `q`를 복원 | 동작은 가능하나 **파싱이 계약**이 된다 — 사용자가 그 문자를 타이핑하면 깨진다. B의 위험을 코드로 덮는 구조 |
| **D. 요청 바디의 별도 필드** | `{query, ctx, profile}` | **채택.** `query`가 오늘과 **바이트 동일**이라 §2.1의 세 오염이 원리적으로 발생하지 않는다. 프로필이 로그·임시보관에 안 섞인다. 되돌리기는 필드를 안 보내면 끝 |

> **사용자 확정 (다)를 코드로 만족시키는 방식**: "다른 구분표시를 쓰라"는 지시의 목적은 *기존 라운드 카운트 정규식이 이 단계 조각을 세지 않게 하는 것*이다. D안은 조각을 질의에 넣지 않으므로 `query.split(CLARIFY_JOINER).length-1`이 **정의상** 변하지 않는다 — 구분자 선택 문제 자체가 사라진다. 목적을 더 강하게 달성하므로 D를 택했고, 이 판단 근거를 여기 남긴다.

## 4. ② 이해확인 단계 (understandConfirmStep)

### 4.1 무엇을 하나

`understandConfirmStep(q, uc)` — LLM 1회(짧은 판단 호출), `search()`보다 **앞**이라 근거자료를 안 본다.

```
if (!config.understandConfirm)        return null;   // 스위치 off
if (uc.state === 'confirmed')         return null;   // 이미 "네"를 받음
if (uc.rounds >= UNDERSTAND_MAX_ROUNDS /*3*/) return { assumed: true };   // 백스톱(§4.4)
if (!gemini.hasAnyKey())              return null;   // 키 없음 = 그냥 통과(fail-open)

판정 호출 → {clear:true}  → null (기존 흐름 그대로)
           {clear:false, restate:"…"} → 확인 되묻기
```

되묻기 응답(사용자 확정 (나)의 화법 그대로):

```
answer  : "제가 이해한 게 맞는지 먼저 확인할게요."
clarify.question : "저는 「<재진술>」로 이해했는데, 맞나요?"
clarify.options  : [ {label:"네, 맞아요"}, {label:"아니요, 다시 설명할게요"} ]
note    : "질문을 확인하고 있어요"        ← UI 상태 표시(등급 아님, §8에서 유지 대상)
ctxNext : { uc:{ rounds:<현재+0>, state:'none' } }
confirmKind : "understand"
```

- **원 질문을 그대로 되풀이하지 않는다**(사용자 확정 (나)). 재진술은 AI가 자기 말로 바꾼 문장이어야 한다.
- 선택지 2개는 `CLARIFY_OPTION_MAX = 3` 이내라 기존 렌더러 그대로 쓴다.

### 4.2 판정 프롬프트 규약 (환각 0)

`decideClarify`와 같은 "짧고 빠른 판단 호출" 패턴을 따른다: `thinkingBudget: 0`, `responseMimeType: 'application/json'`, `temperature: 0.1`, `timeout 12000`(2026-08-14 정정: 8000은 Gemini API 최소 deadline 10초 미만이라 매 호출 400 거부 — H-37 F3 근본원인).

```
너는 대한민국 해양수산 법령 챗봇의 "질문 이해 판정기"다. 질문에 **답하지 마라.**
[질문] "…"
판단 기준
1. 이 문장이 무엇을 묻는지 한 가지 뜻으로 읽히면 clear:true.
2. 주어(누가)·대상(무엇을)·행위 중 하나가 빠져 뜻이 둘 이상으로 갈리면 clear:false.
3. ★재진술(restate)에는 법령·조문·수치·결론을 **절대 넣지 마라.** 질문의 뜻만 바꿔 말한다.
   (근거자료를 아직 읽지 않은 단계다 — 여기서 법 이야기를 하면 그게 곧 환각이다)
4. 기준2에 걸렸을 때만 이 기준을 본다(순서가 중요하다).
   - 한 문장으로 다시 말해 뜻을 하나로 좁힐 수 있으면 clear:false — 그 문장을 restate 에 담아 확인한다.
   - 다시 말해 봐도 뜻이 둘 이상 남아 무엇을 물었는지 고를 수 없으면 clear:true — 확인해도 얻을 게 없다.
   "애매하니까 일단 clear:true"가 아니다(애매한지는 기준2가 이미 판정했다).
{"clear":true} 또는 {"clear":false,"restate":"…(60자 이내, 존댓말 아님·평서문)"}
```

> **★2026-08-14 수정(적대검증 F3)** — 초판의 기준4는 *"애매하면 clear:true 로 물러나라"* 한 줄이었다(옛 문구 원문은 커밋 `d054a45ed`. 회귀 테스트 T24가 그 문자열의 부재로 수정 여부를 판정하므로 이 문서에도 그대로 옮겨 적지 않는다).
> 이 문장은 기준2(*"뜻이 둘 이상으로 갈리면 clear:false"*)와 **문자 그대로 상충**한다 — 기준2가 잡아내는
> 상황이 곧 "애매한" 상황이라, 모델이 기준4를 우선 적용하면 이 단계는 **원리적으로 아무것도 안 하게 된다.**
> 프로덕션 실키 검증에서 이해확인이 **0/2 발동**한 것이 이 설계 결함으로 설명된다. 위 문구는 두 기준의
> **순서와 판정축**(재진술로 뜻이 하나로 정해지는가)을 명시해 상충을 없앤 것이다.

**서버측 후검사(프롬프트만 믿지 않는다 — `decideClarify:750`의 hint 대조와 같은 취지)**:
`restate`에 `제\d+조`·`법률`·`벌금`·`과태료`·`징역`·`「…」` 토큰이 하나라도 있으면 그 판정을 **버리고 `null`**(= 확인 안 함). 법 이야기를 시작한 재진술은 이 단계의 것이 아니다.

### 4.3 "네" / "아니요" 처리

| 사용자 선택 | 클라이언트 | 서버가 받는 것 | 서버 동작 |
|---|---|---|---|
| **네, 맞아요** | `query` 그대로, `ctx.uc = {rounds:n, state:'confirmed'}` | 같은 `q` | ①을 건너뛰고 ②부터 평소대로. **답이 결정론적으로 재현된다**(같은 q → 같은 흐름) |
| **아니요, 다시 설명할게요** | 입력창 포커스 + 안내문("어떤 상황인지 조금 더 구체적으로 적어주세요"). 사용자가 새로 입력한 문장이 **새 `query`**. `ctx.uc = {rounds:n+1, state:'none'}` | 새 `q` | ①을 다시 판정. `rounds`가 3에 닿으면 §4.4 |

### 4.4 3회 백스톱 (사용자 확정 (라))

`UNDERSTAND_MAX_ROUNDS = 3`. `uc.rounds >= 3`이면 **판정 호출 자체를 하지 않고**(비용·지연 0) `assumed` 상태로 통과한다 — `decideClarify:704`의 `rounds >= CLARIFY_MAX_ROUNDS` 조기 반환과 완전히 같은 결정론적 장치다.

그리고 최종 답변 **첫 줄**에 서버가 직접 아래 문장을 붙인다.

> **확정 문구(고정, 변형 금지)**
> `질문을 정확히 이해하지 못한 채 제가 추정해서 답변드려요 — 아래 내용이 물으신 것과 다르면 다시 말씀해 주세요.`

- **프롬프트로 시키지 않는다.** 모델이 지시를 어길 수 있다(라이브에서 `decideClarify` 기준3이 뚫린 전례, `legal_retriever.js:757` 주석). 서버가 문자열로 붙인다.
- **스트리밍과의 정합**: `synthesizeAnswerStream` 첫 chunk보다 **먼저** `{type:'delta', text:<고지문+'\n\n'>}` 한 줄을 쓰고, `full` 누적값에도 같은 문자열을 선행 포함시켜 `done.answer`와 화면이 어긋나지 않게 한다(`routes/legal.js:848-853` 루프 앞).
- **2차 조회 경로(`:891 raw && raw.answer`)에도 붙인다** — 그 경로는 `delta` 없이 `done.answer` 한 줄로 나가므로 문자열 앞에 붙이면 끝이다.
- 이 문장은 **신뢰등급이 아니라 그 답변 한 건의 조건 고지**다. §8에서 지우는 대상이 아니다.

### 4.5 정직한 비용 기록 (숨기지 않는다)

이 단계는 **모든 질문에 Gemini 호출 1회를 더한다.** H-31 실측에서 답변 지연은 사실상 Gemini 호출 하나에서 나왔다 — 즉 이 기능은 체감 지연을 늘린다. R0(회귀 0)이 성립하는 것은 **스위치가 off일 때뿐**이다. 대안 2개를 적어 두되 **이번 설계에서는 채택하지 않는다**(요청받지 않은 최적화를 미리 넣지 않는다, 카파시 2):

- (대안1) `search()`와 **병렬 실행** 후 판정이 `clear:false`면 검색 결과를 버린다 → 직렬 지연은 사라지지만 `expandQueryTerms`(Gemini, 10s) 호출이 버려질 수 있다.
- (대안2) 결정론적 사전컷(길이·구체 명사 수)으로 명백히 구체적인 질의는 LLM 없이 통과 → 규칙을 새로 지어내야 해서 이 단계의 판단 근거가 흐려진다.

## 5. ③ 상황질문 — 범위좁히기 (scopeNarrowStep)

### 5.1 원칙 — 법 이름을 묻지 않는다

사용자 확정 (마) 그대로다. **묻는 것은 사용자가 아는 상황**(어떤 배를 타는가)이고, 그 답으로 **어느 법을 볼지는 서버가 정한다.** 기존 되묻기·트리가 이미 쓰는 방식을 질문 맨 앞단까지 확장하는 것이고, **새 UI 타입을 만들지 않는다** — `clarify` 스키마 + `clarifyHTML` 버튼 그대로다.

### 5.2 선택지는 어디서 오나 (2안, 판단과 근거)

| 안 | 선택지 출처 | 판정 |
|---|---|---|
| **S1(채택)** | 기존 계층자산의 **분기 노드 데이터** — `vessel_doc_tree.json` 루트 `질문:"어떤 배에 관한 것인가요?"` / `선택지:[어선(어선법 제2조제1호) · 수상레저기구(수상레저안전법 제2조제3호) · 그 밖의 선박(선박법 제1조의2제1항)]`, 다음 단계는 그 자식 노드 | **LLM 0회 · provenance 있음 · 매번 같은 문구.** H-36이 11종 자산에 `질문`+`선택지`를 미리 심어 둔 이유가 정확히 이것이다(H-36 설계 4항) |
| S2 | AI가 질문을 보고 즉석 생성 | 유연하지만 문구가 매번 달라지고, 근거 없는 구분을 지어낼 수 있다(`decideClarify`의 알려진 약점). **탈락** |

> ⚠**정직 기록 — 설계가 사용자 예시를 그대로 못 준다**: 사용자가 든 예시 `어선 / 상선 / 극지상선`, `낚시어선 / 일반어선`은 **현재 자산에 그 라벨이 없다.** `vessel_doc_tree.json` 루트는 `어선 / 수상레저기구 / 그 밖의 선박`이고, 극지 항해·상선 구분은 별도 축이다. 라벨을 이 설계가 지어내면 그게 곧 환각이므로 **자산이 가진 라벨만 쓴다.** 사용자 예시대로 물으려면 자산(`vessel_doc_tree.json`) 확장이 필요하고, 그건 별도 라운드다 → §10 미결 ②.

### 5.3 언제 발화하나 — **R2(검색 후) 확정** (사용자 확정 (카), 2026-08-11)

초판은 R1/R2 두 안을 제시하고 사용자 확인을 기다렸다. **사용자가 R2 시나리오를 보고 승인해 확정됐다** — 발화 판정은 `search()` **뒤**에서 검색 결과의 분포를 보고 한다(§5.6에 승인받은 시나리오 원문). R1은 채택하지 않는다.

| 안 | 판정 방법 | 장단 |
|---|---|---|
| **R2(확정)** | `search()` 결과의 **분포**로 판정: 상위 K건이 서로 다른 법 **N개 이상**에 걸치고, 1위 대비 점수차가 **X% 이내**로 접전이며, 자산 루트의 선택지가 그 법들을 실제로 **갈라놓을 수 있을 때**(각 선택지에 매핑된 법 집합이 서로 겹치지 않을 때)만 발화 | 결정론적·측정 가능·환각 0. "구멍탐지류는 AI보다 로직 우선"(CLAUDE.md 결정로그)과 같은 성격. **화면상으로는 여전히 "맨 앞에서 상황을 묻는" 동작**이고 사용자에게 법 이름을 절대 보여주지 않는다 |
| R1(미채택) | 검색 전에 질문 문장만 보고 판정(키워드 또는 AI 1회) | "질문 맨 앞단"이라는 표현에 문자 그대로 부합하나, 근거 없이 판정해야 해 `matchZoneTreeTopic`이 겪은 오탐 문제(H-36 §1.1: 부분문자열 충돌 1,555건)를 다시 만든다 |

**R2가 "맨 앞단"을 어기지 않는 이유**: 검색은 **후보를 모으는 내부 계산**일 뿐 사용자에게 아무것도 보여주지 않는다. 사용자가 보는 첫 화면은 여전히 **상황을 묻는 질문 하나**이고, 법 이름은 끝까지 노출되지 않는다. 즉 "맨 앞단에서 상황을 묻는다"는 요구는 그대로 지켜지고, 검색은 *그 질문을 물을 자격이 있는지*를 근거 있게 판정하는 데만 쓰인다.

**임계값**: K·N·X는 구현 착수 시 `_dashboard/audit/*.md`에서 뽑은 질문 코퍼스(적대검증이 쓴 132,306건)로 **실측해 정한다** — 지금 숫자를 지어내지 않는다. 발화율 목표는 H-36 게이트와 같은 기준으로 잡는다: **오탐이 나도 "되묻기 한 번"에서 멈추고, 사용자가 안 고르면 그대로 끝난다.**

### 5.4 깊이와 라운드

- 깊이는 **자산 트리의 깊이**가 상한이다(데이터로 유한 → 무한루프 원리적 불가). H-36 미결① 사용자 확정("트리 기반 경로는 한계를 두지 말자")을 그대로 승계한다. 인위적 라운드 캡을 **넣지 않는다** — "없으면 뭐가 잘못되나"를 한 문장으로 못 쓰는 상한은 넣지 않는다(CLAUDE.md 결정로그).
- 다만 `ctx.scope` 배열 길이는 **자산 트리 최대 깊이**(현재 `vessel_doc_tree.json` 기준 3)를 넘으면 서버가 그 요청의 scope를 무시하고 기존 흐름으로 간다(변조·재생 방어). 이건 상한이 아니라 **데이터 정합성 검사**다.
- **`CLARIFY_MAX_ROUNDS`(=4)는 건드리지 않는다.** `ctx.scope`는 `query`에 없으므로 `:703`의 계산에 애초에 잡히지 않는다(§3.1 D안의 직접 귀결).

### 5.5 고른 답이 검색에 반영되는 경로

```
qForSearch = ctx.scope.length ? (q + ' ' + ctx.scope.map(s => s.label).join(' ')) : q
search(qForSearch, {canonicalOnly})     ← 시그니처 무변경(기존 함수 안 건드림)
decideClarify(q, contextPages)          ← ★원 질문 q 를 넘긴다(라벨을 섞지 않는다)
synthesizeAnswerStream(q, contextPages) ← ★원 질문 q
```

- `scope`가 비면 `qForSearch === q` → **R0 성립**.
- `decideClarify`·`synthesize`에 라벨을 안 섞는 이유: 섞으면 `:703` 라운드 계산은 안 변해도(구분자가 없으니) **답변 프롬프트에 사용자가 안 쓴 낱말이 들어간다.** 답변 문장과 `filterSourcesByAnswer`(`:860`)의 교차확인 기준이 흔들린다. 상황 정보는 **검색 후보를 고르는 데만** 쓰고, 답변은 원 질문에 답한다.

### 5.6 ★사용자가 승인한 구체 시나리오 (그대로 박아 둔다)

아래는 사용자에게 제시해 **"검색 후"로 확정받은 그 흐름**이다. 구현·검증 시 이 시나리오를 그대로 재현 테스트로 만든다.

```
[사용자]  구명조끼 몇 개 필요해요?

  ── 서버 내부(화면에 안 보임) ─────────────────────────────
  ① 이해확인      : 뜻이 한 가지로 읽힌다 → clear:true, 통과
  ② zoneTreeStep : ZONE_ASK(구역을 묻는 어미구)가 없다 → null
  ③ search()      : 상위 후보가 어선법·수상레저안전법·유선및도선사업법·
                    선박안전법 … 여러 선박종류 계열에 걸치고 점수가 접전
  ④ scopeNarrow  : "이 질문은 선박종류 축에서 갈린다"고 판정
                    → vessel_doc_tree.json 루트 노드의 질문·선택지를 그대로 꺼낸다
  ──────────────────────────────────────────────────────────

[나리야]  배 종류에 따라 갖춰야 할 수량이 달라져서, 하나만 여쭤볼게요.
          어떤 배에 관한 것인가요?
          [ 어선 ]  [ 수상레저기구 ]  [ 그 밖의 선박 ]

[사용자]  (어선 클릭)
          ※ query 는 "구명조끼 몇 개 필요해요?" 그대로. ctx.scope 에만 {vessel_kind:'어선'} 이 쌓인다

[나리야]  (어선 계열로 좁혀진 근거로 답변, 또는 자산에 다음 갈림길이 있으면 한 번 더)
```

**이 시나리오가 보증하는 것**
- 사용자에게 **법 이름을 한 번도 보여주지 않는다**(사용자 확정 (마): "법 영역은 물어보는 사람도 모르는 내용이잖아").
- 선택지 문구는 `vessel_doc_tree.json` 루트의 `질문`·`선택지[].label` **원본 그대로**다 — 매번 같고, 각 라벨에 근거 조문(어선법 제2조제1호 / 수상레저안전법 제2조제3호 / 선박법 제1조의2제1항)이 붙어 있다.
- 사용자가 아무 버튼도 안 누르면 **거기서 끝난다**(H-36 게이트와 같은 안전 성질).

⚠ 초판 §5.2의 정직기록은 그대로 유효하다 — 사용자가 예로 든 `상선 / 극지상선`, `낚시어선 / 일반어선`은 현재 자산에 없어 이 시나리오도 자산이 가진 3개 라벨로 그렸다(§11 미결②).

## 6. 기존 해역트리 키워드 게이트와의 관계 — 이번엔 걷어내지 않는다

### 6.1 지금 게이트가 하는 일

`matchZoneTreeTopic(:1426)`은 ①`ZONE_ASK`(구역 축을 묻는 어미구) ②`ZONE_SUBJECT`(배·조업 어휘) **2중 조건**을 통과해야 트리로 들어간다. 실측 발화율: 설계 시 43,956건 중 6건, 적대검증 재측정 132,306건 중 6건(0.0045%), 그중 오탐 4~5건. 전부 되묻기에서 멈춘다.

### 6.2 새 단계가 이 일을 흡수한다(개념상)

③ 상황질문은 "이 질문이 어느 주제/축에 속하는가"를 **사용자에게 물어서** 정한다. 키워드 게이트가 문장에서 추측하던 것을 사용자 응답으로 대체하는 것이므로, 성숙하면 게이트는 불필요해진다.

### 6.3 그래도 이번에 안 걷어내는 이유 + 마이그레이션 경로

**이유**: 해역트리 경로는 라이브에서 3단 검증 + 적대검증 + 회귀 스위트 36건(`local_server/scripts/test_zone_tree_wiring.js`)으로 굳어 있다. 새 단계가 프로덕션에서 안정화되기 전에 이걸 걷어내면 **검증된 경로를 미검증 경로로 바꾸는 것**이다.

**경로(이번 태스크에서는 구현·제거 금지)**:

| 단계 | 할 일 | 완료 판정 |
|---|---|---|
| M0 | 이번 설계 구현 + `scopeNarrow` off로 배포 | R0 회귀 0(§9-1) |
| M1 | `scopeNarrow` on. **③을 ②보다 뒤에 둔 채로** 관찰 | 트리 발화 건수·리프 도달률이 이전과 동일. 스위트 36건 유지 통과 |
| M2 | 계측: 실사용 질의 중 "트리가 발화한 것"과 "③이 발화한 것"의 교집합·차집합을 로그(질의 원문 아닌 **분류 결과만**) | ③이 트리 발화 6건을 전부 커버함을 수치로 확인 |
| M3 | ③을 ②보다 **앞**으로 옮긴다(한 줄 이동). 트리는 여전히 남아 `null`일 때만 뒤에서 받는다 | 스위트 36건 재통과 + 배선 전/후 응답 대조 |
| M4 | 그때 비로소 `matchZoneTreeTopic`의 키워드 조건을 걷어낸다(트리 자체와 `resolveZoneTreePath`는 그대로 — 게이트만 교체) | 리프 14개 전수 도달 유지(L-77 성공기준) |

**M4 전까지 `matchZoneTreeTopic`·`zoneWordHit`·`ZONE_ASK`·`ZONE_SUBJECT`는 한 줄도 건드리지 않는다.**

## 7. ④⑤ 온디바이스 프로필

### 7.1 저장 (클라이언트)

- 키: `localStorage['nariya_profile_v1']`. 기존 `nariya_history_v1`(대화기록)·`LS_DEVICE_ID`와 같은 원칙(`_CHATBOT.md` §0-A "대화 이력").
- 구조: `{ version:1, fields:{ <필드>:{v, at} }, freeText:{v, at} }` — **필드마다 `at`(저장/수정 시각, ISO+09:00)** 을 둔다. 문서 단위 타임스탬프로는 ⑤의 신선도 표시를 필드별로 못 만든다(사용자 확정 (아)).
- 필드는 **`_CHATBOT.md` §1의 기존 프로필 필드를 그대로 쓴다**(새 어휘를 만들지 않는다):
  `직군` · `선박용도`(낚시어선/어선/레저/일반) · `톤수` · `길이` · `어업종류` · `면허·자격` · `주 조업구역` · `야간조업` · `관심분야`(자유 텍스트).
- 사용자 확정 (바)의 "선종·톤수·길이·업종"은 위 필드에 1:1 대응한다(선종=선박용도, 업종=어업종류). `길이`만 신규 추가 — `tonnage_facet.json`이 이미 길이 임계값(선박안전법 12m 등)을 갖고 있어 쓰임이 있다.

### 7.2 UI (사용자 확정 (바) 그대로)

- 채팅 헤더(`ai_chat.js:1163-1171`, 지금 `‹ / 🕘 / ×` 3개)에 **설정 버튼 `⚙` 1개 추가** → 패널 안에 **"나에 대해서 설명하기"** 버튼.
- 흐름: **대분류 → 하위 계층 → …** 전부 버튼. 예: `어업인 / 비어업인 / 해양종사자 / 공무원 / 그 밖` → (어업인) `어선 / 낚시어선 / 양식 / 그 밖` → `톤수 구간` → `길이 구간` → `업종` → **마지막에만 자유 텍스트(관심분야)**.
- **버튼 라벨의 출처**: 톤수·길이 구간은 `tonnage_facet.json`(H-36 E, facet154·구간선택지354)에서 그대로 꺼낸다 — 지어내지 않는다. 직군 대분류는 사용자 확정 (바)의 낱말을 그대로 쓴다.
  ⚠ `tonnage_facet.json`의 구간이 최대 9개라 `CLARIFY_OPTION_MAX=3`과 충돌한다(H-36 E절 미결). **설정 화면은 되묻기가 아니라 폼이므로 3개 상한을 적용하지 않는다**(세로 목록으로 그린다). 되묻기 쪽에 톤수 축을 쓸 때의 상한 문제는 여전히 미해결로 남는다 → §10 미결 ⑤.
- **"내 정보 보기 / 이 항목만 지우기 / 전체 초기화"** 를 같은 패널에 둔다(H-36 후속에서 오케스트레이터가 권고했던 항목). 전체 초기화는 확인 1회.

### 7.3 서버로 가는 흐름 (서버 무상태 원칙과의 정합)

```
[기기 localStorage]  ── doSend() 가 매 요청에 스냅샷 첨부 ──▶  POST /api/legal/ask {profile}
                                                                │
                                                     이 요청 처리 중에만 메모리에서 읽음
                                                                │
                          ✗ 파일 저장 ✗ 로그 ✗ pendingAnswers ✗ knowledge candidate
                                                                │
                                                       응답 후 그대로 소멸
```

- 기존 원칙("서버는 세션 상태를 안 든다")과 **충돌하지 않는다** — 서버는 여전히 아무것도 기억하지 않고, 매 요청이 자기 맥락을 통째로 들고 온다. `CLARIFY_JOINER`가 질의 문자열로 하던 일을 프로필은 별도 필드로 할 뿐, **무상태라는 성질은 동일**하다.
- R1(§3.3)이 이 그림의 계약이다. 구현 시 `grep`으로 검증한다(§9-6).
- 전송량: 프로필은 수백 바이트 수준. 매 요청 첨부해도 무시할 수 있다.

### 7.4 ⑤ 프로필 기반 되묻기 스킵/확인 (profileConfirmStep)

**핵심 설계 — 새 판단기를 만들지 않고 `decideClarify`의 결과를 가로챈다.**

> **★2026-08-11 재설계 — 확인은 "조건(축) 단위"다** (사용자 확정 (자): *"3번은 따로 확인해야해" / "관련 따로해야한다고"*).
> 초판은 `ctx.prof.use='accepted'` 하나로 **그 질문의 되묻기 전체를 건너뛰었다.** 그러면 프로필이 채운 축(선박용도)에 "네"를 눌렀을 뿐인데 프로필이 **모르는 축**(해상이냐 내수면이냐)까지 함께 확정돼 버린다. 사용자가 이 위험을 명시적으로 지적해 **축 단위 확인**으로 바꿨다.

#### 7.4.1 상태를 축 단위로 든다

```jsonc
"prof": {                                  // ctx.prof — 배열이다(초판은 객체 1개였다)
  "decided": [
    { "axis": "선박용도", "label": "낚시어선", "use": "accepted" },
    { "axis": "톤수",     "label": "9.77톤",   "use": "rejected"  }
  ]
}
```

- 축 하나에 대한 "네/아니요"는 **그 축에만** 적용된다. 다른 축은 여전히 미확정이다.
- `decided[]`는 **누적**된다 — 축 A를 확인한 뒤 축 B를 또 확인할 수 있고, 그때마다 카드가 한 번씩 뜬다.
- `axis` 값은 §7.1의 프로필 필드명을 그대로 쓴다(새 어휘를 만들지 않는다).

#### 7.4.2 판정 절차

```
clarify = await decideClarify(q, contextPages)          // 기존 그대로(무수정)
if (!config.profileConfirm || !clarify.needed) → 기존 흐름 그대로

axis = 이 되묻기가 묻는 축 = clarify.options 중 프로필 값과
       **문자 그대로 일치**하는 라벨이 있는 필드 (없으면 null)

if (axis === null)                       → 기존 되묻기 그대로 출력(프로필이 모르는 축)
if (decided 에 이미 axis 가 'rejected')  → 기존 되묻기 그대로 출력(이번엔 프로필 무시)
if (decided 에 이미 axis 가 'accepted')  → 그 축은 확정된 것으로 보고
                                            **decideClarify 를 한 번 더 호출하지 않는다.**
                                            대신 그 축 라벨을 qForSearch 에 더해 **재검색**하고,
                                            **그 결과로 decideClarify 를 다시 돌린다** →
                                            남은 다른 축이 있으면 그 되묻기가 정상적으로 뜬다
else                                     → "프로필 확인" 카드로 치환(아래 문구)
```

**★핵심**: `accepted`가 하는 일은 *"답변으로 건너뛰기"* 가 **아니라** *"그 축만 채워 넣고 되묻기 절차를 계속하기"* 다. 사용자 확정 (아)의 *"그 즉시 그 조건으로 답변(재차 되묻지 않음)"* 은 **"같은 축을 또 묻지 않는다"** 는 뜻으로 읽는다 — 사용자 확정 (자)가 그 해석을 명시적으로 확정해 줬다(초판의 반대 해석은 폐기).

- **일치 판정은 완전일치/포함만 쓴다. 의미 유사도·임베딩·AI 판정은 쓰지 않는다.** 오탐이 나면 *사용자가 말하지 않은 조건으로 답이 확정된다* — 되돌릴 수 없는 방향의 오류다. `decideClarify:763`의 "같은 조건 재질문 차단"이 라벨 완전일치를 쓰는 것과 같은 논리(패러프레이즈 대조는 오탐이 크다).
- **무한루프 백스톱**: `accepted` 처리로 `decideClarify`를 다시 부를 때, **직전에 프로필로 확정한 축의 라벨을 `qForSearch`에 넣었으므로** 같은 축을 또 물으면 `decideClarify:763`(라벨이 질의에 있으면 폐기)이 이미 막는다… **가 아니다.** `qForSearch`는 `search()`에만 넘어가고 `decideClarify(q, …)`에는 원 질문 `q`가 간다(§5.5) → `:763`이 안 걸린다. 그래서 **결정론적 백스톱을 새로 둔다**: `decided[]`에 이미 있는 축의 라벨이 새 `clarify.options`에 다시 나오면 그 되묻기를 폐기하고 답변으로 넘어간다. 재호출은 **축당 1회**로 제한한다(축 수는 프로필 필드 수로 유한).

**확인 카드 문구(신선도 병기 — 사용자 확정 (아))**

```
answer : "저장해두신 정보가 있어서 먼저 확인할게요."
clarify.question : "저장된 정보로는 **낚시어선**이신 것 같아요(2026-07-30 저장). 이 조건으로 답변드릴까요?"
clarify.options  : [ {label:"네, 그 조건으로"}, {label:"아니요, 이번엔 다른 조건이에요"} ]
note   : "저장된 정보를 확인하고 있어요"
ctxNext: { prof:{ decided:[ …기존…, {axis:"선박용도", label:"낚시어선", use:null} ] } }
confirmKind : "profile"
```

- 날짜는 해당 **필드의 `at`** 을 KST(`YYYY-MM-DD`)로 표기한다(CLAUDE.md 시간 표기 규칙).
- **"네, 그 조건으로"** → 그 축만 `use:'accepted'` → 재검색 후 **남은 축을 계속 되묻는다.**
- **"아니요, 이번엔 다른 조건이에요"** → 그 축만 `use:'rejected'` → **그 축은 이번 요청에서만 프로필을 무시**하고 평소대로 AI 되묻기. **프로필 자체는 수정하지 않는다**(사용자 원문 "이번엔"). 카드 아래에 작은 링크로 "저장된 정보 고치기 →"(설정 패널 열기).

#### 7.4.3 축 2개짜리 실제 흐름 (사용자가 든 예: 톤수 + 해상/내수면)

프로필에 **톤수만** 있고 해상/내수면은 없다고 하자.

```
[사용자] 우리 배 정박신고 해야 하나요?
[나리야] 저장해두신 정보가 있어서 먼저 확인할게요.
         저장된 정보로는 9.77톤이신 것 같아요(2026-07-30 저장). 이 조건으로 답변드릴까요?
         [ 네, 그 조건으로 ]  [ 아니요, 이번엔 다른 조건이에요 ]
[사용자] (네)            → ctx.prof.decided = [{axis:'톤수', use:'accepted'}]
[나리야] 조건에 따라 답이 갈려서, 하나만 더 여쭤볼게요.      ← ★여기가 초판에서 사라졌던 질문
         바다인가요, 하천·호소 같은 내륙의 물인가요?
         [ 바다 ]  [ 하천·호소 ]
[사용자] (바다)          → 기존 CLARIFY_JOINER 경로(' — 바다')로 누적
[나리야] (9.77톤 + 바다 기준으로 답변)
```

**두 축이 서로 다른 운반로를 쓴다는 점에 주의**: 프로필로 확정된 축은 `ctx.prof.decided[]`에, AI 되묻기로 고른 축은 기존대로 `query`의 `' — '` 누적에 실린다. 이건 의도된 분리다 — 전자는 사용자가 **타이핑하지 않은** 정보(프로필)라 질의에 섞으면 §2.1-3(로그·임시보관 저장)에 걸리고, 후자는 사용자가 화면에서 직접 고른 값이라 기존 규약 그대로 두는 것이 회귀가 없다.

### 7.5 ★두 되묻기 경로(위키·트리)에 **처음부터 같이** 건다 (사용자 확정 (차))

초판은 트리 경로 적용을 미결④로 미뤘으나, 사용자가 *"처음부터 같이 넣고 테스트 하자."* 로 확정했다. 두 경로에 **같은 후처리 함수**를 걸되, 걸리는 자리와 주의점이 다르다.

| | 일반(위키) 되묻기 | 트리 되묻기 |
|---|---|---|
| 만드는 곳 | `decideClarify()` (`legal_retriever.js:696`) — LLM이 그 자리에서 생성 | `clarifyFromZoneTree()` (`:1556`) — 자산 `선택지[]`를 그대로 꺼냄 |
| 반환 모양 | `{needed, intro, question, options[{label,hint}]}` | **완전히 같은 모양**(`:1561-1566`) |
| 거는 자리 | `routes/legal.js:817` 직후 | `routes/legal.js:793`의 `zoneTreeStep()` 반환 직후 |
| 후처리 적용 | 가능 — `options[].label` ↔ 프로필 값 문자열 대조 | **가능. 같은 함수를 그대로 쓴다** — 두 경로의 `options` 스키마가 같기 때문 |
| 대조 대상 축 | 그때그때 다름(LLM이 고른 축) | 자산이 정한 축(`tree.축` = 해역/항해구역/조업해역) → **프로필 `주 조업구역`과 대응** |

**⇒ "가로채는 후처리" 방식은 두 경로 모두에 그대로 적용된다.** 반환 스키마가 같아서(H-36이 의도적으로 맞춰 둔 설계 — `H36_live_wiring_design.md` §5) 후처리 함수 하나면 된다.

**다만 트리 경로에만 있는 주의점 3가지**(이걸 안 지키면 H-36 회귀):

1. **`accepted` 후 트리 경로는 재검색이 아니라 "경로 복원"으로 이어져야 한다.** 트리는 `query`의 `' — 라벨'` 누적으로 위치를 복원한다(`resolveZoneTreePath:1459`). 프로필로 확정한 구역 라벨을 `ctx`에만 두면 트리는 그 사실을 **모른다.** → **트리 경로에서 `accepted`가 나오면, 그 라벨을 `zoneTreeStep()`에 넘기는 질의에 한해** `q + CLARIFY_JOINER + label`로 합성해 넘긴다(**요청 바디의 `query`는 그대로 두고, 그 함수에 넘기는 지역 변수에서만**). 근거: 트리 경로는 이 문자열이 곧 계약이라 다른 운반로가 없다.
   ⚠이때 `matchZoneTreeTopic`의 `q0`(`:1427`)는 `split(JOINER)[0]`이라 **원 질문 그대로** 유지된다 → 주제 판정은 안 흔들린다(§2.1-1의 세 오염 중 두 개가 원리적으로 회피된다). 남는 하나는 `rest`(`:1476`) 오염인데, 이 경우엔 **그 라벨이 실제로 사용자가 확정한 값**이라 암시하강이 그리로 내려가는 것이 정확히 의도한 동작이다.
2. **`rejected`면 그 라벨을 절대 합성하지 않는다** — 트리는 원래대로 되묻는다.
3. **회귀 판정**: `config.profileConfirm=false` 또는 `profile` 미전송이면 `zoneTreeStep()`에 넘어가는 문자열이 **오늘과 바이트 동일**이어야 한다(R0). `test_zone_tree_wiring.js` 36건은 프로필을 안 보내므로 **무수정 통과해야 한다** — 통과 못 하면 설계가 틀린 것이다.

## 9. ⑥ 대기 상태 전수 열거 (CLAUDE.md 확정 원칙)

> CLAUDE.md 결정로그(2026-08-09): *"대기·보류·유예를 도입하는 설계는 '대기 중 상태 변화'를 표로 전수 열거"* — 관찰창 결함 3건이 전부 이 표의 빈칸에서 나왔고, 문제는 표를 **만들긴 했는데 전수가 아니었던 것**이었다.

### 9.0 이 설계의 대기는 성질이 다르다 (먼저 짚는다)

mmis 관찰창은 **서버 프로세스가 타이머를 들고 기다렸다.** 이 설계의 대기는 **서버에 존재하지 않는다** — "대기 중"이란 오직 *"사용자 화면에 버튼 카드가 떠 있고 아직 안 눌렀다"* 는 뜻이고, 서버는 매 요청을 독립적으로 처리한다. 그래서 "프로세스 종료로 유실"·"타이머 중복 발사" 계열은 **원리적으로 발생하지 않는다.** 그래도 아래 표는 그 사실에 기대지 않고 전수로 적는다.

대기 3종: **(a) 이해확인 응답 대기** · **(b) 상황질문 응답 대기** · **(c) 프로필조건 확인 응답 대기**

### 13.1 지금 무슨 일이 벌어졌나 (실측, `H32_zone_tree_design.md` §11.11)

고시 확장(L-80)으로 `zone_tree.json`의 적용항목이 **79 → 186건**(고시 107건 추가)이 됐다. 배선 코드는 **한 줄도 안 고쳤는데** 화면이 바뀌었다:

| 질의(되묻기 완료 상태) | 확장 전 | 확장 후 |
|---|---|---|
| `… — 평수구역` | 규정 5건 | **65건 · 본문 17,281자** |
| `… — 연해구역` | 규정 6건 | **66건 · 본문 18,062자** |
| `… — 근해구역 이상 — 원양구역` | 규정 5건 | **55건 · 본문 15,476자** |
| `배로 영해까지 나가도 되나요?`(해역 트리) | 15건 | 15건(불변 — 해역 트리는 안 건드렸다) |

두 가지가 동시에 깨졌다.

- **(A) 분량**: `renderZoneAnswer()`(`legal_retriever.js:1598`)는 `collectZoneRules()`가 모은 것을 **유형별로 전부 펼친다**(`:1608-1613`). 상한이 없다. 채팅 말풍선에 1.8만 자가 쏟아진다.
- **(B) 거짓 문구**: `:1623-1625`가 *"고시(행정규칙)의 구역별 설비·수량 기준 … 은 여기 들어 있지 않아요"* 라고 **하드코딩**돼 있는데, **지금은 107건이 들어 있다.** 사용자에게 보이는 틀린 문장이다.

**근본원인(L-81)**: ①분량을 제한하지 않는 렌더러 ②데이터의 범위를 **코드가 산문으로 단언**하는 면책 문구 — 둘 다 자산이 커지는 순간 각각 "쏟아짐"과 "거짓말"이 된다.

### 13.2 (A)의 해법 — "상위 N건 + 더보기"가 아니라 **질문어 기반 관련도 필터**

사용자 확정 (타)가 단순 자르기를 배제했다. **사용자가 실제로 입력한 질문 키워드로 그 리프의 적용항목을 한 번 더 걸러, 관련도 높은 것부터 보여준다.**

**왜 단순 자르기가 답이 아닌가**: 지금 순서는 `유형`(의무→완화→…) 순이고 그 안은 자산 순서다 — **질문과의 관련도가 아니다.** 상위 N건만 남기면 *"구명조끼 몇 개?"* 를 물었는데 질문과 무관한 "의무" 항목 10건이 남고 정작 구명설비 항목이 잘려나갈 수 있다. **자르기 전에 정렬이 먼저다.**

**재사용할 기존 로직 — 새로 짜지 않는다**

| 쓸 것 | 위치 | 그대로 쓸 수 있나 |
|---|---|---|
| `termsOf(query)` | `legal_retriever.js:142` | **그대로 재사용.** 질의를 토큰화하고 STOPWORDS를 빼며, 4자 이상 토큰은 어미를 1~2자 잘라낸 변형까지 만든다(한국어 활용 대응) |
| `sliceRelevant()`의 **역가중 아이디어** | `legal_retriever.js:504-520` | **로직은 재사용 불가, 아이디어는 그대로.** 그 함수는 마크다운 본문을 `## ` 절로 쪼개는 전용 코드라 규정 객체엔 못 쓴다. 하지만 **"이 문서 안에서 몇 개 조각에 등장하는지(절-내 문서빈도)로 역가중해, 소수 조각에만 있는 단어를 우선한다"** 는 핵심 아이디어는 그대로 옮긴다 — 이 자산에서 `선박`·`구역` 같은 낱말은 **거의 모든 항목에 있어 변별력이 0**이므로 역가중이 없으면 순위가 무의미해진다(`:511-514` 주석이 위키에서 실측한 것과 같은 현상) |
| `scoreOne()` | `legal_retriever.js:483` | **재사용 불가.** `index.json` 페이지 객체(`law`/`topic`/`file`/`themes`)를 전제한다. 규정 객체(`제목`/`인용`/`대상`/`조건`/`근거법령`)는 필드가 다르다 → 같은 형태의 **작은 전용 스코어러**를 새로 둔다 |

**설계: `rankZoneRules(rules, query)`**

```
terms = termsOf(q0)                     // q0 = 원 질문(CLARIFY_JOINER 앞) — 되묻기 라벨은 뺀다
                                        //  ★라벨(예: '평수구역')을 넣으면 그 낱말이 전 항목에 있어 순위가 뭉개진다
hay(rule) = 제목 + 인용 + 대상 + 조건 + 적용제외 + 주의 + 근거법령      // 항목 하나의 검색 대상 문자열
df[t]     = terms 각 낱말이 이 리프의 항목 몇 개에 나오는지            // 역가중 분모
score(r)  = Σ_t ( hay(r).includes(t) ? w(t)/df[t] : 0 )
            w(t) = 제목에 있으면 3, 그 밖은 1                        // scoreOne 의 제목 가중과 같은 취지
```

**표시 규칙(확정)**

1. **`score > 0`인 항목만 "질문과 관련 있는 규정"으로 앞에 낸다** — 점수 내림차순, 그 안에서는 기존 `유형` 순서(`ZONE_KIND_ORDER`)를 유지해 읽기 흐름을 지킨다.
2. **`score === 0`인 나머지는 "이 구역의 다른 규정 N건"으로 접어서** 제목 줄만 낸다(근거·인용문은 생략). **버리지 않는다** — 트리의 가치는 "그 구역에서 달라지는 것의 목록"이고, 사용자가 안 물었다고 규정이 사라지면 안 된다.
3. **모든 항목의 `score`가 0이면**(질문어가 하나도 안 걸릴 때 — 예: `우리 배 어디까지 갈 수 있나요?`처럼 구역 자체를 물은 경우) **정렬을 적용하지 않고 기존 순서 그대로** 내되, ②의 접기는 적용한다(유형별 상위 몇 건만 펼침). 이 경우가 트리 되묻기의 정상 경로라 **여기서 회귀가 나면 안 된다** → 검증 대상 1순위.
4. **`주의`·`적용제외`는 접힌 항목에서도 항상 보인다** — H-36 배선 전 필수 규약 ②("`주의` 필드를 반드시 함께 노출")를 접기가 무력화하면 안 된다.
5. **분량 상한을 문자 수로 걸지 않는다** — 자르는 지점이 항목 중간이 되면 인용문이 잘려 환각과 구분이 안 된다(`H36_adversarial_review.md` §5-A "다만 단서 절단"이 같은 계열의 사고였다). 상한은 **항목 개수**로만 건다.

**이 설계가 "고장난 기능에 안전장치 달기"가 아닌 이유**(CLAUDE.md 결정로그 검문): *"이 기능이 아예 없으면 어떻게 되나?"* → 사용자는 1.8만 자를 그대로 받는다. 즉 **없으면 지금 실제로 못 쓰는 상태**다. 상한이 아니라 **표시 규칙**이고, 데이터는 하나도 버리지 않는다.

### 13.3 (B)의 해법 — 면책 문구를 **자산에서 뽑아 쓴다** (L-81 교훈 ③ 그대로)

**바꾼 뒤(데이터에서 조립)**:

| 문구 조각 | 데이터 출처 | 지금 값으로 렌더하면 |
|---|---|---|

| **변하지 않는 한 문장** | 하드코딩 유지 | "**목록에 없다고 해서 그런 규정이 없다는 뜻은 아닙니다.** 정확한 확인은 소관부서에 문의하세요." |

1. **점수순 전역 재배치 대신 "유형 그룹 안에서" 점수순 정렬.** 설계 표시규칙 1은 `score>0`을 별도 섹션으로 앞에 내라고 했으나, 그러면 답변이 두 가지 구조(평면 목록 + 유형 그룹)로 갈리고 `처벌(법정형)` 머리말·유형별 건수 같은 기존 규약이 두 곳에 흩어진다. 유형 그룹은 그대로 두고 **그 안에서** 점수순(안정정렬)으로 두면 같은 목적을 달성하면서 기존 렌더 구조·회귀 테스트가 전부 유지된다.
2. **`ZONE_FOLD_MIN=20` 추가(설계에 없던 것).** 설계대로 모든 리프에 접기를 적용했더니 **원래 문제가 없던 작은 리프까지 접혀** 영해(15건·4.3천 자)에서 항목 5건이 제목만 남았다 — 접기는 L-81의 1.8만 자 폭증을 막으려는 것이지 작은 리프의 내용을 줄이려는 것이 아니라, 항목 20건 이하는 접지 않는다.
3. **접기 안내 문구를 "적중 여부"에 따라 갈랐다.** 질문어가 하나도 안 걸렸는데 *"질문과 관련 있는 것부터"* 라고 쓰면 **거짓말**이다(그때 실제로 한 일은 "유형별로 앞에서부터"). 트리 되묻기의 정상 경로가 바로 이 무적중 경우라 그냥 두면 상시 거짓 문장이 나갔을 것이다.

**설계대로 한 것**: `termsOf()` 재사용 · `sliceRelevant()`의 문서빈도 역가중 이식(항목-간 df) · `scoreOne()` 미재사용(전용 소형 스코어러) · 제목 가중 3 · 점수 0 항목은 삭제 없이 접기 · `주의`·`적용제외` 보유 항목은 점수 무관 **전량 펼침** · 상한은 문자 수가 아닌 **항목 개수** · 면책 문구 전량 자산 조립.

**남은 것**: 큰 리프가 여전히 ~1만 자다. 잔여 분량의 대부분은 규약②로 강제 펼친 `주의`·`적용제외` 항목(연해 19건·평수 16건)이고, 그 항목들의 **인용문만** 접으면 3.1~3.7천 자가 더 줄지만 "원문 그대로 보여준다"는 이 자산의 가치와 상충한다 → **사용자 판단 대기**(임의로 줄이지 않았다).

## 14. ★질문 유형(경계형 vs 요건형) 구분 — L-84 근본해법 (**✅2026-08-13 구현 완료**)

> **§13과의 관계**: §13은 *"길다"* 는 증상을 고쳤다(1.8만→1만 자). 사용자는 그 결과를 보고 **원인이 따로 있다**고 지적했다 — 원문:
> **"어디까지 갈 수 있냐고 물었는데... 물어보지도 않은 것에 대해서 대답할 필요는 없는 거야."**
> 즉 문제는 분량이 아니라 **경계를 물었는데 요건 목록을 답한 것**이었다(L-84). 이 절이 그것을 고친다.
> §13(관련도 정렬·접기·면책문구 조립)은 **요건형 답변 안에서 그대로 재사용**한다 — 한 줄도 다시 짜지 않았다.

### 14.1 무엇을 갈랐나 (확정 규칙)

| 질문 | 오늘까지 | 이제 |
|---|---|---|
| **경계형** — "우리 배 어디까지 갈 수 있나요? — 근해구역" | 규정 57건·9,843자 | **843자** — 구역 경로 + 그 구역의 정의(경계) + 규정 **건수만** + [네/아니요] 확인 |
| 그 확인에서 **"네"** | — | §13 답변 **바이트 그대로**(9,843자) |
| 그 확인에서 **"아니요"** | — | 같은 경계 답변에서 안내 한 줄만 빠진 것(800자), **확인을 다시 내지 않는다** |
| **요건형** — "구명조끼 싣고 어디까지 나갈 수 있나요? — 평수구역" | 규정 65건·10,584자 | **그대로**(확인 없이 바로 §13 답변) |
| **순수 요건형** — "구명조끼 몇 개 필요해요?" | 게이트 불발 → 위키 흐름 | **그대로**(트리에 들어오지도 않는다) |

### 14.2 유형 판정 — 새 어휘 목록을 지어내지 않았다

**ⓐ 경계형의 정의는 이미 코드에 있다**: 트리 진입 게이트 `ZONE_ASK`(구역 축을 묻는 어미구 21개)가 그것이다.
그래서 `zoneTreeStep()`에 들어온 질문은 **전부 경계형 어미**를 갖고 있다 — 오케스트레이터가 물은 *"ZONE_ASK를 그대로 경계형의 정의로 재사용할 수 있나"* 의 답은 **"진입 조건으로는 맞지만, 그것만으로는 안 갈린다"** 이다.

**ⓑ 왜 안 갈리나(실측)**: `ZONE_ASK` + 요건 어휘가 **섞인** 질문이 실제로 있다 — 회귀 스위트 T8이 쓰는
`"우리 배에 구명조끼 싣고 어디까지 나갈 수 있나요?"`, `"무선설비 없는 배로 어디까지 나갈 수 있나요?"` 가 그것이다.
"ZONE_ASK ⇒ 전부 경계형"으로 두면 이 질문들까지 짧은 답을 받아 **§13이 만든 관련도 정렬이 통째로 死문**이 된다.

**ⓒ 확정 판정식** — *원 질문이 **구역 축 어휘 말고 다른 것**을 지목했고, 그 말이 **이 구역 규정 본문에 실제로 나오면** 요건형.*

```
terms = termsOf(q0)                                   // §13과 같은 토큰화(재사용)
      − 수치+단위 토큰("20톤"·"12m")                    // 자기 배를 설명한 조건값(톤수는 별개 축 E, L-82)
      − 구역 축 어휘                                    // ZONE_SUBJECT ∪ ZONE_ASK 낱말 ∪ 트리 라벨
요건형 ⇔ 남은 낱말 중 하나라도 zoneRuleHay(rule) 에 등장   // §13과 같은 검색 대상 문자열(재사용)
```

- **축 어휘의 출처가 전부 기존 코드·자산이다**(`ZONE_SUBJECT`·`ZONE_ASK`·`zone_tree.json` 라벨) — 요건 어휘 목록을 새로 만들지 않았다. 오케스트레이터 지시(*"지어내지 말고 근거를 삼아라"*)를 이렇게 만족시켰다.
- 한 글자 조각 처리: `ZONE_ASK`는 **구(句)** 라 쪼개면 '수'·'갈'·'있'이 나와 **뺀다**(두면 '수량'·'수산물'까지 축 어휘가 된다). 반대로 낱말 목록인 `ZONE_SUBJECT`의 '배'는 **남긴다**(빼면 '배로'·'배가'가 요건 지목으로 잘못 잡힌다 — 실제로 구현 중 이 버그가 났고 T9가 잡았다).
- **틀리는 방향이 안전한 쪽이다**: 경계형으로 잘못 보면 사용자는 짧은 답 + 버튼 한 번(데이터 손실 0), 요건형으로 잘못 보면 L-84가 지적한 그 화면이 다시 나온다. 그래서 애매하면 **경계형** 쪽으로 물러난다.

**판정 실측**(리프에 도달한 질의):

| 질의(원 질문) | 판정 | 근거 |
|---|---|---|
| 우리 배 어디까지 나갈 수 있나요? | 경계형 | 축 어휘 뺀 낱말 0개 |
| 낚싯배로 제주도까지 갈 수 있나요? | 경계형 | '제주도'는 규정에 없다 |
| 20톤 어선인데 어디까지 갈 수 있나요? | 경계형 | '20톤'은 수치+단위(조건값) |
| 배로 영해까지 나가도 되나요? | 경계형 | '영해'는 트리 라벨(축 어휘) |
| 우리 배에 구명조끼 싣고 어디까지 나갈 수 있나요? | **요건형** | '구명조끼'가 규정 본문에 있다 |
| 무선설비 없는 배로 어디까지 나갈 수 있나요? | **요건형** | '무선설비'가 규정 본문에 있다 |

### 14.3 상태를 어떻게 나르나 — 새 규약을 만들지 않는다

§3.1이 신규 단계 3종(이해확인·상황질문·프로필)에 대해 **별도 필드(D안)** 를 택한 것과 달리, 이 확인은 **기존
`CLARIFY_JOINER` 누적 방식을 그대로 쓴다.** 이유는 그 두 대기의 성질이 다르기 때문이다:

| | §3의 신규 3단계 | §14의 요건 확인 |
|---|---|---|
| 무엇을 나르나 | 프로필·이해상태(서버 로그에 남으면 안 되는 것 포함) | "요건도 볼래요?"에 대한 예/아니요 한 조각 |
| 라운드 카운트 | 사용자 확정 (다) — **세면 안 된다** | 트리 되묻기와 같은 성질이라 **세도 된다**(트리 경로는 애초에 상한 밖 — §5.4) |
| 클라이언트 변경 | 필요(ctx 왕복) | **0줄**(`pickClarifyOption`이 이미 하는 일 그대로) |

**라운드 예산 실측**: 가장 깊은 경로(`수상 → 해수면 → 배타적 경제수역 → 접속수역`)가 3조각, 여기에 확인 1조각을
더해 **최대 4** — `CLARIFY_MAX_ROUNDS`(=4)와 같다. 그리고 이 경로는 트리가 답을 내므로 `decideClarify()`까지
가지 않는다(리프에 규정이 0건이라 트리가 물러나는 경우에만 도달하는데, 14개 리프 전부 규정이 있다). 회귀 T9-⑩이 이 값을 고정한다.

**라벨 충돌(L-77 재발 방지)**: `네, 서류·장비 기준도 알려주세요` / `아니요, 여기까지면 돼요` —
22개 노드의 `라벨`·`선택지[].label` 23개와 **부분문자열 관계가 0건**이고, 이 라벨을 붙여도 `resolveZoneTreePath()`가
잡는 노드가 **하나도 안 바뀐다**(전 라벨 × 2 = 46회 스윕). 둘 다 T9-⑨가 회귀로 고정한다.

### 14.4 경계형 답변에 무엇을 싣나 (그리고 왜 그것만인가)

```
쉽게 말하면, 여쭤보신 구역은 **근해구역**, 그 범위는 이래요.
**확인한 구역**: 항해구역 → 근해구역 이상 → 근해구역 (항해구역(선박 능력))     ← ①경로
**근해구역의 범위**: 동쪽은 동경 175도, 서쪽은 동경 94도, …                  ← ②경계(자산 `정의`)
**참고**: (그 노드의 `메모`)                                              ← 구역 자체의 성질
이 구역에서 달라지는 규정은 74개 … 원문에서 확인된 것만 **57건**이에요
(적용법령 1건 · 의무 51건 · 제한 4건 · 완화 1건).                          ← ③건수만
여기서는 건수만 알려드렸어요 — 그 내용이 필요하시면 아래에서 골라 주세요.        ← 확인이 붙을 때만
**이 목록의 한계**: … (zoneCoverageNote, §13과 같은 함수)                  ← 건수의 커버리지
        [ 네, 서류·장비 기준도 알려주세요 ]  [ 아니요, 여기까지면 돼요 ]
```

- 규정의 **제목·인용·의무는 한 건도 싣지 않는다**(T9-①이 리프별로 전수 검사한다).

- 말미 면책은 `zoneCoverageNote()`를 **그대로 호출**한다 — 건수만 말해도 "그 건수가 전부는 아니다"는 같은 한계가 걸리고, 문구를 두 벌로 만들면 자산이 바뀔 때 한쪽만 따라간다(L-81 교훈③).

2. **확장 답변의 `**{라벨}란**` 표기는 그대로 뒀다** — 고치면 §13 답변의 "바이트 동일" 증명이 깨진다. 다음에

4. **경계형/요건형 판정은 그 리프의 규정 집합에 의존한다**(같은 질문이라도 리프가 다르면 갈릴 수 있다).

### 15.3 설계 대비 바꾼 것과 이유

1. **상황질문 발화 판정에 ⓑ(질문어 ↔ 분기 항목 이름 대조)를 더했다.** 설계 §5.3의 R2(검색 결과의 법 분포)만으로는 표본 800건에서 발화율이 8.6~36.9%였고, 걸린 질문 대부분이 *"검색이 두 계열의 법을 함께 물어왔을 뿐, 답이 배 종류로 갈리지는 않는"* 것이었다(농산물 검사수수료·해적 보험). §13·§14가 쓰는 `termsOf()` 대조를 그대로 옮겨 "질문이 지목한 것이 실제로 여러 분기에 있는가"를 함께 요구한다 — 새 기법이 아니라 이미 검증된 기법의 재사용이다.
2. **ⓒ를 "법 집합 분할"에서 "한 갈래로 확정됐으면 묻지 않는다"로 바꿨다.** 설계 문구대로 *"각 선택지의 법 집합이 겹치지 않을 때만"* 을 요구하면 **설계 자신의 승인 시나리오(구명조끼)가 발화하지 않는다** — 그 질문의 상위 후보(어선안전조업법·선박구명설비기준·양식산업발전법)가 `vessel_doc_tree.json`에 **아예 없는 법**이라 어느 분기에도 안 매핑되기 때문이다(자산의 법 커버리지 21법 < 검색 코퍼스 74법). 그래서 분할을 **양성 조건이 아니라 음성 필터**로 쓴다.
3. **프로필 `accepted` 뒤 `decideClarify` 재호출을 하지 않는다.** 설계 §7.4.2는 "재검색 후 되묻기를 다시 돌려 남은 축을 묻는다"였으나, 구현은 **accepted 라벨을 처음부터 `qForSearch`에 넣어** 한 번의 검색·한 번의 판정으로 같은 결과를 낸다(남은 축은 그 판정에서 자연히 뜬다). 관측 가능한 동작은 같고 LLM 호출이 하나 줄며, "같은 축을 또 물으면 폐기"(§9.1 #21) 백스톱은 그대로 있다.
4. **프로필 확인 카드 문구에서 `**굵게**`를 뺐다.** 설계 §7.4.2 예시는 `**낚시어선**`이었는데, 되묻기 질문은 클라이언트가 `esc()`로만 그린다(`answerBodyHTML`을 안 거친다) — 그대로 두면 화면에 별표가 찍힌다. **사람 정독(L-75 3단계)에서 발견**해 `"낚시어선"`(따옴표)으로 바꿨다.
5. **프로필 패널의 톤수·길이는 버튼이 아니라 숫자 입력이다.** 설계 §7.2는 `tonnage_facet.json`의 구간을 버튼으로 꺼내라고 했으나, 그 자산의 임계값은 **법마다 다른 경계**(154 facet)라 하나의 공통 구간표가 없다. 클라이언트에 구간을 상수로 박으면 자산이 바뀔 때 화면이 거짓말을 한다(L-81). 그 대신 숫자+단위로 저장한다 — 다만 그러면 톤수 값이 되묻기 선택지 라벨과 문자 그대로 일치하는 일이 거의 없어 **톤수 축은 사실상 확인이 안 걸린다**(안전한 방향의 실패). → §11 미결⑤와 함께 남긴다.
6. **`assumed` 고지문을 트리 답변에도 붙인다.** 설계 §3.4는 ⑦(합성)·2차 조회 경로만 적었으나, 3회 연속 이해 실패 뒤 트리 답변만 고지 없이 나가면 같은 종류의 답변에 표시가 갈린다. 스위치 off 상태에서는 발생할 수 없는 경로다.
