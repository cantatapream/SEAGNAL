## 0. 왜 만드는가 / 이번 범위

### 배경 — 사용자와 확정한 것 (대화 원문 병기, CLAUDE.md 결정로그 규약)

사용자 질문: **"기상특보 뜨면 어디까지 다닐 수 있나요?"** 류의 질문은 B(해역·항해구역 트리)로 풀리지 않는다. 확인해 보니 이 규정은 **구역이 아니라 선종(어선/일반선박/유도선/레저)×특보종류(전체/개별, 등급)** 로 갈리는 별개의 축이었다. 그래서 B의 하위가 아니라 **독립된 14번째 자산**으로 만들기로 확정했다(L-82 "축이 다르면 억지로 한 트리에 합치지 말 것").

질문 순서에 대해 사용자가 **"물어봐야 할 것을 미리 반드시 지정해놓아야 하는거야?"** 라고 물었고, 그에 대한 확정 결론은:

> **축(선종·특보종류)과 그 안의 데이터(수치·조문)는 미리 검증해서 고정하되, 질문 순서는 고정하지 않고 "암시 하강"(질문에 이미 나온 축은 안 물어봄, 기존 `resolveZoneTreePath`류 패턴과 같은 원리)으로 유연하게 처리한다.**

## 1. 두 축이 실재한다는 확인 (L-82 — 넘겨짚지 말고 직접 확인)

### 1.1 선종 축 — D(`vessel_doc_tree.json`)를 **직접 열어** 대조했다

지시대로 D의 선종 계층을 그대로 재사용할 수 있는지 노드 단위로 대조했다. 결과:

| 이 자산의 노드 | D의 노드 | 관계 |
|---|---|---|
| `ship` 선박 | `ship` 선박 | 동일 |
| `fishing_vessel` 어선 | `fishing_vessel` 어선 | 동일 |
| `angling_vessel` 낚시어선 | `angling_vessel` 낚시어선 | 동일 |
| `ocean_fishing_vessel` 원양어선 | `ocean_fishing_vessel` 원양어선 | 동일 |
| `other_fishing_vessel` 그 밖의 어선 | `other_fishing_vessel` 그 밖의 어선 | 동일 |
| `water_leisure_craft` 수상레저기구 | `water_leisure_craft` 수상레저기구 | 동일(D의 하위 동력/무동력은 **안 만듦** — §1.2) |
| `general_ship` 그 밖의 선박(일반선박) | `general_ship` 〃 | 동일 |
| `excursion_ferry` 유선·도선 | `excursion_ferry` 유선·도선 | 동일 |
| **`domestic_passenger_ship` 내항여객선** | `passenger_ship` 여객선 | ★**이 자산에만 있는 파생 분류** |
| **`other_general_ship` 내항여객선 외의 선박** | `cargo_ship` 화물선·그 밖의 선박 | ★**부분 대응**(이 노드가 더 넓다) |

**겹치는 것 8개 / 이 자산에만 있는 것 2개.** 지시대로 **D는 한 글자도 고치지 않았다**(읽기만 했다).

**왜 D에 없는 노드를 만들어야 했나** — 해상교통안전법 시행규칙 별표 10이 **내항여객선(제1호)과 그 밖(제2호)** 을 완전히 다른 표로 가른다. 즉 이 주제에서는 *국제항해 여부*가 노드 레벨의 갈림길이다. 그런데 D는 국제항해를 노드가 아니라 **리프의 잔여 축(`추가확인`)** 으로 둔다(D 설계 §3.3). 축의 쓰임이 다르므로 D를 고쳐 맞추지 않고, 이 자산에만 있는 파생 분류로 남겼다(L-82).
`other_general_ship`이 D의 `cargo_ship`보다 넓은 이유: 별표 10 제1호가 **내항**여객선만 다루므로 **국제항해 여객선**은 제2호(=이 노드)로 떨어진다. D의 `cargo_ship`(여객선·유도선이 아닌 선박)에는 그 배가 들어가지 않는다.

**D에 있는데 이 자산이 노드로 안 만든 것과 그 이유**
- 동력/무동력수상레저기구 — 수상레저안전법 제22조는 **활동 자체**를 금지하고 동력 여부로 가르지 않는다. 노드를 만들면 답이 달라지지 않는 질문만 하나 는다(zone_tree §3.4 "한정연해구역"과 같은 판단).
- 유조선/산적화물선/그 밖의 화물선 — 별표 10은 화물 종류로 갈리지 않는다. 시정 0.5km 행에서만 유조선·가스운반선·화학제품운반선을 지목하므로 그 행의 `대상` 필드로 표현했다.

**VTS 관제대상선박은 노드로 만들지 않았다.** 선박교통관제법의 통제는 *선종*이 아니라 **①관제구역이라는 장소 + ②관제대상선박 요건**으로 결정되는 중첩 규제라 선종 축이 아니다(L-82). 루트에 통제항목으로 달아 모든 리프가 상속하게 하고, `조건` 필드에 "관제구역 안의 관제대상선박일 것"을 명시했다.

**1단계 배타성은 우리가 그은 것이 아니다** — 해상교통안전법 시행규칙 별표 10 제2호 가목이 **법 스스로** 수상레저기구·낚시어선·유선 및 도선·어선을 이 기준에서 빼고 각자 소관법으로 보낸다. D의 1단계(선박안전법 적용제외)와 같은 성격의, 원문에 실재하는 경계다.

### 1.2 특보 축 — 등급 체계를 raw에서 확인했다

| 계열 | 현상 | 등급 | 근거 |

| 예비특보 | (위와 같음) | — | 기상법 제13조의2제2항 |

## 2. ★"전체 발효 시" vs "개별 특보만"을 어떻게 표현했나 (지시 1항 후단)

통제항목의 `특보` 필드가 이 구분을 담는다. **핵심은 `표현` 필드다.**

```jsonc
"특보": {
  "표현": "포괄" | "열거" | "시계제한" | "특보아님" | "해당없음",
  "원문표현": "기상특보(「기상법」 제14조제2항에 따른 해양기상특보)",  // 원문 문구 그대로
  "현상": ["태풍","풍랑","폭풍해일"],     // 포괄이면 **확장근거가 있을 때만** 채운다
  "등급": ["주의보","경보"],
  "등급표현": "주의보 이상",              // 원문 표현 보존(있을 때만)
  "조합": [ {"현상":["태풍"],"등급":["주의보","경보"]},
            {"현상":["풍랑"],"등급":["경보"]} ],   // ★§2.2
  "확장근거": {"법령":"기상법","계층":"시행령","조문":"제9조제4항"},
  "시계": "시정 1킬로미터 이내(여객용 수면비행선박은 11킬로미터 이내)",
  "예비특보": false
}
```

- **`포괄`** — 원문이 특보를 통째로 가리킨다. 대표 사례: 유·도선법 제8조제4항 *"유ㆍ도선은 기상특보(「기상법」 제14조제2항에 따른 해양기상특보를 말한다. 이하 같다) 발효 시 운항할 수 없다."* 이 경우 그 포괄어가 실제로 무엇을 뜻하는지는 **다른 조문이 말해 줄 때만** `현상`을 채우고, 그 조문을 `확장근거`에 남긴다. 여기서는 조항 스스로 기상법 제14조제2항을 인용하므로 해양기상특보 3종으로 확장할 수 있었다.
- **`열거`** — 원문이 현상을 직접 열거한다. 대표 사례: 수상레저안전법 제22조제1호 6종.
- **`시계제한`** — 특보가 아니라 시정·가시거리 기준. 같은 조문에서 함께 출항·운항을 가르므로 갈래로는 다루되 **특보와 절대 묶지 않는다**(§4.2).
- **`특보아님`** — 기상·해상 상태를 기준으로 삼지만 특보라는 낱말을 쓰지 않는 것(낚시 시행령 제19조제1호 "초당 풍속 12미터 이상 … 예보"). 갈래를 가르지 않되 답변에는 그대로 실린다.
- **`해당없음`** — 기상과 무관(관할·정의·양벌 등).

**확장근거를 채울 수 없으면 `현상`은 `null`로 둔다.** 예: 어선안전조업법 제10조제1항의 "기상특보"는 그 법이 정의하지 않으므로 `현상: null`이다(시행규칙 별표 1이 태풍·풍랑·폭풍해일을 열거하지만, 그건 별표 1 항목의 몫이다).

### 2.2 `조합` — 사람 정독에서 나온 필드 (L-79 재현)

어선안전조업법 시행규칙 별표 1 제1호는 **"태풍주의보ㆍ태풍경보ㆍ풍랑경보"를 한 칸에** 묶는다 — 태풍은 등급 불문, 풍랑은 **경보만**이다. 처음엔 `현상=[태풍,풍랑] 등급=[주의보,경보]`로 적고 그 미묘함을 산문 `등급표현`에 써 두었다. 매칭기 데모를 돌려 보니 **풍랑주의보 질문에 "풍랑경보 → 모든 어선 출항·조업 제한" 행이 딸려 나왔다.**

L-79가 지적한 바로 그 실패다 — *"데이터가 표현할 수 있는 것을 산문 주석으로 대신하지 말 것."* 그래서 `조합=[{현상,등급}, …]` 필드를 만들어 **현상과 등급을 쌍으로** 적고, 빌더·검증기·매칭기 셋이 같은 규약(`grade_ok(e, 등급, 현상그룹)`)을 쓰게 했다. `현상`·`등급`은 그 합집합으로 남겨 표시·호환에 쓰고, **합집합이 어긋나면 빌드가 실패**한다.
없으면 무엇이 잘못되나(한 문장): *풍랑주의보만 떴는데 "풍랑경보 → 모든 어선 출항·조업 제한"이 답으로 나가 사용자가 근거를 오독한다.* 해당 항목은 2건이다(어선 별표 1 제1호 · 별표 10 제1호 경보·태풍 행).

## 3. 자산 스키마

### 3.1 최상위 — 축이 둘이라 `축` 배열이다

```jsonc
{
  "generated","scope","semantics","caveats","summary","scan","unmapped",
  "축": [
    { "id":"vessel_kind",     "종류":"트리", "라벨":"선종", "진입키워드":[…], "D_대응_요약":"…", "tree":{…} },
    { "id":"weather_warning", "종류":"목록", "라벨":"기상특보 종류", "provenance":[…], "현상":[…10종…], "등급":[…3종…], "진입키워드":[…] }
  ]
}
```

`zone_tree.json`이 축이 셋이라 `trees[]`를 둔 것과 같은 이유다. 다만 여기서는 **두 축의 성격이 달라서**(트리 / 목록) 키 이름을 `축`으로 하고 `종류`를 명시했다.

### 3.2 노드 — zone_tree·vessel_doc_tree의 규약을 그대로 이식

```jsonc
{
  "id","라벨","정의",
  "D_대응": { "자산":"vessel_doc_tree.json", "id":"…", "라벨":"…", "관계":"동일|부분 대응|파생" },
  "provenance": [ {법령,법령_slug,계층,조문,법령ID,파일,인용} ],   // ★출처 없는 노드 금지
  "구분근거": [ … ],      // 형제와 배타임을 보이는 조문(있을 때만)
  "중첩주의": "…", "중첩주의_REVIEW": "…",
  "질문","선택지":[{label,hint,next}],   // ★비-리프에만, 선택지 ≤3
  "통제": [ …통제항목… ],                 // payload — 경로 상속
  "추가확인": [ {축,질문,선택지,영향,자산참조,주의} ],   // 리프에만
  "특보질문": {…},  "상속항목수", "적용항목수", "적용제외로_멈춘_항목"   // ★리프에만, 빌더가 계산
}
```

**★라벨 == 선택지 label 불변식(빌드 게이트).** L-77이 실측한 결함 ②는 *노드의 `라벨`과 부모의 `선택지[].label`이 달라 그 리프에 영영 도달할 수 없었던 것*이다. 이 자산은 둘을 **같게 고정**하고 빌더·검증기가 둘 다 검사한다.

### 3.3 통제항목(payload)

```jsonc
{
  "제목": "풍랑주의보 → 총톤수 15톤 미만 어선의 출항 및 조업 제한",
  "유형": "출항·운항 통제",   // 8값: 출항·운항 통제|활동금지|안전조치|완화·예외|적용대상|적용제외|관할|처벌
  "대상": "총톤수 15톤 미만인 어선",
  "특보": { …§2… },
  "근거법령","근거법령_slug","계층","근거조문","법령ID","행정규칙ID","파일","인용",
  "별표": {"번호":"별표 1","형식":"표(원문 줄 그대로 인용)"},
  "조건","적용제외","위임","주의","REVIEW",
  "적용제외_대상법": "어선안전조업및…"   // 유형이 적용제외일 때만 (§3.4)
}
```

**불변식**: `인용`은 **스크립트가 raw에서 직접 읽어 채운다**. 사람이 타이핑한 인용문은 검증기가 대조할 수 없어 **환각이 그대로 통과하는 유일한 통로**가 되므로, 초안에서 `특보.확장근거`에 인용문을 손으로 넣었던 것을 걷어내고 **그 필드 자체를 빌드 게이트로 금지**했다(§9의 사람 정독에서 발견).

### 3.4 `적용제외_대상법` — 상속이 틀린 답을 만드는 자리 (L-79 계열)

원양어선 리프는 어선안전조업법이 **통째로** 적용되지 않는다(시행령 제3조제1항제2호). 경로 상속만 하면 그 법의 태풍·풍랑·폭풍해일 통제가 그대로 답으로 나가고 특보 질문까지 그 법 기준으로 만들어진다.
없으면 무엇이 잘못되나(한 문장): *원양어선에 적용되지 않는 법의 출항·조업 제한이 답으로 나간다.*
그래서 적용제외 항목에 `적용제외_대상법`(slug)을 적고, 코드는 상속 목록을 **적용되는 것 / 적용제외로 멈춘 것**으로 가른다. **멈춘 항목을 버리지 않는다** — 화면에서 "이 법은 당신 배엔 적용되지 않는다"를 근거와 함께 보여야 하기 때문이다(L-79 교훈②: 소리 없이 규정을 잃는 쪽으로 틀리는 안전장치는 안 넣느니만 못하다). 실측: 원양어선 리프는 상속 27건 중 **적용 13 / 멈춤 14**.

### 3.5 별표는 **줄 블록을 원문 그대로** 싣는다

별표 1·2·10·14는 괘선(`┌─┬┐`)으로 그린 표라, 한 칸의 뜻이 여러 줄에 걸쳐 있고 공백을 접으면 옆 칸 글자와 섞인다. H(자격면허등급) 자산이 별표 병합셀을 구조화하려다 "새 값/이어지는 값"을 구별할 수 없어 포기하고 표를 verbatim으로 담은 것과 같은 판단이다(MASTER_PLAN H-36 H절 "환각 0 모범사례"). **억지 구조화로 오답을 만들지 않는다.**
부작용은 정직하게 적었다 — 별표 10 제2호의 "통제절차" 칸은 4개 행에 병합돼 있어, 어느 행의 줄 블록에도 다른 칸의 조각이 함께 보인다. 그 사실을 해당 항목의 `주의`에 명시했다.

## 4. 질문·선택지 — 데이터에서 계산한다

### 4.1 선종 축(트리)

zone_tree·vessel_doc_tree의 규칙 그대로: 모든 비-리프는 `질문`·`선택지`를 갖고, `선택지[].next`는 실재하는 자식 id이며, **선택지 수 = 자식 수 ≤ 3**(`CLARIFY_OPTION_MAX`). 빌드 게이트가 검사한다.

```jsonc
// root
"질문": "어떤 배에 관한 것인가요?",
"선택지": [ {"label":"어선", …}, {"label":"수상레저기구", …}, {"label":"그 밖의 선박(일반선박)", …} ]
// general_ship
"질문": "그 배가 어떤 배인가요?",
"선택지": [ {"label":"내항여객선"}, {"label":"유선·도선"}, {"label":"내항여객선 외의 선박"} ]
```

### 4.2 ★특보 축 — "묻지 않아도 답이 같으면 묻지 않는다"

특보 질문은 **리프마다 빌더가 데이터에서 계산**한다. 규칙 한 줄: *어떤 갈래를 골라도 걸리는 항목 집합이 같으면 그 질문은 하지 않는다.* (zone_tree §3.4 "답이 달라지지 않는 질문만 하나 늘기"와 같은 원리.)

그래서 실제로:
- **수상레저기구**: 제22조가 6종을 똑같이 금지하므로 현상 갈래가 3개로 줄고, 태풍은 등급 질문이 없다(예외가 주의보에만 열리는 5종만 등급이 갈린다).
- **어선**: 태풍은 등급 불문이라 등급을 안 묻고, **풍랑만** 주의보/경보로 갈려 그때만 묻는다.
- **원양어선**: 어선안전조업법이 적용제외라 남는 것이 루트 항목뿐이고, 그 항목들은 모든 특보에 똑같이 걸리므로 **갈래가 2개**(특보 / 제한된 시계)로 줄었다.

**"제한된 시계"는 걸리는 항목 집합이 어느 특보와 같더라도 절대 묶지 않는다.** 초판에서 수상레저기구 리프의 태풍과 집합이 같아 실제로 `태풍·제한된 시계`라는 선택지가 만들어졌다 — 사용자에게 "제한된 시계가 특보의 일종"이라는 **없는 사실**을 보여 주는 라벨이라 규칙으로 막았다.

### 4.3 미결 — 특보 선택지가 3개를 넘는 리프가 있다

| 리프 | 선택지 수 | 선택지 |
|---|---|---|
| 낚시어선 | 5 | 호우·대설·강풍 / 태풍 / 풍랑 / 폭풍해일 / 제한된 시계 |
| 원양어선 · 그 밖의 어선 | 4 | (태풍·풍랑·폭풍해일) / 제한된 시계 · 태풍 / 풍랑 / 폭풍해일 / 제한된 시계 |
| 수상레저기구 | 4 | 호우·대설·강풍 / 태풍 / 풍랑·폭풍해일 / 제한된 시계 |
| 유선·도선 | 6 | 호우·강풍 / 대설·황사·건조·폭염 / 태풍 / 한파 / 풍랑·폭풍해일 / 제한된 시계 |

**억지로 묶지 않았다** — E(톤수 사전)가 9구간을 그대로 둔 것과 같은 판단이다(억지로 줄이면 원문에 없는 묶음을 만든다). `summary.특보선택지_상한초과`에 그대로 싣고 caveats에도 적었다.

**★배선 시 검토할 대안(제안 → 사용자 기각, 2026-08-13)**: 이 축은 **실시간 기상특보 데이터로 자동 채울 수 있는 유일한 축**이었다. 사용자에게 제안했으나 **"실제 기상정보와 연동할 필요가 없음, 법률적인 정보만 알려주면 됨"으로 기각**됨 — 이 챗봇은 법령 정보 안내가 목적이지 실시간 기상 판단 도구가 아니라는 판단. 배선 시 이 축도 다른 축과 동일하게 **버튼 되묻기**로 처리한다(특보선택지 상한초과 4개 리프의 렌더링 방식만 별도 검토).

### 5.2 인용 추출 — `quote_of()`를 zone_tree에서 이식하되 `mark_cut`을 항상 켠다

zone_tree는 회귀조건(기존 항목 불변) 때문에 "끝이 잘렸는데 표시가 없다"는 수정을 고시 항목에만 켰고, 법률계열 1건이 표시 없이 잘려 있다는 사실을 다음 라운드 과제로 남겼다(그 설계 §11.5 ④). **이 자산은 신규라 그 제약이 없으므로 처음부터 켰다.**
`with_proviso()`("다만" 단서 절단 방지, 커밋 `22bc398d6`의 재발방지 규약)도 그대로 이식했다 — 단서를 떨어뜨리면 화면의 "원문"이 예외 없는 규정으로 보여 **원문보다 엄격해진다.**

### 5.3 스캔 — 3중 조건(특보어 × 출항·운항어 × 제한어)

74법 raw 전체(법률계열 + 행정규칙 + 별표) **3,699 파일 · 24,592 조문**을 훑었다. 특보어가 나온 법 **53법**, 3중 조건을 통과한 후보가 나온 법 **21법**, 그중 이 자산에 실제로 기여한 법 **6법**.

**⚠ 반대 방향은 성립하지 않는다** — 후보 0건이 "그 법에 이 주제 규정이 없다"는 확증은 아니다(합성 정의어·문장분리 경계라는 사각지대, zone_tree §5.2와 같은 성질). 그래서 `scan.laws_without_candidates`는 참고 수치로만 싣고 그 뜻을 `scan.설명`에 명시했다.

## 8. 암시 하강 매칭 설계 (`loop/match_weather_warning_tree.py` — **이번엔 배선 안 함**)

### 8.1 질문 순서를 고정하지 않는다 — 그런데도 선종을 먼저 묻게 되는 이유

사용자 확정: *"질문 순서는 고정하지 않고 암시 하강으로 유연하게 처리한다."* 그래서 이 모듈은 순서를 상수로 박지 않는다. **질의에 이미 나온 축은 건너뛴다.**

다만 실제로는 선종이 먼저 정해질 수밖에 없다 — **특보 질문의 선택지가 그 선종에 실재하는 특보로만 만들어지기 때문이다**(§4.2, 리프마다 `특보질문`이 다르다). 즉 순서가 우리가 정한 규칙이 아니라 **데이터 의존관계**에서 나온다. 사용자가 특보를 먼저 말했으면 그 축은 이미 채워져 있어 다시 묻지 않고, 선종만 물은 뒤 곧바로 답으로 간다.

### 8.2 흐름

```
질의 "낚시어선인데 풍랑주의보 뜨면 나갈 수 있나요?"
  ↓ resolve_vessel(query, tree)      선종 축 복원 (원질문 + ' — ' 조각들)
  ↓ resolve_warning(query)           특보 축 복원 (현상·등급·시계·포괄어)
  ↓ 선종 미해결이면  → 선종 질문(노드의 질문·선택지 그대로)
  ↓ 리프 도달 & 특보 미해결이면 → 리프의 `특보질문`에서 꺼내 묻기(현상 → 등급)
  ↓ 다 좁혀지면      → answer_scope(): 걸리는 항목 / 적용제외로 멈춘 항목
```

반환 스키마는 `decideClarify()`와 같은 모양(`{needed, intro, question, options[{label,hint}]}`)이라 배선 시 `routes/legal.js`·`ai_chat.js`를 안 고쳐도 된다(D §9.4(a)·B §9.3(a)와 같은 결론).

### 8.3 라벨 매칭에서 지킨 것 (L-77·L-78 재발방지)

- **`라벨` == `선택지 label` 불변식**을 빌드 게이트로 강제했다(L-77 결함②의 원천 차단).
- **단일어절 한글 라벨(`어선`)은 띄어쓰기 토큰의 선두에서만** 인정한다 — `낚시어선으로`의 `어선`은 인정하지 않는다(L-77 결함①의 부분문자열 함정).
- **기호·공백이 든 라벨(`유선·도선`, `그 밖의 선박(일반선박)`)** 은 공백을 무시한 부분문자열로 찾되, **원문 인덱스로 되돌려** 경계를 검사한다(L-78: *비교는 정규화한 문자열에서, 경계 판정은 원문에서*).
- **부분문자열 관계인 라벨**(`내항여객선` ⊂ `내항여객선 외의 선박`)은 점수(조각 완전일치 3 > 조각 포함 2 > 원질문 포함 1) → 깊이 → **라벨 길이** 순으로 갈랐다.
- **등급어(`주의보`·`경보`)만은 토큰 선두 매칭을 쓰지 않는다** — `풍랑주의보`처럼 현상어에 붙어 한 낱말이 되므로 토큰 선두에 오는 일이 거의 없다. 이 결함은 자체 시험 T4가 실제로 잡았다.
- **일상어와 겹치는 현상어**(호우·대설·황사·건조·한파·폭염)는 뒤에 `주의보|경보|특보`가 따라올 때만 인정한다 — *"작년에 **건조**된 선박"* 을 특보로 읽지 않기 위해서다. 태풍·풍랑·폭풍해일·강풍은 단독으로도 인정한다.

### 8.4 답변 범위 — 배선 전 필수 규약④("물어본 것에만 답한다")의 이 자산 적용

L-84가 만든 규약④는 *"경계형 질문에 요건 목록을 통째로 얹지 말라"* 이다. 이 자산에 오는 질문("나갈 수 있나 / 어디까지 다닐 수 있나")은 **통제 가부 자체가 물어본 것**이라 B(해역)와 대응이 다르다. 그래서 매칭기가 항목을 두 묶음으로 나눠 돌려준다:

| 묶음 | 유형 | 처리 |
|---|---|---|
| **핵심**(바로 답한다) | 출항·운항 통제 · 활동금지 · 완화·예외 · 안전조치 · 적용제외 | 물어본 것 그 자체 |
| **확인후**(물으면 펼친다) | 처벌 · 관할 · 적용대상 | *"위반하면 어떻게 되는지도 알려드릴까요?"* |
| **적용제외로 멈춘 항목** | (상속됐지만 그 배엔 적용 안 되는 것) | 버리지 않고 **함께 보여 준다**(L-79) |

실측(유·도선 + 태풍주의보): 핵심 10건 / 확인후 10건. 배선 시 이 분리를 렌더러가 지키면 규약④를 **설계 단계에서** 충족한다(사후 수정이 아니다).

### 8.5 배선 시 남는 쟁점(미결)

1. **특보 선택지 3개 초과**(§4.3) — 렌더링 방식 또는 실시간 특보 자동 채움.
2. **라운드 예산** — 이 자산은 선종 최대 2회 + 특보 최대 2회 = **최대 4라운드**다. B 배선 때 `CLARIFY_MAX_ROUNDS`를 트리 깊이로 갈음한 것과 같은 처리가 필요하다(H-37 잔여 ⑧ "깊이 4+ 자산 배선 전 별도 처리").
3. **B·E와의 교차** — 유·도선의 평수구역(B), 어선·유도선의 톤수(E)는 `추가확인.자산참조`로 가리키기만 했다. 한 대화에서 자산을 갈아타는 규칙은 B 설계 §9.3(d)의 미결과 같은 사안이다.
4. **canonical 게이트와의 관계** — 이 자산도 raw 직인용이라 B·D와 같은 미결이다.
5. **REVIEW 6건의 노출 규약** — 처벌·연결이 불확실한 항목을 답변에 낼 때 `REVIEW` 문구를 반드시 함께 보여야 한다(A의 "법정형이지 선고형이 아님", 출입항의 "폐지된 구법 인용 `주의` 동반노출"과 같은 성격).

### 9.1 사람 정독에서만 나온 결함 7건 (정직 기록 — L-75가 또 재현됐다)

| # | 무엇이 잘못됐나 | 원인 | 조치 |
|---|---|---|---|
| 1 | **처벌 항목 4건의 인용문에 형량이 없었다** — 제목은 "6개월 이하 징역 또는 500만원 이하 벌금"인데 인용은 해당 호만(유도선법 제41조) 또는 도입문만(낚시법 제53조·수상레저 제64조·어선안전조업법 제49조) | 앵커를 호 또는 도입문 **한쪽만** 잡았다 | 앵커를 **도입문**으로 통일하고 `wide`+`span`을 키워 **형량과 해당 호를 한 인용문에** 담게 함 + `also`로 그 호가 실재하는지 추가 검증 |

### 9.2 매칭기 자체 시험 (L-77·L-78 규약)
