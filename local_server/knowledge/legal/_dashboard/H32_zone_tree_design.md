## 0. 왜 만드는가 / 이번 범위

### 배경

서류 트리 파일럿(H-36)이 확인한 것: **"AI가 매번 즉석으로 74법을 훑어 갈림길을 판단"하는 대신, 미리 raw를 훑어 업무개념의 계층을 데이터로 만들어 두면 되묻기(`decideClarify`)가 그 데이터를 타고 내려갈 수 있다.**

이번 주제(해역·항해구역)를 두 번째로 고른 이유는 후보 문서(`H32_hierarchy_candidates.md` §2)가 밝힌 그대로다 — **`legal_retriever.js`의 `decideClarify()` 주석이 실사례로 들고 있는 갈림길이 바로 이것**이다:

> `CLARIFY_MAX_ROUNDS` 주석(`local_server/services/legal_retriever.js`): *"…그 답에 따라 ②**하천·호소냐 바다냐**(적용 법령·처벌이 아예 다르다)를 한 번 더 물어야 제대로 답이 나온다."*

즉 지금 LLM이 질문마다 근거자료 9,000자를 읽고 즉석으로 만들어 내는 그 질문을, **미리 데이터로 만들어 두는 것**이 이번 작업이다. (실제 코드 연결은 이번 범위 밖 — §9.)

## 1. 데이터 형태 — 왜 산문 위키가 아니라 JSON인가

서류 트리 설계 §1과 같다. `wiki/comparisons/`류 산문은 **사람이 읽는 글**이고, 이 자산은 **프로그램(`decideClarify`)이 타고 내려가는 구조**여야 한다. 그래서 H-35 `delegation_graph_full_73.json`·H-36 `vessel_doc_tree.json`과 같은 성격의 **신규 JSON 아티팩트**로 만들고, 헤더 규약도 그대로 따른다:

```
{ "generated", "scope", "semantics", "caveats"[], "summary"{}, "scan"{}, "unmapped"{}, "trees"[] }
```

`caveats`는 **정직하게 한계를 적는 자리**다. 이 주제의 한계는 §7에 정리하고 그대로 JSON에 싣는다.

**서류 트리와 다른 점 하나 — 최상위가 `tree` 하나가 아니라 `trees` 배열이다.** 이유는 §3.2.

## 2. 스키마

### 2.1 최상위

```jsonc
{
  "generated": "2026-08-10T..+09:00",
  "scope": "74법 raw 전수 스캔 — '해역·항해구역' 계층 트리",
  "semantics": { "트리가_셋인_이유": "...", "적용_상속": "...", "구역범위": "...", "질문_선택지": "..." },
  "caveats": ["…"],
  "summary": { "laws_in_scope": 74, "files_scanned": 906, "articles_scanned": 21884, … },
  "scan":    { "laws_with_zone_term": [...], "laws_with_candidates": [...], … },
  "unmapped":{ "유형_단위": [ … ] },
  "trees": [ { "id", "축", "설명", "진입키워드":[…], "tree": {…노드…} }, … ]
}
```

### 2.2 노드(공통) — 서류 트리 §2.2를 그대로 이식

```jsonc
{
  "id": "territorial_sea",              // 프로그램용 안정 식별자(영문 snake_case)
  "라벨": "영해",                        // 사용자에게 보이는 법률 용어 그대로
  "정의": "기선으로부터 12해리의 선까지에 이르는 수역",   // raw 원문 요지
  "provenance": [                       // ★출처 없는 노드 금지
    { "법령": "영해 및 접속수역법", "법령_slug": "영해및접속수역법", "계층": "법률",
      "조문": "제1조", "법령ID": "001438",
      "파일": "raw/01_해양주권정책/영해및접속수역법/법률.txt",
      "인용": "대한민국의 영해는 기선(基線)으로부터 측정하여 …" }
  ],
  "구분근거": [ … ],        // 형제와 배타임을 보이는 조문(있을 때만) — 서류 트리와 동일
  "포함근거": { … },        // ★신설: 부모에 포함된다는 관계의 근거(§2.4)
  "서열": 3,                // ★신설: 항해구역 트리 전용 순서(§2.5)
  "질문": "…",              // ★비-리프에만 (§4)
  "선택지": [ { "label": "…", "hint": "…", "next": "<자식 id>" } ],
  "적용": [ …적용항목… ],    // ★payload — 어느 노드에나 올 수 있다(상속 규약은 아래)
  "children": [ …노드… ],
  "추가확인": [ … ],        // 리프에만 — 트리로 안 쪼갠 잔여 축
  "메모"/"주의": "…"        // 판단이 애매했던 노드의 정직 메모
}
```

**★적용 상속 규약**: 어떤 구역에 적용되는 규정 = **루트에서 그 리프까지 경로상 모든 노드의 `적용`을 합집합**으로 모은 것. 서류 트리의 서류 상속과 같은 이유다 — 리프마다 복제하면 법 하나가 개정될 때 N군데를 고쳐야 해서 §8의 유지보수 매칭이 무너진다.

### 2.3 ★적용 항목 — 서류 트리의 `서류` 배열을 이 주제에 맞게 재설계

서류 트리의 리프 payload는 `{서류명, 근거법령, 근거조문, 구분(필수/조건부), 조건}`이었다. 이 주제의 payload는 "그 구역에서 무엇이 달라지는가"라서, **"무엇을(제목)·어떤 성격으로(유형)·누구에게(대상)·어느 범위까지(구역범위)"** 를 담도록 다시 짰다.

```jsonc
{
  "제목": "외국인이 어업활동을 하려면 선박마다 허가를 받아야 한다",   // 한 문장 요지(원문 기반)
  "유형": "허가·신고",     // 적용법령 | 의무 | 제한 | 허가·신고 | 완화 | 관할 | 처벌
  "대상": "외국인",        // 누구에게 걸리는가(원문이 밝힌 수범자). 없으면 null
  "근거법령": "배타적 경제수역에서의 외국인어업 등에 대한 …",
  "근거법령_slug": "배타적경제수역에서의외국인어업등에대한주권적권리의행사에관한법률",
  "계층": "법률",          // 법률 | 시행령 | 시행규칙
  "근거조문": "제5조",
  "법령ID": "010297",      // _meta.json families.<계층>.법령ID (H-29 11항·L-74)
  "파일": "raw/…/법률.txt",
  "인용": "① 외국인은 특정금지구역이 아닌 배타적 경제수역에서 …",   // ★스크립트가 raw에서 직접 읽어 채운다
  "구역범위": "이 구역만",  // 이 구역만 | 이 구역 이상 | 이 구역 이하   (§2.5)
  "조건": null,            // 언제 적용되는지(원문 문구 기반)
  "적용제외": "…",         // 있을 때만
  "위임": [ { "법령":"…", "계층":"시행령", "조문":"제4조" } ],   // 있을 때만
  "주의": "…"              // 판단이 애매했던 항목의 정직 메모
}
```

**왜 `유형`을 넣었나**: 같은 구역 안에서도 "이 법이 적용된다"(적용법령)와 "이걸 해야 한다"(의무)와 "여기선 완화된다"(완화)는 사용자에게 전혀 다른 정보다. 서류 트리는 payload가 전부 "갖춰 둘 서류"라 이 축이 필요 없었지만, 이 주제는 **완화(평수구역의 기상특보 예외 등)가 실제로 존재**해서 성격 표시가 없으면 답변 조립이 어렵다. 값은 7개로 고정하고 빌더·검증기가 둘 다 검사한다.

**불변식**(서류 트리와 동일): `인용`은 **스크립트가 raw 파일에서 직접 읽어 채운다**(사람이 타이핑하지 않는다). 앵커 문구가 그 조문에 없으면 **빌드 자체가 실패**한다(§6).
`인용`에 적용하는 유일한 가공은 **①공백 접기 ②이미지 태그(`<img …>`) 제거**다(어선안전조업법 제15조처럼 한자가 그림으로 들어간 조문이 있다). 문장이 중간에서 시작하면 앞에 `…`를 붙여 잘렸음을 드러낸다.

### 2.4 `포함근거` — "이 구역이 부모 안에 든다"의 근거를 따로 적는 자리

대부분의 포함관계는 정의 조문이 직접 말해 준다(예: 수상 = 해수면 + 내수면). 그런데 **접속수역 ⊂ 배타적 경제수역**은 그렇게 적은 조문이 없다 — 두 조문이 각각 밝힌 거리 범위(기선 12~24해리 / 12~200해리)를 대조해야 나온다. 이런 관계를 정의 provenance와 섞으면 "조문에 그렇게 써 있다"는 오해를 만들므로, **`포함근거: {설명, 근거[]}`** 라는 별도 필드에 *왜 그렇게 읽었는지*와 *대조한 두 조문*을 함께 싣는다.

### 2.5 `서열`·`구역범위` — 항해구역 트리에만 있는 두 필드

raw는 항해구역을 **순서가 있는 것**으로 다룬다. 실측 문구:

- 「선박설비기준」 제108조의4: *"**근해구역 이상**을 항해하는 선박"*
- 같은 기준: *"**연해구역이하**를 항해구역으로 하는 총톤수 500톤 이상의 선박"*
- 선원법 제86조제1항제1호: *"**연해구역 이상**을 항해구역으로 하는 선박(어선은 제외한다)"*
- 선박안전법 시행규칙 제14조제1항제1호: *"국제항해 및 **근해구역 이상**의 항해구역을 항해하는 선박"*

그래서 항해구역 노드에는 `서열`(평수 1 · 한정연해 2 · 연해 3 · 근해 4 · 원양 5)을 두고, 적용항목에는 `구역범위`("이 구역만" / "이 구역 이상" / "이 구역 이하")를 둔다. **이 서열은 우리가 매긴 순위가 아니라 원문 표현을 데이터로 옮긴 것**이다.

없으면 어떻게 되나(카파시 — 상한·필드를 넣기 전에 자문): "연해구역 이상"인 의무를 연해 노드에만 달면 형제인 근해·원양 리프가 그 의무를 상속받지 못해 **답이 틀린다**. 반대로 그 의무를 루트로 올리면 평수구역까지 딸려와 역시 틀린다. 두 오답 사이를 정확히 가르는 최소 장치라서 넣었다. 해역 트리·조업해역 트리는 이런 표현이 없으므로 `서열`을 두지 않고, 그 트리에서 "이 구역 이상"을 쓰면 빌드가 실패한다.

## 3. 계층 도출 — 상향식, 임의분류 금지

### 3.1 방법

1. raw에서 **정의 조항**(`정의`, `적용범위`, `…의 종류`, `적용제외`)을 읽어 **실제로 법이 정의한 구역 용어**만 모은다.
2. 그 용어들 사이의 **상하·배타 관계를 조문으로 확인**한다.
3. 근거가 확인된 것만 노드로 만든다. **하향식으로 "이쯤에서 나누면 좋겠다"고 지어내지 않는다.**

### 3.2 ★가장 중요한 발견 — "구역"은 한 줄로 이어지는 하나의 계층이 아니다

후보 문서 B절은 *"내수면 ⊂ 수상, 평수 ⊂ 연해 ⊂ 근해 ⊂ 원양"* 을 한 묶음으로 적었다. 실제로 raw를 훑어 보니 **두 표현은 서로 다른 축**이었다:

| 축 | 무엇으로 정해지나 | 근거 |
|---|---|---|
| **해역(장소)** | 그 지점이 어디냐 — 국가 관할의 문제 | 영해법 제1조(12해리)·제3조의2(24해리), EEZ법 제2조(200해리), 내수면어업법 제2조제1호, 수상레저안전법 제2조제6~8호 |
| **항해구역(선박 능력)** | 그 배의 **선박검사증서에 지정·기재된 구역** | 선박안전법 제8조제2항·제3항, 같은 법 시행규칙 제15조제1항 |
| **어선 조업해역** | 어선안전조업법이 조업·항행을 제한한 해역 | 어선안전조업법 제2조제4·6·7호(특정해역/조업자제해역/일반해역), 원양산업발전법 제2조제10호(해외수역) |

세 축은 서로 포함관계가 아니다. **한 트리로 합치려면 근거 없는 상위 노드를 지어내야 한다** — 그건 이 작업의 제1원칙 위반이다. 그래서 **축마다 뿌리를 따로 두고(트리 3개), `진입키워드`로 갈라 들어가게** 했다.

*검토했으나 채택하지 않은 대안*: ①루트에 "무엇이 궁금하세요(위치/배/조업)"라는 축 선택 노드를 두기 → 그 노드는 법정의가 없어 `provenance`를 채울 수 없다(출처 없는 노드 금지 위반). ②항해구역을 해역 트리 리프의 `추가확인`으로 밀어 넣기 → 항해구역 쪽 적용항목이 15건이라 "축"이 아니라 "각주"가 되어 정보가 사장된다.

### 3.3 각 트리의 분기와 그 근거

**① 해역(`sea_area`)**

**③ 어선 조업해역(`fishing_operation_area`)** — 어선안전조업법 제2조제7호의 *"「원양산업발전법」 제2조제10호에 따른 해외수역을 제외한 해역 중 특정해역 및 조업자제해역을 제외한 모든 해역"* 이라는 일반해역 정의가 **네 구역의 관계를 한 문장에 담고 있다**(= 법이 스스로 그은 완전 분할). 루트 provenance로 이 문장을 그대로 실었다.

### 3.4 트리로 쪼개지 **않은** 축

- **한정연해구역**(수상레저기구의 등록 및 검사에 관한 법률 시행령 제2조제1호나목) — 실재하는 구역이지만 노드로 만들지 않았다. 법률계열에 이 구역 전용 의무가 없고 세부기준이 전부 고시라, 노드를 만들면 **답이 달라지지 않는 질문만 하나 늘기** 때문이다. `서열` 표(§2.5)에는 2번으로 남겨 두었다.
- **국제항해 여부·총톤수·선박 국적**: 서류 트리와 마찬가지로 트리 레벨이 아니라 적용항목의 `조건`/`대상`과, 리프의 **`추가확인`**(축·질문·선택지·영향)으로 표현한다. 예: 영해·접속수역·그 밖의 EEZ 리프에는 "그 선박이 외국선박인가요?"(영해법 제5조 등 외국선박에만 걸리는 7개 항목이 켜짐), 원양구역 리프에는 "총톤수 5천톤 이상인가요?"(의료관리자). `영향`은 새 주장을 만들지 않고 **이미 검증된 적용항목의 제목만** 가리킨다.
- **연안해역·환경관리해역·해양용도구역 등 행정계획상 구역**: `unmapped`에 사유와 함께 기록(§5.4).

## 4. 비-리프 노드의 `질문`·`선택지`

서류 트리 §4의 규칙을 그대로 따른다.

1. **모든 비-리프는 `질문`과 `선택지`를 반드시 갖는다**(빌드 시 강제 — §6).
2. `선택지[].label`은 **raw에 실재하는 법률 용어**를 쓴다("근해구역 이상"도 원문 표현이다).
3. `선택지[].next`는 반드시 **그 노드의 자식 id**(참조 무결성 검사).
4. `선택지[].hint`는 그 용어의 법정의를 한 문장으로 풀어 쓴 것 — 정의 조항을 벗어나지 않는다.
5. `질문`은 존댓말 한 문장, 기존 `decideClarify`의 `intro`/`question` 규약과 호환.
6. **선택지 3개 이하**(`CLARIFY_OPTION_MAX = 3`). 이 규칙 때문에 어선 조업해역 루트를 (특정해역/조업자제해역/일반해역/해외수역) 4갈래로 두려던 초안을 **3갈래 + "그 밖의 해역" 아래 2갈래**로 다시 쪼갰다(서류 트리에서 "그 밖의 선박"을 3갈래로 다시 쪼갠 것과 같은 조치).

### 예시

```jsonc
// 해역 트리 루트 — decideClarify()가 지금 즉석 판단으로 묻고 있는 바로 그 갈림길
```

## 5. 추출 방법론

### 5.1 조문 분리 — 계열별 이중 형식 (L-54)

서류 트리와 동일. 법률·시행령·시행규칙은 `[제10조] 제목` **대괄호** 마커, 행정규칙(고시)은 `제7조(제목) ①…` **무대괄호** 마커. 스캔은 두 형식을 모두 처리하고, payload는 법률계열에서만 뽑는다(§5.4).

### 5.2 스캔 — "구역 용어 × 규범 문구" 2중 조건

서류 트리는 "동사 × 서류명사 × 장소구" 3중 조건이었지만, 이 주제는 **구역 용어 자체가 이미 강한 신호**라 2중이면 충분하다.

- **구역 용어**: `평수구역|한정연해구역|연해구역|근해구역|원양구역|내수면|해수면|영해|접속수역|배타적 경제수역|대륙붕|연안해역|경비수역|특정해역|조업자제해역|일반해역|해외수역|조업한계선|조업자제선|운항구역|항해구역|항행구역`
- **규범 문구**: `하여야 한다|해야 한다|받아야|아니 된다|아니한다|적용한다|적용하지|제한할 수 있다|금지|허가를|신고하여야|면허를|처한다|과태료|할 수 없다|하여서는`

두 조건을 같은 문장(항·호 단위로 쪼갠 700자 이내 조각) 안에서 요구한다. 후보 문장이 곧 트리 항목은 아니다 — 정의조항·부칙 경과조치·설비 수량 기준이 섞여 있어 사람이 추려 넣었다(§5.4).

**⚠ 반대 방향도 성립하지 않는다 — 후보 0건은 "그 법에 구역 규범이 없다"는 확증이 아니다** (2026-08-10 감사로 확인, §6.1). 사각지대가 두 가지 실측됐다:

1. **합성 정의어** — 법이 구역들을 묶어 한 낱말로 정의해 쓰면 위 구역용어 목록에 걸리지 않는다. 실제 사례: 선박평형수관리법은 영해·내수·배타적경제수역을 묶은 **"관할수역"**(제2조제11호)만 쓴다 → 적용범위 조문(제3조제2항)이 통째로 누락됐다.
2. **문장분리 경계** — 구역 용어와 규범 문구가 서로 다른 조각으로 갈리면 2중 조건이 성립하지 않는다. 실제 사례: 해양폐기물 및 해양오염퇴적물 관리법 제3조는 각 호(영해·내수/배타적 경제수역)와 "…적용한다"가 다른 조각이라 후보 0건인데, 내용은 트리에 실제로 들어가 있다.

그래서 산출물 JSON의 `scan.laws_without_candidates`는 **"스캔 후보도 없고 트리에도 반영되지 않은 법"** 만 담고, 후보 0건인데 사람이 원문에서 찾아 넣은 법은 `scan.laws_in_trees_without_candidates`로 따로 뺀다(둘의 합 = `summary.laws_without_scan_candidates`).

### 5.3 앵커 방식과 그 함정 두 가지(정직 기록)

SPEC에는 "어느 법 몇 조 + 그 조문에 있어야 할 문구(앵커)"만 적고, 인용문·법령ID·파일경로는 빌더가 raw에서 읽어 채운다. 이번에 **앵커 방식 자체의 함정 두 가지를 실측으로 만났다**:

1. **호환한자(U+F9FC)** — 외국인어업법 제5조제3항의 `표지(標識)`에서 `識`이 일반 U+8B58이 아니라 CJK 호환한자 U+F9FC였다. 눈으로는 똑같아 보이는데 문자열 매칭이 실패한다. → **앵커에 한자를 넣지 않는다**(빌더 주석에 명시).
2. **흔한 단어 앵커** — 어선안전조업법 제15조의 앵커를 `선단`으로 잡았더니 **조문 제목("어선의 선단 편성 조업")이 먼저 걸려** 인용문이 제목만 담았다. 서류 트리에서 5건의 오인용을 만든 것과 같은 실패모드다. → 앵커는 **의무 문구 전체**로 잡는다.

### 5.4 무엇을 트리에서 **뺐나**(scope-out)

| 유형 | 예 | 사유 |
|---|---|---|
| 구역별 설비·수량 기준(고시) | 「선박설비기준」 객석 단위면적표(근해구역 이상 0.85㎡ / 연해·한정연해 0.55 / 평수·내수면 0.45), 자기컴퍼스·음향수신장치 비치 기준 | **안전장비 트리(D) 소관** — 같은 시점에 별도 진행 중이라 중복을 만들지 않는다 |
| 해역 이름이 붙은 행정계획·용도구역 | 연안관리법의 연안통합관리계획·연안용도해역, 해양공간계획법의 해양용도구역 | "내가 지금 어디 있느냐"로 답이 갈리는 축이 아니다 |
| 부칙·경과조치의 구역 표현 | 선박직원법 시행령 부칙(근해구역·원양구역 외국선박 승무경력 인정) | 현재 의무가 아니다 |
| 자격·임용 요건의 구역 표현 | 해양사고의 조사 및 심판에 관한 법률 제9조의2(원양구역 항행 선박 선장 경력) | 심판관 자격요건이지 그 구역의 의무가 아니다 |
| 정의 인용만 있는 조문 | 수상레저기구의 등록 및 검사에 관한 법률 제2조제4~6호 | 다른 법 정의를 끌어 쓴 것뿐 |

이 목록은 산출물 JSON의 **`unmapped`** 키에 그대로 들어 있다.

## 6. 완결성·정확성 판정 — 무엇을 "다 뽑았다"로 보는가

**성공 기준(검증 가능, 카파시 4)**:

1. **커버리지 수치 공개**: 74법 전부를 스캔했음을 파일 수·조문 수로 밝히고, 어디까지 좁혀졌는지(구역 용어 등장 → 후보 문장 → 트리 반영)를 법 수로 보고한다.
2. **전량 재대조(표본 아님)**: 트리에 들어간 **모든** 노드 provenance·적용항목에 대해, 빌드 스크립트가 raw를 열어 ①그 조문이 실재하는지 ②그 조문 본문에 앵커 문구가 실제로 있는지 ③**뽑아낸 인용문 안에 그 앵커가 실제로 들어 있는지**를 확인한다. 하나라도 실패하면 **빌드 실패**(JSON을 만들지 않는다).
   - ③은 이번에 새로 넣은 검사다. 서류 트리의 인용 추출 함수는 항(①) 표시만 보고 시작점을 잡아, **호(1. 2. 3.) 목록이 긴 조문에서 앵커가 인용문 밖으로 밀려나도 조용히 통과**했다. 이번 초안에서 실제로 재현돼(유선 및 도선 사업법 제3조 등) 검사와 추출 로직을 함께 고쳤다.
3. **질문·선택지 무결성**: 비-리프에 `질문`·`선택지`가 있고, `next`가 실재하는 자식 id이며, 선택지 수 = 자식 수 ≤ 3.
4. **유형·구역범위 무결성**: `유형`은 7개 값, `구역범위`는 3개 값 중 하나. `서열`이 없는 트리에서 "이 구역 이상"을 쓰면 실패.
   리프의 `추가확인[].영향`은 **같은 트리에 실재하는 적용항목 제목**만 가리켜야 한다(깨진 `next` 참조와 같은 성격의 환각 통로라서 같이 막았다).
5. **독립 재대조**: 빌더 로직을 **재사용하지 않는 별도 스크립트**(`loop/verify_zone_tree.py`)가 파일 통짜 문자열로 다시 대조한다 — ①인용문이 그 파일에 실제로 있는지 ②그 인용문의 **위치가 그 조(條) 구간 안**인지(헤더 위치를 훑어 구간을 계산, 빌더처럼 딕셔너리로 쪼개지 않음) ③법령ID가 `_meta.json`과 맞는지 ④요약 수치가 실제 개수와 맞는지.
6. **재현성**: 빌드·검증 모두 스크립트 1회 실행으로 재현된다.

## 7. caveats (JSON에 그대로 실은 한계 목록)

1. **트리가 세 개다.** "평수 ⊂ 연해 ⊂ 근해 ⊂ 원양"과 "내수면 / 영해 ⊂ EEZ"는 같은 축의 계층이 아니다 — 전자는 선박검사증서에 적히는 "배의 능력", 후자는 "지점의 국가 관할"이다. 한 줄로 이어 붙이면 사실과 다르다.
2. 접속수역 ⊂ EEZ는 두 조문의 거리 범위를 대조해 얻은 관계다(`포함근거`에 명시).
3. **평수구역의 법정의에 "호소(호수와 늪)ㆍ하천"이 들어 있어 해역 트리의 "내수면"과 지리적으로 겹친다.** 축이 달라 오류는 아니지만, "내수면이니 평수구역은 아니다"라고 읽으면 틀린다.
4. **같은 낱말이 법마다 다른 뜻이다** — 해양경비법의 "근해수역"은 접속수역을 가리키고(제2조제4호), 선박안전법의 "근해구역"은 동경 94~175도의 항해구역을 가리킨다(시행규칙 제15조제4항).
5. 고시 계열은 스캔만 하고 payload로 담지 않았다(안전장비 트리 소관).
6. "한정연해구역"은 실재하지만 노드로 만들지 않았다(§3.4).
7. 트리에 담은 것은 원문에 문장으로 적힌 것뿐이다.
8. 자치법규·국제협약·별표 디렉토리는 스캔 대상이 아니다.
9. `조건`·`적용제외`는 원문 문구를 옮긴 것이지 정규화한 값이 아니다 — 거리·톤수 구간을 프로그램이 판정하려면 별도 파싱이 필요하다.
10. **2026-08-10 정밀수정**: 감사가 찾아낸 선박평형수관리법 제3조제2항("관할수역" 적용범위) 누락을 영해·EEZ 두 노드에 반영했다(§6.1).
11. **스캔의 사각지대**(§5.2): 합성 정의어(`관할수역`)와 문장분리 경계 때문에 후보 0건으로 나온 법이 있다 — `scan.laws_without_candidates`를 "구역 규범이 없는 법"으로 읽으면 안 된다. `관할수역`을 정규식에 넣으면 새로 걸리는 3법 9건 중 8건은 아직 트리에 반영하지 않았다(§6.1).

## 8. 유지보수 통합 설계 (H-29 연동 — **설계만**, 이번엔 배선 안 함)

서류 트리 설계 §8과 **완전히 같은 구조를 재사용한다.** 그 설계가 §8.3(d)에서 밝힌 조건 — *"새 트리도 모든 노드·항목에 `{근거법령, 계층, 근거조문}` provenance를 갖출 것"* — 을 이 트리가 그대로 지켰기 때문이다. 즉 **provenance 규약이 곧 유지보수 인터페이스**라는 주장이 이번에 실제로 검증됐다.

### 8.1 조인 키

`law_change_queue.json`(H-29가 주 1회 적재)의 각 항목은 `{law.slug, layer, changed_articles[].조문번호}`를 갖고, 이 트리의 모든 노드 provenance·적용항목은 `{근거법령_slug, 계층, 근거조문}`을 갖는다 → **조인 키는 `(slug, layer, 조문번호)`** 하나면 된다. `changed_articles[]`가 빈 변동(법령명·소관부처 변경)은 법 단위(slug)로 조인한다. `법령ID`도 처음부터 실어 두었으므로 법령명이 바뀌어도 추적이 끊기지 않는다(L-74).

### 8.2 제안 파이프라인 (다음 라운드 구현 대상)

```
detect_law_changes.py (H-29, 이미 있음)
        ↓  law_change_queue.json
[신규] loop/flag_trees.py                    ← 이번엔 만들지 않음
        ├ 큐의 각 item에서 (slug, layer, 조문번호) 추출
        ├ vessel_doc_tree.json · zone_tree.json 을 순회하며 같은 키를 가진 항목 탐색
        └ 매치되면 사이드카 파일에 review 플래그
             _dashboard/zone_tree_review.json
```

**설계 결정 4가지(서류 트리 §8.3과 동일한 근거)**: (a) 트리를 직접 고치지 않고 사이드카에 쓴다(트리는 빌드 산출물이라 손으로 고치면 다음 빌드에 날아간다). (b) **자동 재빌드하지 않는다** — 개정으로 앵커 검증이 실패하는 것은 "사람이 봐야 한다"는 정상 신호이고, 자동 재빌드는 그 신호를 지운다. (c) 시행일 예약은 큐의 `scheduled_for`를 그대로 쓴다. (d) 트리 파일명만 바꿔 같은 스크립트를 재사용한다 — **이 트리는 그 재사용 가능성을 처음으로 시험하는 두 번째 사례**이므로, `flag_trees.py`는 처음부터 트리 파일 목록을 인자로 받도록 만들 것을 권한다.

## 9. 되묻기(`decideClarify`) 연동 설계 (**설계만**, 이번엔 배선 안 함)

### 9.1 지금의 `decideClarify()`와 이 트리의 관계

`local_server/services/legal_retriever.js`의 `decideClarify()`는 질문마다 Gemini를 1회 호출해 근거자료(상위 6페이지 × 1,500자)를 읽히고 되묻기 JSON `{needed, intro, question, options[{label,hint}]}`을 만든다. 그 주석이 실사례로 든 갈림길이 *"하천·호소냐 바다냐"* 이고, **그게 이 트리 `sea_area`의 1단계 질문 그대로**다. 트리를 붙이면 이 갈림길에서 LLM 호출 0회로 같은(그리고 매번 동일한) 질문을 낼 수 있다.

### 9.2 제안 흐름

```
질문 "낚싯배에서 술 마시면?" / "우리 배 어디까지 나갈 수 있나요?"
  ↓
[신규] matchZoneTree(query)          ← trees[].진입키워드 와 대조(LLM 0회). 여러 트리가 걸리면 우선순위: 해역 > 조업해역 > 항해구역
  ↓ 매치되면
[신규] clarifyFromTree(node)         ← 트리에서 질문·선택지를 그대로 꺼냄(반환 스키마는 기존과 동일)
  ↓ 사용자가 버튼 선택 → 질의에 ' — 내수면' 이 붙어 재질의
[신규] resolveTreePath(query, tree)  ← 질의에 붙은 라벨로 현재 노드 복원
  ↓ 리프 도달
경로상 `적용` 합집합(+ 구역범위 규칙, §2.5)으로 답변 조립
  ↓ 매치 안 되면
기존 decideClarify() 그대로 (폴백)
```

### 9.3 연동 시 반드시 지킬 것

- **(a) 반환 스키마를 기존과 동일하게 유지**하면 `routes/legal.js`·`ai_chat.js`를 한 줄도 안 고쳐도 된다(서류 트리 §9.4(a)와 같은 결론).
- **(b) 라운드 상한**: 사용자 확정(2026-08-10, MASTER_PLAN H-36 미결①) — **트리 경로는 깊이가 데이터로 유한하므로 인위적 상한을 두지 않는다.** 이 트리의 최대 깊이는 4(해역: 수상→해수면→EEZ→접속수역)라 되묻기가 최대 3회 이어질 수 있다.
- **(c) 트리 라벨 문자열이 경로 복원의 계약이다**(`CLARIFY_JOINER = ' — '`). 라벨을 바꾸면 진행 중 대화가 깨진다 → 라벨은 **법률 용어 그대로 고정**.
- **(d) ★이 트리 고유의 쟁점 — 두 축이 한 대화에서 함께 필요할 수 있다.** "내 배로 제주도까지 갈 수 있나요?"는 *항해구역*(배의 능력)과 *해역*(위치) 둘 다 걸린다. 트리를 여러 개 두었으므로 **한 대화에서 트리를 갈아타는 규칙**이 필요하다. 세 가지 안이 있고, **어느 쪽인지는 사용자·오케스트레이터 결정 사항으로 남긴다**:
  1. 한 대화에 트리 하나만(첫 매치 트리로 끝까지). 가장 단순, 대신 반쪽 답.
  2. 리프 도달 후 다른 트리의 `진입키워드`가 질의에 남아 있으면 그 트리로 이어서 되묻기(트리 간 체이닝).
  3. 리프 도달 시 답변 본문에 "항해구역이 연해구역이라면 여기에 ○○이 더 붙습니다"처럼 병기(코드 변경 최소, 답이 길어짐).
  → 상한·분기를 새로 넣기 전에 *"이게 없으면 무엇이 잘못되나"* 를 한 문장으로 쓸 수 있어야 한다는 원칙(CLAUDE.md)에 따라, 지금 답할 수 있는 건 1번뿐이라 **기본값은 1번, 확장은 사용자 지시 후**로 둔다.
- **(e) canonical 게이트와의 관계**는 서류 트리와 동일한 미결 사항이다(트리는 raw 직인용이라 위키 canonical 여부와 축이 다르다) — 다음 라운드 결정.
