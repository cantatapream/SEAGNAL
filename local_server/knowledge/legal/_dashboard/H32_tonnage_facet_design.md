## 0. 왜 트리가 아니라 "사전"인가 (E절 판단을 그대로 이어받음)

`H32_hierarchy_candidates.md` E절은 톤수 축을 이렇게 평가했다:

> **주의**: **단독 트리로 만들면 안 된다.** 톤수는 그 자체로 답을 주지 않고 항상 다른 축(선박 종류·의무 종류)과 결합해서만 의미가 있다. 별도 트리가 아니라 **공통 "축(facet) 사전"**으로 만들어 여러 트리가 참조하게 하는 편이 맞아 보인다.

이 판단을 그대로 채택한다. "총톤수 20톤"만으로는 아무 답도 나오지 않는다 — **20톤이 무엇을 가르는지는 법마다 다르기 때문**이다(선박법에선 소형선박 정의, 해양환경관리법에선 오염물질 수거 의무 대상, 선박입출항법에선 계선신고 대상). 그래서 이 자산은:

- **트리가 아니다** — 루트도 리프도 없다. 다른 트리(선박종류·해역 등)가 "톤수 갈림길"을 만났을 때 **참조하는 부품**이다(§7).
- **하나의 통합 구간표가 아니다** — 항목 단위가 **(법령 · 계층 · 조문 · 축)** 이다. 같은 20톤이라도 조문이 다르면 별개 항목이다(§2.1의 "왜 합치지 않는가").

### ★사용자 확정 — 숫자 입력이 아니라 "구간 선택지"로 (2026-08-10, 착수 직후 반영)

착수 지시는 처음 *"톤수는 숫자를 직접 물어야 한다"*(숫자 입력 → 구간 매핑)였으나, 착수 직후 **수정 지시**가 왔다. 원문 인용:

> "**'몇 톤인가요?'류 숫자 직접입력 방식을 버리고, 대신 다른 트리들과 똑같은 '선택지 클릭' 방식으로 바꿔라.** 이유: 사용자가 정확한 톤수를 모를 수 있고, 정확한 숫자를 몰라도 대략 어느 구간인지는 고를 수 있는 게 더 편하다."
> "**★중요**: 이 구간 경계값은 **법마다 다를 수 있다** — 어떤 법이 '소형선박'을 20톤 미만으로 보고 다른 법은 5톤 미만으로 볼 수 있다. 그러니 **법/맥락 단위로 구간을 따로 만들어야** 한다."
> "선택지 개수 제한(기존 트리의 3개 이하 규칙)은 이 주제엔 안 맞을 수 있다 … 억지로 3개로 줄이지 말고, 실제 raw에 있는 구간 수 그대로 반영하되, 너무 많으면(예: 5개 이상) 사용자 확인이 필요하다고 caveats에 남겨라."

이 수정은 **1차 추출을 끝내기 전(raw 스캔 규칙 확정 단계)에 반영**했다 — 숫자입력 스키마로 데이터를 만든 적이 없으므로 후속 변환 패스는 없었다. (원문 인용을 병기하는 이유는 CLAUDE.md 결정로그의 *"사용자 발언을 설계 문서로 옮길 때 원문 인용을 병기"* 규칙 때문이다. 요약만 남기면 나중에 대조가 불가능하다.)

## 2. 스키마

### 2.1 facet 항목 (사전의 1건)

```jsonc
{
  "id": "gt__선박법__법률__제1조의2",     // 축코드__법슬러그__계층__조문 (안정 식별자)
  "축": "총톤수",                          // 총톤수 | 국제총톤수 | 재화중량톤수 | 길이 | 선박길이 …
  "단위": "톤",                            // 톤 | 미터
  "맥락": "정의",                          // ★조문 제목 원문 그대로(우리가 요약한 값이 아니다)
  "근거법령": "선박법", "근거법령_slug": "선박법",
  "계층": "법률", "근거조문": "제1조의2",
  "법령ID": "000068",                      // _meta.json families.<계층>.법령ID (H-29 11항·L-74)
  "파일": "raw/04_선박해운/선박법/법률.txt",
  "질문": "이 선박의 총톤수는 어느 구간에 속하나요? (「선박법」 제1조의2 「정의」 기준)",
  "선택지": [ …§2.2… ],
  "임계값": [ …§2.3… ],
  "경계": [ { "값": 20.0, "표기": "20톤", "경계값_귀속": "위" }, … ],   // 오름차순
  "주의": "선택지가 9개다 — …"            // 판단이 애매하거나 사람이 봐야 하는 항목만
}
```

**★왜 (법·계층·조문·축) 단위인가 — 합치면 안 되는 이유**
`H32_hierarchy_candidates.md` **C절**이 인허가 유형에 대해 경고한 것과 같은 함정이다: *"같은 단어가 법마다 다른 강도를 뜻할 수 있어 … 법을 가로질러 한 트리로 합치면 틀린다."* 톤수는 더 심하다 — 숫자가 같아도 가르는 대상이 다르다. 실측 사례(§5.2 `용어_충돌`): **"소형선박"이 선박법에선 총톤수 20톤 미만, 선박직원법 시행령에선 25톤 미만, 선박안전법에선 선박길이 12미터 미만, 수색구조법 시행령에선 100톤 미만**이다. 하나의 "소형선박 구간표"를 만들었다면 **네 법 중 셋에 틀린 답**을 주게 된다.

### 2.2 선택지(구간) — 되묻기가 그대로 꺼내 쓰는 데이터

```jsonc
{
  "label": "총톤수 20톤 이상 100톤 미만",
  "이상": 20.0, "초과": null, "미만": 100.0, "이하": null,   // null인 쪽은 제한 없음(무한)
  "단위": "톤",
  "결과": [ { "문구": "총톤수 100톤 미만", "인용": "총톤수 100톤 미만인 부선", "임계값": 1 } ],
  "hint": "원문 조건: 총톤수 100톤 미만"
}
```

- **`결과`는 우리가 해석한 결론이 아니라 그 구간에서 실제로 걸리는 원문 조건·원문 문장**이다. `임계값`은 그 facet의 `임계값[]` 인덱스라 되짚어 볼 수 있다.
- 해당하는 조건이 없는 구간은 `결과: []` + hint에 *"이 구간에는 이 조문의 총톤수 조건이 적용되지 않는다"* 로 **정직하게 빈 값**을 준다(억지로 뭔가를 채우지 않는다).
- 트리 노드의 `선택지[{label,hint,next}]`와 모양이 호환된다 — 다만 `next`(다음 노드) 대신 **`결과`(그 구간이 뜻하는 것)** 를 갖는다. 사전은 트리가 아니라서 갈 곳이 없기 때문이다(§7의 연동 규약).

**구간 경계의 뜻**: `이상`/`초과`는 하한, `미만`/`이하`는 상한. 이상·미만 쌍에서는 경계값이 **위 구간**에, 초과·이하 쌍에서는 **아래 구간**에 속한다. 한 경계에 두 방식이 섞이면 그 값만 떼어 **"정확히 N톤"** 단일점 구간을 만든다(§3.3).

### 2.3 임계값 항목

```jsonc
{
  "문구": "총톤수 20톤 미만",          // raw에서 정규식이 잡은 그대로
  "값": 20.0, "표기": "20톤", "단위": "톤", "비교": "미만",
  "인용": "총톤수 20톤 미만인 기선 및 범선 2. 총톤수 100톤 미만인 부선",
  "상위인용": "② 이 법에서 \"소형선박\"이란 다음 각 호의 어느 하나에 해당하는 선박을 말한다. 1. 총톤수 20톤 미만인 기선 및 범선 …"
}
```

**불변식**
1. `인용`·`상위인용`은 스크립트가 raw에서 직접 읽어 채운다. 사람이 타이핑하지 않는다.
2. `문구`·`인용`·`상위인용`은 그 조문 원문(공백 정규화)의 **부분문자열**이어야 한다 — 아니면 빌드 실패.
3. `문구`는 반드시 `인용` 안에 들어 있어야 한다 — 인용이 잘려 정작 숫자가 빠지는 사고를 막는 게이트(실제로 이 게이트 때문에 인용 시작점 로직을 한 번 고쳤다).
4. **`상위인용`이 400자를 넘으면 담지 않는다(null)** — 앞부분만 잘라 담으면 정작 임계값이 빠진 "맥락 없는 맥락"이 되어 오해를 부른다.

**★`상위인용`을 따로 두는 이유**: 호(號)만 인용하면 *"1. 총톤수 20톤 미만인 기선 및 범선"* 이 되어 **이 20톤이 무엇을 정의하는지가 통째로 사라진다.** 항(項) 문장까지 올려 잡으면 *"이 법에서 「소형선박」이란 …"* 이 함께 보인다. 인용은 짧고 정확하게, 맥락은 별도 필드로 — 두 마리를 한 필드에 담으려다 어느 한쪽을 잃지 않기 위한 분리다.

## 3. 추출 규칙 — 무엇을 "기준값"으로 보는가

### 3.1 정규식(축 × 숫자 × 단위 × 괄호 × 비교어)

```
(국제총톤수|총톤수|재화중량톤수|적재톤수|선박길이|선체의 길이|길이)
  [가이는은을를]? ([0-9][0-9,]*(\.[0-9]+)?) (만|천)? (톤|미터)
  (\([^)]{0,120}\))?                       ← 괄호 삽입구
  [을를이가인의]? (이상|미만|초과|이하|넘는|넘지|이내)?
```

- **괄호 삽입구를 건너뛴다**: 해양환경관리법 시행규칙 제73조 *"총톤수 100톤(군함과 경찰용 선박의 경우에는 경하배수톤수 200톤) 미만"* — 이 처리가 없으면 비교어를 못 찾아 조용히 누락된다(실측으로 발견해 추가).
- **정규화**: `넘는`→초과, `넘지(아니하는)`→이하, `이내`→이하. 표현만 다른 같은 뜻이다. (`이내`는 법률계열 전수에서 수산업법 시행령 제37조 *"총톤수 3톤 이내"* 1건뿐.)
- **`만`·`천` 배수**: `5천톤`→5000, `2만톤`→20000, `20,000톤`→20000.

### 3.2 무엇을 **기준값으로 보지 않는가**(→ `보류`)

| 사유 | 실례 |
|---|---|
| 비교어가 없다 = 가르는 기준이 아니라 단순 서술 | 수산업법 시행령 제37조 *"총톤수 3톤까지 선복량을 늘리거나"* |
| 숫자 표기의 자릿수 구분이 불완전해 값을 확정할 수 없다 | 선박직원법 시행령 부칙 표의 *"총톤수 2,00톤 이상"* (200인지 2,000인지 원문만으론 정할 수 없다 → **지어내지 않는다**) |

법률계열 전수에서 `보류`는 **1건**뿐이다(위 수산업법 사례). "거의 다 잡혔다"가 아니라 **"거른 것이 무엇인지 한 건까지 남겨뒀다"**는 뜻이다.

### 3.3 ★부칙(附則)을 자른다 — 자르지 않으면 옛 수치가 현행으로 둔갑한다

raw의 법률계열 파일은 마지막 조문 뒤에 **부칙 전문**이 이어 붙어 있다. 조문 분리기가 이를 자르지 않으면 **마지막 조가 부칙 전체를 삼킨다.** 실측 사례:

- 「어선법 시행규칙」 **제77조는 본문이 "삭제"** 인데, 부칙 경과조치의 톤수·길이 4종이 그 조문의 기준값으로 딸려 들어왔다.
- 「선박직원법 시행령」 **제26조(과태료의 부과기준)** 에 **1984년 부칙의 승무기준표**(총톤수 500톤/2만톤 등 9종)가 붙었다.

→ 조문 분리 시 첫 `부칙` 줄에서 자른다. **241개 법률계열 파일 전수 확인 결과, 첫 `부칙` 줄 뒤에 `[제N조]` 마커가 다시 나오는 파일은 0개**라 이 컷은 안전하다(추정이 아니라 전수 확인). 별도 `부칙*.txt` 파일과 `*_발췌.txt`(다른 법 조문을 이 법 폴더에 발췌해 둔 것 — 그대로 쓰면 provenance가 엉뚱한 법으로 붙는다)도 같은 이유로 제외하고, 제외한 파일과 그 등장 수는 `scan.제외파일`에 남긴다.

### 3.4 계열 범위 — 고시(행정규칙)를 담지 않은 이유

74법 전수 스캔은 **법률계열 + 고시계열 둘 다** 돌렸다(수치는 §5.1). 그러나 사전에는 법률·시행령·시행규칙만 담았다. 근거:

1. 고시 등장 1,290건의 대부분이 **「선박설비기준」(248) · 「선박소방설비기준」(128) · 「어선설비기준」(123)** 류의 **설비 규격표**다 — "이 배가 어느 구간이냐"를 묻는 갈림길이 아니라 "그 구간의 배에 무슨 설비를 몇 개" 라는 **다른 축**이고, 그 축은 선박종류 트리의 `장비` 배열(`H32_vessel_doc_tree_design.md` §11)이 이미 담당한다. 여기 또 담으면 같은 데이터가 두 자산에 갈라져 유지보수가 무너진다.
2. 나머지 상당수는 **항만시설사용료 표·정박지 지정 고시·표준어선형 설계도면** 등 특정 항만·특정 선형의 세부표다(선박 분류 기준이 아니다).
3. 고시 raw에는 **표 이미지 OCR 전사본**이 섞여 있어(같은 설계 §11.6) 값의 신뢰 수준이 계열마다 다르다 — 사람 확인 없이 사전에 넣을 수 없다.

→ **수치는 전부 `scan.행정규칙`에 공개**해 다음 라운드가 그대로 이어받게 한다(숨기지 않는다). *이 판단은 착수 지시("74법 raw 전수 스캔")를 스캔 범위가 아니라 **채택 범위**에서 좁힌 것이므로 최종 보고에서 확인 대상으로 올린다.*

## 4. 구간(band) 계산 — 정확히 언제 무엇이 적용되는가

1. 그 조문·그 축의 임계값들에서 **서로 다른 값**을 뽑아 오름차순 정렬 → 경계(cut point).
2. 각 경계마다 **그 값 자체가 어느 구간에 속하는지**를 원문 비교어로 정한다: 이상/미만 → 위 구간(`귀속: 위`), 초과/이하 → 아래 구간(`귀속: 아래`).
3. 경계를 하나씩 지나며 구간을 닫고 연다 → **빈틈도 겹침도 원리적으로 생기지 않는다.**
4. 각 구간의 `결과`는 **그 구간 안의 모든 값에서 참인 조건**만 담는다(구간 내부에서 참·거짓이 갈리지 않으므로 대표점 하나로 판정).

### ★혼재 경계 — 독립 검증이 실제로 잡아낸 결함

같은 값에 **두 방식이 섞이는 경우**가 실재한다. 수산업법 시행령 제37조에는 *"총톤수 3톤 **미만**"* 과 *"총톤수 3톤 **이내(=이하)**"* 가 함께 있다. 처음엔 "이상/미만 방식을 택하고 `주의`를 단다"로 처리했는데, **독립 재대조 스크립트가 표본 스윕으로 "3톤 이상" 구간 안에서 조건의 참·거짓이 갈린다(3.0에선 참, 3.5에선 거짓)"는 것을 잡아냈다.** 애매함을 메모로 덮으면 데이터가 조용히 틀린다.

→ 혼재 경계는 **그 값만 떼어 "총톤수 정확히 3톤" 단일점 구간**을 만든다(`귀속: 단독`). 구간은 `3톤 미만` / `정확히 3톤` / `3톤 초과` 세 개가 된다. 정확하고, 사용자도 고를 수 있다.

*(이 사건은 CLAUDE.md 결정로그의 **"구현자가 만든 테스트는 구현자의 가정을 공유한다 → 독립 검증이 필요하다"** 를 이번에도 그대로 재현했다. 빌더 자체 검증은 이 결함을 통과시켰다 — 빌더와 같은 대표점 계산을 썼기 때문이다.)*

## 7. 다른 트리와의 연동 — **제안만**(이번엔 기존 파일을 고치지 않았다)

사용자 지시 6항에 따라 `vessel_doc_tree.json` 등 **다른 자산은 한 글자도 고치지 않았다**(다른 에이전트가 동시 작업 중). 아래는 다음 라운드 제안이다.

### 7.1 참조 규약 — 트리의 `추가확인`에 facet id를 건다

선박종류 트리는 톤수 축을 이미 리프의 `추가확인`으로 갖고 있다(`H32_vessel_doc_tree_design.md` §3.3·§4). 거기에 **필드 하나만 더하면** 된다:

```jsonc
// vessel_doc_tree.json 의 리프 (제안 — 이번에 적용하지 않음)
"추가확인": [
  { "축": "총톤수",
    "facet_ref": "gt__선박법__법률__제26조",     // ★추가되는 필드 하나
    "영향": ["선박국적증서", "선박검사증서"] }
]
```

- **`질문`·`선택지`를 트리에 복제하지 않는다.** 트리는 `facet_ref`만 갖고, 되묻기가 사전에서 꺼내 쓴다. 복제하면 법 개정 시 두 곳을 고쳐야 해 유지보수가 무너진다(서류 상속 규약을 만든 것과 같은 이유).
- **`facet_ref`는 배열이어도 된다** — 한 리프가 여러 법의 톤수 기준에 걸릴 수 있다(어선이면 어선법 기준과 선원법 기준을 함께 물어야 할 수 있다).

### 7.2 되묻기 흐름 (제안)

```
트리가 리프에 도달 → 남은 `추가확인` 중 facet_ref가 있는 것
   ↓
facetOf(ref) 로 사전에서 항목을 꺼낸다 (LLM 0회)
   ↓
{ needed:true, intro, question: facet.질문,
  options: facet.선택지.map(b => ({ label: b.label, hint: b.hint })) }   ← 기존 decideClarify 반환 스키마와 동일
   ↓
사용자가 구간 클릭 → 질의에 ' — 총톤수 20톤 미만' 이 붙어 재질의
   ↓
resolve: 질의 조각을 facet.선택지[].label과 문자열 대조해 어느 구간인지 복원
   ↓
그 구간의 `결과`(원문 조건·인용)를 답변 근거로 넘긴다
```

**설계 결정(연동 시 지킬 것)**
- **(a) 반환 스키마를 기존 `decideClarify()`와 동일하게 유지**하면 `routes/legal.js`·`ai_chat.js` 무변경으로 붙는다(자매 설계 §9.4(a)와 같은 원칙).
- **(b) `label` 문자열이 경로 복원의 계약이다.** 라벨을 바꾸면 진행 중인 대화가 깨진다 — 라벨은 빌더가 원문 표기에서 결정론적으로 만들므로, **표기 규칙을 바꾸는 것은 계약 변경**임을 인지할 것(자매 설계 §9.4(d)와 같은 성격).
- **(c) ~~`CLARIFY_OPTION_MAX = 3` 과 충돌한다.~~ → ✅ 해소(2026-08-15)**: 사용자 지시로 상한을 **3 → 10** 으로 올렸다. 이 사전의 선택지는 최대 **9개**(154개 항목 중 4개 이상은 8개뿐 — 4개 3건·5개 3건·9개 1건, 나머지 146건은 2~3개)라 **전부 새 상한 안**이다. 아래 원문은 결정 경위 기록으로 남긴다. 참고로 당시 예상과 달리 상한을 손대는 쪽이 됐는데, 근거는 클라이언트 `.nrya-clarify-btns` 가 이미 `flex-wrap:wrap` 이라 버튼 수가 늘어도 줄바꿈될 뿐 **잘라 먹지 않는다**는 점이 확인됐기 때문이다(= 3 상한이 막으려던 사고가 애초에 일어나지 않는다).
- ~~**(c-원문)** `CLARIFY_OPTION_MAX = 3` 과 충돌한다.~~ 이 사전엔 4개 이상인 항목이 있다(§5.3, 최대 9). 트리 쪽은 3개 상한을 빌드 게이트로 강제하고 있으므로, **사전을 되묻기에 붙이려면 상한 처리 방침을 먼저 정해야 한다** — 억지로 3개로 줄이지 말라는 사용자 지시가 있으므로 UI 쪽(스크롤·2단 질문)이나 상한 자체를 손대는 쪽이 될 텐데, **결정은 사용자에게 넘긴다.** (CLAUDE.md: *"상한은 '없으면 뭐가 잘못되나'를 한 문장으로 못 쓰면 넣지 않는다"* — 여기서 3개 상한이 막는 사고는 "UI가 선택지를 잘라 먹는다"로 명확하므로, 상한을 없애는 게 아니라 **UI를 고치는 쪽**이 맞아 보인다.)
- **(d) 사전 단독으로 답을 만들지 않는다.** 이 자산은 "어느 구간인지"만 가른다. 구간에 따른 의무는 조문(인용)과 다른 트리가 정한다.

### 7.3 유지보수(H-29 연동) — 조인 키가 이미 같다

`law_change_queue.json`의 항목은 `(slug, layer, 조문번호)`를 갖고, 이 사전의 모든 facet도 `근거법령_slug`·`계층`·`근거조문`을 갖는다 → **조인 키가 그대로 일치**한다. 자매 설계 §8.3의 `flag_*.py` 를 **파일명만 바꿔 재사용**할 수 있다(그 설계 §8.3(d)가 말한 "provenance 규약이 곧 유지보수 인터페이스"의 두 번째 사례). `법령ID`도 처음부터 실어 두었다(나중에 백필하는 것보다 싸다).

**자동 재빌드는 하지 않는다** — 조문이 개정되면 인용·문구 대조가 실패해 빌드가 깨지는데, 그건 **정상적인 "사람이 봐야 한다" 신호**다.

## 8. caveats (JSON에 그대로 실은 한계 목록)

1. 이 사전은 "무엇을 하라"를 말하지 않는다 — **어느 구간인지만** 가른다. 단독으로 답변 근거로 쓰면 안 된다.
2. **한 조문 안에 대상이 서로 다른 조건이 섞여 있을 수 있다.** 예: 선박법 제1조의2제2항은 *"총톤수 20톤 미만인 기선 및 범선"* 과 *"총톤수 100톤 미만인 부선"* 을 함께 정하는데, 구간 계산은 숫자만 보므로 20톤 미만 구간의 `결과`에 부선 조건도 함께 뜬다. **숫자 구간만으로 답을 확정하지 말고 반드시 `인용`의 대상(기선·범선·부선·동력어선 등)을 함께 봐야 한다.**
3. `이내`→`이하`, `넘는`→`초과` 정규화를 했다(표현만 다른 같은 뜻).
4. 항목 단위가 (법·조문·축)이라 같은 법 안에서도 조문마다 항목이 따로 있다 — 중복이 아니라 가르는 대상이 다르기 때문이다.
5. 행정규칙(고시) 계열은 커버리지 집계만 하고 사전에 담지 않았다(§3.4).
6. 부칙·발췌 파일은 제외했다(§3.3).
7. **별표·별지 서식은 이번 스캔 대상이 아니다** — 승무기준표(선박직원법 별표)처럼 **별표에만 있는 톤수 구간은 이 사전에 없다.**
8. `맥락`은 조문 제목을 그대로 옮긴 것이지 "무엇을 가르는지"의 요약이 아니다.
9. 선택지 5개 이상인 항목은 되묻기 UI에 그대로 쓰기엔 많다(§5.3) — 사람 확인 필요.
10. "길이"·"선박길이"·"국제총톤수" 등 서로 다른 법률 용어는 합치지 않았다(법마다 측정 방법·정의 조문이 다르다).
