## 1. ★최상위가 단일 루트가 아니라 `subtrees`인 이유 (이 설계의 핵심)

### 1.1 문제 — "신고"는 법마다 다른 것을 뜻한다

C절 주의사항이 지적한 그대로다. 실측으로 확인한 예:

| 법 | "신고"가 뜻하는 것 | 실제 강도 |
|---|---|---|
| 수산업법 제48조 | **신고어업** — 이걸 해야 어업을 개시할 수 있다. 유효기간 5년(같은 조 제4항), 위반 시 벌칙 | 진입규제 |
| 유선 및 도선 사업법 제3조제1항 | 총톤수 5톤 미만·정원 13명 미만·영업구역 2해리 미만이면 **면허 대신 신고**(같은 법 시행령 제3조) | 진입규제(면허의 하위 강도) |
| 낚시 관리 및 육성법 제25조 | **낚시어선업 신고** — 신고요건(선령·설비·안전성검사·선장 자격·전문교육)을 갖춰야 수리된다 | 진입규제(사실상 허가급) |
| 낚시 관리 및 육성법 제33조 | **출입항 신고** — 이미 영업 중인 자가 매 출항마다 하는 절차 | 진입규제 아님 |
| 해운법 제18조 | **휴업·폐업 신고** — 이미 면허받은 자의 사후 절차 | 진입규제 아님 |

**같은 단어가 같은 법 안에서도 다른 층위에 있다**(낚시법 제25조 vs 제33조). 그러므로 "면허 > 허가 > 등록 > 신고" 같은 **법을 가로지르는 단일 강도 순서를 우리가 정하면 그건 지어낸 것**이 된다 — 어느 조문에도 그런 서열이 적혀 있지 않다.

### 1.2 결정

**최상위 = `subtrees`(법령별 하위트리의 배열).** 각 서브트리는 자기 법 안에서만 계층을 갖는다. 서브트리 사이를 잇는 상위 노드는 **만들지 않는다.**

빌더가 이 원칙을 **코드로 강제**한다(§6 검증 5번): 한 서브트리 안의 모든 노드 provenance·모든 의무 항목의 `근거법령_slug`가 그 서브트리의 법과 같아야 하며, 다르면 빌드 실패. 즉 **법 경계를 넘는 데이터는 물리적으로 들어갈 수 없다.**

### 1.3 그럼 되묻기는 어디서 시작하나 — 진입점이 다르다는 것을 정직하게

`vessel_doc_tree.json`은 루트에 "어떤 배에 관한 것인가요?"라는 **첫 질문**이 있어 대화가 트리 안에서 시작된다. 이 트리는 그럴 수 없다 — 첫 질문이 "어느 법에 관한 것인가요?"가 되면 사용자가 답할 수 없기 때문이다(사용자는 법 이름을 모른다. 그래서 챗봇을 쓴다).

→ **진입은 기존 검색(`search()`)이 한다.** 질문에서 법이 좁혀진 뒤 그 법의 서브트리로 들어간다. 74법을 아우르는 인위적 상위 분류를 만드는 대신, **이미 잘 도는 검색을 진입점으로 재사용**한다(§9). 트리를 억지로 하나로 합치지 않기 위해 치르는 대가이고, 이게 C절 주의사항을 지키는 유일한 방법이다.

**검토했으나 채택하지 않은 대안**: ①74법을 분야(어업/레저/해운/항만/환경)로 묶는 상위 노드 — 그 분야 구분은 어느 조문에도 없다(지어낸 분류). ②면허/허가/등록/신고를 1단으로 올리고 그 밑에 법을 두기 — §1.1이 보인 대로 같은 단어의 의미가 법마다 달라 **1단에서 이미 틀린다.**

## 2. 스키마

### 2.1 최상위

```jsonc
{
  "generated": "2026-08-10T..+09:00",
  "scope": "74법 raw 전수 스캔 — '인허가 유형(면허/허가/신고/등록)' 법령별 계층 트리",
  "semantics": { "법단위_분리": "…", "의무_상속": "…", "질문_선택지": "…", "추가확인": "…" },
  "caveats": [ … ],
  "summary": { … },
  "scan":    { … },          // 74법 전수 스캔 커버리지(어디까지 봤는지)
  "unmapped":{ … },          // 스캔에 걸렸으나 서브트리를 만들지 않은 것 + 사유
  "subtrees":[ { …법령별 하위트리 루트… } ]

```

### 2.2 노드(공통) — 선례 규약 그대로 + `법령_slug` 추가

```jsonc
{
  "id": "susaneop__myeonheo_eoeop",   // 전역 유일. 서브트리 루트 id가 접두어(법 경계를 id에서도 보이게)
  "라벨": "면허어업",                  // 사용자에게 보이는 법률 용어 그대로(임의 조어 금지)
  "법령_slug": "수산업법",             // ★모든 노드에 필수 — 법단위 분리 검증의 키(§6-5)
  "인허가유형": "면허",                // 면허 | 허가 | 등록 | 신고 | 복합 | (루트는 null)
  "정의": "정치망어업·마을어업을 하려는 자가 시장·군수·구청장에게 받아야 하는 면허",
  "provenance": [                     // ★출처 없는 노드 금지
    { "법령":"수산업법", "법령_slug":"수산업법", "계층":"법률", "조문":"제7조",
      "법령ID":"…", "파일":"raw/…/수산업법/법률.txt",
      "인용":"① 다음 각 호의 어느 하나에 해당하는 어업을 하려는 자는 시장ㆍ군수ㆍ구청장의 면허를 받아야 한다." }
  ],
  "질문": "…",                         // ★비-리프에만
  "선택지": [ {"label":"…","hint":"…","next":"<자식 id>"} ],   // ★3개 이하
  "children": [ … ],                   // 비-리프
  "의무": [ …의무항목… ],               // ★리프에만(최소 1건 — 취득 근거)
  "추가확인": [ … ]                     // 리프의 잔여 축(트리로 안 쪼갠 조건)
}
```

**서브트리 루트도 리프일 수 있다.** 그 법에 인허가 체계가 하나뿐이면(예: 수산부산물재활용촉진법 = 처리업 허가 하나) 자식을 만들지 않는다. 자식이 1개뿐인 분기는 **되묻기에서 물을 것이 없는 가짜 갈림길**이므로 만들지 않는다.

### 2.3 의무 항목

```jsonc
{
  "의무명": "근해어업·연안어업·구획어업 허가 취득",
  "유형": "취득",                       // 취득 | 유효기간 | 후속신고 | 제재
  "근거법령": "수산업법", "근거법령_slug": "수산업법",
  "계층": "법률",                        // 법률 | 시행령 | 시행규칙
  "근거조문": "제40조", "법령ID": "…",
  "파일": "raw/…/수산업법/법률.txt",
  "인용": "① 총톤수 10톤 이상의 동력어선…을 사용하는 어업(이하 \"근해어업\"이라 한다)을 하려는 자는 어선 또는 어구마다 해양수산부장관의 허가를 받아야 한다.",
  "수준": "3년 이하의 징역 또는 3천만원 이하의 벌금",   // 유형=제재일 때만
  "비고": null
}
```

**불변식**:
1. `인용`은 **빌더가 raw에서 직접 읽어** 채운다(사람이 타이핑하지 않는다).
2. SPEC에는 "어느 법 몇 조에 이런 문구가 있다"(=앵커)만 적는다. 앵커가 그 조문 원문에 없으면 **빌드 실패**.
3. `유형: "제재"` 항목은 **사람이 안 쓴다** — 빌더가 그 법의 벌칙·과태료 조문을 열어 근거조문을 참조하는 호(號)를 찾아 자동으로 만든다(§5.3).
4. `근거법령_slug`는 반드시 그 서브트리의 법과 같다(§6-5).

## 3. 계층 도출 — 상향식, 법이 그어둔 선만 쓴다

### 3.1 무엇을 "인허가"로 보는가 (진입규제 판정 기준)

**채택**: 어떤 사업·어업·행위를 **개시하는 것 자체를 조건 짓는** 것 — 원문 문형이 `…을 (하려는|경영하려는|영위하려는) 자는 … (면허를 받아야|허가를 받아야|등록하여야|신고하여야) 한다`.

**제외**(진입규제가 아님 — `unmapped.유형_단위`에 기록):

| 유형 | 예 |
|---|---|
| 이미 인허가받은 자의 후속 절차 | 변경신고·휴업·폐업·재개업 신고(해운법 제18조, 수상레저안전법 제41조 등) — 단, 리프의 `의무`에 `유형:"후속신고"`로는 담는다 |
| 매 회차 절차 신고 | 출입항 신고(낚시법 제33조·선박입출항법 제4조·어선안전조업법 제8조) |
| 사고·발견 신고 | 항로표지법 제17조, 수색구조법 제19조 |
| 행정계획 승인·실시계획 승인 | 항만법 제10조, 신항만건설촉진법, 해양공간계획법 |
| 기관 지정(사업자 진입이 아니라 공적 업무 위탁) | 농수산물품질관리법 제9조·제64조, 폐기물관리법 제17조의2 |
| 개인 신분 등록 | 출입국관리법 제31조 외국인등록 |

**경계 판단을 남긴 것**: 자격면허(수상레저안전법 제5조 조종면허, 도선법 제4조 도선사면허)는 "사업 진입"이 아니라 "사람의 자격"이지만, **사용자 질문("면허 있어야 돼요?")의 축이 같고 조문 문형도 같아** 채택했다. 노드에 `인허가유형: "면허"` + `대상: "자격"`으로 구분해 표시한다. *(이 판단은 지시 문언을 넓힌 쪽이므로 최종 보고에서 확인 대상으로 올린다.)*

### 3.2 서브트리 안의 계층은 어디서 오나 — 3가지 근거만 허용

1. **장(章) 구조**: raw 원문에 `제2장 면허어업`, `제3장 허가어업과 신고어업`, `제4장 어획물운반업`처럼 법 스스로 그어둔 편제가 있다. 이걸 그대로 쓴다.
2. **정의 조항**: 수산업법 제2조가 "어업"·"어획물운반업"을 각각 정의한다 → 그 정의가 형제 노드의 배타성 근거가 된다.
3. **조문 자체의 항(項) 분기**: 수산업법 제40조 ①근해어업 ②연안어업 ③구획어업처럼 한 조문이 항으로 갈라둔 것.

**하향식으로 "이쯤에서 나누면 좋겠다"고 지어내지 않는다.** 세 근거 중 어느 것도 없으면 나누지 않고 리프로 둔다.

### 3.3 선택지 3개 상한 때문에 다시 쪼갠 실례

`decideClarify()`의 기존 상한이 `CLARIFY_OPTION_MAX = 3`이라 4갈래를 만들면 되묻기 UI가 선택지를 잘라 먹는다(선례 설계 §4-6). 그래서:

- **수산업법**: 초안은 (면허어업/허가어업/신고어업/어획물운반업/어구생산업등) **5갈래**였다 → 루트를 정의 조항(제2조) 근거로 **(어업 / 어획물운반업 / 어구생산업·어구판매업) 3갈래**로 묶고, `어업` 밑을 **(면허어업 / 허가어업 / 신고어업) 3갈래**로 다시 쪼갰다. 깊이는 늘었지만 **모든 분기가 원문 근거를 갖는다.**
- **낚시 관리 및 육성법**: (낚시터업 허가/낚시터업 등록/낚시어선업 신고) 3갈래로 둘 수도 있었으나, 원문 편제가 `제3장 낚시터업`·`제4장 낚시어선업`이므로 **(낚시터업 / 낚시어선업) 2갈래 + 낚시터업 밑 (허가 / 등록) 2갈래**로 편제를 따랐다. 편제가 있으면 편제가 우선이다.

### 3.4 트리로 쪼개지 **않은** 축 — 왜 `추가확인`으로 남겼나

인허가를 실제로 가르는 축은 유형 말고도 더 있다:

- **수면 구분**(해수면/내수면/사유수면 — 낚시터업 허가↔등록, 내수면어업법 제11조제1항↔제2항)
- **총톤수·정원·영업구역 구간**(유·도선 면허↔신고 = 5톤·13명·2해리, 수산업법 근해↔연안 = 10톤)
- **국적**(EEZ 외국인어업법은 외국인만 대상)

이 축들은 **분기 조건이지 별도 계층이 아니다** — 이미 형제 노드를 가르는 기준으로 `선택지[].hint`에 원문 수치와 함께 들어가 있다. 리프에 남은 잔여 축만 `추가확인`으로 담는다(선례 §3.3과 같은 결론, 같은 이유: 트리 레벨로 올리면 같은 의무가 리프마다 복제돼 유지보수가 무너진다).

## 4. 비-리프 노드의 `질문`·`선택지`

규칙은 선례 §4와 동일하다:

1. 모든 비-리프는 `질문`·`선택지`를 반드시 갖는다(빌드 시 강제).
2. `선택지[].label`은 **raw에 실재하는 법률 용어**를 쓴다(임의 조어 금지).
3. `선택지[].next`는 반드시 그 노드의 **자식 id**(참조 무결성 검사).
4. `선택지[].hint`는 그 유형의 대상·기준을 원문 근거 안에서 한 문장으로 푼 것. **hint도 근거를 벗어나지 않는다.**
5. `질문`은 존댓말 한 문장, 기존 `decideClarify`의 `intro`/`question` 규약과 호환되는 톤.
6. **선택지 수 = 자식 수, 3개 이하**(위반 시 빌드 실패).

## 5. 추출 방법론

### 5.1 조문 분리 — 계열별 이중 형식 (L-54)

raw는 계열마다 조문 마커가 다르다. 하나의 정규식으로 짜면 **고시계열에서 조용히 0건**이 된다(`_LESSONS.md` L-54).

| 계열 | 파일 | 마커 |
|---|---|---|
| 법률·시행령·시행규칙 | `법률.txt`·`시행령*.txt`·`시행규칙.txt` | `[제10조] 제목 (시행 …)` — **대괄호** |
| 고시·훈령 등 행정규칙 | `행정규칙/*.txt` | `제7조(제목) ①…` — **무대괄호** |

74법 전수 스캔은 **두 형식을 모두** 돌린다(커버리지 수치). 다만 **트리에 채택한 근거는 법률·시행령·시행규칙 계열뿐**이다 — 인허가의 근거는 법률유보 원칙상 법률·대통령령·부령에 있고, 실제로 스캔에서도 고시의 "…하려는 자는 신고하여야 한다"류는 이미 인허가를 받은 자의 서식·절차 안내였다(§7 caveat 3).

### 5.2 후보 추출 — "의도구 × 인허가 동사" 2중 조건

- **의도구**(진입 의사): `하려는` / `하려면` / `하고자 하는` / `경영하려` / `영위하려` / `업으로 하려` / `받으려는`
- **인허가 동사**: `면허를 받아야` / `허가를 받아야` / `등록을 하여야`·`등록하여야` / `신고하여야`·`신고를 하여야` / `지정을 받아야`
- 두 조건이 **같은 문장 안**에 있어야 후보다.

**적응 이력(정직 기록)**: 처음엔 인허가 동사만으로 법률계열을 훑었더니 **61법** 400여 문장이 걸렸는데 대부분이 변경·휴업·폐업·사고 신고였다. 의도구 조건을 더하니 법률계열 **42법**(고시계열까지 합친 최종 스캔은 **43법·243건**)으로 줄었고, 남은 것의 대다수가 실제 진입규제였다. 그래도 §3.1의 제외 유형(출입항 신고 등)이 섞여 있어 **사람이 한 번 더 추렸다** — 스캔은 후보를 주는 것이지 답을 주지 않는다.

### 5.3 ★제재(벌칙·과태료)는 사람이 안 쓰고 **자동 연결**한다

리프의 "이 인허가를 안 받으면 어떻게 되나"는 사용자 질문 빈도가 높은데, 사람이 옮겨 적으면 금액·형량을 틀릴 위험이 크다(그리고 그게 곧바로 오답이 된다). 그래서 **결정론적으로 뽑는다**:

1. 그 법 `법률.txt`에서 제목이 `벌칙`·`과태료`인 조문을 모은다.
2. 각 조문을 항(①②③…)으로 나누고, 항의 머리글(각 호 앞부분)에서 **제재 수준**을 읽는다 — 예 `다음 각 호의 어느 하나에 해당하는 자는 3년 이하의 징역 또는 3천만원 이하의 벌금에 처한다.`
3. 각 호(`1.`, `2.` …)에서 그 리프의 **근거조문을 참조하는 호**를 찾는다(`제40조`를 찾되 `제40조의2`는 정규식 `제40조(?!의)`로 배제).
4. 그 호의 문장을 **그대로** `인용`으로, 2에서 읽은 문구를 `수준`으로 싣는다.

이 방식이면 "제106조제1항제3호 — 제40조제1항부터 제3항까지 … 허가를 받지 아니하거나 등록을 하지 아니하고 수산업을 경영한 자 → 3년 이하의 징역 또는 3천만원 이하의 벌금"이 **원문 문자열 그대로** 들어간다. H-28·H-33에서 반복 확인된 "구멍탐지류는 AI보다 로직 우선" 원칙의 같은 적용이다.

**한계(정직)**: 벌칙 조문이 근거조문을 **조문번호로 참조하지 않고 행위로만 서술**하면(예: "이 법에 따른 어업권을 취득하지 아니하고 어업을 경영한 자") 자동 연결이 못 잡는다. 못 잡은 것을 지어내지 않고 그냥 비운다.

### 5.4 무엇을 트리에서 뺐나(scope-out) — 정직 기록

§3.1 표의 제외 유형이 그대로 `unmapped.유형_단위`에, 후보는 나왔으나 이번에 서브트리를 만들지 않은 법이 `unmapped.법_단위`에 사유와 함께 들어간다. **"안 했다"와 "없다"를 구분해 적는다.**

## 6. 완결성·정확성 판정 — 무엇을 "다 뽑았다"로 보는가

**성공 기준(검증 가능, 카파시 4)**:

1. **커버리지 수치 공개**: 74법 전부를 스캔했음을 파일 수·조문 수로 밝히고 "후보 발견 N법 / 서브트리 구축 M법"을 정직하게 보고한다. *(정확도가 아니라 "어디까지 봤는지".)*
2. **전량 재대조(표본 아님)**: 트리의 **모든** 의무 항목·노드 provenance에 대해 빌더가 raw 파일을 열어 ①그 조문이 실재하는지 ②그 조문 본문에 앵커 문구가 실제로 있는지 확인. 하나라도 실패하면 **빌드 실패**(JSON을 만들지 않는다).
3. **인용문 자기검증**: 뽑아낸 `인용`이 앵커를 실제로 담고 있는지 재확인(문장 경계 탐지가 실패해 엉뚱한 데를 자르는 것을 막는다 — 선례에서 실제로 5건이 이 방식으로 걸러졌다).
4. **질문·선택지 무결성**: 비-리프에 `질문`·`선택지`가 있고, `선택지[].next`가 실재하는 자식 id이며, 선택지 수 = 자식 수 ≤ 3.
5. **★법단위 분리 검사**: 서브트리 안의 모든 노드·의무의 `법령_slug`/`근거법령_slug`가 그 서브트리의 법과 일치. 하나라도 다르면 빌드 실패. *(§1.2 — 이 트리의 존재 이유를 코드로 못박은 검사.)*
6. **리프 최소 내용**: 리프는 `의무`를 최소 1건(취득 근거) 갖는다. 자식이 1개뿐인 노드는 없다.
7. **재현성**: `python3 local_server/knowledge/legal/_dashboard/loop/build_permit_tree.py` 1회 실행으로 재현된다.
8. **독립 재대조**: 빌더의 조문분리 로직을 **재사용하지 않는** 별도 검증 모드(`--verify`)로, raw 파일을 통짜 문자열로 읽어 `인용`이 부분문자열로 실재하는지, 그리고 그 인용이 정말 그 근거조문 범위 안에서 나오는지(조문 경계를 문자열 검색으로 따로 구해) 다시 확인한다. **"빌드가 통과했다"와 "내용이 맞다"는 다른 문제다.**

### 초안에서 실제로 걸러낸 오류(정직 기록)

빌드가 한 번에 통과했다고 내용이 맞는 것은 아니었다. 산출물을 사람이 읽어 대조한 결과 **4종의 결함**을 잡아 고쳤다:

1. **인용문이 괄호 안 "…말한다."에서 잘려 정작 의무 문구를 안 담음(7건)** — 양식산업발전법 제10조제1항이 `… 시장ㆍ군수ㆍ구청장(서울특별시 한강의 경우에는 … 기관을 말한다. 이하 같다)의 면허를 받아야 한다`인데 괄호 안에서 문장이 끊겨 **"면허를 받아야 한다"가 인용문에서 사라졌다.** 수산종자산업육성법 제21조제1항·수산업법 제71조제1항도 같은 형태. → `sentence_end()`를 새로 만들어 **괄호 깊이 0인 자리의 '다. '만** 문장 끝으로 인정하도록 고쳤다. *(선례 `H32_vessel_doc_tree_design.md` §6이 겪은 5건과 같은 원인 — 같은 함정을 두 번째로 밟았다는 뜻이라 이번엔 함수로 분리해 못박았다.)*
2. **호(號) 가지번호를 못 봐서 여러 호가 한 인용문에 뭉침** — 낚시법 제55조 `3. … 3의2. … 3의3. …`, 해운법 제59조 `1. … 1의2. …`가 통째로 한 덩어리로 잡혔다. 숫자+마침표만 보는 정규식의 전형적 실패(`_LESSONS.md` **L-61·L-62**와 같은 함정). → 호 경계 정규식에 `\d+(?:의\d+)?\.`를 반영.
3. **제재 자동연결의 과다 매칭** — `제6조`로 뭉뚱그리면 **제6조제7항(신고)** 관련 벌칙이 **제6조제1항(허가)** 리프에 붙는다(원양산업발전법). 도선법도 `제4조`로 잡으면 제4조제6항(면허증 재발급) 과태료가 "무면허 제재"인 양 붙었다. → 항까지 지정한 참조(`제6조제1항`·`제20조제3항` 등)로 좁혔다. 그 결과 도선사면허 리프는 제재가 **0건**이 됐는데, 확인해보니 도선법 벌칙 조문 어디에도 제4조제1항 위반을 처벌하는 호가 없다 — **없는 것을 지어내지 않고 비웠다.**
4. **조 머리글 혼입** — 항 기호가 없는 조문(마리나항만법 제28조의4)에서 `[제28조의4] 휴업 또는 폐업의 신고 (시행 …)`가 인용문에 딸려왔다. → `strip_head()`를 인용 추출 앞단에도 적용.

**자동연결이 못 잡은 것도 그대로 남겼다**: 수산업법 면허어업의 진짜 벌칙은 제106조제1항제1호(`이 법에 따른 어업권을 취득하지 아니하고 어업을 경영한 자`)인데 그 호가 **제7조를 조문번호로 참조하지 않아** 자동 연결에서 빠졌다. 지어내 채우는 대신 그 노드의 `비고`에 사실을 적었다(§5.3 한계의 실례).

**행정규칙 40건 후보의 실제 내용(직접 확인)**: 스캔은 고시계열에서도 후보 40건을 잡았는데, 전수로 읽어보니 **전부** 항만시설 사용허가·항만 내 사진촬영 허가·항만견학 허가·입출항/화물반출입 신고·승무정원 감원 협의 등 **시설 이용·절차**였고 사업 진입규제는 하나도 없었다. caveat 3은 추정이 아니라 이 확인의 결과다.

## 7. caveats (JSON에 그대로 실을 한계 목록)

1. **법을 가로지르는 인허가 강도 서열은 이 트리에 없다.** 어떤 법의 "신고"가 다른 법의 "허가"보다 무거울 수 있다(§1.1). 서브트리끼리 비교하면 안 된다.
2. 이 트리는 **진입규제**(사업·행위를 개시하려면 받아야 하는 것)만 담는다. 변경·휴업·폐업·출입항·사고 신고, 행정계획 승인, 기관 지정, 개인 신분 등록은 제외했다(§3.1).
3. 근거는 **법률·시행령·시행규칙 계열**에서만 채택했다. 행정규칙(고시) 665개 파일도 스캔했으나 인허가 근거로 채택된 것은 없다.
4. `의무` 중 `유형:"제재"`는 **벌칙 조문이 근거조문을 조문번호로 참조한 경우에만** 자동 연결된다. 행위만 서술한 벌칙은 못 잡는다(§5.3 한계).
5. 트리에 있는 유효기간·후속신고는 **원문에 있는 것만** 담았다. 없다고 표시된 것이 "제도상 없다"는 뜻은 아니다(우리가 못 찾았을 수 있다).
6. 자치법규(`raw/_자치법규/`)·별표/별지 서식은 이번 스캔 대상이 아니다.
7. `hint`의 수치(톤수·정원·해리 등)는 원문 문구를 옮긴 것이지 우리가 해석해 정규화한 값이 아니다.
8. 후보가 나온 법 중 이번에 서브트리를 만들지 않은 법이 **18개** 있다(`unmapped.후보는_있으나_서브트리를_만들지_않은_법` — 손으로 세지 않고 코드가 뽑는다). **"인허가가 없다"가 아니라 "이번 라운드에 안 만들었다"** 이다.
9. **★스캔의 recall은 100%가 아니다(실측으로 확인).** 도선법은 스캔 후보가 **0건**인데도 서브트리가 있다 — 제4조제1항이 `도선사가 되려는 사람은…`이라 의도구(`하려는`)에 걸리지 않았기 때문이다. 즉 **후보 0건인 31법 중에도 다른 문형의 인허가 조문이 있을 수 있다.** 이 사실을 산출물의 `scan.설명`에도 그대로 실었다.

## 8. 유지보수 통합 설계 (H-29 연동 — **설계만**, 이번엔 배선 안 함)

선례 §8과 **완전히 같은 구조**를 쓴다. 근거: 선례 §8.3(d) — *"새 계층 주제가 채택될 때도 같은 파이프라인을 쓴다. 조건은 하나뿐 — 새 트리도 모든 노드·항목에 `{근거법령, 계층, 근거조문}` provenance를 갖출 것."* 이 트리는 그 규약을 그대로 지키므로 **조인 키가 이미 맞아 있다**.

```
detect_law_changes.py (H-29, 이미 있음)
        ↓  law_change_queue.json  { law.slug, layer, changed_articles[].조문번호 }
[신규] loop/flag_permit_tree.py               ← 이번엔 만들지 않음
        ├ 큐의 각 item에서 (slug, layer, 조문번호) 추출
        ├ permit_tree.json 순회하며 같은 키의 노드·의무 항목 탐색
        └ 사이드카 _dashboard/permit_tree_review.json 에 review 플래그
```

**설계 결정(선례와 동일한 이유로 동일하게 간다)**:
- **(a) 트리를 직접 고치지 않고 사이드카에 쓴다** — 트리는 빌더의 결정론적 산출물이라 손으로 고치면 다음 빌드에서 날아간다.
- **(b) 자동 재빌드하지 않는다** — 개정으로 앵커 검증이 실패하는 것은 **정상적인 "사람이 봐야 한다" 신호**다. 자동 재빌드는 그 신호를 지운다.
- **(c) `법령ID`를 처음부터 provenance에 싣는다**(H-29 11항·L-74) — 법령명이 바뀌어도 추적이 안 끊긴다. 나중에 백필하는 것보다 싸다.
- **(d) 이 트리에만 있는 추가 조인 축**: `유형:"제재"` 의무는 **벌칙 조문**이 근거다. 벌칙 조문이 개정되면 트리의 리프가 바뀌어야 하는데, 조인 키 `(slug, "법률", 벌칙조문번호)`로 이미 잡힌다(별도 설계 불필요).

## 9. 되묻기(`decideClarify`) 연동 설계 (**설계만**, 이번엔 배선 안 함)

### 9.1 진입점이 선례와 다르다

`vessel_doc_tree.json`은 주제 매칭(`matchDocTreeTopic`) 후 **트리 루트의 첫 질문**부터 시작한다. 이 트리는 §1.3대로 **법이 먼저 정해져야** 들어갈 수 있다.

```
질문 "낚싯배 하려면 뭐 받아야 돼요?"
  ↓
기존 search() — 상위 페이지의 법을 집계해 후보 법 slug 추출        ← 신규 코드 없음(재사용)
  ↓ 그 slug의 서브트리가 permit_tree.json에 있으면
[신규] clarifyFromPermitTree(subtreeRoot)   ← 트리에서 질문·선택지를 그대로 꺼냄(LLM 0회)
  ↓ 사용자 선택 → 질의에 ' — 낚시어선업' 이 붙어 재질의
[신규] resolvePermitPath(query, subtree)    ← 라벨로 현재 노드 복원
  ↓ 리프 도달
리프의 의무[] 를 근거로 답변 조립(취득→유효기간→후속신고→제재 순)
  ↓ 서브트리가 없거나 법이 안 좁혀지면
기존 decideClarify() 그대로 (폴백)
```

```js

 * @param {string} slug - 법 슬러그(검색 결과 상위 페이지의 법)
 * @returns {{matched:boolean, subtree?:object}}
 */

/**

 * @param {object} node - permit_tree.json 의 비-리프 노드
 * @returns {{needed:true, intro:string, question:string, options:Array<{label:string,hint:string}>}}
 *   기존 decideClarify()의 반환 스키마와 **완전히 동일** — 라우트·클라이언트 무변경.
```

### 9.3 연동 시 반드시 지킬 것

- **(a) 반환 스키마를 기존과 동일하게 유지한다** — `{needed,intro,question,options[{label,hint}]}` 그대로면 `routes/legal.js`·`ai_chat.js`를 한 줄도 안 고쳐도 된다(카파시 3).
- **(b) 라운드 상한**: H-36 미결①이 **이미 확정**됐다 — *"트리 기반 경로(깊이가 데이터로 유한해 무한루프가 원리적으로 불가능)는 인위적 라운드 캡 없음"*(2026-08-10 사용자 확정). 이 트리의 최대 깊이는 3(수산업법: 루트→어업→면허어업)이므로 그 확정이 그대로 적용된다. **새로 결정할 것이 없다.**
- **(c) 라벨 문자열이 계약이다** — `resolvePermitPath`가 `' — '` 뒤 문자열을 라벨과 대조하므로, 라벨을 바꾸면 진행 중인 대화가 깨진다. 라벨은 **법률 용어 그대로 고정**한다.
- **(d) ★법 경계를 넘는 되묻기를 만들지 말 것.** 서로 다른 서브트리의 선택지를 한 질문에 섞으면 §1.1의 오류를 UI 층에서 되살리는 것이 된다. 되묻기 한 번은 **한 서브트리 안에서만** 이뤄진다.
- **(e) canonical 게이트와의 관계는 미정** — 이 트리도 raw 직인용이라 위키 `answerCanonicalOnly` 정책과 축이 다르다. H-36 미결②와 같은 쟁점이며 **이번 범위 밖**이다.
