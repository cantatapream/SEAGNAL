## ★교차확인 — 열흘 전 결과와 구버전 3건이 **똑같다**

저장소에 이미 있는 `_dashboard/admrul_fresh_report.json` 은 **2026-09-10** 실행분이고
`fresh 797 / stale 3 / renamed 24 / unknown 0 / mismatch 0` 이다.
**stale 3 이 이번 실행과 같은 3건이다.**

두 가지를 뜻한다 —
1. **판정이 재현된다.** 열흘 간격, 다른 실행, 같은 답. 구버전 3건은 흔들리는 값이 아니다.
2. **열흘 동안 안 고쳐졌다.** 그때도 3건이었고 지금도 3건이다. → **B단계에서 이 3건을 다시 받아오는 것이 첫 일이다.**

한편 이번 1차의 `unknown 107 / mismatch 65` 는 그때(0/0)와 다른데, 그쪽은 **pass2 를 거친 뒤의 수치**다
(`renamed 24` 가 그 흔적). 즉 1차만 놓고 "나빠졌다"고 읽으면 안 된다 — A-1b 를 돌려야 비교 가능한 값이 된다.

## 완주시킨 방법 — 죽어도 잃지 않게 만들었다

1차 실행은 389건에서 죽었다. 원인을 찾아보니 **컨테이너가 놀면 회수됐다가 다시 뜬다**(`uptime` 이
"up 0 min"). 그때 백그라운드 프로세스가 **전부** 죽는다 — 감시견까지 같이 죽는 것으로 확인했다.

그래서 두 가지를 붙였다.
- **`--progress <파일>`** — 한 건 판정할 때마다 JSONL 한 줄을 붙이고 `flush` + `os.fsync` 까지 한다.
  죽어도 그 줄까지는 디스크에 남는다.
- **`--resume <같은 파일>`** — 이미 판정한 제목은 다시 묻지 않는다.
  실행 로그에 `이어받기: 이미 판정된 514건은 다시 묻지 않는다 (남은 310건)` 처럼 찍힌다.

기본값은 바꾸지 않았다 — 서버 크론(`--out` 만 준다)은 종전과 똑같이 돈다.

감시견(`fresh_watchdog.sh`)은 60초마다 살았는지 보고 죽었으면 `--resume` 으로 되살린다.
**감시견 자신도 컨테이너 재시작은 못 버틴다** — 그건 파일 머리말에 적어 뒀다.
