> 목적: 진행하며 겪은 실수·오설계를 **문제→원인→교훈→조치**로 남겨, 다음에 같은 작업을 할 때 동일 문제가 재발하지 않게 한다.
> 규칙: **추가만**(오래된 항목도 지우지 않음). 새 실수·교훈이 생기면 맨 아래에 append. **작업 착수 전 이 문서 + `MASTER_PLAN.md`·`_SCHEMA.md`·`_CHATBOT.md`·`CLAUDE.md`를 먼저 정독한다(불변식).**

## L-1. 병렬 공유파일 경합으로 데이터 손실 (2026-07-18)
- **문제**: 35-wide 병렬 수집에서 공용 타법 파일(의료법 등) 인용추적 일부가 동시쓰기 경합으로 손실.
- **원인**: 여러 에이전트가 **같은 공유 파일**에 동시 write.
- **교훈**: 병렬은 **각자 자기 파일만 쓸 때만** 안전. 공유 파일(리뷰큐·log·공용 타법·graph 허브) 쓰기는 경합 위험.
- **조치**: 공유파일 쓰기는 **단독(직렬)**. 병렬 에이전트는 판정·산출만 반환하고, 공유파일 반영은 메인이 한 곳에서 직렬 적용(예: `apply_resolutions.py`, `merge_review_gen.py`). CLAUDE.md "병렬 작업 안전 규칙"에 명문화됨.

## L-2. 자동승급 과보수 — "처벌 단어 있으면 무조건 draft" (2026-07-20)
- **문제**: 위키 86%가 draft(챗봇 인용불가). auto_promote가 처벌·별표 **단어만 있으면** draft로 남겨, 실제론 원문 그대로 인용이라 승급 가능한 페이지 수백 개를 방치.
- **원인**: 승급 판정을 "민감 단어 포함 여부"라는 **표면 신호**로만 함(내용이 원문 인용인지 grounding 안 함).
- **교훈**: "처벌 조문 포함 = 사람 필요"는 틀림. **원문(raw)과 grep로 대조해 그대로 인용이면 기계검증 가능** → AI 승급 안전. 진짜 사람 필요는 **별표 이미지 OCR 판독값**과 **AI 추론 매핑**뿐.
- **조치**: `draft_reverify.js`(원문 grounding 재판정) 도입. `_SCHEMA.md` 5절 이원화 규칙을 **grounding 기준**으로 정제(아래 L-2 반영).

## L-3. 리뷰큐 — 유형 무시하고 전부 "수치 입력란" (2026-07-20)
- **문제**: 리뷰 카드 전부에 "확정 값(예: 10)" 수치 입력란. 그러나 fable5 분류 결과 미승인 97건 중 **수치 확정형은 0건**(전부 해석·연결·재수집형).
- **원인**: 리뷰를 **한 유형(OCR 수치 확정)** 으로만 가정하고 UI를 만듦.
- **교훈**: 리뷰는 유형이 다양(값확정 / 해석승인 / 재수집 / 구조). 입력 UI도 유형별이어야.
- **조치**: 카드 유형별 입력 — `AI 제안값` 필드 있으면 **값 입력**, 없으면 **승인/기각 + 선택 메모**(수치 입력 제거). `legal_review.html`·`ai_chat.js` 반영.

## L-4. 리뷰큐에 "AI가 해결 가능한 것"이 대량 혼입 (2026-07-20)
- **문제**: 사람 검토 큐 97건 중 실제로 사람이 필요한 건 **~54건뿐**. 나머지는 ①공개법령 재수집으로 해결(needs_collect) ②원문 이미 raw에 있어 재대조로 확정(resolved). "원문 미확보"류는 거의 전부 law.go.kr 공개법령이라 **에이전트가 재수집**하면 될 것을 사람에게 넘겼음.
- **원인**: 감사·수정 단계가 "확인 필요"를 만들 때 **AI로 해소 가능한지 먼저 판정하지 않고** 전부 사람 큐로 보냄.
- **교훈**: 사람 큐에 넣기 전에 **AI 자동 트리아지**(resolved/needs_collect/human)를 먼저 태워 사람 부담을 최소화.
- **조치**: `review_resolve.js`(원문 grounding 재검증, 읽기전용 판정) → resolved는 자동확정, needs_collect는 수집 트랙, human만 큐 유지. 향후 감사가 REVIEW를 만들 때도 이 트리아지를 선행.

## L-5. canonical 필터 부재 — 미검증 draft가 답변에 샐 위험 (2026-07-20)
- **문제**: index.json이 draft·canonical 구분 없이 전체를 담고, `/api/legal/ask`가 status를 안 봐서 **미검증 draft도 답변 근거로 나갈 수 있었음**.
- **교훈**: 답변엔진은 **검증된 canonical만 인용**해야(환각0 불변식). 단, canonical이 적을 때 필터를 켜면 답변이 비니 **스위치로 제어**.
- **조치**: canonical 필터 **선(先)구축 + 스위치 OFF**(`answerCanonicalOnly`, 기본 false). 검증 쌓인 뒤 ON. ⚠ **켜기 전 `lint_index.py`로 index 재빌드 필수**(status 미기재면 전 concept 제외→답변 0건). 상세 MASTER_PLAN E절.

## L-6. 서버 config POST가 다른 필드를 덮어씀 (2026-07-20)
- **문제**: `/api/legal/config` POST가 `{exposure}`만 통째로 써서, 새 필드(`answerCanonicalOnly`)를 저장하면 exposure가 날아갈 구조였음.
- **교훈**: 부분 설정 저장은 **기존을 읽어 머지**해야. 통째 덮어쓰기 금지.
- **조치**: config POST를 **머지 방식**으로(기존 읽고 넘어온 필드만 갱신).

## L-7. silent success — 0페이지 승격인데 ok:true (2026-07-20, 적대적 리뷰로 발견)
- **문제**: `applyToWikiPages`가 대상 페이지를 하나도 못 찾아 0개 승격했는데도 `ok:true`를 반환(주석·약칭·신규 표기 파싱 실패).
- **교훈**: "성공"을 **실제 효과(승격 수)** 로 판정해야. 0건이면 정직하게 알림. 산출은 **적대적 리뷰**(다른 에이전트가 반증 시도)로 검증.
- **조치**: promotedCount===0이면 정직한 note 반환. 주석/약칭/신규/경로이탈 파싱 보강. `apply_resolutions.py`도 "승격 0인 resolved"를 별도 경고 출력.

## L-8. UI 오구현 — 지시와 다른 위치에 탭 생성 (2026-07-20)
- **문제**: "AI 챗봇을 통합관리자 AI탭의 **하위 탭**으로"인데 top-level "나리야 법령" 탭을 만들고, "FAB만"인데 하단 탭을 생성.
- **원인**: 지시를 정확히 재확인하지 않고 구현.
- **교훈**: UI 위치·구조 지시는 **문구 그대로** 재확인 후 구현. 애매하면 조용히 고르지 말고 확인.
- **조치**: 탭 제거→FAB only(메인 탭에서만) + 관리자 콘솔은 AI탭 서브탭. 이후 지시 재독 습관화.

## L-9. 감사 full률 하락을 회귀로 오해 (2026-07-18~20)
- **문제**: 라운드마다 full률이 떨어져(예: 8차 g0 4.4%) 위키가 나빠진 걸로 오해할 뻔.
- **원인**: 감사는 **직전 실패+최난도 재질문(3페르소나)** 설계라 라운드마다 난도가 오름. 또 draft 미승급이 많으면 인용가능(full)이 낮게 잡힘.
- **교훈**: full률은 절대치가 아니라 **설계된 적대적 값**. **전수(70법) 측정 전엔 결론 금지**. 표본 1그룹으로 회귀 판정하지 말 것.
- **조치**: AUTO_RUN_LOG에 "전수측정 전 결론보류" 명시. 하락 신호는 감시목록에만 누적.

- **문제**: 리졸버 97건 판정이 task-notification에서 truncate돼 전체 적용 불가.

## L-11. main 머지 시 dirty tree로 checkout 실패 (2026-07-20)
- **문제**: `git checkout -B main origin/main`이 백그라운드 워크플로가 파일 쓰는 중이라 dirty tree로 실패.
- **교훈**: 백그라운드 쓰기 중엔 브랜치 체크아웃 위험.
- **조치**: 체크아웃 없이 **fast-forward push**(`git push origin <branch>:main`). 충돌 시 pending 먼저 커밋.

## L-12. 모델 과다 사용으로 크레딧 소진 — 작업에 맞는 모델 선택 (2026-07-20)
- **문제**: draft 재검증을 fable5×high effort×70+에이전트(10그룹 병렬)로 돌리다 **usage credits 소진**(다수 에이전트 실패, 33법 미처리).
- **원인**: 기계적 grounding 검증(원문 grep 대조)에 **과한 모델·과한 effort**를 씀. 병렬 볼륨도 큼.
- **교훈**: 작업 성격에 **모델을 right-size**. 창의·난추론이 아니라 **원문 대조·상태 판정** 류는 중간급이면 충분.
- **조치(모델 정책, 사용자 확정 2026-07-20)**:
  - **🚫 fable 모델은 사용자가 명시 지시할 때만 사용**(기본 금지).
  - **검증·재판정(reverify·resolve)** = `sonnet`·`medium`(정확성 필요·창의 불필요). fable-high는 과함, haiku는 법률 grounding 미달 위험.
  - **부트/목록 읽기**(json Read) = `sonnet`·`low` 또는 `haiku`.
  - **effort는 기본 medium 이하**, 정말 어려운 판정만 high.
  - **전(全)70법 반복 패스를 남발하지 않는다** — 미처리분만 재개(마커로 추적).
  - 크레딧/한도 실패는 마커를 안 남기므로 **리셋 후 미완법만 자동 재개**.

## L-13. 재수집 후 파이프라인 계획에서 lint(그래프·링크 재생성) 단계 누락 직전 (2026-07-21, 사용자가 발견)
- **문제**: D단계 needs_collect 재수집(raw 100건) 완료 후 "wiki_rebuild → 감사" 순서로 밤샘 자동 파이프라인을 짰는데, **wiki_rebuild와 감사 사이에 lint(`lint_xref.js`/`lint_full.js`/`lint_index.py`/`lint_build.py`) 단계가 계획에서 빠져 있었음**. 내가 스스로 발견 못 하고 **사용자가 지적**해서 알아챔.
- **원인**: H-9(감사→통합수정→lint재봉합→재감사) 루프는 "감사 이후 수정"엔 적용했지만, "재수집으로 인한 새 콘텐츠 반영"에도 **똑같이 lint가 선행돼야 한다**는 걸 별도 케이스로 인지하지 못함. wiki_rebuild가 새 wiki 텍스트/링크를 만들면 `graph.json`·교차링크(index)가 그 상태를 반영 못 한 채로 있고, 그대로 감사하면 감사가 **낡은 인덱스/그래프**를 보게 됨.
- **교훈**: "**위키 콘텐츠(텍스트·링크)를 바꾸는 모든 파이프라인의 끝에는 반드시 lint_index→lint_build가 와야 다음 단계(감사·재검증)가 최신 상태를 본다**"는 원칙은 감사-수정 루프뿐 아니라 **재수집-반영 루프에도 동일하게 적용**해야 함. 파이프라인을 새로 짤 때마다 "이 단계가 wiki 텍스트/링크를 바꾸는가? 바꾼다면 바로 다음에 lint가 있는가?"를 체크리스트로 자문할 것.
- **조치**: `MASTER_PLAN.md` H-20에 표준 순서 명문화(재수집→wiki_rebuild→lint[xref/full/index/build/human_workload]→reverify→audit). 이후 세션은 재수집이 있었으면 이 순서를 기본값으로 따르고, 생략하고 싶으면 이유를 먼저 설명할 것.
