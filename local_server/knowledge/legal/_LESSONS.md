## L-1. 병렬 공유파일 경합으로 데이터 손실 (2026-07-18)
- **문제**: 35-wide 병렬 수집에서 공용 타법 파일(의료법 등) 인용추적 일부가 동시쓰기 경합으로 손실.
- **원인**: 여러 에이전트가 **같은 공유 파일**에 동시 write.
- **교훈**: 병렬은 **각자 자기 파일만 쓸 때만** 안전. 공유 파일(리뷰큐·log·공용 타법·graph 허브) 쓰기는 경합 위험.
- **조치**: 공유파일 쓰기는 **단독(직렬)**. 병렬 에이전트는 판정·산출만 반환하고, 공유파일 반영은 메인이 한 곳에서 직렬 적용(예: `apply_resolutions.py`, `merge_review_gen.py`). CLAUDE.md "병렬 작업 안전 규칙"에 명문화됨.

## L-2. 자동승급 과보수 — "처벌 단어 있으면 무조건 draft" (2026-07-20)
- **문제**: 위키 86%가 draft(챗봇 인용불가). auto_promote가 처벌·별표 **단어만 있으면** draft로 남겨, 실제론 원문 그대로 인용이라 승급 가능한 페이지 수백 개를 방치.
- **원인**: 승급 판정을 "민감 단어 포함 여부"라는 **표면 신호**로만 함(내용이 원문 인용인지 grounding 안 함).
- **교훈**: "처벌 조문 포함 = 사람 필요"는 틀림. **원문(raw)과 grep로 대조해 그대로 인용이면 기계검증 가능** → AI 승급 안전. 진짜 사람 필요는 **별표 이미지 OCR 판독값**과 **AI 추론 매핑**뿐.
- **조치**: `draft_reverify.js`(원문 grounding 재판정) 도입. `_SCHEMA.md` 5절 이원화 규칙을 **grounding 기준**으로 정제(아래 L-2 반영).

## L-3. 리뷰큐 — 유형 무시하고 전부 "수치 입력란" (2026-07-20)

- **교훈**: 리뷰는 유형이 다양(값확정 / 해석승인 / 재수집 / 구조). 입력 UI도 유형별이어야.
- **조치**: 카드 유형별 입력 — `AI 제안값` 필드 있으면 **값 입력**, 없으면 **승인/기각 + 선택 메모**(수치 입력 제거). `legal_review.html`·`ai_chat.js` 반영.

## L-4. 리뷰큐에 "AI가 해결 가능한 것"이 대량 혼입 (2026-07-20)
- **문제**: 사람 검토 큐 97건 중 실제로 사람이 필요한 건 **~54건뿐**. 나머지는 ①공개법령 재수집으로 해결(needs_collect) ②원문 이미 raw에 있어 재대조로 확정(resolved). "원문 미확보"류는 거의 전부 law.go.kr 공개법령이라 **에이전트가 재수집**하면 될 것을 사람에게 넘겼음.
- **원인**: 감사·수정 단계가 "확인 필요"를 만들 때 **AI로 해소 가능한지 먼저 판정하지 않고** 전부 사람 큐로 보냄.
- **교훈**: 사람 큐에 넣기 전에 **AI 자동 트리아지**(resolved/needs_collect/human)를 먼저 태워 사람 부담을 최소화.
- **조치**: `review_resolve.js`(원문 grounding 재검증, 읽기전용 판정) → resolved는 자동확정, needs_collect는 수집 트랙, human만 큐 유지. 향후 감사가 REVIEW를 만들 때도 이 트리아지를 선행.

## L-13. 재수집 후 파이프라인 계획에서 lint(그래프·링크 재생성) 단계 누락 직전 (2026-07-21, 사용자가 발견)

- **원인**: H-9(감사→통합수정→lint재봉합→재감사) 루프는 "감사 이후 수정"엔 적용했지만, "재수집으로 인한 새 콘텐츠 반영"에도 **똑같이 lint가 선행돼야 한다**는 걸 별도 케이스로 인지하지 못함. wiki_rebuild가 새 wiki 텍스트/링크를 만들면 `graph.json`·교차링크(index)가 그 상태를 반영 못 한 채로 있고, 그대로 감사하면 감사가 **낡은 인덱스/그래프**를 보게 됨.
- **교훈**: "**위키 콘텐츠(텍스트·링크)를 바꾸는 모든 파이프라인의 끝에는 반드시 lint_index→lint_build가 와야 다음 단계(감사·재검증)가 최신 상태를 본다**"는 원칙은 감사-수정 루프뿐 아니라 **재수집-반영 루프에도 동일하게 적용**해야 함. 파이프라인을 새로 짤 때마다 "이 단계가 wiki 텍스트/링크를 바꾸는가? 바꾼다면 바로 다음에 lint가 있는가?"를 체크리스트로 자문할 것.
- **조치**: `MASTER_PLAN.md` H-20에 표준 순서 명문화(재수집→wiki_rebuild→lint[xref/full/index/build/human_workload]→reverify→audit). 이후 세션은 재수집이 있었으면 이 순서를 기본값으로 따르고, 생략하고 싶으면 이유를 먼저 설명할 것.

- **★addendum(2026-07-21, 어촌ㆍ어항법 C그룹 자치법규 재확인 세션) — 파일명↔본문 불일치의 정확한 근본원인 규명**: 위에서 "raw 스크래핑 단계의 데이터 품질 버그로 보인다"고 추정만 했던 것을 이번에 코드 대조로 확정했다. `_dashboard/loop/collect_ordin.py`의 `fetch(mst)` 함수가 `lawService.do?target=ordin&ID={mst}`로 호출하는데, `mst` 변수에는 검색결과의 **`자치법규일련번호`**(예: 강화군 어항관리 조례 = 2071089)가 들어있다. 그런데 law.go.kr이 실제로 그 값을 받는 파라미터명은 `ID=`가 아니라 **`MST=`**다(`자치법규상세링크` 필드가 명시: `.../lawService.do?...&MST=2071089&...`) — `ID=`는 전혀 다른 필드(**자치법규ID**, 예: 강화군 어항관리 조례의 자치법규ID는 2161036으로 별개 값)를 가리키는 파라미터라서, `ID=2071089`로 조회하면 우연히 자치법규ID=2071089인 **다른 지자체의 무관한 조례**(이 경우 "삼척시정주요업무 등의 평가에 관한 규칙")가 반환된다. 즉 원인은 "스크래핑 품질 저하"가 아니라 **API 파라미터명 오적용(ID↔MST 혼동)**이라는 명확한 코드 버그였다.

- **원인**: 구멍 하나를 발견·해결하면 "이 항목은 끝났다"고 여기고 넘어가기 쉽지만, 같은 법 안의 유사 항목(같은 위임조문·같은 종류의 지정/고시 구조)은 **같은 이유로 같은 구멍이 나 있을 가능성이 높다** — 특히 그 원인이 개별 항목의 우연이 아니라 구조적 결함(수집 스크립트의 맹점 등, L-20 부칙 사례가 정확히 이 패턴)일 때는 사실상 필연적으로 전파된다.
- **교훈/표준 절차**:
  1. 구멍 발견 시, 그 항목이 속한 법 안에서 **동일 패턴(같은 위임조문·같은 종류의 지정·같은 데이터 형태)을 가진 다른 항목**을 목록화한다.
  2. 목록의 각 항목에 대해 **개별적으로 수집 여부·구멍 여부를 확인**한다("하나 고쳤으니 나머지도 됐겠지"라고 추정 금지).
  3. 원인이 **구조적 결함**(스크립트가 특정 JSON 경로/API 파라미터를 애초에 놓침)으로 판명되면, 결함을 고치는 과정을 진행하고 **결함 해결이 확인된 시점에 동일 결함으로 구멍났을 다른 미수집 항목들도 함께 수정**한다.
  4. 확인·전파수정 결과를 작업 로그(`_dashboard/stage_b_collection_targets.md` 등)에 "유사항목 전수확인 완료(구조적결함 아님)" 또는 "구조적결함 확인 → N개 항목 함께 수정" 형태로 남긴다.
- **이미 이 원칙대로 처리된 선례**: L-20(부칙 JSON 이중중첩 구조결함) 발견 후 나머지 8개 법의 부칙도 함께 재수집. 도선법 제주항 사례에서 목포항·포항항 등 다른 도선구도 함께 재확인.
- **적용 범위**: 이번 두 사례에 국한되지 않고 **앞으로 모든 collection_hole/wiki_lag 개별 항목 수정 시 표준으로 적용**한다(Stage B 잔여 배치·Stage C·9차 감사 전 구간).

## L-26. `lsDelegated`(법령→행정규칙 위임 API)가 폐지된 구 일련번호를 반환해 collection_hole을 만들 수 있다 — 최초 조회가 안 걸리면 lawSearch로 현행본을 직접 재검색할 것 (2026-07-21, 항만재개발및주변지역발전에관한법률 Stage C 재빌드 세션)

## L-28. 감사 에이전트(general-purpose Agent 도구 접근권 보유)에게 "감사 하나를 통째로" 맡기면, 그 에이전트가 스스로 Agent/Task 도구로 하위 그룹(예: A/B/C/D)을 또 비동기 위임했다가 결과를 취합 못 하고 무한 대기에 빠질 수 있다 (2026-07-24, 9차 감사 웨이브3 재착수 세션)
- **문제**: 「선박안전법」 9라운드 감사를 위임한 Agent가 스스로 판단해 질문군을 4그룹(검사·증서/구조·설비/화물·형식승인/총괄)으로 나눠 각각 별도 하위 Agent를 비동기 디스패치했다. 그런데 하위 에이전트가 완료돼도 그 완료 알림은 (그 하위 에이전트를 실제로 스폰한) 중간 에이전트에게 가야 하는데, 중간 에이전트는 이미 자기 턴을 끝내고 "대기 중"이라는 텍스트만 반환한 채 정지해 있었다 — 오케스트레이터(나)에게는 중간 에이전트의 "완료" 알림만 오고, 그 알림은 실제로는 미완성 상태였다(감사파일 미갱신·마커 없음). SendMessage로 두 번 재개시켜봐도 같은 패턴("아직 하위그룹 기다리는 중")이 반복돼 총 두 차례 시도(약 30만 토큰)가 사실상 낭비됐다.
- **근본원인**: 비동기 Agent 위임은 트리 구조로 무한정 중첩될 수 있는데, 중간 노드가 자기 하위 노드의 완료를 "기다리는" 방법이 마땅치 않다(폴링 금지 원칙과 충돌). 최상위 오케스트레이터만 하위 에이전트 완료 알림을 확실히 받는 구조라, 중간 위임 계층이 생기면 그 계층의 완료 처리가 구조적으로 불안정해진다.
- **교훈**: 법 하나짜리 감사·리뷰류 단일 작업 단위는 **하위 에이전트로 절대 쪼개지 말고 그 에이전트 혼자(Read/Grep/Write/Edit/Bash만) 끝내도록 프롬프트에 명시 금지 문구를 박아넣을 것**("Agent/Task 도구로 하위 위임 금지, 너 혼자 처리"). 오케스트레이터(최상위)가 여러 법을 병렬로 나누는 것까지는 안전하지만, 그 밑에서 또 나누는 재귀적 팬아웃은 위험하다.

## L-29. admrul(행정규칙) 원문 raw 파일 중 다수는 API의 `조문내용` 단순 조회가 아니라 **첨부 PDF/HWPX를 pdftotext로 전사**해 수집된 것 — API 재조회로 "덮어쓰기"하면 안 된다 (2026-07-27, admrul ID 290건 재검증 후속 재수집 세션)

## L-30. 행정규칙 첨부파일 목록에서 "본문"을 자동 선택할 때, `.pdf`로 끝나는 첫 파일을 그냥 고르면 "조문별제개정이유서"(부속 설명문서)를 본문으로 잘못 집을 수 있다 (2026-07-27, admrul PDF 126건 전문 재수집 세션)

- **근본원인**: "PDF 확장자 = 본문"이라는 안이한 가정 — 첨부파일이 여러 개일 때 어느 것이 실제 조문 전문인지는 파일명(이유서/신구대조표 등 키워드)과 상대적 크기(본문이 이유서보다 훨씬 큼)로만 구분 가능한데, 이 구분 로직이 처음부터 없었다.
- **교훈**: 첨부파일 여러 개 중 본문을 고를 때는 ①"이유서"·"신구대조표"·"취지" 등 부속서류 키워드가 든 파일명을 먼저 제외하고, ②그래도 후보가 여럿이면 실제로 받아서 **크기가 가장 큰 것**을 본문으로 선택할 것(`pick_fulltext_pdf()` 패턴). triage 단계에서 고른 파일명(`attach_name`)을 실제 추출 단계에서도 그대로 재사용해(다시 고르지 않고) 두 단계 결과가 어긋나지 않게 할 것.
- **조치**: `triage_admrul_pdf.py`·`extract_admrul_pdf.py`에 `pick_fulltext_pdf()`/`attach_name` 고정 재사용 로직 반영 완료. 재triage로 오염된 20건 포함 전량 재분류함.

## L-31. law.go.kr 첨부 PDF 다수는 한글 어절 사이에 실제 공백 문자(U+0020)가 없이 글자 간격(자간)만으로 시각적 띄어쓰기를 구현한다 — 단순 텍스트 추출은 문장을 통째로 붙여버린다 (2026-07-27, admrul PDF 126건 전문 재수집 세션)
- **문제**: PyMuPDF `get_text()`로 admrul 첨부 PDF를 추출했더니 "미개량기술을확보하고, 산업적이용가치가낮아추가적인연구개발필요성" 처럼 여러 단어가 공백 없이 붙어 나왔다. 커밋 전 5개 샘플을 무작위 검증하다 발견함 — 5건 중 2건은 공백이 아예 없었고 1건은 부분적으로만 있었다.
- **근본원인**: 이 PDF들의 내부 텍스트 스트림 자체에 공백 글리프가 없다(생성 도구가 어절 간격을 글자 진행폭(advance width) 조정만으로 구현하고 실제 space 문자를 넣지 않음). `get_text('words')`처럼 공백 기준으로 단어를 나누는 API는 애초에 공백이 없으니 한 줄 전체를 "단어 하나"로 묶어버려 무용지물이었다.
- **교훈**: 이런 PDF는 **글자(char) 단위 bbox 좌표**를 직접 봐야 한다 — `get_text('rawdict')`로 각 글자의 개별 bbox를 얻어, 연속 글자 간 수평 간격(gap)이 평균 글자높이의 일정 비율(실측상 어절 내부는 0 이하, 어절 경계는 0.33~0.6배로 뚜렷이 갈림 — 안전하게 0.15배를 임계값으로 사용)을 넘으면 공백을 삽입해 재구성한다. 이 임계값은 문서마다(특히 양쪽정렬 문단은 어절 간격이 좁아짐) 달라질 수 있으니 너무 타이트하게 잡지 말 것 — 실측에서 0.35는 일부 정렬 문단을 놓쳤고 0.15가 안전했다.
- **조치**: `extract_admrul_pdf.py`의 `extract_pdf_text()`를 이 gap-aware 방식(`extract_page_gapaware()`)으로 교체. 앞으로 이 저장소에서 PDF 텍스트를 새로 추출하는 스크립트를 짤 때는 이 패턴을 재사용할 것 — 처음부터 `get_text()`를 그대로 믿지 말고 최소 몇 페이지는 원문 대조로 띄어쓰기 검증할 것.

- **문제**: Agent 툴로 법당 1개씩 10개 에이전트를 동시에(격리 워크트리 없이, 같은 세션의 같은 워킹디렉토리·같은 git index에서) 디스패치했다. 각 에이전트는 서로 다른 법의 서로 다른 위키 파일만 편집했는데도(파일 자체는 안 겹침), 10개 중 6~7개가 "커밋했더니 내 것이 아닌 다른 법의 파일도 같이 들어가 있다"고 보고했다 — 예: 내수면어업법 에이전트의 편집이 갯벌법 에이전트의 커밋에, 독도법·국제항해선박항만보안법·마리나항만법의 편집이 각각 다른 형제 에이전트의 커밋에 섞여 들어감.
- **근본원인**: "네가 수정한 파일만 `git add`해라"라고 지시했지만 **`git add -A`/`git add .`처럼 전체를 스테이징하는 명령을 명시적으로 금지하지 않았다**. 여러 에이전트가 동시에 파일을 수정 중인 공유 워킹디렉토리에서, 한 에이전트가 (자기 파일만 add한다고 생각하며) `git add -A`를 실행하면 **그 순간 워킹트리에 존재하는 모든 미스테이징 변경(다른 에이전트가 아직 커밋 전인 것 포함)이 함께 스테이징**된다.
- **다행히 무손실**: 이번엔 6~7건 모두 "섞여 들어간 편집"이 전부 **이미 완결된(반쯤 쓰다 만 게 아닌) 정상 편집**이었어서, 내용 손상은 없었다(각 에이전트가 `git diff HEAD`로 자기 편집이 온전히 반영됐는지 직접 확인). 하지만 만약 스윕 당한 에이전트가 파일을 **쓰는 도중**(예: Edit 절반 완료)이었다면 그 미완성 상태가 그대로 커밋됐을 것 — 이번엔 운이 좋았을 뿐 구조적으로 위험한 패턴이다.
- **부수 피해**: 이 스윕 도중 오케스트레이터가 별개로 커밋 하나(committer 메타데이터 문제로 stop hook이 지적)를 `git commit --amend`로 고치는 사이, 그 커밋을 만든 에이전트가 이미 원본을 원격에 먼저 push해버려 로컬/원격이 갈라졌다. 내용이 완전히 동일함을 diff로 확인 후 force-push 없이 origin 버전으로 안전하게 리셋해 해결했으나, 그 여파로 `main` 브랜치도 (해시만 다르고 내용은 같은) 별개 커밋으로 갈라져 명시적 merge(충돌 1건, append 위치 중복이라 수동 해결)로 재조정해야 했다.
- **교훈**: 여러 에이전트를 같은 브랜치·같은 워킹디렉토리에서 병렬 디스패치할 땐, 프롬프트에 "네 파일만 add"뿐 아니라 **"`git add -A`·`git add .`처럼 전체를 스테이징하는 명령은 절대 쓰지 말고, 반드시 `git add <네가 수정한 정확한 파일 경로>`처럼 파일을 하나하나 지정해서 add하라"를 명시적으로 금지해야 한다.** 격리가 진짜 필요하면(에이전트가 서로 다른 파일만 건드리는 게 보장 안 되는 작업) `Agent`/`Workflow`의 `isolation: 'worktree'` 옵션으로 각자 별도 워크트리를 주는 것이 근본적으로 더 안전하나, 비용(디스크·설정 시간)이 들어 지금처럼 "법당 완전히 분리된 파일셋"이 보장되는 작업에는 과할 수 있다 — 이번처럼 "add 명령 제한"만으로도 실제 위험(스윕)은 막을 수 있었다.
- **조치**: 그룹1 6~7건의 스윕은 전부 `git diff HEAD`로 무손실 확인 후 그대로 두었다(되돌리지 않음, 커밋 재작성은 더 위험). 오케스트레이터의 amend-vs-push 경합은 diff 대조 후 origin 버전으로 리셋, main은 명시적 merge로 재조정 완료. **재발방지**: 그룹2부터는 에이전트 프롬프트에 위 금지문구를 명시.
