# 나리야 법률 챗봇 — 마스터 플랜

> 형식은 저장소 관례(`knowledge/00_MASTER_PLAN.md`)를 따른다: 비전·불변식 → 로드맵 대시보드(단일 상태표) → 단계별 상세.
> **산출물 본문은 여기 넣지 않는다 — 경로만 둔다.** 총괄 설명은 [`README.md`](./README.md), 목차는 [`index.md`](./index.md).

## 1. 비전 / 최종 목표
어민·낚시인·레저인이 **자연어로 물으면**, 위키에 근거해 **정확한 조·항·호·금액·출처로, 환각 없이** 답하는 텍스트 법률 챗봇 "나리야".

### 불변식 (모든 단계에서 절대 깨지면 안 되는 것)
- **환각 0** — 위키 원문에 없으면 지어내지 않고 "확인되지 않음"으로 답한다.
- **출처 강제** — 모든 답에 (법령 제N조, 시행일)·concept ID.
- **온디바이스 프라이버시** — 사용자 프로필·대화는 기기에만, 서버 저장 금지.
- **정직** — 법 자체의 공백은 "규정 없음"으로 표기(메우지 않음).
- **삭제 금지** — 폐지·구법은 `_legacy/`로 이동만.

## 3. 단계별 상세
각 단계: **[목표]·[진행방식]·[완료기준(DoD)]·[현재상태]·[산출물]·[리스크]**

### A. 수집  ✅
- **목표**: 해양·수산 법 73 + 별표 + 고시 + 조례 원문을 raw로.
- **진행방식**: 국가법령정보센터 API(eflaw/admrul/ordin). 위임 기반 고시 정밀 수집.
- **DoD**: 핵심 3종(법·별표·고시) 73/73 확보.
- **현재상태**: ✅ 법73·별표2,676·고시483(73/73)·조례84(표본).
- **산출물**: `raw/` · `_dashboard/collection_report.md`
- **리스크**: 조례 표본 + 일부 오염(파일명≠내용) → D에서 재수집.

### B. 위키 구축(ingest)  ✅
- **목표**: 법당 사용자가 물을 모든 규제주제를 개념 페이지로 + 처벌 3축 정밀 + 타법·테마 링킹.
- **진행방식**: 다수 에이전트(10) 동일 지침(`_SCHEMA.md`) 병렬, Sonnet.
- **DoD**: tier-1 65법 전부 커버, 처벌 조·항·호·금액.
- **현재상태**: ✅ concept 780, statutes 73, glossary 763, graph 73노드.
- **산출물**: `wiki/concepts/`·`statutes/`·`annexes/` · `index.md`
- **리스크**: 초기 빌드가 일부 조문 누락 → C에서 발견·보강.

### C. 검증 루프  🔄
- **목표**: "위키가 실제 질문에 답하나"를 질문으로 검증하고 구멍을 메운다.
- **진행방식**: 감사(법당 100~150문항, 전문가+일반인, full/thin/missing/collection_hole/awkward 판정) → 수정(없는페이지 생성·심화·별표/고시 반영) → 재감사. 자율 오케스트레이터 15분 주기, 세션한도 자동 재개.
- **DoD**: (missing+thin+collection_hole)/전체 < 5% 또는 라운드 대비 개선<3%p 또는 3라운드.
- **현재상태**: 🔄 1차 완료(구멍36%) → 수정1(+227p) → **2차 감사 중**.
- **산출물**: `_dashboard/audit/*.md`, `log.md`
- **리스크**: 세션 사용량 한도로 벽시계 지연(손실은 없음, 자동 재개).

### D. 정합·재수집  ⏳
- **목표**: 780페이지 전역 링킹 재봉합 + still_missing 표적 해소.
- **진행방식**: lint(색인·graph·백본·양방향링크·테마허브 재생성) 1회 + 타법 목록 표적수집(eflaw/admrul) + 조례 수집버그 수정 재수집 + 이미지 별표 OCR.
- **DoD**: 비대칭 링크갭 대폭 감소, index/graph 최신, 핵심 타법 인용 채움.
- **현재상태**: ⏳ (C 수렴 후 착수) — 현재 링킹은 페이지 내부만 최신, 전역은 오래됨.
- **산출물**: `wiki/graph.json`·`_backbone.md`, `_dashboard/gen_index.py`, `collect_*.py`
- **리스크**: 이미지 별표(HWP/PDF) OCR은 처벌 수치 정확성상 사람 확인 필요.

### E. 챗봇 엔진(query)  ⏳
- **목표**: 질문→맞는 개념 찾고→프로필로 좁히고→규칙대로 답.
- **진행방식**: 하이브리드 검색(glossary+임베딩(topic_embedding 재사용)+graph 홉) → 적용범위 조건으로 프로필 필터 → `_CHATBOT.md` 규칙(정의우선·점진공개·인용·모르는구어 되물음) 합성. 앱 코드는 CLAUDE.md 규칙 준수.
- **DoD**: 대표 질문셋(구명조끼·음주운항·조개껍데기 등)에 정확+점진공개+출처, 환각 0, 못찾으면 되물음.
- **현재상태**: ⏳ 설계 확정(`_CHATBOT.md`), 미구축.
- **산출물**: `local_server/services/legal_retriever.js`(신규 예정) 등
- **리스크**: 검색 품질이 승부처 — glossary + 임베딩 2단 필요(순수 키워드는 오라우팅).

### F. 앱 UI + 피드백  🎨
- **목표**: 사용자 챗봇 화면 + 관리자 검토(따봉↑↓·후보·REVIEW) + 데이터 배선.
- **진행방식**: 통합관리자센터 AI탭 하위 "AI 챗봇"(앱 디자인 준수, 상세 AI 분석 리포트). `_feedback`/`_candidates` 실데이터 연결.
- **DoD**: 따봉↓ → 후보 큐 → AI 재분석 → 관리자 승인 → 위키 반영 end-to-end.
- **현재상태**: 🎨 관리자 목업 완료(아티팩트), 실배선 미착수.
- **산출물**: `index2.html`(AI탭), `_feedback/`·`_candidates/`
- **리스크**: 프라이버시(대화 온디바이스) 유지하며 피드백만 수집하는 설계 필요.

### G. 운영(자율성장)  ⏳
- **목표**: 법 개정을 자동 감지해 그 법만 재빌드·재감사 + 사용자 피드백으로 계속 성장.
- **진행방식**: 주기적 재인제스트(시행일·본문 diff) → 바뀐 법만 C 루프 트리거, 옛 조문 `_legacy/`. `_candidates` 승인분 정식 편입.
- **DoD**: 개정 발생 시 사람 개입 없이 해당 법 위키 갱신·재검증.
- **현재상태**: ⏳ 설계됨, 미구축(cron만 붙이면 됨).
- **산출물**: 재인제스트 스케줄러(신규)
- **리스크**: 개정 오탐/누락 → diff 정확도 검증 필요.
