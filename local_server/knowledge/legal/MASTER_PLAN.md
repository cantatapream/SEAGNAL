## 1. 비전 / 최종 목표
어민·낚시인·레저인이 **자연어로 물으면**, 위키에 근거해 **정확한 조·항·호·금액·출처로, 환각 없이** 답하는 텍스트 법률 챗봇 "나리야".

### 불변식 (모든 단계에서 절대 깨지면 안 되는 것)
- **환각 0** — 위키 원문에 없으면 지어내지 않고 "확인되지 않음"으로 답한다.
- **출처 강제** — 모든 답에 (법령 제N조, 시행일)·concept ID.
- **온디바이스 프라이버시** — 사용자 프로필·대화는 기기에만, 서버 저장 금지.
- **정직** — 법 자체의 공백은 "규정 없음"으로 표기(메우지 않음).
- **삭제 금지** — 폐지·구법은 `_legacy/`로 이동만.

## 3. 단계별 상세
각 단계: **[목표]·[진행방식]·[완료기준(DoD)]·[현재상태]·[산출물]·[리스크]**

### A. 수집  ✅
- **목표**: 해양·수산 법 73 + 별표 + 고시 + 조례 원문을 raw로.
- **진행방식**: 국가법령정보센터 API(eflaw/admrul/ordin). 위임 기반 고시 정밀 수집.
- **DoD**: 핵심 3종(법·별표·고시) 73/73 확보.
- **현재상태**: ✅ 법73·별표2,676·고시483(73/73)·조례84(표본).
- **산출물**: `raw/` · `_dashboard/collection_report.md`
- **리스크**: 조례 표본 + 일부 오염(파일명≠내용) → D에서 재수집.

### B. 위키 구축(ingest)  ✅
- **목표**: 법당 사용자가 물을 모든 규제주제를 개념 페이지로 + 처벌 3축 정밀 + 타법·테마 링킹.
- **진행방식**: 다수 에이전트(10) 동일 지침(`_SCHEMA.md`) 병렬, Sonnet.
- **DoD**: tier-1 65법 전부 커버, 처벌 조·항·호·금액.
- **현재상태**: ✅ concept 780, statutes 73, glossary 763, graph 73노드.
- **산출물**: `wiki/concepts/`·`statutes/`·`annexes/` · `index.md`
- **리스크**: 초기 빌드가 일부 조문 누락 → C에서 발견·보강.

### C. 검증 루프  🔄
- **목표**: "위키가 실제 질문에 답하나"를 질문으로 검증하고 구멍을 메운다.
- **진행방식**: 감사(법당 100~150문항, **중복없이 유형별** T1단순의무·T2벌칙·T3별표까지봐야답·T4적용범위/정의·T5예외/프로필조건·T6타법연결·T7구어, 전문가+일반인 관점) → **위키만으로 답 시도해 판정**(full/thin/missing/collection_hole/awkward) + **답변방식 준수 8항목 동시 점검**(정의우선·행정처분차수(1~4차)·벌칙항별구간·처벌정밀도·타법연결·프로필조건컬럼·점진공개구조·출처) → 수정(없는페이지 생성·심화·별표/고시 반영) → 재감사(회귀 확인). 자율 오케스트레이터 15분 주기, 세션한도 자동 재개, 10에이전트 병렬(Sonnet).
- **★완결 순서(사용자 합의)**: 보고는 하되 **프로세스는 멈추지 않는다**. ①1차 감사는 65/65 **유효 완결**(실패·에이전트죽음·미수집으로 못 끝난 법은 **같은 라운드로** 재실행)이어야 수정 착수 → ②수정은 **실패 0**이어야 2차 감사 착수 → ③1차·수정·2차·수정·3차… 순환.
- **★수정 방향 5단계(사용자 확정 2026-07-16)** — 매 라운드 이 순서:
  1. **2차(직전) 감사 지적사항 수정** — 없는페이지 생성·thin 심화·hole 반영.
  2. **새 수집 원문 = 기준법 위키 재생성** — 시행령/시행규칙/별표/고시/조례 신규수집 시 그 법 재인제스트+재감사(불변식). 타법은 뻗어나온 지점만.
  3. **OCR 문제 부분 재수정** — 별표가 이미지(`<img>`/HWP/PDF)라 텍스트 못 뽑은 것(보험료율표·기준임금표·구조기준 등) **자동 OCR 시도→위키 반영**, 단 **처벌 수치는 `REVIEW`(사람확인) 플래그**를 달아 관리자 검토 큐로(정확도 리스크 정직 표기).
  4. **재감사 = 약점 집중 + 페르소나별(사용자 확정)** — 직전에 **full로 잘 답한 문항은 제외**, **thin·missing·hole만 재질문** + **수준별 신규질문**. 규모: **법당 300문항(2026-07-17 200→300 상향)= (직전 미흡분 재질문: thin·missing·hole 전부) + 신규질문, 변호사/전문가·일반인·해양종사자 3페르소나 합산**. 감사 실행 시 사용자 승인 없이 바로 가동(예산 개방).
  5. **보완 반복** — 목표 답변률 도달까지.
- **★병렬 방식(사용자 확정 2026-07-16)**: 감사·수정을 **법당 개별 워크플로(per-law)** 로 돌린다. 그룹 묶음(워크플로당 동시 2)보다 동시성이 높다 — 4코어에서 25개 워크플로 동시 실행 검증됨(에이전트가 API 대기 중심이라 코어 초과해도 동작). **전 법을 각각 독립 워크플로로 한 번에**(사용자 확정 2026-07-17 — 25배치 제한 해제) 최대 동시성으로. 단 진짜 천장은 토큰예산이라 총 처리량은 예산이 정하고(한 창에서 못 끝난 법은 리셋 후 자동 재개), 벽시계·실패격리만 개선됨. 인라인 법객체로 실행(idx-boot는 LLM 오카운트 위험). 세션한도 실패는 리셋 후 resumeFromRunId 자동 재개. 진짜 천장은 토큰예산(한 라운드 ~수백만~1천만 토큰)이라 하루 총량은 예산이 정하나, 벽시계·실패격리는 개선.
- **DoD(사용자 확정, 2026-07-18 재정의)**: **스코프 내 답변률(full) ≥ 90%.** ★"스코프 내"의 뜻: **판례·법리·다툼의 여지·순수 원문공백(입법공백)은 스코프 밖**(챗봇이 답할 게 아니라 실무자·유권해석 영역, `_CHATBOT.md`§5-2) → full 미달로 세지 않는다. 명확한 조문은 반드시 안내하고 소관부서 연락처로 마무리. (감사 원측정 full은 적대적 재질문 라운드라 낮게 나오므로, 스코프 밖 항목을 제외한 답변율로 판정)
- **현재상태**: 🔄 1차(full61%) → 수정1 → 2차(45%) → 수정2+OCR → 3차(65/65, full40%) → 수정3 → **4차(70/70)** → **수정4(189작업 완료)** → **5차 감사 70/70 완결(2026-07-18, 15,551문항, full 18.0%·thin·missing 다수)**. ★full 하락은 매 라운드 약점집중+난도상승(300문항 3페르소나) 설계 탓, 위키는 성장(회귀 통과). **5차 gap 701건 분류: A(위키로 즉시)12%·B(원문재수집)20%·C(OCR)1%·D(원문공백·법리·스코프밖)67%** → fix→감사 반복만으론 90% 불가(D가 천장) → **D단계(수집)로 전환**. 35파도 성공(점진 램프). 현황판 아티팩트 발행.
- **산출물**: `_dashboard/audit/*.md`, `log.md`
- **리스크**: 세션 사용량 한도로 벽시계 지연(손실은 없음, 자동 재개).

### D. 정합·재수집  🔄
- **목표**: 5차 감사가 드러낸 구조적 구멍(B 원문재수집 20%·C OCR 1%) 해소 + 소관부서 연락처 확보 + 전역 링킹 재봉합. **핵심은 "수집 범위를 먼저 누락 없이 확정하고, 그 리스트대로 수집하고, 수집됐는지 대조검증"**(사용자 확정 2026-07-18).
- **★진행방식 = 수집 3단계 (사용자 확정 2026-07-18)**:
  1. **범위확정(map_scope_cell.js)** — 각 기준법 원문(법률·시행령·시행규칙)을 직접 전수훑기해 **수집해야 할 가지 전체**를 누락0으로 도출: 내부위임(시행령/시행규칙/고시/별표) + **타법 인용조문(그 조문까지 타고 감) + 그 조문이 요구하는 별표·고시까지**. raw 대조로 "N개 중 M개 미수집" **매니페스트**를 `_dashboard/scope/<slug>.md`에 저장. = 수집 체크리스트.
  2. **수집(collect_fix_cell.js)** — 매니페스트 미수집목록대로 국가법령정보센터 DRF(OC=hyoo1431)로 실제 수집 → raw 저장 → 위키에 연결·반영 → **소관부서·연락처(전화) 메타 추가**(`_CHATBOT.md`§5-4). 폐지고시는 현행 ID로 재수집. **지자체 고시 등 수집곤란은 억지수집 대신 "각 지자체 고시에 따름·관할 소관부서(☎) 확인" 안내로 대체**(§5-3). **판례·법리·다툼은 손대지 않음**(스코프 밖).
  3. **검증(대조)** — 수집 후 매니페스트 각 항목이 실제 raw에 들어왔는지 대조(체크리스트 완결). 실패항목은 재수집 or 수집곤란 정직표기.
- **★기준법 vs 타법 수집 깊이 (사용자 확정 2026-07-18)**: 기준법 라인은 **전량 수집(OCR 포함)**, 타법 라인은 원문 보유하되 **거쳐가는 조문 + 그 조문의 별표/고시까지만**(타법 전체 개념화 X). 상세 `_SCHEMA.md` 0-A.
- **★기준법 시행령·시행규칙 = 전문 전량 (사용자 확정 2026-07-18)**: 기준법의 시행령·시행규칙은 일부 조문 발췌가 아니라 **전문(전 조문) 전량**을 보유해야 한다. collect 셀 **0.5단계**에서 DRF 현행본과 조문수·마지막조문을 대조, 부분이면 전문 보완수집. (발췌는 타법에만 해당.)

## H. 지식그래프·LINT — 위키 사이의 연결고리(신경망)  🔄 (설계됨·부분구축, 사용자 심화요청 2026-07-19)

> 사용자 핵심 요구: "모든 위키가 단어로 끝나지 않고, 법마다 **연결고리**를 걸어 **신경망**을 만든다. 이 신경망을 **천천히** 키우는 방안을." 카파시 LLM-위키 개념 + 마크다운-드리븐(md가 진실원천) + MEMORY 스킬 방식에 입각.

### H-0. 개념 정의 (두 층)
- **연결고리(그래프) = 신경망**: 위키peedia식 멀티홉. `[[링크]]`·`## 타법 연결` 표·`wiki/comparisons/`(테마 허브)·**정의 허브(백본)**·`graph.json`(nodes/edges)로 페이지↔페이지, 법↔법을 잇는다. 한 페이지에서 못 푸는 질문은 **링크를 타고 데이터를 받아와** 답한다(`_SCHEMA.md` 4·5절). 링크가 곧 챗봇의 **추론 경로**다.
- **LINT = 그 신경망의 무결성 검사기**: 소프트웨어 lint가 코드오류를 잡듯, 우리 lint(`_dashboard/loop/lint2.js·lint_hubs.js·lint_index.py·lint_build.py`)는 **연결오류**를 잡는다 — ①dangling(착지 없는 `[[링크]]`) ②asym(A→B인데 B→A 역링크 없음) ③미등록 노드(graph.json 누락) ④허브 공백(피인용 최다인데 정의 허브 없음). 결과는 `_dashboard/lint_report.json`·`lint_todo.md`.
- **현재 상태(정직)**: graph.json 노드 153·엣지 존재, concepts 918·comparisons 20·annexes 80. 그러나 **신경망이 성기다** — asym 링크갭 200건, 정의 허브 공백(선박안전법·공유수면·항만법), 최대 테마 `신고_허가_면허` 허브 미생성. 6차 감사도 62개 법에서 "graph.json 노드 미반영·lint 미실행·comparisons 0개·cross-page 미전파"를 반복 지적 → **LINT를 정규 단계로 승격**이 필요.

### H-1. 마크다운-드리븐 원칙 (진실원천은 md, graph.json은 파생)
- 링크는 코드가 아니라 **각 concept `.md` 안에 산다**: 본문 `[[링크]]`·`## 타법 연결` 표·frontmatter(`cites:`/`backlinks:`). 사람이 md만 고치면 된다.
- `graph.json`은 **빌드 산출물**: lint 스크립트가 md 전량을 파싱해 재생성한다. (MEMORY.md가 대화→md 반영이듯, 여기선 **md→graph 파생**.) 그래프를 직접 손대지 않는다.

### H-2. LINT을 감사 사이클의 정규 단계로 (audit→lint 자동 체이닝)
- 매 감사 라운드 종료 후 `lint`를 돌려 위 4종 결함을 리포트→`lint_todo.md`로 **다음 라운드 자동 과제화**. 감사가 이미 "lint 미실행"을 잡으므로, **audit 다음에 lint를 체이닝**(자율 오케스트레이터에 추가).

### H-3. 신경망을 "천천히" 키우는 3층 점진 전략 (카파시: 단순우선·외과수술식·조금씩 검증)
- **L1 백본(정의 허브)**: 피인용 최다 법부터 정의 허브 concept 신설 → 역링크 **착지점** 확보(신경망의 허브 뉴런). 우선순위(lint_report): 해양환경관리법(21)·영해및접속수역법(19)·**선박안전법(28, 최약결손)**·공유수면(28)·항만법(25).
- **L2 테마 허브(comparisons)**: 여러 법이 같은 주제를 다루면 교차 비교표로 **수평 연결**. 잔여 최대 테마 `신고_허가_면허`를 **행정행위 강도 3분해**(면허/허가/신고·등록)로 신설.
- **L3 역링크(양방향)**: A가 B를 인용하면 B에도 "이 법을 인용하는 법들" 백링크 → asym 200건 점진 해소(테마별 상위부터: 검사_등록 16 → 폐기물 9 → 음주운항 9 …).
- **속도규칙**: 한 라운드에 **상위 N건만**(예: 정의 허브 1~2개 + asym 상위 테마 1개). 대량 일괄생성 금지 — 조금씩, 재색인·재감사로 검증하며.

### H-4. 챗봇(앱)에서의 활용

### H-7. ★감사→통합수정(content+lint 동시)→재감사 — 구멍 재발 차단 (사용자 확정 2026-07-19)

**문제(사용자 진단, 데이터로 확인)**: 현재 루프(raw수집→위키생성(rebuild)→감사→rebuild→감사)는 **연결(lint 신경망)을 꿰매는 단계가 없다.** 6차 감사 결과, missing/thin의 다수가 "raw엔 있는데 위키에 **연결·반영** 안 됨"(wiki_lag·비대칭링크·허브미연결·타법미인용) 유형 — 즉 **수집 구멍이 아니라 연결 구멍**이다. rebuild만 반복하면 내용은 채워도 연결이 안 꿰매져 **같은 구멍이 매 감사 재발**한다. 감사를 더 돌리는 게 해법이 아니다.

**해법**: 감사 다음에 **통합 수정 단계**를 두어, **감사 리포트의 gap 목록을 입력으로 content와 lint(연결)를 한 에이전트가 동시에 고친다.** 그 뒤 재감사로 회귀 확인. (감사 = 구멍을 찾는 검증가능 목표 → 그 목표를 통과할 때까지 수정 = 카파시 목표기반 실행.)

**통합 수정 단계 절차 (법별 1에이전트, 병렬 안전)**:
1. `_dashboard/audit/<법>.md`(그 법의 감사 gap)를 읽어 **유형분기**:
   - **wiki_lag**(raw엔 있는데 위키 미반영) → raw에서 수치·조문을 위키 본문/annex로 **옮김**(content).
   - **연결 결손**(비대칭링크·허브미연결·타법미인용·정의사슬 미완) → `[[링크]]`·역링크(backlink)·`## 타법 연결` 표·`comparisons` 허브를 **추가**(lint/연결).
   - **진짜 수집 구멍**(raw 자체 없음) → 재수집 큐로(별도 파이프라인, 이 단계에서 만들지 않음).
2. **자기 법의 파일만 쓴다 → 법별 병렬 안전**(CLAUDE.md 병렬규칙 준수).
3. **라운드 끝 공유 허브 재봉합은 ⚠경합위험 → 단독(직렬)**: `graph.json`(md→파생 재생성)·`_glossary`·교차 테마 허브(comparisons)는 여러 법이 함께 쓰므로 lint 스크립트(`lint_build`/`lint2`/`lint_hubs`)로 **한 번에 단독** 처리.
4. lint가 **비대칭·dangling·미등록노드·허브공백을 재측정** → `lint_report.json`·`lint_todo.md` 갱신 → 다음 라운드 자동 과제.
5. **재감사**로 회귀 확인(그 gap이 실제로 막혔나).

**즉 루프 재정의**: ~~수집→rebuild→감사→rebuild~~ → **수집 → (초기)rebuild → [감사 → 통합수정(content+lint 동시, 법별 병렬) → 공유허브 lint 재봉합(단독) → 재감사] 반복**. 7차부터 이 통합수정 루프를 표준으로 한다(6차 감사 완료 직후 착수).

**산출물**: `audit_fix_cell`(신규 — 감사gap 구동 content+lint 통합수정, 법별 병렬) + lint 단독 재봉합 체이닝. **DoD**: 재감사 시 연결결손(비대칭·허브미연결·타법미인용) gap이 라운드마다 감소, wiki_lag 0 수렴.

### H-8. ★⚠REVIEW 데이터 = 감사 채점 보류 (사용자 확정 2026-07-19)
- **규칙**: 감사(질문/답변 검증)는 **아직 사람이 검증하지 않은 ⚠REVIEW 데이터**(별표 이미지 OCR 판독값 등)에 의존하는 질문을 **full/thin/missing/hole 어느 것으로도 채점하지 않는다** → `review_pending`으로 **별도 집계**(정답으로도 오답으로도 세지 않음). 사유: 인간 검증 UI(Phase F ⚠REVIEW 검증 큐)가 아직 없어 그 값의 정오를 신뢰할 수 없다. 지금 채점하면 미검증 값으로 위키를 잘못 판정한다.
- **재개 시점**: 인간 검증 UI 완성 → 사람이 원문이미지 vs AI추출 대조·승인 → **그때 review_pending 질문들을 감사에 재편입**(재질문). 그 전까지는 ⚠REVIEW 밖(확정분)만 채점 대상.
- **반영**: `audit_sim.js` 판정에 `review_pending` 추가(2026-07-19). 6차 감사 최종 집계 시 review_pending은 분모에서 제외해 스코프-내 full률을 계산.

### H-9. ★lint를 자율(무인) 자동화 루프에 편입 — 폰이 꺼져 있어도 lint+위키 동시 진행 (사용자 확정 2026-07-19)
- **문제**: H-7 통합수정(content+lint 동시)이 **사람이 붙어 있을 때만** 돌면 자동화의 의미가 없다. 자율 스케줄러(자동재개 트리거·G절 자율성장)가 사용자 부재 중 돌릴 때 **rebuild·감사만 하고 lint를 안 하면**, 무인 사이클이 또 연결 구멍을 남긴다.
- **규칙**: **자율(무인) 사이클의 표준 1턴 = 감사 → 통합수정(content+lint, 법별 병렬) → 공유허브 lint 재봉합(단독) → 재감사**. 즉 자동재개 트리거가 깨어날 때마다 rebuild/audit뿐 아니라 **lint(비대칭·dangling·미등록노드·허브공백 재측정 + md→graph 재생성 + 신규 백링크/허브 보강)까지 자동 수행**한다. lint 결과는 `lint_report.json`·`lint_todo.md`에 누적, 활동은 `AUTO_RUN_LOG.md`에 기록(사람 부재 중 lint가 무엇을 꿰맸는지 복명).
- **안전**: 법별 통합수정은 자기 파일만 쓰므로 병렬 안전. 공유허브(graph.json·_glossary·comparisons) lint 재봉합은 ⚠경합위험 → **단독(직렬)**. ⚠REVIEW 데이터는 H-8대로 채점·확정 대상에서 제외(사람 승인 전까지 lint가 그 값을 canonical로 승격하지 않음).
- **반영 대상**: 자동재개 트리거 프롬프트(무인 사이클 정의에 lint 단계 추가), G절 자율성장(재인제스트 스케줄러가 collect→rebuild→**lint**→audit 전 사이클 트리거), `audit_fix_cell`(H-7)와 lint 체이닝을 트리거가 함께 호출.
- **DoD**: 사용자 부재 중 자율 사이클이 감사구멍뿐 아니라 **연결구멍(lint)도 매 사이클 줄인다**. AUTO_RUN_LOG에 "이번 사이클 lint: 비대칭 N건 해소·허브 M개 신설·graph 노드 K개 등록" 형태로 기록.

### H-12. ★자율루프 3대 보완 — 메타출처·승인이원화·수집환류 (사용자 확정 2026-07-19 "모두 진행")

## H-24 (2026-07-21) ★구멍(hole) 발견 시 유사 항목 전체로 패턴 전파 확인 의무화 (사용자 확정)

도선법 제주항 승하선구역처럼 **한 법(또는 한 항목)에서 수집 구멍이 발견됐을 때, 그 법 안에 동일한 형식/구조를 가진 유사 항목들(예: 다른 도선구·다른 지정구역 등)에도 똑같은 구멍이 있는지 함께 확인하지 않고 그 항목 하나만 고치고 넘어가는 것**을 금지한다.

**확정 절차** (앞으로 모든 collection_hole/wiki_lag 개별 항목 수정 시 표준 적용):
1. 구멍을 하나 발견하면, 먼저 **그 항목이 속한 법 안에서 동일한 패턴(같은 위임조문·같은 종류의 지정/고시·같은 데이터 형태)을 가진 다른 항목들이 있는지 목록화**한다(예: 도선법의 다른 도선구, 어떤 법의 다른 지정해역/지정구역 등).
2. 그 목록 각각에 대해 **같은 방식으로 수집이 됐는지/구멍이 있는지 개별 확인**한다 — "하나 고쳤으니 나머지도 됐겠지"라고 추정하지 않는다.
3. 구멍을 만든 원인이 **구조적 결함**(수집 스크립트가 특정 JSON 경로·특정 API 파라미터를 애초에 놓치는 등, L-20 부칙 사례처럼)으로 판명되면, 그 결함을 고치는 과정을 진행하고, **결함이 실제로 해결됐다고 확인된 시점에는 동일 결함으로 구멍이 났을 수 있는 다른 미수집 항목들도 함께 재수집·수정**한다(한 항목만 고치고 끝내지 않는다).
4. 이 확인·전파수정 과정을 `_dashboard/stage_b_collection_targets.md`(또는 해당 작업 로그)에 "유사항목 전수확인 완료/구조적결함 아님" 또는 "구조적결함 확인 → N개 항목 함께 수정" 형태로 기록한다.

## H-28 (2026-07-27) ★위임체인 전수조사 — 감사(질문 시뮬레이션) 대신 로직 기반 전수 대조로 collection_hole 원천 예방 (사용자 제안, 로드맵 반영·미착수)

10차 감사 완료 후 collection_hole 68법(387건) 재검증 과정에서, 재검증에 쓴 방법(`lsDelegated` API로 법의 위임조문정보를 직접 조회해 raw/`_admrul.json`과 대조) 자체가 **감사가 우연히 찾아낸 항목만이 아니라 전체 조문에 대해 선제적으로 할 수 있는 작업**임이 확인됨. 사용자가 "굳이 감사(질문 시뮬레이션)로 우연히 찾을 게 아니라, 애초에 73법 전 조문을 위임체인 끝까지 전수 대조하면 collection_hole이 발생할 이유가 없지 않냐"고 제안.

**핵심 통찰(오케스트레이터 의견, 사용자 동의)**:
- 감사는 **확률적 발견**이다 — 시뮬레이션 질문이 우연히 그 위임 지점을 건드려야만 구멍이 드러난다. 안 건드리면 영원히 안 보일 수 있다.

## H-29 (2026-07-27) ★법령·고시 최신성 변동감지(활류) 시스템 — 날짜범위 필터 광역질의 + 매치 시에만 딥다이브 (사용자 제안, 로드맵 반영·미착수)

기존 로드맵의 "활류(사서가 지속적으로 법령이 최신인지 검증)" 기능을 어떻게 구현할지에 대한 설계 논의. 사용자 질문 2가지: ①법률 자체의 제정/개정/폐지를 어떻게 감지할 것인가 ②현재 없는 위임 행정규칙·고시가 나중에 신설되거나 기존 것이 개정·폐지되는 것을 어떻게 감지할 것인가.

**오케스트레이터 의견(사용자 동의)**: 이것도 감사(AI)가 아니라 **로직 기반 차분(diff) 감지**로 해야 한다 — "바뀌었는지 여부"는 API 응답을 저장해둔 이전 스냅샷과 비교만 하면 되는 기계적 작업이기 때문.

**설계**:
1. **법률 자체 변동**: law.go.kr `lawSearch`(법령 목록조회)는 개정일자/공포일자 **범위 필터**를 지원한다. 73법을 매번 개별 재조회하는 대신, "최근 N일 이내 개정된 해양수산부·해양경찰청 등 소관 법령" 같은 **넓은 범위 질의를 주기(예: 주 1회) 1번만** 날리고, 그 결과를 73법 목록(법령명/MST)과 대조 → 매치되는 법만 "MST 갱신(신법 시행)" 신호로 보고 깊은 재수집 트리거.

### 추진 배경

H-34 MVP를 만들며 드러난 한계③(여러 소스 페이지에 걸친 흐름을 못 합침)을 사용자가 실사용 스크린샷으로 지적한 자리에서, "그 조문이 실제로 무엇을 위임했는지"를 위키 표 순서 근사치가 아니라 **진짜로 추적**하려면 무엇이 필요한지 논의가 이어졌다. 사용자가 연속 질문으로 물은 것: ①위키방식(사람이 읽고 링크 거는 방식)과 프로그램 방식(원문 위임 문구를 정규식으로 전수 추적하는 방식)의 효과성·커버리지·속도·비용 차이를 데이터로만 설명해달라 ②"원문에 위임 문구가 안 적혀 있으면 아예 못 찾는다"는 말이 실제로 무슨 뜻인지 실사례로 설명해달라(예: "시험과목은 별표2와 같이 하고, 해양수산부장관이 정하여 고시한다"처럼 위임 대상이 텍스트에 명시된 경우와, 그렇지 않은 경우의 차이) ③이 추적 방식을 적용해도 위키가 여전히 필요한지(그래프가 촘촘하면 위키 없이 그래프만으로 실시간 답변이 가능하지 않은가) ④환각 0 원칙과 이 방식의 관계(원문을 그때그때 읽고 종합하는 것 자체가 환각 위험 아닌가, 그 위험을 미리 차단하는 장치가 위키 구축 과정 아니었나).

오케스트레이터가 실측·구조 데이터로 답한 요지: 그래프는 "조문↔조문"이 연결돼 있다는 **사실**은 즉시·저비용으로 알려주지만, 그 연결이 **무엇을 의미하는지**(정의 충돌·예외·톤수 구간 등을 종합한 결론)는 여전히 해석이 필요하고, 이 해석을 사용자 질문마다 실시간으로 하면 시간 압박 속에서 검증 없이 나가는 것이라 환각 0 불변식과 정면으로 충돌한다. 반면 위키는 이 해석을 **미리, 여러 사용자에 걸쳐 상각되는 비용으로, 검증(REVIEW→승인)까지 거쳐** 만들어두는 구조라, 같은 해석 작업이라도 안전장치가 다르다. 또한 그래프는 조문↔조문만 연결할 뿐 "사용자의 자연어 질문↔어느 조문"을 잇는 것은 여전히 별개 계층(검색·리트리버, 위키 페이지의 제목·키워드에 의존)의 역할이라, 그래프가 아무리 촘촘해도 위키(와 그 검색 메타데이터)를 대체하지 못한다. 이 설명을 사용자가 확인·동의하며, 그래프의 용도를 **위키 제작을 도울 것**(Track A)과 **위키의 공백을 찾을 것**(Track B) 두 가지로 좁히고, 실시간 서빙에는 배선하지 않기로 확정했다.

**노드별 질문·선택지(사용자 추가지시 반영 완료)**: 비-리프 5개 노드 전부에 `질문`+`선택지[{label,hint,next}]`. 빌더가 ①선택지 존재 ②선택지수=자식수 ③`next` 실재 ④선택지 3개 이하(`CLARIFY_OPTION_MAX=3`)를 검사해 위반 시 빌드 실패(이 규칙 때문에 "그 밖의 선박" 초안 4갈래를 3갈래+화물선 하위 2갈래로 재구성). 예: root 질문 "어떤 배에 관한 것인가요?" → 어선(어선법 제2조제1호)/수상레저기구(수상레저안전법 제2조제3호)/그 밖의 선박(선박법 제1조의2제1항). 트리로 안 쪼갠 잔여 축은 리프의 `추가확인` 필드에(예: "국제항해에 종사하나요?" → 영향받는 서류 10개).

**유지보수(H-29 연동) 설계**: 조인 키 `(slug, layer, 조문번호)` — `law_change_queue.json`의 `changed_articles[]`와 같은 축이라 매칭이 단순함. ①트리 직접 수정 대신 사이드카(`vessel_doc_tree_review.json`)에 플래그만 ②**자동 재빌드는 하지 않음** — 개정으로 앵커 검증이 실패하는 건 정상적인 "사람이 봐야 한다" 신호이고, 자동 재빌드는 이 신호를 지워버림 ③새 계층 주제도 provenance 규약만 지키면 같은 스크립트를 재사용 가능(=이 규약 자체가 유지보수 인터페이스) ④`법령ID`(H-29 11항·L-74)를 처음부터 스키마에 포함(나중에 백필하는 것보다 저렴).

**되묻기 연동 설계**: `matchDocTreeTopic(query)`/`clarifyFromTree(node)`/`resolveDocTreePath(query, tree)` 3함수 제안, 반환 스키마를 기존 `decideClarify()`와 동일하게 유지해 `routes/legal.js`·`ai_chat.js` 무변경으로 붙게 설계. 트리 라벨 문자열이 `CLARIFY_JOINER` 경로복원의 계약이라 함부로 바꾸면 진행중 대화가 깨진다는 점 명시.
