이 문서는 **법률 위키를 소비하는 쪽(챗봇)** 의 동작 규칙이다.
위키를 만드는 규칙은 `_SCHEMA.md`, 여기는 그 위키로 **어떻게 답하는가**.

## 0. 결정된 방향 (2026-07)
- **음성 비서 호출 기능 폐기.** 기상 정보는 사용자가 지도·레이어로 직접 둘러보는 게 빠르고,
  법률 정보를 음성으로 한꺼번에 쏟으면 혼란을 준다. → **텍스트 챗봇(턴제)** 로 간다.
- **기존 직군 분류 시스템(`knowledge/jikgun`, `knowledge/graph`) 재사용 안 함.** 직군·소속·취미는
  챗봇이 대화 중 자연스럽게 물어 얻는다.
- **프로필은 챗봇이 대화로 획득하고 기기에만 저장**(서버 저장 금지), 다음 질의의 필터로 재사용.

## 0-A. 운영 결정 (확정) — `_SCHEMA.md`에서 이관(2026-07-27, 답변/표출 규칙이라 여기가 맞음)

| 항목 | 결정 |

| 첫 구축 대상 | **수산업법**부터 (근간 허브 법) → 어선법·어선안전조업법으로 확장 |

| Gemini 키 | 기존 기상용 키 **공유**(`gemini_client.js`). |
| 답변 원칙 | **모든 답변에 근거 조문(법령명·조문·시행일) 명시 + 하단 면책 고지**("참고용, 최종 확인은 공식 출처"). |
| 근거 = 전체 사슬 | 별표·시행규칙 하나만 대지 말고, 거기에 닿게 된 **법률 → 시행령 → 시행규칙 → 별표 전체 도출 경로**를 함께 제시(설득력↑). 예: "법 제10조 → 시행규칙 제4조 → 별표 3". 각 단계 딥링크 제공. **근거 목록은 "관련 있어 보이는 것 전부"가 아니라 답변이 실제로 밟은 추론 경로여야 한다**(사용자 확정 2026-08-04) — 법 하나를 법률→시행령→시행규칙→고시 순으로 끝까지 보여준 뒤에야 다음 법으로 넘어간다, 여러 법이 뒤섞여 나오지 않는다. **구현(2026-08-04, MVP)**: `legal_retriever.js`의 `groupCitationChainByFlow()`가 답변에 실제 인용된 줄만(`filterCitationChainByAnswer`) 첫 등장 법 순서로 묶고 그 안에서 tier(법률→시행령→시행규칙→고시) 순 정렬. ⚠**아직 raw 원문에서 "이 조문이 실제로 무엇을 위임했는지"를 그때그때 실시간 추적하는 게 아니라, 위키 근거조문 표에 이미 적힌 법률·조문·tier 필드를 재배열하는 수준**이다 — 완전한 실시간 위임체인 추적은 다음 로드맵 후보(law.go.kr API 재조회 필요, 규모가 커서 보류). |
| 지도 표출 화법 | 그릴 수 있으면(좌표 기반) **바로 그려서 보여주고**, 못 그리면 조용히 공식 표로 안내. **"이건 못 그린다"는 메타 설명은 사용자에게 하지 않는다.** |
| 답변 톤 | 딱딱한 법조문 나열 금지. **결론 먼저 → 필요한 근거**. 본문 첫 문장을 **"쉽게 말하면~"으로 열어** 결론을 일상어로 짧게 요약한 뒤 조문·처벌 근거를 잇는다(두괄식 — 맨 끝 마무리 말로 붙이지 않는다, 2026-08-04 확정). 갈래·조건별로 나뉘는 설명은 "*" 같은 밋밋한 기호로 뭉뚱그리지 말고 **"1. → 가. → 1)"(더 깊으면 "가)→(1)→(가)") 순으로 단계를 매겨 위계를 드러낸다**(2026-08-04 확정, 조문 팝업의 항①→호1.→목가. 표기와 같은 원칙). 대화가 유연하게 이어지게 한다(과잉 설명도 금지). |
| 준용·포괄인용 | AI가 억지 해석하지 않고 **링크 + REVIEW 플래그**, 사람이 범위 확인. |
| 대화 이력 | **온디바이스에 저장**(서버 미저장), 프로필도 이 이력에서 이어짐. **구현(2026-08-04)은 원래 구상(카카오톡처럼 한 채팅방을 위로 스크롤해 과거 로드)과 다르다** — 헤더의 🕘 버튼을 누르면 **날짜별로 묶은 지난 질문 목록**이 뜨고, 항목을 탭하면 그 질문·답변만 다시 보여주는 방식으로 구현됨(`localStorage nariya_history_v1`, 질문·답변 텍스트만 저장·근거법령은 미저장, 최대 200건). 연속 스크롤 방식으로 바꾸고 싶으면 별도 논의 필요. |
| 지도·구역 표출 | **좌표(경위도)가 명시된 별표만 폴리곤화**한다. 좌표 없이 지형지물·한글로만 서술된 구역은 **폴리곤 대상에서 제외**(공식 별표 이미지로만 표출). 폴리곤은 빈 배경이 아니라 **실제 지도 위에 오버레이**한다. |
| 지도 탭 연동 | 채팅에 **별도 프롬프트 박스를 두지 않는다**(공간 낭비). **폴리곤/지도를 탭하면 확대 팝업**이 열리고, 그 팝업 안에 핀치줌·**"해양종합정보 탭에서 보기"**·X를 모두 넣는다. "탭에서 보기" → 기존 딥링크(`assistant=ocean`, 좌표는 `assistant=tide`의 lat/lon 방식)로 **`ocean-map-section` 열고 위치 이동 + 폴리곤 오버레이**(풍랑·파고 레이어와 함께). |

## 1. 프로필(온디바이스) — 대화로 채운다
고정 폼/자동감지가 아니라, 필요할 때 되물어 얻는다. 얻은 값은 기기에만 저장·재사용.
법률 답 필터에 쓰는 핵심 필드:

| 필드 | 예 | 쓰임 |
|---|---|---|
| 선박 톤수 | 5톤 / 9.77톤 / 30톤 | concept `적용범위(톤수)` 조건 매칭 |
| 선박 용도 | 낚시어선 / 어선 / 레저 / 일반 | 낚시어선법 vs 어선법 vs 수상레저법 분기 |
| 어업 종류 | 연안자망 / 근해통발 / 양식 … | 허가·신고·금어기 분기 |
| 면허·자격 | 소형선박조종사 / 해기사 급수 | 승무기준·자격 |
| 주 조업구역 | 특정해역 / 조업자제해역 (연근해) · 태평양 / 대서양 / 인도양 (원양, 원양산업발전법 제6조④) | 구역 규제·출항통제 |
| 야간조업 | 예 / 아니오 | 야간장비 의무 |

원칙: **모르면 묻는다.** 답이 프로필에 의존(톤수로 갈리는 의무 등)하는데 값이 없으면,
장황하게 다 나열하지 말고 필요한 한 가지를 되물어 좁힌다. ("배가 몇 톤이세요?")

### 1-A. 대화 설계 결정 — 멀티턴 되물음 우선, 안 되면 조건별 분기 폴백 (H-21 사용자 확정 2026-07-21, Phase E 설계 메모)
- **1순위(권장)**: 위 원칙대로 **에이전트가 한 번에 한 조건만 되물어 좁혀가는 멀티턴 대화**. 예: "정박신고 의무 있어?" → "배가 몇 톤이세요?" → (답변) → 톤수 조건에 맞는 답만 제시. 필요하면 두세 번 더 되물어 좁힐 수 있다(예: 톤수 다음 용도, 용도 다음 조업구역 등 — 최대 3턴 정도가 사용자 경험상 적정).
- **2순위(폴백)**: 만약 실제 구현 단계에서 멀티턴 되물음이 **대화 턴 수 제한·API 구조 등으로 불가능**하다고 판명되면, 처음 답변에 **조건별 분기를 전부 제시**하는 방식으로 대체한다(예: "5톤 미만이면 A, 5톤 이상이면 B" 식으로 한 번에 나열). 이 경우도 프로필 값이 이미 있으면 해당 분기만 골라 답한다.
- 어느 쪽이든 **위키 데이터 구조(적용범위·예외 표에 톤수·용도·구역 조건 컬럼)가 전제조건**이라, 이 문서 1절의 프로필 필드·감사의 "프로필조건" 체크 기준은 두 방식 모두에 공통으로 적용된다.
- **이 절은 설계 결정만 기록한 것 — 실제 구현은 Phase E(답변엔진) 착수 시점.**

### 1-C. 프로필을 **미리 채워두는 길**도 생겼다 — 설정(⚙) 패널 (H-37 §7, 2026-08-14 구현·스위치 off)
1절이 말한 "대화로 물어 얻는다"는 방식은 그대로 유지된다. 여기에 **사용자가 스스로 미리 적어두는 길**이
하나 더 생겼다(사용자 확정 2026-08-11 "챗봇에 설정버튼을 하나 추가해서 그 안에 사용자 정보가 들어가도록").

- 채팅 헤더 **⚙ → "나에 대해서 설명하기"**: 1절 표의 필드(직군·선박용도·톤수·길이·어업종류·면허/자격·
  주 조업구역·야간조업·관심분야)를 **버튼으로 고르거나 직접 입력**해 둔다. 저장 위치는 그 기기의
  `localStorage['nariya_profile_v1']` **뿐**이고, 필드마다 저장 시각(`at`)을 함께 남긴다.
- 질문할 때 그 스냅샷이 요청 바디의 **별도 필드 `profile`** 로 함께 간다. 서버는 **그 요청을 처리하는
  동안만** 읽고 파일·로그·임시보관 어디에도 쓰지 않는다(설계 §3.3 R1 — `grep`으로 검증·회귀 고정).
- 되묻기와의 관계: 되묻기 선택지 라벨과 프로필 값이 **문자 그대로 일치**할 때만, 그 되묻기가
  *"저장된 정보로는 "낚시어선"이신 것 같아요(2026-07-30 저장). 이 조건으로 답변드릴까요?"* 확인 카드로
  바뀐다. **"네"는 그 축(조건) 하나만 확정**하고, 프로필이 모르는 다른 축은 평소대로 계속 되묻는다
  (사용자 확정 "3번은 따로 확인해야해"). **"아니요"는 이번 질문에서만** 그 값을 무시한다(프로필은 안 고친다).
- 지금은 서버 스위치 `profileConfirm`(기본 **false**)로 잠겨 있다 — 켜기 전까지 동작은 종전과 100% 같다.

### 1-B. 되묻기 구현 — 구조화 버튼 선택지 (사용자 확정 2026-08-03, 구현 완료)
1-A의 "1순위 멀티턴 되물음"을 **자유 텍스트가 아니라 버튼 선택지**로 구현했다. 이 챗봇은 대화 이력을
서버에 전혀 보내지 않는 **완전 단발성 구조**라, 자유 텍스트로 되물으면 사용자의 답이 새 단발 질의로
들어가 원래 맥락이 사라진다. 버튼이면 "이어지는 답인지 새 질문인지" 판정 자체가 필요 없다.

- **별도의 빠른 판단 단계**: 검색으로 근거(contextPages)를 확보한 직후, 무거운 종합답변
  (`synthesizeAnswerStream`)을 만들기 **전에** `legal_retriever.decideClarify(query, contextPages)`가
  "되물어야 하는 질문인가"만 짧게 판단한다(사고 끄고 JSON만 받는 호출 — `expandQueryTerms`·
  `pickCandidateLaws`와 같은 패턴). 되물을 게 있으면 종합답변을 **아예 만들지 않고** 질문 + 선택지
  2~3개 + 한 줄 안내만 내려보낸다(`POST /api/legal/ask` done 이벤트의 `clarify` 필드).
- **선택지는 그 순간 검색된 근거 조문에서만 만든다(환각 0)**. 고정 목록이 아니다 — 예: 해상교통안전법
  제39조가 처벌 대상을 "조타기를 조작하거나 그 조작을 지시하는 자"로 규정하니, 그 조문을 근거로
  "조타 담당인가요, 일반 승객인가요?"를 묻는다. 근거자료에서 그 구분의 근거를 찾을 수 없으면
  되묻지 않는다(`needed:false`). 판단이 애매하거나 실패(키 없음·타임아웃·파싱 실패)해도 조용히
  `needed:false`로 물러나 **기존 답변 흐름 그대로** 진행한다.
- **맥락 조립은 클라이언트가 한다**(서버 세션 저장 없음): 버튼을 누르면 `"원래질문 — 선택라벨"`로
  합쳐 **기존 질문 전송 로직 그대로** 다시 보낸다. 합쳐진 질의에는 조건이 이미 문장에 들어 있으므로
  같은 조건을 또 묻지 않는다. 한 번 고른 선택지 묶음은 비활성 — 중복 전송 방지.
- **되묻기는 최대 2라운드 — 그 천장은 프롬프트가 아니라 코드로 막는다**: 프롬프트에도 "이미 조건이
  붙었으면 묻지 마라"(기준3)가 있지만 모델이 이를 어기면 버튼→되묻기→버튼 무한루프가 된다(검토에서
  실증). 그래서 `decideClarify` 첫머리에서 질의에 붙은 결합자(`' — '`, em dash U+2014 앞뒤 공백 —
  클라이언트 `pickClarifyOption`이 쓰는 그 구분자) **개수 = 이미 지나온 라운드 수**를 세어
  `CLARIFY_MAX_ROUNDS`(=2)에 닿으면 **Gemini를 부르지도 않고** `needed:false`로 물러난다.
  ⚠ 상한이 1이 아니라 2인 이유: 한 번 좁혀도 갈래가 남는 질문이 실제로 있다 — "낚시어선에서 술
  마시면?"은 ①선장·선원이냐 승객이냐 를 물은 뒤에도 ②하천·호소냐 바다냐(적용 법령·처벌이 다르다)를
  한 번 더 물어야 한다. 같은 조건을 두 번 묻지 않게 하는 1차 방어선은 여전히 프롬프트 기준3이고,
  이 상한은 그게 뚫렸을 때의 백스톱이다.
  ⚠ 클라이언트 구분자와 서버 `CLARIFY_JOINER` 중 한쪽만 바꾸면 이 차단이 뚫린다.
- **hint 조문번호 대조(환각 0)**: 모델이 근거자료에 없는 조문번호를 hint(버튼 툴팁)에 지어넣는 사례가
  확인돼, 파싱 후 hint의 `제N조` 토큰이 근거자료 원문에 문자 그대로 없으면 **그 hint만 비운다**(선택지
  라벨은 유지). 질문·라벨 전체 문자열 대조는 하지 않는다 — 패러프레이즈 오탐으로 정상 되묻기가 죽는다.
- **되묻기 응답의 근거목록**: 답변 문장이 없어 `filterSourcesByAnswer`(문장 기반 교차확인)를 쓸 수
  없으므로, 되묻기 판단이 실제로 읽은 상위 `CLARIFY_TOPK`건까지만 싣는다(원본 최대 15건 → 6건).
- **답변 원칙과의 관계**: 되묻기가 이 앞단에서 걸러주므로 답변 프롬프트 **규칙3은 "여기서는 되묻지
  말고 있는 정보로 답하라"** 로 바뀌었다(규칙3 ↔ 규칙8 충돌 해소). **규칙8(관련 주체 빠짐없이
  나열)은 유지** — 되묻기로 좁혀지지 않는 진짜 다자간 케이스(선장·선원·승객·화주가 각각 다른 의무)를
  위해 필요하다.
- 구현: `services/legal_retriever.js decideClarify` · `routes/legal.js POST /api/legal/ask`
  · `client/js/ai-chat/ai_chat.js clarifyHTML/pickClarifyOption` · `client/css/ai_chat.css .nrya-clarify*`.

## 2. 점진적 공개 (처벌·다차수 답변의 핵심 규칙)
처벌이 **차수(1/2/3차…)·상황에 따라 갈리는 경우**, 한 번에 전부 쏟지 않는다.

1. **1차 답**: ① "이건 **상황(단속 횟수 등)에 따라 달라진다**"를 먼저 알리고,
   ② **가장 흔한 경우(통상 최초/1차)의 처벌만** 제시한다. ③ 출처(법·별표)를 단다.
2. **되물음**: "2차 이후(또는 특정 차수)도 알려드릴까요?" 로 끝낸다.
3. **확장 답**: 사용자가 원하면(또는 특정 차수를 지정하면) 그때 **차수별 전체(1→2→3→4차)** 를 제공.

> 데이터를 숨기는 게 아니다 — 위키(`## 행정처분 체계` 별표)엔 1~4차가 전부 있다.
> 한 번에 안 쏟아 혼란을 줄이는 **UX 규칙**이다.

### 예시 (어선안전조업법 승선원 변동 신고 미실시)
- 턴1 — "승선원 바뀌었는데 변동 신고 안 하면?"
  → "단속 횟수에 따라 달라져요. 보통 **최초 단속 땐 경고** 수준입니다.
     2차·3차 이후는 더 무거워지는데, 그 부분도 알려드릴까요?" *(출처: 시행규칙 별표N)*
- 턴2 — "응, 3차는?" / "전부 알려줘"
  → "1차 경고 → 2차 ○○ → 3차 ○○ → 4차 ○○ …" (전체 또는 지정 차수)

같은 원리를 **벌금 구간·과태료 상한·톤수별 의무** 등 "조건에 따라 갈리는" 모든 답에 적용:
먼저 통상/대표값 + "조건에 따라 다름" → 되물음 → 필요 시 전체.

## 3. 인용 규율 (환각 0)
- 법률 답의 근거는 **위키 원문 인용만**. 위키에 없으면 "확인되지 않는다"고 말한다(지어내지 않음).
- 처벌은 **조·항·호·금액 그대로**. 뭉개기 금지.
- 답변은 **출처 concept ID를 달고** 나간다 → 따봉↓ 시 그 페이지를 정확히 가리켜 관리자 큐로 연결.
- **★검증된 것만 인용 = canonical 필터 (사용자 확정 2026-07-20)**: 사용자에게 나가는 답변 근거는 **검증 완료(`status: canonical`) 페이지만**. 미검증 `draft`(별표 OCR 오독 처벌수치 등)는 답변 근거로 쓰지 않는다 — 틀린 값이 사용자에게 새면 안 되기 때문. 구현은 서버 스위치 `nariya_config.json.answerCanonicalOnly`(기본 OFF=검증 쌓일 때까지 현행 전체검색, 검증 후 ON). **켜기 전 index.json을 status 포함 재빌드 필수**(안 하면 답변 0건). 상세 절차·취지는 `MASTER_PLAN.md` E절 "canonical 안전필터". statute(법령 원문 자체)는 검증 대상이 아니라 필터 통과.

## 4. 검색 (하이브리드) — 엔진 구현 시
★**순차가 아니라 "동시에 점수 매겨 최고점 카드 선택"이다.** glossary가 무조건 첫 관문이 아니다.
- **① 직접 매칭** — 질문 단어가 개념 **제목·정의·본문에 그대로** 있으면 바로 그 카드(강한 신호). "구명조끼"·"음주운항"처럼 **법에도 적힌 정식 명칭**은 여기서 곧장 잡힌다. (glossary는 이때 기여 안 함, 있어도 무해)
- **② glossary 구어 매핑**(`wiki/_glossary.md`) — 사람 말 ≠ 정식 명칭일 때만 번역: "조개껍데기"→폐기물, "술 먹고 배 몰면"→음주운항. (띄어쓰기 무시) = **정식 명칭이 아닌 말을 위한 안전망**.
- **③ 임베딩 검색**(`services/topic_embedding.js` 재사용) — 바꿔 말한 질문(패러프레이즈)을 의미로 잡는다.
- **④ 그래프 홉**(`wiki/graph.json`) — 위에서 잡은 개념의 관련개념·테마허브까지 확장.
①②③을 **함께 돌려 점수 합산 → 가장 잘 맞는 카드** 선택. 그 뒤 **프로필 필터**(1절 필드 ↔ concept `적용범위·예외` 조건 컬럼)로 좁힌다.

### 4-U. 모르는 구어 해소 (미등재 용어 → 웹 → 사용자 확인)
1·2·3 다 돌려도 **확실한 개념이 안 잡히면**(점수 낮음/모호), 지어내지 말고 아래를 순서대로 한다:
1. **먼저 우리 DB(위키·glossary) 재확인** — 정말 없는지.
2. **없으면 웹 검색으로 그 말의 뜻을 확인** — 예: "깔때기"가 DB에 없으면 웹에서 "깔때기(어구)"가 무엇인지 찾는다.
3. **찾은 뜻을 사용자에게 되물어 확인** — "'깔때기'는 통발류 어구를 말씀하시는 게 맞을까요?" (추정을 사실처럼 답하지 않는다)
4. **사용자가 맞다고 하면** 그 뜻으로 다시 개념 검색(1·2·3) → 답변. 동시에 이 구어→개념 매핑을 **`_candidates` 방에 학습 후보로 적재**(관리자 승인 시 glossary에 정식 편입).
- 원칙: **DB 우선 → 웹은 '뜻 확인'용 → 확정은 사용자 되물음**. 웹 내용을 법적 근거로 인용하지 않는다(근거는 항상 위키 원문).

## 5. 답변의 경계와 마무리 (스코프·소관부서·수집불가 안내) — 사용자 확정 2026-07-18

챗봇이 "어디까지 답하고, 어떻게 끝맺는가"의 고정 규칙.

**5-1. 명확한 조문 = 반드시 안내한다**
- 조문이 명확히 적혀 있고 의미를 명확히 해석할 수 있으면, **그 조문까지는 반드시** 안내한다. (얼버무리거나 "실무 문의"로 회피하지 않는다.)
- 기준법이 시행령·시행규칙·별표·고시·타법으로 **타고 들어간 그 지점의 조문**도, 명확하면 반드시 안내한다.

**5-2. 판례·법리·다툼의 여지 = 답하지 않는다 (스코프 밖)**
- 해석이 갈리거나(학설·판례), 이해관계가 얽혀 결론이 불명확한 논점은 **챗봇이 답할 영역이 아니다.** 실무자·유권해석이 관리할 부분.
- 이런 경우: **명확한 조문까지만 안내하고 거기서 끊는다.** 그 다음은 "이 부분은 개별 사안·해석에 따라 달라져 여기서 단정하지 않는다. 관할 소관부서에 확인하시는 것이 정확하다"로 마무리(5-4 연결).
- **즉 DoD의 답변율(full)은 "이 스코프 안"에서 측정한다.** 판례·법리·다툼·순수 원문공백은 "규정 없음/확인불가" 정직 표기가 이미 정답이며, full 미달로 세지 않는다.

**5-2-A. ★"답하지 않는다"로 끝난 논점은 대기열에 남기지 말고 그 문장을 고쳐 둔다 (사용자 확정 2026-09-19)**
> 사용자 원문: *"이 부분은 소관부처 해석 판례가 있어야 하는 부분이기 때문에 내 지시사항에 따르면
> 그 답변은 소관부처 문의 또는 법리해석이 필요한 부분은 답변하지 않으니 닫혀야 하는게 맞지 않니?"*

맞다. 5-2 에 해당하는 논점은 **이미 답이 정해진 것**이다 — "여기서 단정하지 않고 소관부서로 넘긴다"가
그 논점의 정답이다. 그러니 사람 승인을 기다리는 대기 항목으로 남겨 둘 이유가 없다.

⚠**그런데 카드만 닫으면 챗봇은 하나도 바뀌지 않는다 (2026-09-19 코드로 확인).**
`legal_retriever.js` 의 `markUnresolvedReview()` 는 **위키 문장 안에 `REVIEW` 라는 글자가 있는지**로
[미확인] 여부를 정한다 — `review_queue.md` 의 승인란은 보지 않는다. 그래서 절차는 두 가지를 **함께** 한다:

1. **위키 문장을 다시 쓴다** — `⚠REVIEW-…: …확인 필요` 를 5-2·5-4 마무리 문구로 바꾸고 `REVIEW` 글자를 없앤다.
   예: *"…까지는 「○○법」 제N조에 따른다. 그 다음은 개별 사안ㆍ해석에 따라 달라져 여기서 단정하지 않는다.
   정확한 판단은 **○○부 ○○과(☎ 000-000-0000)** 로 확인하시기 바란다."*
   (연락처는 그 쪽 상단 메타의 `소관부서`ㆍ`연락처` 를 쓴다 — 5-4.)
2. **그 카드를 닫는다** — `- 승인: [ ] 해당 없음 — 5-2 스코프 밖(판례ㆍ법리ㆍ소관부서 실무확인)` 로 적는다.

이렇게 하면 그 쪽의 미해결 줄이 줄어 `_SCHEMA.md` §5-D ⓐ 를 통과하게 되고, 자연히 canonical 로 올라간다.

⚠**먼저 5-1 을 적용한다** — 조문이 명확한 부분은 **반드시 안내해야 한다.** 그러니 한 장씩 열어
*"조문으로 답이 하나로 정해지나, 아니면 진짜로 두 가지 읽기가 경합하나"* 를 가른 뒤에 적용한다.
낱말로 일괄 분류해서는 안 된다 — `human_workload.py` 의 분야별 집계는 카드 글에 그 낱말이 있는지로
나눈 것이라 **실제와 다르다**(2026-09-19 표본 확인: '수집대기'로 분류된 3장이 전부 법리 문제였다).

**5-2-B. 승급(캐노니컬) 판정 절차는 `_SCHEMA.md` §5-D 를 따른다 (2026-09-19 신설)**
원문과 같으면 자동으로 올리되, **처벌ㆍ과태료ㆍ형량ㆍ금액ㆍ기간ㆍ수량ㆍ규격 등 숫자로 된 법적 효과**가
있으면 **서로 다른 두 번의 재점검**(①기계 EXACT 대조 ②다른 에이전트의 귀속ㆍ단위 확인)을 거친 뒤에 올린다.
자세한 절차ㆍ대상 낱말ㆍ기록 의무는 `_SCHEMA.md` §5-D.

**5-3. 수집 불가 영역(지자체 고시·부처 내부지침·미제정 위임고시·타 정부시스템 소관) = 정직하게 안내로 대체한다**
- 행정규칙·고시(국가법령정보센터 게재분)는 수집돼 있으니 그대로 인용.

**5-4. 답변의 마무리 = 소관부서 연락처(전화번호)**

> ⚠**정정 (2026-09-25 · 등록부 `D-4`) — 이 규칙이 **어디에서** 지켜지는지가 바뀌었다.** 지우지 않고 붙인다.
> `§6-13③`(2026-08-18 오후)이 *"답변 끝 연락처 요약 제거"* 를 확정했다 — 본문의 조문 표기를 누르면
> 그 팝업이 같은 시행일자·전화번호를 보여주므로 **같은 내용이 두 곳에 있었다**는 까닭이었다.
> 그런데 이 절은 그대로 *"답변의 마무리 = 연락처"* 라고 읽혀서, 두 절이 **서로 어긋난 채** 남아 있었다.
>
> 실측(2026-09-25, `services/legal_retriever.js`): 프롬프트가 이렇게 적고 있다 —
> *"소관부서·연락처·근거자료의 기준일을 답변 마지막에 각주로 따로 붙이지는 않는다(**화면이 답변 끝에 따로 붙인다**)"*.
> ⇒ **연락처는 여전히 사용자에게 간다. 다만 모델이 본문 끝에 적는 것이 아니라 화면이 붙인다.**
> 이 절의 규칙은 **수집불가·판단보류 안내를 연락처로 마무리한다**는 뜻으로만 살아 있다(§5-2·§6-E 연결).
- 명확한 답을 준 뒤, 그 법률·행정규칙에 적힌 **소관부서와 연락처(전화번호)를 안내**하는 것이 답변의 완성이다.
- 형식 예: "…입니다(출처: ○○법 제N조). 자세한 사항은 **○○부 ○○과(☎ 000-000-0000)** 로 문의하세요."
- 수집 불가(5-3)·스코프 밖(5-2)으로 끊을 때도 이 소관부서 연락처로 마무리한다.

> `§6-13③` 이 답변 끝 요약을 없앴고, 기준일은 **화면이 붙인다**(위 §5-4 정정과 같은 까닭).
> ⇒ **stale 을 투명하게 보여준다는 뜻은 그대로 유효하다.** 바뀐 것은 **적는 자리**다 —
> 모델 본문이 아니라 화면·팝업이다. 모델에게 이 줄을 요구하는 검사를 새로 만들지 않는다.
- 모든 법률 답변 끝에 근거 법령의 **기준일**을 붙인다: 예) "(「선박안전법」 2026-07-18 기준)". 위키 개념 상단 메타의 `updated`(또는 원문 `_meta.json`의 시행일)를 그대로 노출.
- 취지: 위키가 개정에 뒤처졌을 가능성을 **숨기지 않고** 사용자에게 드러내, "언제 기준 정보인지"를 스스로 판단하게 한다. (재수집 스케줄러가 갱신하면 이 날짜도 자동 최신화 — MASTER_PLAN Phase G.)

**5-9. 별표 이미지 표시 = 도해·그림은 이미지로, 수치·설명은 텍스트로 (사용자 확정 2026-07-18)**
> ⚠**2026-09-25 실측(D-10) — 아래는 「확정된 설계」이고 아직 화면이 그렇지 않다.**
> 지금 챗봇은 답변 **본문에 그림을 넣지 않는다** — `ai_chat.js` 에 답변 본문용 `<img>` 조립이 **0곳**이고,
> 그림은 `b.img` 가 있을 때 **「🖼 이미지」 단추**(`class="nrya-img"`)로 새 창에서 연다. 즉 **눌러야 본다.**
> 이 문서 아래 300행이 스스로 「채팅 인라인 이미지 렌더는 **Phase F**」라 적어 두었으니, 위 문장들은 **예정**으로 읽어야 한다.
> (표·수치를 텍스트로 답하는 대목은 이미 지켜지고 있다 — 그쪽은 OCR 텍스트를 쓴다.)
- 질문에 해당하는 별표에 **도해·그림(엔진 구조도, 조업방식 도해, 표지 도안 등 텍스트로 표현 불가한 시각정보)**이 있으면, 텍스트 설명과 **함께 그 이미지를 채팅창에 표시**한다.
  - 예) "엔진 어떻게 생겼어?" → 해당 법 별표의 엔진 도해 이미지를 띄운다.
  - 예) "○○ 조업방식은?" → 조업방식 **설명 텍스트**(별표 원문/OCR)와 **도해 이미지**를 함께 제공. (텍스트는 텍스트대로, 이미지는 이미지대로.)
- **이미지 속 수치·표는 OCR로 이미 텍스트화**돼 있으니(`_SCHEMA.md` 0-A 별표 이미지 규칙) 그 수치는 **텍스트로 정확히 답**하고, 도해는 **이미지로 보여준다**. 수치를 이미지로 떠넘기지 않는다.
- 근거 데이터: 위키/annex 메타 `이미지파일`(우리가 보존한 별표 도해 원본). **법령 별표의 공식 도해는 원본을 표시**하고, 일반 장비·어구의 시각확인은 기존대로 외부 이미지 검색 링크(4절 계열)로 처리한다 — 둘을 구분.
- 엔진/앱 구현은 Phase E(답변에 이미지 메타 첨부)·Phase F(채팅 인라인 이미지 렌더)에서. 지금 단계에서는 **별표 도해 이미지 원본을 유실하지 않게 보존**하는 것이 핵심.

## 6. 되묻기·근거 표출 규칙 (사용자 확정 2026-08-17 — 실제 앱 화면 지적 기반, 설계 배경은 `MASTER_PLAN.md` H-40)

1절·1-B절의 되묻기 설계와 0-A의 "근거 = 전체 사슬" 원칙을 **화면에서 실제로 어떻게 보여줄지**까지 확정한 것. 사용자가 프로덕션에서 "배에서 술마시면 어떻게돼?"를 4라운드 되묻기로 통과한 실세션 스크린샷을 근거로 지적했다.

**6-1. 되묻기 화면**
- **누른 선택지에 선택 표시를 남기고, 안 누른 선택지도 함께 남긴다.** 되묻기 카드가 대화에 계속 남아 있는 것 자체가 "최종 답변에 이른 과정"의 표현이다(사용자 원문: *"그 말풍선이 계속 남아 있음으로써 최종 답변까지 이르는 과정을 표현하고자 한 거였거든"*).
- **사용자 말풍선은 그리지 않는다** — 버튼으로 보낸 것은 카드의 선택 표시가 대신한다. ⚠**서버로 보내는 질의 문자열은 종전대로 `원래질문 — 라벨1 — 라벨2` 누적을 유지**한다(1-B절의 라운드 계산·중복 차단이 그 문자열에 의존한다). 화면 표시와 전송값을 분리하는 것이지 전송값을 줄이는 것이 아니다. 지난 질문 목록·피드백 전송에는 누적 전체를 그대로 싣는다(관리자가 어떤 조건의 답변이었는지 재현해야 하므로).
- **선택지는 세로 1열**로 쌓는다(가로 흐름 배치 금지). 되묻기 카드에만 적용한다.
- **되묻기 응답에는 "참고용입니다. 최종 확인은 공식 출처를 확인하세요."를 붙이지 않는다** — 아직 답이 아니라 조건을 좁히는 중이므로 면책 대상이 없다. 안내 문구(`추가 정보가 필요해요`)만 남긴다. 최종 답변에는 종전대로 붙인다.
- **되묻기 라운드 상한은 5**(2026-08-21 사용자 확정, 종전 10 → 그전 4).
  ★왜 다시 내렸나: 10 으로 올린 근거가 *"같은 조건 재질문 차단이 실질 방어선"* 이었는데, **그 방어선이
  뚫려 있다는 것이 라이브 표본에서 확인됐다**(20법, 2026-08-21). CCTV 질문에서 2회차와 4회차가 같은
  축("어떤 법률에 따라 설치된 CCTV인가")이었는데 차단 4겹이 하나도 안 걸렸다 — 전부 **직전 한 라운드만**
  보는 데다, 모델이 라벨을 `국제항해선박 및 항만시설의 보안에 관한 법률…` → `국제항해선박법` 으로 줄여 써
  완전일치가 깨졌다(그 약칭은 공식 약칭표 720건에 없다). 같은 표본에서 답변까지 평균 2.5회,
  되묻기 없이 답한 법은 20 중 3법뿐이었다. 방어선이 제대로 설 때까지 천장을 낮춰 사용자를 덜 가둔다.
  ⚠5 아래로는 내리지 않는다 — D-트리(H-36) 가장 깊은 경로 + 확인이 4라운드다.
- (종전 기록) **되묻기 라운드 상한 10**(그전 4). 사용자 확정: *"되묻기를 4회 이상 해도돼. 동일한 내용만 물어보지 않는다면"*. 상한을 늘린 만큼 **같은 조건 재질문 차단이 유일한 실질 방어선**이 되므로, 라벨 완전일치 차단에 더해 **질문 문장이 사실상 같은 경우**(표현만 바꾼 재질문)도 결정론적·보수적으로 차단한다.
- 이미 고른 선택지 묶음은 그대로 잠근다(다시 고르려면 새 질문).
- 채택하지 않은 것: "이대로 답변 받기" 버튼(라운드가 길어질 때 중간 이탈용) — 사용자 판단으로 보류.

**6-2. "잘 모르겠어요" 선택지 (신설)**
- 되묻기 선택지에 **항상 하나 더** 붙인다(전문용어가 나온 되묻기에만 붙이는 것이 아니다 — 전문용어 여부를 모델 판단에 맡기면 들쭉날쭉해진다). 2·3라운드에도 계속 붙인다.
- 사용자가 누르면 **①그 되묻기가 쓴 용어의 뜻을 2~3줄로 쉽게 ②각 갈래를 한 줄씩 요약 ③같은 선택지를 다시 제시**한다. 뜻·요약은 근거자료에 있는 내용으로만 만든다(없으면 "확인되지 않는다" — 환각 0).
- 갈래별 요약은 **한 줄씩**이다. 여기서 전부 답해버리면 2절 점진 공개 원칙이 무너진다.
- 실패(키 없음·타임아웃·파싱 실패)하면 조용히 **원래 되묻기를 그대로** 다시 낸다(1-B절 폴백 규약과 동일).

**6-3. 근거 목록 = 답변이 밟은 흐름 전체 + 주체별 묶음**
- 0-A의 "근거 = 전체 사슬"을 화면에서 끝까지 지킨다. 사용자가 제시한 완결 형태(예: 어선 음주):
  - 어선원: 법 제33조(준수의무) → 시행규칙 제20조(준수할 조치사항) → 시행규칙 제18·19조(안전·보건조치 내용) → 고시「어선원 안전ㆍ보건 및 재해예방 기준」제31조(음주·마약 금지, 0.03%) → 시행령 별표5 / 법 제58조제5항제7호(과태료)
  - 어선소유자: 법 제31조(안전조치) → 시행규칙 제18조 → 고시 제31조 → 법 제53조제1호(5년↓·5천만원↓)
- **답변이 주체별로 나뉘어 있으면 근거도 그 묶음으로 나눈다.** 판정은 답변 문장에 실제로 적힌 소제목으로만 하고, 불분명하면 나누지 않는다(틀리게 나누느니 한 줄기로 둔다).
- 위키 표가 여러 조를 묶어 적은 행(`제52~55·57조`)은 **답변이 인용한 조만 별도 줄로 쪼개** 보여준다. 원문에 없는 조를 만들지 않는다(쪼갠 결과 안에 있고 답변 문장에도 있는 조만).
- ⚠ 근거가 통째로 사라지는 실패는 대부분 **표기 파싱 한계**에서 온다 — 자세한 사례는 `_LESSONS.md` L-101.

**6-4. 조문 팝업은 인용된 조·항·호만**
- 답변이 `제58조제5항제7호`처럼 특정했으면 팝업은 **그 항의 머리문장 + 그 호만** 보여준다. 나머지 항·호는 **"조문 전체 보기"** 버튼으로 펼친다(사용자 원문: *"실질적으로 어떤 규정 몇 항 몇 호까지 정확하게 특정된 상황에서 굳이 필요 없는 부분까지 표현할 필요는 없잖아"*).
- **부칙(개정 이력)은 조문 본문에서 분리**해 기본 접힘으로 둔다(지금은 마지막 항에 섞여 통째로 노출됨).
- 항·호를 특정하지 못한 인용(범위·나열·전체)은 종전대로 강조 없이 나열한다 — 억지로 한 곳을 칠하지 않는다.
- **근거 카드의 미리보기 발췌도 같은 항·호**를 보여준다(지금은 hit가 없으면 첫 항을 써서 답변과 무관한 문장이 뜬다).

**6-5. 답변 본문의 조문 인용은 눌러서 원문을 연다**
- 본문에 `「법령명」 제58조제5항제7호`처럼 **법령명이 명시된** 인용이 있으면 그 글자 자체를 눌러 조문 팝업을 연다. 별표 인용(`시행령 별표5`)도 같다.
- 어느 법인지 확정하는 순서: ①근거 목록의 정식 법령명과 문자 그대로 일치 ②약칭표(6-7)로 변환해 일치 ③**후보가 둘 이상이거나 못 찾으면 링크하지 않는다**(엉뚱한 법의 원문을 여는 것이 훨씬 나쁘다).

**6-6. 소관부서·연락처 표기**
5-4의 "답변의 마무리 = 소관부서 연락처"를 화면에서 잘리지 않게 한다 — **부처명 / (부서명) / 전화번호**를 줄로 나누고, 전화번호는 지역번호 뒤에서 한 번 더 줄바꿈한다. ⚠**표시만 나누고, 눌러서 거는 번호는 통번호를 유지**한다.

**6-7. 법령 약칭 (신설)**
- 답변은 「어선안전조업법」처럼 약칭을 쓰는데 위키·근거 목록은 정식 명칭이라 글자가 달라 링크·검색이 어긋난다. 이를 잇는 **약칭표**를 둔다: `_dashboard/law_aliases.json`(수집기 `_dashboard/loop/collect_law_aliases.py`).
- **약칭은 API가 준 값만 쓴다.** 원천은 `lawSearch.do`의 `법령약칭명` 하나뿐이다(상세 API의 `법령명약칭`은 빈 값 — `_LESSONS.md` L-102).
- **모호하면 쓰지 않는다** — 같은 약칭이 두 법에 걸리거나, 약칭이 다른 법의 정식명과 겹치면(「어선안전조업법」은 현 약칭이자 개명 전 정식명) 매칭 대상에서 제외한다.
- **위키 페이지에는 약칭을 적지 않는다**(사용자 확정) — 법 하나에 페이지가 여럿이라 복제하면 변경 시 전수 수정이 필요하고 누락이 곧 불일치가 된다. 표 1개를 정식 법령명으로 조인한다.
- **검색에도 적용**한다(사용자가 약칭으로 물어도 정식명 페이지가 잡히게).
- 표는 **매일 도는 개정 감지 스캔이 자동 최신화**한다(약칭 신설·변경·개명). 자동 반영하되 변경 이력을 남긴다.
- 답변 프롬프트는 **법령명을 정식 명칭 그대로** 쓰게 한다(링크가 법을 특정할 수 있게).

**6-8. 답변 뒤 "이어서 질문할까요?" 3버튼 (`MASTER_PLAN.md` H-36 후속 ①, 2026-08-18 구현)**
- 최종 답변(되묻기 아님) 아래에 항상 3버튼: 🔁 관련해서 더 궁금해요 / 🆕 다른 종류의 질문이에요 / ✅ 궁금증 해소됐어요.
- **서버 왕복 없음** — 전부 클라이언트 상태 전환. "🔁"은 그 답변의 `ctxNext`를 다음에 사용자가 직접 치는 문장 **한 번**에만 예약해 싣는다(§4.3 "아니요, 다시 설명할게요"와 같은 예약 방식). "🆕"은 맥락을 명시적으로 비운다. "✅"는 버튼을 감사 인사로 바꿀 뿐 상태 변화 없음.

- H-36 후속 원 설계의 ②(선박종류·톤수 등 "이미 확인한 사실"을 기기에 영구 저장해 두었다가 재확인하는 것)는 **이번엔 범위 밖**(사용자 확정 2026-08-18) — 3버튼만 구현했다.

**6-10. 근거 목록의 무관한 줄 제거 — 근접성 검사 (2026-08-18, 사용자 확정)**
- **문제**: `filterCitationChainByAnswer`가 ⓐ법 이름이 답변 어딘가에 있나 ⓑ조문번호가 답변 어딘가에 있나 를 **따로** 볼 뿐, 둘이 같은 자리에 붙어 있는지는 안 봤다. 그래서 답변의 「선박직원법」 제2조제1호 때문에 "제2조"가 존재하면 비교 페이지에서 온 「낚시 관리 및 육성법」 제2조 행까지 통과했다(실사용 재현).

  ② 이 줄의 **모법을 못 정하면** 판정 안 함.
  ③ 이 줄의 법이 답변에서 **한 번도 「」로 인용된 적 없으면** 판정 안 함 — 평문·약칭으로만 언급된 법은 단정할 근거가 약하다.

**6-11. 본문 조문 링크 — 하이브리드 (2026-08-18, 사용자 확정)**
- 화면은 지금까지 **근거 목록에 있는 법만** 링크했다. 그래서 답변에 「법령명」 제N조라고 완전한 주소가 적혀 있어도 그 법이 근거 목록에 없으면 링크를 포기했다(사용자 지적: *"정확한 주소가 있는데 왜 못 찾나"*).
- **순서**: ①근거 목록(`citationChain`)의 `tier`·`baseLaw` — 위키 사서가 검증한 값이라 **이쪽이 이긴다** ②없을 때만 답변 본문 주소에서 뽑은 `citeLaws`로 폴백.
- 서버가 `done` 응답에 `citeLaws`(법령명·tier·baseLaw만, 조문 번호는 안 담음)를 실어 보낸다. 재료는 `extractAnswerCitations` → `resolveAnswerLaw`라 **답변 글자 그대로 + 우리가 raw를 가진 법인지 확인**을 거친다(환각 0 유지).
- **추가 비용 없음**: 이 추출은 B11 폴백이 이미 매 답변마다 부르고 있고, 실측 0.04ms다. 화면 쪽 추가 네트워크 호출도 없다.
- 푸시 복원·기록 복원에도 함께 실어 되살린다(`forms`·`citationChain`과 같은 이유).

**6-9. 실사용 지적 5건 확인·수정 (2026-08-18, 배포 후 사용자가 직접 재질문해 재현)**

- **채팅창이 화면 밖으로 튀어나감(앱을 막 켰을 때만, 재오픈하면 정상)**: 확실한 원인은 못 짚었다(재현이 실기기·타이밍 의존적) — `window.visualViewport`가 브라우저 UI가 자리잡기 전 값을 줄 수 있다는 게 유력 후보. 입력창 포커스 때 이미 쓰는 지연 재계산(`setTimeout(fitChat, …)`)을 채팅창 오픈 직후에도 한 번 더 걸었다 — 확신도는 낮은 방어적 조치.
- **"이어서 질문" 클릭 후 맥락이 안 이어짐**(엉뚱한 법 여러 개 나열): decideClarify의 "직전 질문과 이어질 수도 있어요" 확인 후보(§18 최소 절충안, 2026-08-15 기존 기능)가 무관한 선택지들 사이 **맨 끝에 묻혀** 사용자가 못 보고 지나쳤음을 실사용으로 확인. 판단 로직(어차피 애매해서 되물을 때만 후보를 얹는 것)은 그대로 두고, **화면에서만** 이 후보를 맨 앞으로 올리고 🔁 아이콘 + 강조 테두리로 눈에 띄게 그린다(`clarifyHTML`). 근본적인 주제어 자동 연결(D→F→A, `MASTER_PLAN.md` H-37 §18)은 여전히 별도 설계 과제로 남아 있다 — 이번 조치는 **이미 있는 확인 절차를 사용자가 놓치지 않게** 한 것.

**6-12. 조문 본문 안 원문 이미지 — 글자와 그림을 같이 보여준다 (2026-08-18, 사용자 확정)**

**6-13. 조문·별표 팝업 실사용 지적 4건 (2026-08-18 오후, 사용자 스크린샷)**
- **① 별지를 닫으면 한 번 더 닫아야 했다**: 조 없이 별표만 가리킨 인용(`mode:'annex'`)은 열 수 있는 별표가 하나뿐이면 그 별표를 **자동으로 열어 준다**. 그런데 그 별표를 닫으면 뒤에 남는 것이 그 별표 한 줄짜리 목록 팝업이라, 다 봤는데도 같은 것을 한 번 더 닫아야 했다(사용자 원문: *"별지를 연 후 닫았을때 … 바로 닫히는게 아니라"*). → **자동으로 연 경우만**(`bylAutoOpened`) 별표를 닫을 때 목록 팝업도 함께 닫는다. 조 본문에서 사용자가 **직접 누른** 별표는 예전처럼 조문 팝업으로 돌아간다(거기엔 볼 것이 더 있다).

- **③ 답변 끝 연락처 요약 제거**: §6-11 이후 답변 맨 끝에 법별 시행일자·소관부서 연락처를 요약해 붙였는데, 본문의 조문 표기를 누르면 그 팝업이 **같은 시행일자·전화번호**를 보여준다 — 같은 내용이 두 곳에 있었다(사용자 원문: *"아래에 소관부서 번호가 나오지 않도록 해줘 어차피 조문 누르면 나오니까"*). → 답변 끝 요약(`sourceMetaHTML`)을 없애고 **팝업 한 곳**으로 모은다. `contactLineHTML` 은 그 팝업이 계속 쓴다.

- **① ★계층을 무시해 엉뚱한 원문이 열렸다(가장 심각)**: 답변의 "「낚시 관리 및 육성법」 … 같은 법 시행령 제16조제1항"을 누르면 **법률** 제16조(낚시터업의 등록)가 열렸다. 화면의 인용 인식기가 「」 안의 법령명만 읽고 **"시행령"이라는 말을 아예 안 읽었기** 때문이다. 링크가 안 걸리는 것(누락)보다 나쁜, **엉뚱한 원문을 여는** 오류다.

- **② 법령명 표기 통일(사용자 제안)**: 답변 원칙 7번에 *"같은 법"·"동법"·"같은 조"·"이 법" 같은 가리키는 말 금지 — 조문번호를 쓸 때마다 「정식 법령명」을 다시 붙인다*를 넣었다. 시행령·시행규칙도 **낫표 안에** 계층까지 넣어 통째로 쓴다. 문장이 길어지는 대가를 치르더라도, 가리키는 말로 쓰면 그 근거는 사용자가 열어볼 수 없다.

- **④ 이어 질문 맥락 유실 — 진짜 원인은 따로 있었다**: 푸시·기록으로 **복원된 답변에는 `ctxNext` 가 없었다**(서버 보관함도 기기 기록도 안 담았다). 사용자는 푸시로 들어와 답을 보고 🔁 을 눌렀으므로 **주제가 애초에 전송되지 않았다.** 게다가 화면은 "방금 답변 맥락을 이어갈게요"라고 **안내까지 하고 있었다**(거짓 안내).
  → 기기 기록에는 `ctxNext` 전체를, **서버 보관함에는 주제 한 낱말만** 담는다. ⚠서버에 맥락 전체를 담으면 **R1**(서버는 ctx·profile 을 어떤 파일에도 쓰지 않는다)을 깬다 — `prof.decided` 는 프로필 필드명이고 `scope` 는 사용자가 고른 조건이다. 주제만으로 "이어서 질문"은 되살아나고 나머지 축은 기기 안 기록이 든다.

**② 대화 기억 — 이어 물을 때 직전 대화를 통째로 보여준다**
- **왜**: 주제 낱말 하나(`ctx.topic`)만 넘기니 후보는 좋아졌지만(낚시어선업이 선택지에 들어옴) **되묻기를 막지는 못했다** — 방금 낚시어선업 얘기를 해놓고 "어떤 종류의 영업이신가요?"를 또 물었다.

- **대화 단위**: 마지막 답변에서 **6시간**이 지나면 그 대화는 끝난 것으로 보고 이어지지 않는다(사용자 확정). 새 질문을 직접 타이핑하거나 "🆕 다른 종류의 질문이에요"를 누르면 그 자리에서 버린다. ⚠기억을 버리는 판단은 **ctx 를 정한 뒤**에 해야 한다 — 🔁 을 누르고 손으로 친 질문은 `sendCtx` 가 없고 `pendingCtx` 로 들어오므로, 그 전에 버리면 이어 묻기가 통째로 죽는다.
- **압축(비용 상한)**: 누적이 8,000자를 넘으면 **최근 2턴은 통째로**, 그보다 오래된 턴은 **질문 + 답변 첫 문단**만 남긴다. 답변은 원칙 6번이 강제하는 *"쉽게 말하면 ~"* 결론 요약으로 시작하므로 **그 첫 문단이 곧 요약이다** — AI를 다시 불러 요약할 필요가 없다(**비용 0**, 요약하다 뜻이 뒤틀릴 위험 0). 턴 수도 12개로 막는다(줄이기는 글자만 줄이지 턴을 버리지 않으므로).
- **되묻기 강도(사용자 확정)**: **아예 막지 않는다.** *"이미 정해진 것은 다시 묻지 마라. 아직 안 정해졌고 답이 실제로 갈리는 조건은 그대로 물어도 된다."* 아예 막으면 바다/내수면처럼 진짜 갈리는 지점을 한쪽으로 **단정**해 틀린 답이 나간다 — 되묻는 불편보다 그쪽이 훨씬 나쁘다.
- **⚠지난 대화를 근거로 재사용하지 않는다**: 대화 블록에 *"답의 근거는 여전히 [근거자료]뿐이고, 위 대화에 적힌 조문·숫자를 근거로 다시 쓰지 마라"*를 명시했다 — 그때 맞던 조문이 지금 질문에도 맞는지는 이번 근거자료로 다시 확인해야 한다(환각 0).

**6-16. 답변 끝 "근거:" 각주 줄 · 위키 내부 이름 노출 (2026-08-18 밤, 사용자 지적)**
- **① "근거:" 각주 줄이 따로 붙었다**: 문단 끝마다 `* 근거: 「수산업법」 제40조제1항, 「수산업법」 제44조 …`처럼 조문을 다시 모아 적었다. **바로 위 문장에서 이미 밝힌 것**을 한 번 더 늘어놓는 것뿐이라, 사용자에게는 같은 링크가 두 번 나오는 것으로 보인다(사용자 원문: *"본문에 왜 근거라고? 아래쪽에 또 붙는 거야?"*). 화면이 붙이는 게 아니라 **AI가 쓴 글자**다.
  → 규칙 11에 못 박았다: **각주 줄을 따로 만들지 마라.** 조문은 **그것을 설명하는 문장 안**이나 **묶음 제목 옆**, 둘 중 **한 자리에만** 적는다.
- **② ★위키 내부 이름이 답변에 새어 나왔다(별개 결함)**: `[수산업법 — 허가어업]의 "★ 정의부터" 표 및 "근해어업 조업구역·허가정수"` — 이건 **우리가 자료를 정리하려고 붙인 문서명·소제목**이지 법령에 있는 말이 아니다. 사용자에게는 뜻이 통하지 않고, 조문 표기가 아니라 **링크도 안 걸린다**(눌러볼 수 없는 글자).
  → **규칙 12 신설**: [근거자료]의 문서 이름·표 제목·절 제목을 답변에 쓰지 마라. 출처는 **법령명 + 조문번호(필요하면 별표·별지 번호)로만**.
  → **규칙만 믿지 않는다 — 베끼기 쉬운 글자 자체를 바꿨다.** 프롬프트의 근거 블록 머리를 `--- 근거1: [수산업법 — 허가어업] (…) ---` 에서 `--- 근거1: 「수산업법」 (이 자료가 다루는 것: 허가어업 · …) ---` 로 바꿨다. 모델이 머리를 그대로 베끼더라도 이제 나오는 것은 **「수산업법」** — 답변에 그대로 써도 되고 링크도 걸리는 표기다. 되묻기 프롬프트(`decideClarify`)도 같은 이유로 같은 모양으로 맞췄다.
  - ⚠이 방식이 프롬프트 규칙보다 튼튼하다: 규칙은 모델이 어길 수 있지만, **없는 글자는 베낄 수 없다**(L-108 의 교훈 — "규칙을 걸었나"와 "결과가 맞나"는 다른 문제다).

**6-17. ★맥락 유실의 진짜 원인(전송 버튼) · 별표 표 그리기 개선 (2026-08-18 밤)**

**① ★★전송 버튼이 맥락을 통째로 버리고 있었다 — 여러 번 고쳤는데도 안 되던 진짜 이유**
- 사용자가 세 번째로 *"아직도 맥락을 못 찾는 것 같다"* 고 지적해 배포 이력부터 확인했다(모두 성공 — 코드 문제였다).
- 원인: `send.addEventListener('click', doSend)` — 리스너로 **함수를 그대로** 넘겨서, 브라우저가 **클릭 이벤트 객체를 첫 인자로** 준다. `doSend(sendCtx, …)` 가 그것을 "확인 버튼이 들고 온 맥락"으로 받고, `var ctx = sendCtx || pendingCtx` 에서 **이벤트가 이겨 `pendingCtx` 가 통째로 버려졌다.**
- 그래서 **"🔁 관련해서 더 궁금해요"로 예약한 맥락도, "아니요, 다시 설명할게요"로 예약한 맥락도 전송 버튼으로 보내면 전부 사라졌다.** 엔터로 보낼 때만 살아 있었다(그 경로는 `doSend()` 로 인자 없이 부른다) — **휴대폰에서는 버튼을 누르므로 사실상 항상 유실.**
- 이 하나가 그동안의 맥락 작업(§6-15 대화 기억, ctx.topic, 검색 가중치)을 **전부 무력화**하고 있었다. 기능은 다 제대로 들어가 있었는데 **문 앞에서 버려지고 있었다.**
- 교훈: **인자를 받는 함수를 이벤트 리스너로 그대로 넘기지 말 것.** 반드시 감싸서 부른다(`function () { doSend(); }`). 회귀 잠금 2개(이 자리 + 다른 리스너 전수 점검)를 걸었다.

**② 별표 표 — 병합 셀이 있는 표도 표로 그린다**
- **문제**: 같은 별표 안에서도 어떤 덩어리는 표로, 어떤 덩어리는 아스키로 나왔다(사용자 지적).
- **원인 두 가지, 둘 다 "포기가 너무 빨랐다"**: ⓐ줄마다 칸 수가 다르면 **표 전체를 포기**했다 ⓑ여러 열에 걸친 칸을 **맨 끝 칸만** 허용해, 앞쪽 칸이 병합된 표는 첫 칸부터 어긋났다.
- **고침**: ⓐ포기하지 않고 **행을 끊어 이어간다** ⓑ칸의 **양쪽 테두리 위치를 기준행의 열 경계와 맞춰** 몇 열을 덮는지 센다(자리를 추측하는 게 아니라 **원문에 그어진 선을 읽는다**). 못 맞추면 **예전 판정을 그대로 한 번 더** 보고, 그것도 안 되면 아스키로 떨어진다.
- **실측(별표 원문 전수, 구분자 줄 3개 이상인 덩어리 9,227개)**: 표로 그려지는 것 **1,081 → 1,512(+431)**. **못 그리게 된 것 0건 · 이미 그려지던 표의 글자 배치가 달라진 것 0건.**
- ⚠**아직 아스키로 남는 표가 있다** — 사용자가 보낸 수산업법 시행령 별표7 **근해어업**(213줄)이 그렇다. 한 줄 안에 글자와 중첩 표의 구분선이 섞여 있어(`… │목망으로 된   ├────┼────┤`) 줄 단위로는 안전하게 읽을 수 없다. 무리해서 읽으면 **금지기간·금지구역이 엉뚱한 행에 붙는다** — 보기 불편함보다 그쪽이 훨씬 나쁘다(L-109 와 같은 판단). 그 표는 팝업의 **"원본 이미지 보기"**로 원래 모양을 볼 수 있다.

**③ 표 가로 보기(사용자 요청)**
- 칸이 많은 표를 좁은 화면에 `width:100%` 로 욱여넣어 글자가 한 자씩 끊겨 내려갔다. 이제 표는 내용만큼 넓어지고(`min-width:100%` 로 좁은 표는 여전히 꽉 찬다), 넘치면 **감싼 칸 안에서만** 가로로 밀린다(`.nrya-byl-scroll`). ⚠팝업 본문 자체는 가로로 안 밀린다 — 그러면 다른 글까지 잘려 보인다. 칸 최소 폭 88px.

**6-18. 아스키 표를 사용자에게 보이지 않는다 · 표에서 해당 칸만 뽑아 답한다 (2026-08-18, 사용자 확정)**

- **① 표를 못 읽으면 원본 이미지를 먼저 보여준다**: 별표를 열 때 **표로 못 읽는 표가 섞여 있으면**(`bylHasAsciiTable` — `renderBylText` 와 **같은 규칙**으로 덩어리를 나눠 `parseBylTable` 을 미리 돌려 본다) 아스키 대신 **원본 스캔 이미지를 먼저** 그린다. 실측: 별표·별지 2,724건 중 **2,679건(98.3%)**에 원본 이미지가 있다.
  - ⚠**글자를 버리지 않는다** — "글자로 보기"로 언제든 펼친다(검색·복사가 되는 쪽). 서식(별지)이 이미 쓰던 방식과 같다.
  - ⚠**표가 전부 제대로 읽히는 별표는 예전 그대로 글자 먼저** — 그쪽은 글자가 더 보기 좋다(좁은 화면에서 이미지는 작다).
  - 이미지도 없는 45건(1.7%)은 어쩔 수 없이 지금처럼 글자로 보여준다.
- **② 표에서 답이 나오면 해당 칸의 값을 그대로 말한다(답변 원칙 13 신설)**: *"「…」 별표 4를 참고하세요"* 로 넘기지 않는다 — 사용자가 궁금한 것은 표 전체가 아니라 **자기 경우에 해당하는 한 줄**이다. 예: "선망어선의 조업구역"을 물으면 그 표에서 그 어업 종류의 행을 찾아 **"전국 근해"라고 값을 그대로** 적는다.

  - 조건에 따라 값이 갈리면 **질문에 해당하는 갈래만** 답한다(규칙1과 같은 취지). 표에서 그 칸을 못 찾으면 **지어내지 말고** "그 표에서는 확인되지 않습니다"라고 하고, 정말 표 전체를 봐야 할 때만 그 별표를 가리킨다.

## 6-19. 근거 목록에 고시·지침·조례가 실리는 조건 (2026-08-18 라이브 검증 결과 반영)

화면의 "근거 법령" 목록은 개념 페이지의 `## 근거 조문` 표에서 만들어지고, **답변이 실제로 인용한 줄만** 남긴다(`filterCitationChainByAnswer`). 그 대조가 통과하려면 두 가지가 맞아야 한다.

1. **법령 칸의 이름이 답변 문장에 있어야 한다.** 칸에 괄호 주석이 붙어 있어도 된다 — `서해 5도 해상운송비 지원 지침(고시)` 처럼 적혀 있으면 괄호를 뗀 이름으로도 대조한다. `고시(<이름>)` 처럼 갈래 낱말이 이름을 감싼 꼴은 괄호 **안**을 이름으로 본다.
   - ⚠단, 괄호를 떼고 나서 `행정규칙`·`고시`·`세칙` 처럼 **갈래 이름만** 남으면 그 후보는 쓰지 않는다. 그런 낱말은 아무 답변에나 걸려 무관한 줄을 끌고 온다.
   - ⚠법령 칸을 `행정규칙(고시)` 처럼 **갈래만 두 번 적지 마라.** 그 행은 이름이 없어 근거 목록에 실릴 방법이 없다. 정식 명칭을 적어라.
2. **조문 칸이 답변의 인용과 맞아야 한다.** `제5조`·`별표3`·`별지 제1호서식`·묶음(`제13·14조`)·범위(`제1~9조`) 모두 대조한다.
   - 조문 칸이 `전체`(그 고시 전부가 근거)인 행은, 답변이 **그 법 이름 바로 뒤에** 조문·별표를 붙여 인용했을 때만 그 조문을 가리키며 살아남는다. 이름만 스쳐 지나가면 통과하지 않는다.

**사서 작업 시 지침**: 위 조건을 만족하기 어려우면 조문 칸에 `전체` 대신 **실제 조문·별표 번호**를 적는 편이 안전하다. 그리고 본문에서 하위 법령의 내용을 옮길 때는 `(제14조②)` 처럼 조문번호만 적지 말고 **어느 법령의 제14조인지**를 함께 적어라 — 페이지 대표 법령이 모법이라, 번호만 있으면 답변이 그 조문을 모법 것으로 오인해 엉뚱한 출처를 붙인다(실측: 「내항해운에관한업무지침」 제14조②의 8개 비용항목이 「해운법 시행규칙」 제14조제2항으로 인용됐다 — 그 조문에는 제2항 자체가 없다).

## 6-20. 모델에 보내는 자료의 크기 — 순위별 예산 (2026-08-19)

**무엇을 바꿨나.** 검색이 골라온 후보 페이지 전부에 똑같이 10,000자를 주던 것을, **순위에 따라
다르게** 준다.

| 순위 | 본문 예산 |
|---|---|
| 1~3위 | 10,000자 (그대로) |
| 4~6위 | 5,000자 |
| 7위 이하 | 3,000자 |

**왜.** 한 질문에 후보가 12~15개씩 잡혀, 답변 단계에서 모델에 **평균 11만 자**(자료 블록 기준
9만 자)를 밀어넣고 있었다. 고정 문항 25개에 "그 답에 반드시 필요한 문장"을 붙여 어디에 있는지
재보니 —

- **24건이 1~3위 페이지 안**에 있었다(21건은 1위).
- **4위 이하 페이지가 그 문장을 담은 경우는 한 건도 없었다.** 그런데도 페이지당 8,500자씩 차지했다.
- 정답 문장의 위치는 25건 모두 자료 **앞쪽 16% 안**이었다 — 뒤에 묻혀서 못 본 것이 아니다.

**효과.** 자료 블록 평균 **90,398자 → 48,924자(46% 감소)**. 정확성 지표는 그대로다 —
`context_eval`(답에 필요한 문장이 자료에 실림) 24/25 유지·망가짐 0, `page_eval` 게이트 통과,
`search_eval` 법 단위 점수 변동 없음.

**지킨 원칙.**
- **뒤 순위를 버리지 않는다 — 예산만 줄인다.** `sliceRelevant` 가 질문과 가까운 절부터 담으므로
  예산이 줄면 덜 관련된 절부터 빠진다(뚝 끊기지 않는다). 배경설명용으로 뒤 페이지가 필요한
  질문도 있어 통째로 빼는 것은 위험하다.
- **잘린 페이지에도 "여기 없는 내용이 있을 수 있다"는 안내가 그대로 붙는다** — 모델이 발췌 밖을
  보고 "규정이 없다"고 단정하지 않게 하는 장치라 예산과 무관하게 유지된다.
- **근거 조문 표(citationChain)는 이 예산과 무관하다.** 근거 목록은 잘리지 않은 본문에서 뽑으므로
  예산을 줄여도 근거 줄이 사라지지 않는다.

**되묻기 단계는 손대지 않았다** — 상위 6개 × 1,500자로 이미 작다(최대 9,000자). 비용을 지배하는
것은 답변 단계다.

고정 검사: `scripts/test_ask_context.js` 4건(뒤 순위가 짧아졌나 / 그래도 비지 않았나 / 상위는
그대로인가).

## 6-21. 같은 질문에 같은 답 — AI 단계 온도를 전부 0으로 (2026-08-20)

**무엇을 바꿨나.** AI를 부르는 7개 단계 중 온도가 0이 아니던 5곳을 0으로 내렸다.

| 단계 | 하는 일 | 전 → 후 |
|---|---|---|
| 답변 생성(SYNTH) | 근거자료를 읽고 답변 문장을 만든다 | **0.3 → 0** |
| 이해 확인(UNDERSTAND) | "…라는 뜻이 맞나요?" 재진술을 만든다 | 0.1 → 0 |
| 원문 폴백 법 선택(RAW_PICK) | 위키에 없을 때 읽을 법을 고른다 | 0.1 → 0 |
| 모르는 말 해소(UNKNOWN) | 구어의 뜻을 판단한다 | 0.1 → 0 |
| 낱말 뜻 선택(NAVER_PICK) | 웹에서 찾은 뜻 중 하나를 고른다 | 0.1 → 0 |

(검색어 확장·되묻기 판단은 2026-08-19에 이미 0으로 내려 두었다.)

**왜.** 라이브 검증에서 **같은 질문이 회차마다 다른 판정을 받았다.** 5·6·7차 62문항 중
**26건(42%)** 이 한 번 이상 뒤집혔다. 채점자(AI 판정)의 흔들림을 규칙 채점(`regrade.js`)으로
걷어낸 뒤에도 **29%** 가 남았고, 그 남은 몫이 챗봇 자체의 변동이었다.

특히 답변 생성이 문제였다 — **인용 목록은 답변 문장을 대조해 만들어진다**
(`filterCitationChainByAnswer`). 답변 표현이 달라지면 근거 목록까지 함께 흔들린다.

**법령 답변은 같은 질문에 같은 답이 나오는 편이 옳다.** 사용자끼리 답을 맞춰 볼 수 있어야 하고,
"어제는 이렇게 답하더니 오늘은 다르다"는 신뢰를 무너뜨린다.

⚠`thinkingConfig` 는 건드리지 않았다 — 한 번에 두 가지를 바꾸면 무엇이 효과였는지 못 가린다.

**⚠배포 후 실측 — 온도 0으로도 완전히 같아지지는 않는다(2026-08-20).** 같은 질문을 두 번씩
물어 4문항을 대조했다.

| 문항 | 되묻기 경로 | 답변 문장 | 근거 목록 |
|---|---|---|---|
| 연안 정밀안전점검 수중조사 | **같음** | 유사도 38% | 같음(둘 다 빈칸) |
| 수난구호비용 첨부서류 | **다름** | 유사도 66% | 다름(3줄 vs 3줄) |
| 해남군 불꽃놀이 | **다름**(4턴 vs 3턴) | 유사도 39% | 다름(6줄 vs 9줄) |
| 중고 수상레저기구 등록 | **같음** | 유사도 77% | 같음(둘 다 빈칸) |

되묻기 판단은 이미 온도 0인데도 **선택지 내용 자체가 회차마다 달랐다**(수난구호비용: 1회차는
"구조된 선박등의 선장등 및 선원", 2회차는 "종사명령에 따라 수난구호에 종사한 자"). 즉 **Gemini는
온도 0에서도 같은 출력을 보장하지 않는다.**

그래서 **라이브 검증의 흔들림은 구조적으로 남는다.** 온도 0은 흔들림을 줄이는 필요조건이지
충분조건이 아니다. 측정 전략은 이 사실 위에 세워야 한다 —
- 라운드끼리의 대조는 **AI를 안 쓰는 도구**(`regrade`·`page_eval`·`context_eval`·
  `citation_table_scan`·`expansion_probe`)로 한다.
- 라이브로 무엇을 확인해야 할 때는 **전체 65문항을 한 번** 도는 대신 **소수 문항을 여러 번 물어
  다수결**로 본다. 한 번 재고 개선·회귀를 말하면 안 된다.

## 6-22. AI 단계가 조용히 빠진 것을 응답에 남긴다 (2026-08-20)

검색어 확장(`expandQueryTerms`)과 되묻기 판단(`decideClarify`)은 시간초과·키 쿨다운으로 실패해도
**빈 결과로 폴백**해 왔다. 그래서 화면에서도, 검증에서도 **"실패해서 빠진 것"과 "필요 없어서
안 한 것"이 구분되지 않았다.** 같은 질문이 어떤 날은 되묻고 어떤 날은 바로 답하던 원인 중 하나로
의심되는 지점이다.

이제 실패하면 `done` 응답에 `aiDiag: ['expand'|'clarify']` 가 실린다(실패가 없으면 필드 자체가
없어 종전과 문자 그대로 같은 응답이다). 요청마다 새 배열을 만들어 넘긴다 — 모듈 전역에 두면
동시 요청끼리 섞인다.

검증 도구(`ask_live.js`)는 이 값을 `AI단계실패` 로 함께 찍는다. **이 표시가 있는 회차의 결과는
개선·회귀의 근거로 쓰지 않는다.**

## 6-23. 답변이 고시 이름만 써도 그 페이지를 잃지 않는다 (2026-08-20)

**증상.** 답변은 정확한데 **근거 목록이 통째로 비어** 있었다. 라이브 7차에서 갯벌복원사업 지침·
농수산물 검정방법 고시·자연유산 시행규칙 서식·대산항 운영세칙 네 건이 모두 이 모양이었다.
답변 서두에 "사람이 검증한 정식 답변이 아니라 법령 원문을 방금 훑어본 참고 정보입니다"가 붙어
있었다 — **원문 폴백 경로**로 답한 것이고, 폴백은 근거 목록을 만들지 않는다.

**원인.** `filterSourcesByAnswer` 는 답변이 그 페이지의 **모법 이름이나 주제**를 글자 그대로
써야 통과시켰다. 그런데 답변은 그 페이지가 담은 **고시·지침 이름**만 쓰는 일이 흔하다.

```
답변: 「갯벌복원사업 지침」 제14조 관련 [별표 2] …   ← 모법 이름은 안 씀
소스: law = 갯벌 및 그 주변지역의 지속가능한 관리와 복원에 관한 법률
      topic = 갯벌복원사업시행및계획
→ 둘 다 답변에 없으니 페이지를 버린다 → finalSources 가 빔
→ routes 가 "위키에 쓸 근거가 없다"고 보고 원문 폴백으로 다시 답한다
→ 답은 맞는데 근거 목록이 빈다
```

**고친 방식.** 그 페이지의 **근거 조문 줄이 답변 대조를 통과하면** 페이지를 살린다. 새 규칙을
만들지 않고 이미 줄 단위로 검증된 `filterCitationChainByAnswer` 를 그대로 불러, **한 줄이라도
살아남을 때만** 통과시킨다. 그 함수가 법 이름·조문 주인·근접성을 모두 보므로 환각 0 규약은
그대로다.

**확인.** 네 건 모두 폴백이 사라졌다(살아남은 소스 0 → 1~3건). 무관한 답변("오늘 날씨가
좋습니다")이나 법 이름 없이 별표만 스친 답변으로는 여전히 살아나지 않는다.
고정 검사: `scripts/test_citation_chain.js` 3건.

## 6-24. 같은 상황질문을 두 번 묻지 않는다 (2026-08-20)

**증상.** 천연기념물 국외 반출 후 재반입 서식을 묻는 질문에 챗봇이 **"어떤 배에 관한 것인가요?"**
(어선 / 수상레저기구 / 그 밖의 선박)를 물었다. 질문과 아무 상관이 없다. 그래서 직접 입력으로
"배가 아니라 천연기념물 재반입 신고서 양식에 관한 질문입니다"라고 답했더니 **같은 질문이 다시**
나왔다. 빠져나올 길이 없다.

**원인.** 이 물음은 AI 되묻기가 아니라 **상황질문(선박 트리, `scopeNarrowStep`)** 이다. AI 되묻기는
직전 라운드의 질문·선택지를 `ctx.cl` 에 남겨 "표현만 바꾼 같은 되묻기"를 결정론적으로 차단하는데
(§B6), **상황질문 경로는 그 기록을 남기지도, 보지도 않았다.**
선택지 버튼을 누르면 트리가 한 단계 내려가 질문이 달라지지만, **직접 입력은 트리를 못 내려간다** —
그래서 같은 노드에 머물며 같은 질문이 무한히 반복됐다.

**고친 방식.** AI 되묻기와 **같은 장치**를 쓴다(새 저장소를 만들지 않는다).
- `routes` 가 상황질문을 낼 때 `ctx.cl = { q, labels }` 를 남긴다.
- `scopeNarrowStep(query, scope, sources, enabled, prevCl)` 가 그것을 받아, **직전에 낸 질문과
  이번 노드의 질문이 같으면 묻지 않는다**(사용자가 선택지로 답하지 않았다는 뜻이다).

사용자가 버튼을 눌러 트리가 내려갔으면 `node.질문` 이 달라지므로 이 차단에 걸리지 않는다.
고정 검사: `scripts/test_zone_tree_wiring.js` 4건(계약 검사).

## 6-25. 근거 조문 표의 어떤 행이 "절대 못 뜨는" 행인가 — 전수조사와 게이트 (2026-08-20)

**왜 만들었나.** `citation_table_scan.js`(V5-3)는 **우리가 이름 붙여 본 결함 다섯 가지**를 센다.
243건을 0으로 만든 뒤 "그럼 나머지 행은 다 뜨는가"를 처음 물었더니, 10,882행 중 **76행(0.70%)이
어떤 답변으로도 근거 목록에 오를 수 없었다.** 아는 병만 세는 검사로는 이런 행이 안 보인다.

**재는 방법.** 행마다 **그 행에 가장 유리한 답변**을 만들어 실제 대조 함수
(`filterCitationChainByAnswer`)에 넣는다. 유리한 답변이란 「법령 칸 이름」 바로 뒤에 「그 행이 짚는
조문을 코드가 찾는 꼴로」 붙인 문장이다(토큰·묶음 편 것·부칙 열쇠·번호 없는 별표). 최대한 맞춰 준
답변으로도 안 살아나면 현실의 답변으로는 더더욱 안 살아난다. → `_dashboard/loop/reach_eval.js`,
`verify_all.sh` V5-5 게이트(기준선보다 늘면 실패).

**찾아낸 두 원인과 조치.**

| 원인 | 행 | 어디를 고쳤나 |
|---|---:|---|
| 가운뎃점 묶음에 **가지조**가 섞이면 토큰을 하나도 못 뽑음 | 42 | 코드 — `articleEnumTokens` |
| 법령 칸에 **두 법 이상**을 한 칸에 적음 | 53 | 위키 — 법별로 행 분리 |

① `articleEnumTokens` 는 묶음의 끝을 `조(?!의)` 로 못박고 있었다. 그래서
`제37·38·40·41·41조의2·44조`(선박안전법 벌칙)처럼 **가지조가 하나라도 섞이면 그 칸 전체가
토큰 0개**가 됐다. 항목을 `N` / `N의M` / `N조의M` 세 꼴로 읽도록 고쳤고, 느슨해지지 않게
두 가지를 함께 걸었다 — ⓐ끝에 `조`가 붙었거나 마지막 항목이 `N조의M` 일 때만 조 묶음으로 읽는다
(`제53조제2항제5·6·6의2호` 같은 **호 묶음**을 조로 읽으면 없는 조문이 붙는다) ⓑ항목을 먼저 전부
읽어보고 하나라도 못 읽으면 **그 묶음만** 건너뛴다(`제23~25조의2` 가 절반만 펴지는 것을 막고,
같은 칸의 별표 묶음은 살린다). 이 한 번의 수정으로 **21개 법·45개 페이지·56행**이 함께 살아났다.

② 법령 칸 `이 법·시행령`·`양식산업발전법·시행규칙`·`수상에서의 수색ㆍ구조 등에 관한 법률ㆍ시행령`
같은 행은 `lawMentionedInAnswer`(대조의 **첫 줄**)에서 떨어진다 — `lawCellVariants` 가 후보를
칸 문자열 하나만 만드는데 답변이 그 글자를 쓸 일이 없기 때문이다. 조문 대조에 가보지도 못한다.
**코드를 느슨하게 풀지 않고 위키를 나눴다** — 풀면 그 행이 "제7조가 법 것인지 시행령 것인지"를
모른 채 화면에 뜨고, 발췌도 엉뚱한 법에서 끌어올 수 있다("무관한 줄이 붙는 게 더 나쁘다").
63행 중 53행은 기계로 나누고, 짝을 확신할 수 없는 10행은 사람 몫으로 남겼다.

**남은 34행(0.31%)은 0으로 만들지 않는다.** 조문 구조 자체가 없는 고시(도선구간 구간표,
기준임금 고시)가 실재해 0이 될 수 없고, 억지로 0을 만들면 그게 지어내기다. 게이트는 **늘어나는
것만** 막는다.
