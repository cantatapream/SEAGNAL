# 나리야 법률 챗봇 — 답변 설계 규칙

이 문서는 **법률 위키를 소비하는 쪽(챗봇)** 의 동작 규칙이다.
위키를 만드는 규칙은 `_SCHEMA.md`, 여기는 그 위키로 **어떻게 답하는가**.

## 0. 결정된 방향 (2026-07)
- **음성 비서 호출 기능 폐기.** 기상 정보는 사용자가 지도·레이어로 직접 둘러보는 게 빠르고,
  법률 정보를 음성으로 한꺼번에 쏟으면 혼란을 준다. → **텍스트 챗봇(턴제)** 로 간다.
- **기존 직군 분류 시스템(`knowledge/jikgun`, `knowledge/graph`) 재사용 안 함.** 직군·소속·취미는
  챗봇이 대화 중 자연스럽게 물어 얻는다.
- **프로필은 챗봇이 대화로 획득하고 기기에만 저장**(서버 저장 금지), 다음 질의의 필터로 재사용.

## 0-A. 운영 결정 (확정) — `_SCHEMA.md`에서 이관(2026-07-27, 답변/표출 규칙이라 여기가 맞음)

| 항목 | 결정 |
|---|---|
| 사용자 프로필 | **온디바이스(폰) 저장.** 서버 미저장. 챗봇이 대화 중 직군 감지(기존 `assistant.js` jikgun) → 답변에 필요할 때만 톤수·조업형태·조업구역·어업허가종류를 **선제적으로 되물어** 얻고 온디바이스에 누적. "일반 질문인지, 본인 상황 기준인지"도 되물음. |
| 첫 구축 대상 | **수산업법**부터 (근간 허브 법) → 어선법·어선안전조업법으로 확장 |
| 검색 | 처음부터 **전용 검색엔진** 도입(위키 페이지 대상). |
| Gemini 키 | 기존 기상용 키 **공유**(`gemini_client.js`). |
| 답변 원칙 | **모든 답변에 근거 조문(법령명·조문·시행일) 명시 + 하단 면책 고지**("참고용, 최종 확인은 공식 출처"). |
| 근거 = 전체 사슬 | 별표·시행규칙 하나만 대지 말고, 거기에 닿게 된 **법률 → 시행령 → 시행규칙 → 별표 전체 도출 경로**를 함께 제시(설득력↑). 예: "법 제10조 → 시행규칙 제4조 → 별표 3". 각 단계 딥링크 제공. |
| 지도 표출 화법 | 그릴 수 있으면(좌표 기반) **바로 그려서 보여주고**, 못 그리면 조용히 공식 표로 안내. **"이건 못 그린다"는 메타 설명은 사용자에게 하지 않는다.** |
| 답변 톤 | 딱딱한 법조문 나열 금지. **결론 먼저 → 필요한 근거**. 쉬운 내용은 그대로, **이해가 어려운 부분만 "쉽게 말하면~" 예시로 한 번 더** 풀어준다. 대화가 유연하게 이어지게 한다(과잉 설명도 금지). |
| 준용·포괄인용 | AI가 억지 해석하지 않고 **링크 + REVIEW 플래그**, 사람이 범위 확인. |
| 대화 이력 | **온디바이스에 영구 저장**(서버 미저장). 카카오톡처럼 채팅방 유지, **위로 스크롤 시 과거 대화 내역 로드**. 프로필도 이 이력에서 이어짐. |
| 지도·구역 표출 | **좌표(경위도)가 명시된 별표만 폴리곤화**한다. 좌표 없이 지형지물·한글로만 서술된 구역은 **폴리곤 대상에서 제외**(공식 별표 이미지로만 표출). 폴리곤은 빈 배경이 아니라 **실제 지도 위에 오버레이**한다. |
| 지도 탭 연동 | 채팅에 **별도 프롬프트 박스를 두지 않는다**(공간 낭비). **폴리곤/지도를 탭하면 확대 팝업**이 열리고, 그 팝업 안에 핀치줌·**"해양종합정보 탭에서 보기"**·X를 모두 넣는다. "탭에서 보기" → 기존 딥링크(`assistant=ocean`, 좌표는 `assistant=tide`의 lat/lon 방식)로 **`ocean-map-section` 열고 위치 이동 + 폴리곤 오버레이**(풍랑·파고 레이어와 함께). |

## 1. 프로필(온디바이스) — 대화로 채운다
고정 폼/자동감지가 아니라, 필요할 때 되물어 얻는다. 얻은 값은 기기에만 저장·재사용.
법률 답 필터에 쓰는 핵심 필드:

| 필드 | 예 | 쓰임 |
|---|---|---|
| 선박 톤수 | 5톤 / 9.77톤 / 30톤 | concept `적용범위(톤수)` 조건 매칭 |
| 선박 용도 | 낚시어선 / 어선 / 레저 / 일반 | 낚시어선법 vs 어선법 vs 수상레저법 분기 |
| 어업 종류 | 연안자망 / 근해통발 / 양식 … | 허가·신고·금어기 분기 |
| 면허·자격 | 소형선박조종사 / 해기사 급수 | 승무기준·자격 |
| 주 조업구역 | 특정해역 / 조업자제해역 (연근해) · 태평양 / 대서양 / 인도양 (원양, 원양산업발전법 제6조④) | 구역 규제·출항통제 |
| 야간조업 | 예 / 아니오 | 야간장비 의무 |

원칙: **모르면 묻는다.** 답이 프로필에 의존(톤수로 갈리는 의무 등)하는데 값이 없으면,
장황하게 다 나열하지 말고 필요한 한 가지를 되물어 좁힌다. ("배가 몇 톤이세요?")

### 1-A. 대화 설계 결정 — 멀티턴 되물음 우선, 안 되면 조건별 분기 폴백 (H-21 사용자 확정 2026-07-21, Phase E 설계 메모)
- **1순위(권장)**: 위 원칙대로 **에이전트가 한 번에 한 조건만 되물어 좁혀가는 멀티턴 대화**. 예: "정박신고 의무 있어?" → "배가 몇 톤이세요?" → (답변) → 톤수 조건에 맞는 답만 제시. 필요하면 두세 번 더 되물어 좁힐 수 있다(예: 톤수 다음 용도, 용도 다음 조업구역 등 — 최대 3턴 정도가 사용자 경험상 적정).
- **2순위(폴백)**: 만약 실제 구현 단계에서 멀티턴 되물음이 **대화 턴 수 제한·API 구조 등으로 불가능**하다고 판명되면, 처음 답변에 **조건별 분기를 전부 제시**하는 방식으로 대체한다(예: "5톤 미만이면 A, 5톤 이상이면 B" 식으로 한 번에 나열). 이 경우도 프로필 값이 이미 있으면 해당 분기만 골라 답한다.
- 어느 쪽이든 **위키 데이터 구조(적용범위·예외 표에 톤수·용도·구역 조건 컬럼)가 전제조건**이라, 이 문서 1절의 프로필 필드·감사의 "프로필조건" 체크 기준은 두 방식 모두에 공통으로 적용된다.
- **이 절은 설계 결정만 기록한 것 — 실제 구현은 Phase E(답변엔진) 착수 시점.**

### 1-B. 되묻기 구현 — 구조화 버튼 선택지 (사용자 확정 2026-08-03, 구현 완료)
1-A의 "1순위 멀티턴 되물음"을 **자유 텍스트가 아니라 버튼 선택지**로 구현했다. 이 챗봇은 대화 이력을
서버에 전혀 보내지 않는 **완전 단발성 구조**라, 자유 텍스트로 되물으면 사용자의 답이 새 단발 질의로
들어가 원래 맥락이 사라진다. 버튼이면 "이어지는 답인지 새 질문인지" 판정 자체가 필요 없다.

- **별도의 빠른 판단 단계**: 검색으로 근거(contextPages)를 확보한 직후, 무거운 종합답변
  (`synthesizeAnswerStream`)을 만들기 **전에** `legal_retriever.decideClarify(query, contextPages)`가
  "되물어야 하는 질문인가"만 짧게 판단한다(사고 끄고 JSON만 받는 호출 — `expandQueryTerms`·
  `pickCandidateLaws`와 같은 패턴). 되물을 게 있으면 종합답변을 **아예 만들지 않고** 질문 + 선택지
  2~3개 + 한 줄 안내만 내려보낸다(`POST /api/legal/ask` done 이벤트의 `clarify` 필드).
- **선택지는 그 순간 검색된 근거 조문에서만 만든다(환각 0)**. 고정 목록이 아니다 — 예: 해상교통안전법
  제39조가 처벌 대상을 "조타기를 조작하거나 그 조작을 지시하는 자"로 규정하니, 그 조문을 근거로
  "조타 담당인가요, 일반 승객인가요?"를 묻는다. 근거자료에서 그 구분의 근거를 찾을 수 없으면
  되묻지 않는다(`needed:false`). 판단이 애매하거나 실패(키 없음·타임아웃·파싱 실패)해도 조용히
  `needed:false`로 물러나 **기존 답변 흐름 그대로** 진행한다.
- **맥락 조립은 클라이언트가 한다**(서버 세션 저장 없음): 버튼을 누르면 `"원래질문 — 선택라벨"`로
  합쳐 **기존 질문 전송 로직 그대로** 다시 보낸다. 합쳐진 질의에는 조건이 이미 문장에 들어 있으므로
  같은 조건을 또 묻지 않는다. 한 번 고른 선택지 묶음은 비활성 — 중복 전송 방지.
- **재되묻기 무한루프 차단은 프롬프트가 아니라 코드로 한다**: 프롬프트에도 "이미 조건이 붙었으면 묻지
  마라"가 있지만 모델이 이를 어기면 버튼→되묻기→버튼 무한루프가 된다(검토에서 실증). 그래서
  `decideClarify` 첫머리에서 질의에 결합자(`' — '`, em dash U+2014 앞뒤 공백 — 클라이언트
  `pickClarifyOption`이 쓰는 그 구분자)가 있으면 **Gemini를 부르지도 않고** `needed:false`로 물러난다.
  ⚠ 클라이언트 구분자와 서버 `CLARIFY_JOINER` 중 한쪽만 바꾸면 이 차단이 뚫린다.
- **hint 조문번호 대조(환각 0)**: 모델이 근거자료에 없는 조문번호를 hint(버튼 툴팁)에 지어넣는 사례가
  확인돼, 파싱 후 hint의 `제N조` 토큰이 근거자료 원문에 문자 그대로 없으면 **그 hint만 비운다**(선택지
  라벨은 유지). 질문·라벨 전체 문자열 대조는 하지 않는다 — 패러프레이즈 오탐으로 정상 되묻기가 죽는다.
- **되묻기 응답의 근거목록**: 답변 문장이 없어 `filterSourcesByAnswer`(문장 기반 교차확인)를 쓸 수
  없으므로, 되묻기 판단이 실제로 읽은 상위 `CLARIFY_TOPK`건까지만 싣는다(원본 최대 15건 → 6건).
- **답변 원칙과의 관계**: 되묻기가 이 앞단에서 걸러주므로 답변 프롬프트 **규칙3은 "여기서는 되묻지
  말고 있는 정보로 답하라"** 로 바뀌었다(규칙3 ↔ 규칙8 충돌 해소). **규칙8(관련 주체 빠짐없이
  나열)은 유지** — 되묻기로 좁혀지지 않는 진짜 다자간 케이스(선장·선원·승객·화주가 각각 다른 의무)를
  위해 필요하다.
- 구현: `services/legal_retriever.js decideClarify` · `routes/legal.js POST /api/legal/ask`
  · `client/js/ai-chat/ai_chat.js clarifyHTML/pickClarifyOption` · `client/css/ai_chat.css .nrya-clarify*`.

## 2. 점진적 공개 (처벌·다차수 답변의 핵심 규칙)
처벌이 **차수(1/2/3차…)·상황에 따라 갈리는 경우**, 한 번에 전부 쏟지 않는다.

1. **1차 답**: ① "이건 **상황(단속 횟수 등)에 따라 달라진다**"를 먼저 알리고,
   ② **가장 흔한 경우(통상 최초/1차)의 처벌만** 제시한다. ③ 출처(법·별표)를 단다.
2. **되물음**: "2차 이후(또는 특정 차수)도 알려드릴까요?" 로 끝낸다.
3. **확장 답**: 사용자가 원하면(또는 특정 차수를 지정하면) 그때 **차수별 전체(1→2→3→4차)** 를 제공.

> 데이터를 숨기는 게 아니다 — 위키(`## 행정처분 체계` 별표)엔 1~4차가 전부 있다.
> 한 번에 안 쏟아 혼란을 줄이는 **UX 규칙**이다.

### 예시 (어선안전조업법 승선원 변동 신고 미실시)
- 턴1 — "승선원 바뀌었는데 변동 신고 안 하면?"
  → "단속 횟수에 따라 달라져요. 보통 **최초 단속 땐 경고** 수준입니다.
     2차·3차 이후는 더 무거워지는데, 그 부분도 알려드릴까요?" *(출처: 시행규칙 별표N)*
- 턴2 — "응, 3차는?" / "전부 알려줘"
  → "1차 경고 → 2차 ○○ → 3차 ○○ → 4차 ○○ …" (전체 또는 지정 차수)

같은 원리를 **벌금 구간·과태료 상한·톤수별 의무** 등 "조건에 따라 갈리는" 모든 답에 적용:
먼저 통상/대표값 + "조건에 따라 다름" → 되물음 → 필요 시 전체.

## 3. 인용 규율 (환각 0)
- 법률 답의 근거는 **위키 원문 인용만**. 위키에 없으면 "확인되지 않는다"고 말한다(지어내지 않음).
- 처벌은 **조·항·호·금액 그대로**. 뭉개기 금지.
- 답변은 **출처 concept ID를 달고** 나간다 → 따봉↓ 시 그 페이지를 정확히 가리켜 관리자 큐로 연결.
- **★검증된 것만 인용 = canonical 필터 (사용자 확정 2026-07-20)**: 사용자에게 나가는 답변 근거는 **검증 완료(`status: canonical`) 페이지만**. 미검증 `draft`(별표 OCR 오독 처벌수치 등)는 답변 근거로 쓰지 않는다 — 틀린 값이 사용자에게 새면 안 되기 때문. 구현은 서버 스위치 `nariya_config.json.answerCanonicalOnly`(기본 OFF=검증 쌓일 때까지 현행 전체검색, 검증 후 ON). **켜기 전 index.json을 status 포함 재빌드 필수**(안 하면 답변 0건). 상세 절차·취지는 `MASTER_PLAN.md` E절 "canonical 안전필터". statute(법령 원문 자체)는 검증 대상이 아니라 필터 통과.

## 4. 검색 (하이브리드) — 엔진 구현 시
★**순차가 아니라 "동시에 점수 매겨 최고점 카드 선택"이다.** glossary가 무조건 첫 관문이 아니다.
- **① 직접 매칭** — 질문 단어가 개념 **제목·정의·본문에 그대로** 있으면 바로 그 카드(강한 신호). "구명조끼"·"음주운항"처럼 **법에도 적힌 정식 명칭**은 여기서 곧장 잡힌다. (glossary는 이때 기여 안 함, 있어도 무해)
- **② glossary 구어 매핑**(`wiki/_glossary.md`) — 사람 말 ≠ 정식 명칭일 때만 번역: "조개껍데기"→폐기물, "술 먹고 배 몰면"→음주운항. (띄어쓰기 무시) = **정식 명칭이 아닌 말을 위한 안전망**.
- **③ 임베딩 검색**(`services/topic_embedding.js` 재사용) — 바꿔 말한 질문(패러프레이즈)을 의미로 잡는다.
- **④ 그래프 홉**(`wiki/graph.json`) — 위에서 잡은 개념의 관련개념·테마허브까지 확장.
①②③을 **함께 돌려 점수 합산 → 가장 잘 맞는 카드** 선택. 그 뒤 **프로필 필터**(1절 필드 ↔ concept `적용범위·예외` 조건 컬럼)로 좁힌다.

### 4-U. 모르는 구어 해소 (미등재 용어 → 웹 → 사용자 확인)
1·2·3 다 돌려도 **확실한 개념이 안 잡히면**(점수 낮음/모호), 지어내지 말고 아래를 순서대로 한다:
1. **먼저 우리 DB(위키·glossary) 재확인** — 정말 없는지.
2. **없으면 웹 검색으로 그 말의 뜻을 확인** — 예: "깔때기"가 DB에 없으면 웹에서 "깔때기(어구)"가 무엇인지 찾는다.
3. **찾은 뜻을 사용자에게 되물어 확인** — "'깔때기'는 통발류 어구를 말씀하시는 게 맞을까요?" (추정을 사실처럼 답하지 않는다)
4. **사용자가 맞다고 하면** 그 뜻으로 다시 개념 검색(1·2·3) → 답변. 동시에 이 구어→개념 매핑을 **`_candidates` 방에 학습 후보로 적재**(관리자 승인 시 glossary에 정식 편입).
- 원칙: **DB 우선 → 웹은 '뜻 확인'용 → 확정은 사용자 되물음**. 웹 내용을 법적 근거로 인용하지 않는다(근거는 항상 위키 원문).

## 5. 답변의 경계와 마무리 (스코프·소관부서·수집불가 안내) — 사용자 확정 2026-07-18

챗봇이 "어디까지 답하고, 어떻게 끝맺는가"의 고정 규칙.

**5-1. 명확한 조문 = 반드시 안내한다**
- 조문이 명확히 적혀 있고 의미를 명확히 해석할 수 있으면, **그 조문까지는 반드시** 안내한다. (얼버무리거나 "실무 문의"로 회피하지 않는다.)
- 기준법이 시행령·시행규칙·별표·고시·타법으로 **타고 들어간 그 지점의 조문**도, 명확하면 반드시 안내한다.

**5-2. 판례·법리·다툼의 여지 = 답하지 않는다 (스코프 밖)**
- 해석이 갈리거나(학설·판례), 이해관계가 얽혀 결론이 불명확한 논점은 **챗봇이 답할 영역이 아니다.** 실무자·유권해석이 관리할 부분.
- 이런 경우: **명확한 조문까지만 안내하고 거기서 끊는다.** 그 다음은 "이 부분은 개별 사안·해석에 따라 달라져 여기서 단정하지 않는다. 관할 소관부서에 확인하시는 것이 정확하다"로 마무리(5-4 연결).
- **즉 DoD의 답변율(full)은 "이 스코프 안"에서 측정한다.** 판례·법리·다툼·순수 원문공백은 "규정 없음/확인불가" 정직 표기가 이미 정답이며, full 미달로 세지 않는다.

**5-3. 수집 불가 영역(지자체 고시·부처 내부지침·미제정 위임고시·타 정부시스템 소관) = 정직하게 안내로 대체한다**
- 행정규칙·고시(국가법령정보센터 게재분)는 수집돼 있으니 그대로 인용.
- 조례는 수집 가능한 선까지 인용.
- **다음 4종은 국가법령정보센터(DRF)로 구조적으로 답할 수 없다 — 억지로 크롤링 파이프라인을 새로 만들지 않고 "관할 소관부서 문의"로 안내한다**(사용자 확정 2026-07-18, 4번 항목은 2026-07-21 Stage B 재수집 사이클 결과 추가 확정):
  1. **각 지자체 홈페이지에만 올라오는 지자체 고시**(지역 지정·별도기준 등).
  2. **부처 내부지침·업무처리지침 등 비공개/미게재 행정규칙**.
  3. **법이 위임했으나 아직 제정되지 않은 고시**(위임근거는 있으나 고시 자체가 admrul에 없음 — 이번 수집에서 수십 건 확인). "미제정으로 확인된다"고 정직표기.
  4. **관보(gwanbo.go.kr) 공고 형태이거나 타 정부시스템(국가건설기준센터 codil.or.kr 등) 소관으로 게재되는 것** — 위임근거는 있고 실제로 제정·시행 중일 가능성이 높지만, law.go.kr DRF API 자체가 이런 유형을 다루지 않아 우리 수집 파이프라인 구조상 접근 불가. (예: 연안침식관리구역 지정·고시의 좌표, 항로표지 기본계획, 신항만 예정지역 지정 좌표, 각종 검사대행기관·지정기관 실제 목록, 어촌ㆍ어항법 내진설계기준 — 2026-07-21 Stage B 재수집 시 여러 법에서 반복 확인된 패턴). **"미제정"과는 다르다 — 미제정은 아예 없는 것이고, 이건 있지만 우리가 접근 못 하는 것**이므로 안내 문구도 구분한다(아래).
- 안내 형식:
  - 1~3번(지자체/부처지침/미제정): "이 부분은 **각 지방자치단체 고시/소관 부처 지침에 따르며**(또는 **아직 세부 고시가 제정되지 않았으며**), 세부사항은 **관할 소관 부서**로 확인하시는 것이 정확합니다" + 연락처(5-4).
  - 4번(관보·타 정부시스템 소관): "이 부분은 **관보 고시 또는 별도 정부시스템에 게재되는 사항이라 이 서비스에서 원문을 직접 확인할 수 없습니다.** 최신·정확한 내용은 **관할 소관 부서**로 직접 문의해 확인하시기 바랍니다" + 연락처(5-4). (재수집을 계속 시도하는 대신, 답변 단계에서 이렇게 스코프 밖으로 명확히 분리해 안내한다 — 2026-07-21 사용자 확정)
  - **얼버무리지 말고 "왜 여기서 못 답하는지"를 분명히 밝힌 뒤 부서로 넘긴다.**

**5-4. 답변의 마무리 = 소관부서 연락처(전화번호)**
- 명확한 답을 준 뒤, 그 법률·행정규칙에 적힌 **소관부서와 연락처(전화번호)를 안내**하는 것이 답변의 완성이다.
- 형식 예: "…입니다(출처: ○○법 제N조). 자세한 사항은 **○○부 ○○과(☎ 000-000-0000)** 로 문의하세요."
- 수집 불가(5-3)·스코프 밖(5-2)으로 끊을 때도 이 소관부서 연락처로 마무리한다.
- 근거 데이터: 위키 페이지 상단 메타의 `소관부서`·`연락처` 필드(`_SCHEMA.md` 0-A 참조).

**5-5. 서식(별지) = 답변에서 원버튼 다운로드 제공 (사용자 확정 2026-07-18)**
- 질문에 관련된 **별지 서식(신고서·신청서·확인서 등 "서식"류)**이 있으면, 챗봇 답변에 **그 서식을 바로 받을 수 있는 다운로드 버튼**을 붙인다(예: "「어선등록 신청서」 [⬇ 다운로드]"). 사용자가 조문을 읽고 곧바로 제출 서류까지 손에 넣게 하는 것이 목표.
- 근거 데이터: 위키/원문의 서식은 **다운로드 가능한 원본(HWP/PDF)**을 보존·링크한다(`_SCHEMA.md` 0-A 서식 규칙). 원본이 없으면 국가법령정보센터 서식 링크로 대체.
- 엔진/앱 구현은 Phase E(답변에 서식 메타 첨부)·Phase F(다운로드 버튼 UI)에서. 지금 단계에서는 **서식 원본·링크를 유실하지 않도록 수집·보존**만 확실히 한다.

**5-6. 국제협약(SOLAS·MARPOL·STCW 등) = 우리 법 기준으로만 답하고, 협약은 "기반"으로 언급+링크 (사용자 확정 2026-07-18)**
- 우리 해사법령은 국제협약을 국내법화한 것이다. **답변은 항상 우리 법(및 그 시행령·시행규칙·기술기준) 기준으로 한다.** 협약 부속서(Annex)의 기술기준은 **우리가 수집하지 않는다**(우리 법에 이미 반영돼 있음).
- 다만 답변에서 국제협약을 언급하게 될 때는: ①"이 규정은 「○○협약(SOLAS 등)」을 기반으로 만들어졌다"는 **유래를 알려주고**, ②그 협약 원문을 볼 수 있는 **링크를 제공**한다(IMO 등 공식 출처). ③우리 법과 협약 사이에 **차이점이 있으면 그 차이를 짚어준다**(단, 결론은 우리 법 기준).
- 근거 데이터: 위키 개념에 `국제협약 근거`(협약명)·`협약 링크` 메타를 둔다(있을 때). 협약 본문은 raw에 담지 않는다.

**5-7. 판례로 해석이 달라질 수 있는 부분 = "참고사항"으로만 표기 (판례 수집 안 함, 사용자 확정 2026-07-18)**
- 조문 텍스트는 불변이지만 대법원 판례로 실무 해석이 바뀔 수 있다. **판례 자체는 수집하지 않는다**(스코프 밖, 5-2).
- 대신, 해석 다툼의 여지가 알려진 조문에는 답변 말미에 **참고 한 줄**을 붙인다: "※ 참고: 이 부분은 **판례·유권해석에 따라 달라질 수 있으니**, 다툼이 있는 사안은 관할 소관부서·전문가 확인을 권합니다." (단정하지 않되, stale·해석변경 가능성을 사용자에게 투명하게 알림.)
- 근거 데이터: 위키 개념에 `해석주의(판례변동 가능)` 플래그를 둘 수 있다(선택). 플래그가 있으면 챗봇이 이 참고 문구를 자동 첨부.

**5-8. 답변 말미 "최종 확인일" 표기 = stale 위험 투명화 (사용자 확정 2026-07-18)**
- 모든 법률 답변 끝에 근거 법령의 **기준일**을 붙인다: 예) "(「선박안전법」 2026-07-18 기준)". 위키 개념 상단 메타의 `updated`(또는 원문 `_meta.json`의 시행일)를 그대로 노출.
- 취지: 위키가 개정에 뒤처졌을 가능성을 **숨기지 않고** 사용자에게 드러내, "언제 기준 정보인지"를 스스로 판단하게 한다. (재수집 스케줄러가 갱신하면 이 날짜도 자동 최신화 — MASTER_PLAN Phase G.)

**5-9. 별표 이미지 표시 = 도해·그림은 이미지로, 수치·설명은 텍스트로 (사용자 확정 2026-07-18)**
- 질문에 해당하는 별표에 **도해·그림(엔진 구조도, 조업방식 도해, 표지 도안 등 텍스트로 표현 불가한 시각정보)**이 있으면, 텍스트 설명과 **함께 그 이미지를 채팅창에 표시**한다.
  - 예) "엔진 어떻게 생겼어?" → 해당 법 별표의 엔진 도해 이미지를 띄운다.
  - 예) "○○ 조업방식은?" → 조업방식 **설명 텍스트**(별표 원문/OCR)와 **도해 이미지**를 함께 제공. (텍스트는 텍스트대로, 이미지는 이미지대로.)
- **이미지 속 수치·표는 OCR로 이미 텍스트화**돼 있으니(`_SCHEMA.md` 0-A 별표 이미지 규칙) 그 수치는 **텍스트로 정확히 답**하고, 도해는 **이미지로 보여준다**. 수치를 이미지로 떠넘기지 않는다.
- 근거 데이터: 위키/annex 메타 `이미지파일`(우리가 보존한 별표 도해 원본). **법령 별표의 공식 도해는 원본을 표시**하고, 일반 장비·어구의 시각확인은 기존대로 외부 이미지 검색 링크(4절 계열)로 처리한다 — 둘을 구분.
- 엔진/앱 구현은 Phase E(답변에 이미지 메타 첨부)·Phase F(채팅 인라인 이미지 렌더)에서. 지금 단계에서는 **별표 도해 이미지 원본을 유실하지 않게 보존**하는 것이 핵심.
