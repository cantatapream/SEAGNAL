## 1. 원인 분석 — 왜 정량 판단 케이스가 떨어지는가

### 1.1 실패 케이스 재현

| ID | 직군 | 질문 | 현재 답 | 결함 신호 |
|---|---|---|---|---|
| LG-4-01 | local_gov | "풍랑특보 시 해수욕장 운영?" | "현재 발효 중인 풍랑특보는 없습니다." | `expect_decision` 실패 — DECISION_RE(가능/적합/주의/무리/안전/위험/불가/곤란/어렵/좋습/괜찮/조심) 어느 단어도 없음 |
| MOF-4-01 | mof | "파고 2m 어업관리 권고?" | "해당 해역 단기 예보 정보가 없습니다." | 같음. 임계표(MOF wave_m caution=3) 대비 2m 는 "주의 미만 → 통상 운영 가능" 결론이 나와야 하는데 비교 자체가 안 됨 |

### 1.2 근본 원인 (3 갈래)

**(a) synth prompt 의 "정량 판단" 규칙이 *데이터 기반* 분기에만 forcing 돼 있다.**
현 규칙 (assistant.js 1579):
```
"출항/조업/훈련/작업/타도 돼/가능?·괜찮을까?·해도 돼?·위험?·안전?" 류 안전 판단 질의는
수집결과의 정량 수치(파고·풍속·시정·특보)에 근거해 …
```
→ "수집결과의 정량 수치에 근거해" 라는 단서가 LLM 에게 *수집결과가 비면 판단 안 해도 된다* 는 도피로를 만든다.
실제로 LG-4-01 은 `get_warning` 호출 결과 `current:null` (특보 없음) 하나로 끝나며,
MOF-4-01 은 `get_marine_forecast` 가 zone 미해소로 빈 결과를 돌려준다.
→ LLM 은 가장 안전한 "정보 없음" 보고만 출력하고 결정 단어를 생략한다.

**(b) buildPersonalContext 의 임계표 주입 규칙은 *사용자가 직접 단정한 수치* 에만 trigger 된다.**
현 규칙 (assistant.js 724):
```
사용자가 정량 수치를 직접 단정(예: "파고 1.5m 풍속 12m 인데 ~ 가능?")하면
그 수치를 위 임계표와 비교해 *가부 결론을 한 줄 먼저* 답하세요(가능/주의/무리/위험).
```
→ MOF-4-01 ("파고 2m") 처럼 사용자가 수치를 단정한 경우는 trigger 돼야 하나,
   "수치를 *단정* 한다" 는 표현이 약해 LLM 이 "지역 미지정 → 도구 결과 우선" 으로 빠진다.
→ LG-4-01 ("풍랑특보 시") 처럼 *가설 조건문* 인 경우는 trigger 자체가 안 됨. "if 풍랑특보" 라는 조건은
   수치 단정도 아니고 도구 결과도 "특보 없음" 만 보고하므로, 임계표는 사용되지 않는다.

**(c) 임계표 + 직군 표준 운용 절차 (SOP) 의 연결고리가 prompt 에 명시되지 않음.**
local_gov 임계표 comment 에는 이미
> "해수욕장 운영 결정: 파고 ≥1.5m 또는 특보 발효 시 입수 통제"

라는 SOP 가 들어 있다. mof 도
> "정책 권고·통제 발령 기준은 풍랑특보(파고 3m·풍속 14m) 가 표준"

이 있다. 하지만 `thresholdDigest()` 가 출력하는 한 줄 임계표에는 `comment` 가 부록처럼 붙고,
synth prompt 에는 "임계표 + comment + 가설 질의 → SOP 답을 만들라" 는 지시가 없다.
→ 임계표는 보지만 *어떻게 답으로 변환할지* 모르는 LLM 의 무행동(no-op) 으로 귀결.

### 1.3 요약
1) prompt 의 정량 판단 규칙이 "도구 결과 없음" 분기를 다루지 않음
2) 임계표 trigger 조건이 너무 좁음 (단정형만 인정, 가설 조건문 미인정)
3) 임계표 → SOP → 결론 의 사슬이 명시되지 않음

## 2. LG-4-01 패치안 — 가설 조건문 (if-then) 질의 지원

### 2.1 진단
"풍랑특보 시 해수욕장 운영?" 은
- 형식: `IF <기상 조건> THEN <행동 가부>` 의 hypothetical conditional
- 사용자는 *현재* 풍랑특보 여부를 묻는 게 아니라 *그 조건이 발생했을 때 어떻게 해야 하는지* 의 SOP 를 묻는다
- 따라서 "현재 특보 없음" 보고는 *질문에 답하지 않음*

### 2.2 패치 — synth prompt 규칙 추가
**위치**: `assistant.js` 라인 1579 (의사결정형 — 정량 판단 강화) 바로 아래에 새 bullet 1개를 추가.

**BEFORE** (현행):
```
- **(의사결정형 — 정량 판단 강화)** "출항/조업/훈련/작업/타도 돼/가능?·괜찮을까?·해도 돼?·위험?·안전?" 류 안전 판단 질의는 수집결과의 정량 수치(파고·풍속·시정·특보)에 근거해 짧은 한 줄로 가부 결론을 먼저 주세요(예: 파고 ≥2m 또는 풍속 ≥14m/s 또는 풍랑특보 발효면 "무리/주의", 파고 <1m + 풍속 <10m + 특보無면 "가능", 그 사이면 "주의/조건부 가능"). 그 다음 근거 수치 1-2개. 마지막에 "최종 판단은 선장님 몫" 한 번만.
```

**AFTER** (현행 + 추가 bullet):
```
- **(의사결정형 — 정량 판단 강화)** …(현행 유지)… 마지막에 "최종 판단은 선장님 몫" 한 번만.
- **(가설·조건문 질의)** "만약/~시/~라면/~면 어떡해/~떴을 때/~넘으면" 같이 *가설 조건* 을 전제로 SOP·운용 가부를 묻는 질의는, 그 조건이 *현재 발효 중인지* 와 무관하게 **위 [직군 안전 임계표] + comment(직군 SOP) 에 따라 조건부 답을 주세요**. 예: "풍랑특보 시 해수욕장 운영?" → "풍랑특보가 발효되면 해수욕장은 입수 통제가 표준입니다(파고 3m·풍속 14m 기준). 현재는 특보 없음." 처럼 *가설답 + 현 상태 부기* 의 2단 구조로. 결정 단어(가능/주의/무리/통제/권장/적합) 를 반드시 한 단어 이상 포함하세요.
```

### 2.3 기대 답변
> "풍랑특보가 발효되면 해수욕장은 입수 통제가 표준입니다(파고 3m·풍속 14m). 지금은 특보가 없어 통상 운영 가능합니다."

→ DECISION_RE 매치: "통제", "가능", "권장" 후보 단어 3개.

## 3. MOF-4-01 패치안 — 데이터 부재 + 사용자 정량 수치 → 임계표 단독 판단

### 3.1 진단
"파고 2m 어업관리 권고?" 는
- 사용자가 **정량 수치를 단정** ("파고 2m") + **직군 행동 가부** ("어업관리 권고?") 를 묻는 전형적 임계표 질의
- mof 직군: wave_m safe=2 / caution=3 / danger=4 → **2m 는 safe 와 caution 의 경계 (safe 상한)**
- 정책 트리거 SOP: "풍랑특보(파고 3m) 가 표준" → 2m 는 통제 미발령
- 현재는 zone 미해소로 `get_marine_forecast` 가 비고 LLM 이 "정보 없음" 으로 도피

### 3.2 패치 — buildPersonalContext 임계표 규칙 강화
**위치**: `assistant.js` 라인 724 (임계표 주입 규칙 문자열) 의 규칙 본문을 보강.

**BEFORE**:
```
** 규칙: 사용자가 정량 수치를 직접 단정(예: "파고 1.5m 풍속 12m 인데 ~ 가능?")하면
그 수치를 위 임계표와 비교해 *가부 결론을 한 줄 먼저* 답하세요(가능/주의/무리/위험).
수집결과가 비어도 답 가능. 도구 결과가 있으면 보조 근거로 첨부.
```

**AFTER**:
```
** 규칙: 사용자 질의에 정량 수치(파고/풍속/시정/수온/파주기 + 단위 m·m/s·km·℃·s) 가
하나라도 명시되면 — 단정형("파고 1.5m") 이든 조건형("파고 2m 넘으면") 이든 가설형
("풍랑특보 시") 이든 — 그 수치를 위 임계표 및 comment(직군 SOP) 와 비교해
*가부·권고 결론을 한 줄 먼저* 답하세요. 결정 단어(가능/주의/무리/위험/적합/권장/통제/발령/적합)
중 한 단어 이상 반드시 포함. 수집결과가 비어도 임계표만으로 답 가능
— 이때 도구 결과 부재는 결론 뒤에 *현 상태 미확인* 한 줄 부기로만 다루고
"정보가 없습니다" 단독 응답은 금지. 도구 결과가 있으면 결론 뒤에 보조 근거로 첨부.
```

### 3.3 기대 답변
> "파고 2m 는 해양수산부 통제 기준(파고 3m) 미만이라 통상 어업관리 운영이 권장됩니다. 현 해역 예보는 확인되지 않았습니다."

→ DECISION_RE 매치: "권장" (보강 후), 또는 "권고" / "통제" / "주의 미만".

### 3.4 보조: 조건 미충족 시 fallback
사용자 정량 수치가 임계표 모든 metric 의 단위와 매치되지 않으면(예: "어업관리 5건 권고?")
임계표 규칙은 trigger 되지 않고 일반 도구 호출 흐름으로 회귀 — 회귀 안전.

### 4.3 우선순위 주의
`"운영"` 은 "해수욕장 운영" 같이 *명사구의 부분문자열* 로 자주 등장 → 그 자체만으로 결정 신호 보기 어렵다.
회귀 위험을 줄이려면 두 단계로 분리:
```python
DECISION_RE      = re.compile(r"가능|적합|주의|무리|안전|위험|불가|곤란|어렵|좋습|괜찮|조심|권장|권고|발령|통제|허용|중지|중단|보류")
DECISION_RE_WEAK = re.compile(r"운영")   # 다른 결정 단어와 함께 등장 시 보조 신호
```
1차 매치 실패 → `DECISION_RE_WEAK` + (다음 중 하나: "가능|불가|중지|중단|통제|허용|미만|초과|이하|이상") 동시 매치면 통과.
→ "통상 운영 가능" / "운영 중단" 류는 통과, "해수욕장 운영" 단독은 비통과.

## 5. 회귀 위험 분석

### 5.1 위험 매트릭스

| 위험 | 영향 케이스 | 완화 |

| **R2. 가설 답변이 *현재 상태* 보고를 덮어씀** | "풍랑특보 떴어?" 같이 *현재 발효 여부* 만 묻는 질의에 SOP 답을 덧붙여 답이 길어짐 | 새 bullet 의 trigger 조건을 "*가설 조건* 을 전제로 SOP·운용 가부를 묻는" 으로 한정 ("만약/~시/~라면/~면/~떴을 때/~넘으면" 어휘 명시). 단순 발효 여부 질의("떴어?", "있어?")는 발동 안 함. |
| **R3. DECISION_RE 확장으로 다른 카테고리 케이스에서 false-positive PASS** | category 1·2·6 등에서 "권장"/"운영" 단어가 무관하게 등장 | `expect_decision: true` 케이스에만 적용되므로 다른 카테고리는 영향 없음. category 4 PASS 율만 변동. |
| **R4. 보수 임계 SOP 답이 어선 사장님 판단을 침해** | LLM 이 임계표를 과신해 "조업 불가" 단정 | synth prompt 에 이미 "최종 판단은 선장님 몫" 한 번만 덧붙이라는 규칙 (1586) 이 있음. 신규 bullet 에도 같은 closing 적용 — 결정 단어는 "권장/권고/통상" 등 *조언형* 우선 사용 |

### 5.2 비대상 케이스 회귀 보증
- **비도메인** (`expect_no_halluc`): 본 패치는 정량 수치 또는 가설 어휘 trigger 시에만 발동 → 비도메인 회귀 영향 0.
