## 총평 (적합성 점수: **72 / 100**)

마스터 플랜은 "이해→연결→선제→성장" 비전을 5단계로 깔끔하게 분해했고, "산출물은 파일로, 플랜엔 경로만"이라는 추적 원칙을 일관되게 지켰다. Phase 2→1 역순 결정의 근거(직군 지식이 온톨로지 1차 재료)도 합리적이고 의사결정 로그에 남겼다. 직군 표본 2개(fishery/angler)는 앱 데이터 매핑·GAP·선제규칙·용어가 풍부해 Phase 1/3 입력으로 곧장 쓸 만하다. **그러나 치명적 맹점은, 이미 코드로 구현·커밋된 핵심 기능들(웹폴백·딥링크·GPS최근접부이·관리자보안격리·AI온보딩·개인화 style-digest·Porcupine+클라우드STT)이 플랜의 로드맵·DoD·회귀테스트 어디에도 "관리 대상"으로 명시되지 않는다**는 점이다. 즉 플랜은 "앞으로 할 일(P1/P3/P4)"은 그렸지만 "이미 한 일을 어떻게 지키고 검증할지"가 빠져, 부합성은 높아 보이나 추적·거버넌스 관점에서 구멍이 크다. 또한 평가지표·회귀·비용·프라이버시·신선도 같은 교차 관심사가 단계로도 섹션으로도 존재하지 않는다. 구조는 좋고 내용 충실도도 높으나, "운영·검증·교차관심사" 레이어가 통째로 비어 점수를 깎았다.

## 단계 구조 평가

**강점**
- 5단계 분해가 비전(이해/연결/선제/성장/기반)과 1:1로 매핑되어 직관적.
- Phase 2→1 역순이 의사결정 로그로 근거화됨. 직군 지식이 온톨로지 노드/엣지의 1차 재료라는 논리는 타당.
- 각 단계가 [목표·진행방식·세부단계·DoD·상태·산출물·리스크] 공통 템플릿을 따라 비교 가능.

**약점·경계 문제**
- **Phase 0이 "끝난 단계"로 닫혔다.** 실제로는 P1~4 코드가 들어올 때마다 P0 진단배터리(78문항)를 다시 돌려야 하는 **상시 회귀 게이트**다. 1회성 완료로 처리하면 P3/P4가 P0 기능을 깨뜨려도 탐지 못 함. → P0를 "🔁 상시 회귀" 성격으로 재정의 필요.
- **Phase 2의 경계가 모호하다.** "지식베이스 작성"(완료)과 "간이 RAG 연결"(미착수)이 한 단계에 섞여 상태표시가 🚧로 뭉개진다. 둘은 산출물·DoD·리스크가 전혀 다르므로 **Phase 2a(지식)·2b(RAG연결)로 분리**가 맞다.
- **Phase 1↔2 의존 방향이 양방향인데 단방향처럼 그려졌다.** P2가 P1의 입력이지만, P1 온톨로지가 정해지면 P2 직군문서 스키마(노드/엣지 태깅)도 소급 정비해야 한다. 이 되먹임 루프가 명시 안 됨.
- **Phase 3(선제)는 안전·프라이버시·알림빈도 리스크가 가장 큰데** DoD가 "오발신율 허용범위"로만 표현돼 정량 기준이 없다.

**누락된 단계/교차 관심사 (전부 빠짐 — 가장 큰 구조적 결함)**
- **평가지표·회귀 테스트**: 78문항이 P0에만 있고, 단계 전반을 관통하는 "골든셋 + 회귀 게이트"가 없다.
- **비용/토큰 예산**: planQuery+합성+style-digest+(향후)RAG가 토큰을 누적 소비. 단계별 토큰/지연 SLO 부재.
- **프라이버시/데이터 거버넌스**: 프로필·대화·style가 휴대폰 로컬이라는 결정이 플랜에 안 적혀 있다. 서버 로깅(`assistant_log.js`) 범위·보존기간도 미정의.
- **운영 시크릿 관리**: P0 비고에 `KMA_DMDW_*`/TideBED가 흩어져 있을 뿐, "운영 배포 전 시크릿 체크리스트"가 단계로 승격 안 됨.
- **데이터 신선도·검증**: 직군 "최근 동향"과 GAP URL이 시점형인데 만료/재검증 책임자·주기가 P4에만 추상적으로 언급.

## 추적 구조(Route) 평가

**강점**
- "경로만 둔다" 원칙 + 산출물 인덱스 표 + 의사결정 로그 + 변경 이력 = 단일 출처로서 골격 우수. README의 3단계 갱신 절차(생성→플랜경로추가→README인덱스추가)도 명료.

**약점**
- **상태가 3곳에 중복**(로드맵 대시보드/단계 상세/산출물 인덱스). 수기 동기화라 곧 어긋난다. → 단일 상태표 + 나머지는 참조로.
- **기계가독성 미흡(향후 RAG가 이 폴더를 인덱싱한다는 의도와 충돌).** MD에 frontmatter(YAML 메타: id/phase/status/updated/owner/source_date)가 없어 자동 파싱이 어렵다. 직군 파일도 제목·표 형식이 표본 2개에서 미묘하게 다름(angler는 "유형별 세분화 비교표"·"충족도" 칼럼 보유, fishery는 없음) → 스키마 강제 안 됨.
- **변경이력이 파일 단위가 아니라 플랜 1곳에만** 있어, 직군 파일 개별 개정 추적 불가. git 커밋과 MD 이력의 역할 분담이 미정.
- **owner/담당·기한 칼럼 부재** — 미결 질문(커밋 시점·GAP URL 검증 담당)이 영원히 미결로 남을 구조.
- **커밋 미실행 = 컨테이너 휘발 = 전소 위험.** 이건 추적구조 이전의 존립 위험인데 "미결 질문"에 묻혀 있다(아래 리스크 #1).

## 직군 산출물 품질 평가 (표본 fishery/angler 기준)

**강점**
- 앱 도구 매핑이 구체적이고 `[GAP]` 표기가 일관 → Phase1 온톨로지(엔터티=관심사/도구/GAP, 엣지=매핑)·Phase3(트리거 규칙) 입력으로 **거의 그대로 사용 가능**.
- 선제규칙이 "트리거→멘트→근거 앱데이터" 3요소로 정형화 → P3 규칙엔진 추출 용이.
- 용어·동의어 표가 STT 보정/검색확장에 직결, 출처에 공식/비공식 등급 표기(angler)로 신뢰도 관리 시도.

**약점·기계추출 위험**
- **두 표본의 스키마가 불일치**: angler는 "유형별 세분화 비교표", FAQ에 "충족도" 칼럼, 선제규칙 ID가 "규칙 1~8"; fishery는 비교표 없음, 선제규칙 ID가 "TR-F01~08". **ID 네이밍·칼럼 구성이 직군마다 다르면 자동 인덱싱·규칙추출이 깨진다.** → 전 직군 공통 규칙ID 규약(예 `TR-<직군>-NN`)·필수칼럼 고정 필요.
- **선제규칙 트리거가 자연어 산문**("파고 3m 이상 또는 풍속 14m/s 이상")이라 기계가독 조건식이 아니다. P3에서 결국 재작성해야 함 → 차라리 지금 `{metric, op, threshold, unit}` 구조화 권장.
- **GAP 외부연동 URL의 세부경로가 미검증**(플랜도 인정). 운영 노출 시 죽은 링크/오안내 위험.
- **동향 섹션 신선도**: 2025~2026 시점형 다수, 만료표시·재검증주기 없음.

## 핵심 리스크 Top 3 + 완화책

**리스크 1 — 미커밋 산출물 전소 (확실성 높음·영향 치명적)**
모든 지식베이스·플랜이 휘발성 컨테이너에만 존재. 회수 시 수일치 작업이 사라진다.
→ **완화**: 검토 직후 `local_server/knowledge/` 즉시 커밋(코드 변경과 분리한 docs 커밋). 이후 산출물은 생성 즉시 커밋을 기본 규칙으로 README에 명문화.

**리스크 2 — 회귀 부재로 기존 기능 무성 파손 (확실성 중·영향 큼)**
P3/P4 코드가 들어오면 P0에서 검증한 도구 응답·딥링크·STT·보안격리가 조용히 깨질 수 있는데, 상시 회귀 게이트가 없다.
→ **완화**: P0 78문항을 "골든셋"으로 파일화(`phases/phase0_golden.jsonl` 등)하고, 각 Phase DoD에 "P0 골든셋 오류0 유지" 항목 추가. 보안 격리(관리자 도구 미노출) 단위 테스트 1개 필수.
