# bulletin_survey — 통보문 전수조사 (2026-11-12 착수)

## 왜
특보현황을 **통보문 기반**(1분마다 통보문을 확인해 갱신)으로 바꾸기 전에, 2025-01-01 ~ 현재 통보문으로
해역(부모+자식)별 특보의 생애주기를 로직으로 따라갈 수 있는지 검토한다.
대상은 발표·발효·변경(격상·격하)·연장·해제, 예비특보 발효·취소다.
MMIS 방식은 자식 해역과 예비특보 취소에서 계속 틀렸다(사용자 확정 2026-11-12).

## 진행 방식(사용자 확정)
「1개월 수집 → 통보문 구성 확인 → 부모·자식 해역으로 정리 → 다음 달」을 반복하며 천천히 한다.

## 대상
- 관서 8곳: 109 수도권청, 159 부산청, 143 대구청, 156 광주청, 146 전주지청, 133 대전청, 105 강원청, 184 제주청
- 통보문: 특보(rpt=6, 특보종류 풍랑·태풍), 예비특보(rpt=7, 종류 구분 없이 받은 뒤 본문으로 거름)
- 기간: 2025-01-01 ~ 현재

## 파일
- `collect.js` — 목록·본문 수집. 원본을 고치지 않고 `raw/<YYYY-MM>/<관서>.json`에 보관하며, 가져온 시각도 남긴다. 다시 돌리면 없는 것만 받는다.
  - 자격증명은 환경변수 `KMA_DMDW_USER_ID` / `KMA_DMDW_USER_PWD`로만 받는다. **파일·저장소에 넣지 않는다.**
  - 요청 간격은 2.5초다.

## 2026-11-12 접속 확인(구조)
- 목록: `POST /rsw/rest/mfp/wrn/retRswWrnRptList.json`, 값 `{startDate, endDate(YYYYMMDD), stnId, rpt, wrnKindNm}`
  - 돌려주는 값은 `[{code:'6|184|41|202611110200|4|20261111020248', value:'[ 특보 ] 제11-41호 : … / 풍랑주의보 해제 (*)'}]`
- 본문: `POST /rsw/rest/mfp/wrn/retRswWrnRptDetail.json`, 값 `{stnId, rpt:<code>}`
- 특보 본문 칸:
  - t1Title 호수, tmFc 발표, tmIn 입력, t1 제목
  - t2 해당구역(「제주도앞바다(제주도남부앞바다) o 제주도남부앞바다(연안바다 제외)」), t3 발효시각, t4 내용(해제 예고)
  - t6 발효 중 특보(「풍랑주의보 : 남해서부서쪽먼바다, 제주도전해상」), t7 예비특보 현황, other 참고
- 예비특보 본문: t4에 「(2) 풍랑 예비특보 o 11월 09일 오후(12시~18시) : 남해서부서쪽먼바다, 제주도전해상」 꼴로 온다.
  - 취소 통보문(11-8호)은 t1~t3이 비고 t4가 「o 없음」뿐이다. **「아직 안 채워짐」과 구별해야 한다.**
  - 지난 예비특보 기록의 t5(종료)가 취소 뒤 고쳐져 있었다(11-7호 t5 = 11/09 17:58).
- 11/09 사례: 예비특보 취소 통보문 11-8호 입력 17:57:12 → 알림톡 17:58(1분 뒤).
  - 다만 14:00 특보 통보문 11-31호에 이미 「연안바다 제외」와 「예비특보: 없음」이 적혀 있었다.

## 해석 기준 — 자식 해역(연안바다·평수구역) 포함 여부 (사용자 확정 2026-11-12)
> 사용자 원문: *「연안바다 평수구역에 대해서 명명이 안되어 있고 제주도서부앞바다 라고만 표현되면 그 연안바다를 모두 포함하여 풍랑이 해당되는것이고 만약 일부를 포함하거나 일부를 제외하면 그 일부만 제외, 포함 내용이 꼭 들어가거든」*
- 부모 해역 이름만 나오면 → 그 부모에 딸린 **자식 해역 전부 포함**(`config/zone_group_map.js`·`marine_warning_crawler` PARENT_TO_CHILDREN 기준).
- 일부 제외·일부 포함은 통보문에 **반드시 명시**된다(예: 「제주도남부앞바다(연안바다 제외)」) → 명시된 것만 빼거나 넣는다.
- 검산: 이 규칙으로 펼친 결과가 같은 통보문의 「발효 중 특보(t6)」 칸과 맞는지 매 호 대조한다. 어긋나면 예외 사례로 모아 보고한다(추측해서 맞추지 않는다).

## 참고사항(other) 칸 — 상태 변화가 문장으로 적힌다 (사용자 지적 2026-11-12, 2025-01 310건 중 120건에 있음)
- 예비특보 취소: 「…로 예고되었던 동해중부앞바다(강원중.북부앞바다)의 풍랑예비특보는 발표 가능성이 낮아져 해제합니다.」
- 예비특보 시간대 연장: 「…밤으로 되어있던 울릉도.독도의 대설 예비특보는 내일(9일) 오전으로 연장 발표합니다.」
- 해제예고 연장: 「당초, 10일 밤(21~24시)이었던 해제예고를 11일 늦은 오후(15~18시)로 연장합니다.」
- 격상과 해제예고 변경: 「위 해역의 풍랑주의보를 풍랑경보로, 해제예고를 11일 오후로 변경합니다.」
- 일부만 해제: 「충남북부앞바다 중 태안·서산 북쪽 평수구역은 풍랑주의보를 해제하나…」
- 정확한 해제 시각: 「위 구역의 풍랑특보는 09시 30분을 기해 해제되나…」
- ⚠안내 문장(상태 변화 아님): 「해제되겠으나, 내일 … 다시 발표될 가능성이 있으니…」
- 해석 원칙: 확정 표현(해제합니다·연장합니다·변경합니다·연장 발표합니다)일 때만 상태를 바꾼다. 풍랑·태풍 문장만 쓴다(대설·강풍 등은 뺀다).

## 참고사항 AI 해석 — 계획 (사용자 확정 2026-11-12, 2026-11까지 수집을 마친 뒤 착수)
> 사용자 원문: *「참고사항에 대한 내용은 계속 수집하되, 그것을 규칙으로 적용하기에는 작성자의 재량 너무 커 규격화하기 어려울것같아 ai를 활용한 분석이 들어가게하는게 맞는것같은데 … 별도 api를 호출하는 방식으로」* · *「추후 참고사항 ai 호출적용할때 기존 참고사항 데이터를 ai에게 넣어서 어떻게 ai가 해석했는지 결과를 보는방안이 좋겠음」* · *「일단 26년까지 다 모은뒤 다시 검토하자」*
- 정해진 칸(t2 해당구역·t3 발효시각·t6 발효 중·t7 예비특보 현황)은 **규칙으로** 처리한다(2025-01~09 풍랑 특보 1305/1306 검산 일치).
- **참고사항(other)만 AI(별도 API)** 로 해석한다.
  - 정해진 칸만 채운다: 종류(예비취소·예비연장·예비추가·해제예고연장·등급변경·일부해제·정확해제시각·안내), 원문 해역 표현, 새 시각, 근거 문장.
  - 해역 펼치기는 AI가 하지 않고 규칙이 한다(예전 `ai_report_parser.js`는 통보문 전체를 AI에 맡겨 해석 오류가 반복됐다).
- 검증: 근거 문장이 원문에 있는지, 해역 표현이 해역표에 있는지, 같은·다음 통보문의 예비특보 현황(t7)과 맞는지 본다. 어긋나면 관리자 확인으로 보낸다. 정해진 칸과 다르면 정해진 칸을 따른다.
- **첫 단계: 모아 둔 참고사항 전부를 AI에 읽혀 해석 결과를 사용자에게 먼저 보여 준다**(원문·AI 해석·검산 결과를 나란히). 결과를 보고 실시간 적용을 결정한다.
